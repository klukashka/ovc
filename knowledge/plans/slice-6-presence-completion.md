## Problem and outcome

The source S5 implementation is `0afee87700759a5c76177687224b3aa91489a3f9`, recovered onto main `e95d272` in the isolated `feat/chat-presence-completion` worktree. It stores one unconditional account-wide presence row. Closing the last socket on one API overwrites another API's live presence. The source also sends ready before its first presence write and removes closing sockets even when the final write fails. Independent standard and security reviews identify the latter two as major defects.

The result must be account-wide presence that remains online while any API has a live lease, with acknowledged persistence before ready, bounded failure handling and no change to role-based visibility. Existing typing and scheduler behavior is retained except for defects demonstrated by the completion checks.

## Persistent state and ordering

Keep `user_presence (user_id, online_until, last_seen_at)` as the account summary consumed by channel queries, digest flags and the future digest. Add `user_presence_instances (user_id, instance_id, online_until, last_seen_at)` with primary key `(user_id, instance_id)`, a cascading account foreign key and an index on `online_until` for bounded expiry cleanup. Instance identifiers are named UUID values generated once per API process through the existing random source, never client input and never reused after a restart. They are not credentials and are not exposed in browser payloads.

All modifications lock existing user rows `FOR KEY SHARE` in identifier order, initialize and lock their summary rows in identifier order, then modify lease rows. Only then is the summary recomputed from leases. A missing purged account is skipped without recreating it. No presence path takes relationship or channel locks; channel recipients retain the existing documented presence exception. The summary row serializes changes to the same account on different APIs; unrelated accounts do not share a process-wide unbounded mutex wait.

An instance extends only its own lease about once per minute, using the greater of its existing deadline and sampled business time plus 90 seconds; activity instants are also monotonic so an older sampled operation cannot regress either value. Closing its last socket deletes only its own lease. On a close, summary `online_until` is the greater of the closing instant and all retained lease deadlines; on extension it is the greatest lease deadline; it cannot move into the future solely because cleanup ran. `last_seen_at` preserves the greatest real connection activity instant across all leases and the existing summary, never a future lease deadline. A crashed instance is online only until its 90-second lease expires; no expiration event is promised without a later refetch, matching the existing crash behavior. Summary times and all consumers use the same injected business clock.

A bounded `chat.expire_presence` worker job runs once a minute, deletes at most 500 expired lease rows per transaction and stays within a 20-second monotonic execution deadline, including SQL and lock waits, independent of the business clock used to compare expiry. Candidate selection reads identifiers without locking lease rows before the user and summary locks. It follows the same user-summary-lease lock order, rechecks expiry after locking, and does not erase a concurrent renewal or historical summary. The expiry index provides the candidate scan. Every account purge cascades both tables. The job is necessary to prevent crash/restart lease rows growing without bound for accounts that never reconnect.

The migration is still unmerged: revise `00018_user_presence.sql` to create the complete schema together. Test migration up/down and purges; no deployed data conversion is required.

## Gateway lifecycle and failure behavior

Before initial ready, persist the instance lease and summary, without holding the gateway mutex across database work. Await this operation with a deadline that includes admission to the presence writer. Then recheck socket closure, session/account revocation and listener generation before ready. If persistence fails or times out, send no ready and close with the existing reconnectable failure behavior. Authentication that loses validity after persistence releases its unused lease through the same close path; a crash during this interval is bounded by expiry.

Serialize desired state per local account, coalescing repeated transitions into a bounded pending entry; do not allocate an unbounded goroutine per event. Use at most four concurrent writers and cancellation-aware admission, with a five-second end-to-end operation deadline. Reserve one of at most 4096 local account entries before the first durable lease write; this total includes authenticating, active and pending-release accounts, about twice the NFR-3.1 connected-account workload. A full registry refuses new account admission before ready using the existing capacity refusal behavior. Repeated events reuse their account entry. Never drop an accepted pending release to admit another account: free its entry only after confirmed release or confirmed account deletion and after every older write has completed or been definitively cancelled. An uncertain database commit outcome retains the pending release. Test sequential distinct-account churn during database unavailability against this total bound. Capture local state generations so an older completion cannot overwrite a newer reconnect. Readiness waits and clock-route extensions return explicit failure when their operation cannot complete.

A failed closing write retains one pending release per account, emits safe failure diagnostics and is retried by the injected one-minute presence cycle, not by an unbounded retry loop. The closed network socket is not counted as live. The existing test-control presence route returns a `503 service_unavailable` while that instance has an uncommitted release, rather than a successful false assertion of durable closure. Its successful `{online, sockets}` remains local registry state: local offline means that instance's lease was released, not that the whole account is offline. Tests of global presence read REST or the database separately. Shutdown drains releases within its deadline, cancels scheduled work and reports incomplete release; any lease left after process exit expires within its lifetime.

Presence frames use the committed account-wide online state rather than local socket state. A close on one API must never announce offline while another unexpired lease exists. Deferred/debounced sends re-read the aggregate state. Retain the existing per-instance five-second debounce before recipient work and document that this is not a new cluster-wide rate guarantee. Every deferred emission acquires the summary lock again, reads the current aggregate and calls pg_notify in that same transaction before releasing the lock. This orders signal commits and avoids emitting an obsolete sampled state. It does not promise that a previously committed offline frame cannot arrive at a browser after a later online commit; listener delivery remains in commit order and the online frame follows it. Read recipient scope without relationship/channel locks under the existing one-late-presence-frame exception; add no new exception. Typing still authorizes active membership under the channel lock and anonymizes another student.

## Checkable acceptance criteria

- `TestPresenceRemainsOnlineWhileAnotherInstanceHasASocket`: two real gateways share PostgreSQL and the listener; closing A leaves REST presence online, no offline frame reaches recipients and a send does not flag the user for a digest; closing B makes the account offline.
- `TestPresenceLeasesExpireAfterAnInstanceStopsExtending`: injected clock crosses the failed instance's deadline; a live other instance keeps the account online, and without it global presence becomes offline within the lease lifetime.
- `TestReadyWaitsForCommittedPresence`: hold a real summary row lock, prove no ready while held, release it and assert persisted online before ready is observed. A timeout closes without ready; existing revocation and listener-generation races remain covered.
- `TestAFailedPresenceReleaseRemainsPending`: induce a real row-lock timeout, assert test-control failure and preserved pending release, release the lock, drive the injected cycle, then assert successful local offline and durable lease removal. Cover reconnect before recovery and shutdown with a pending release.
- `TestPresenceOperationsRespectAdmissionAndShutdownDeadlines`: bounded work under database contention, no per-event goroutine growth and no callback/database work after completed shutdown. `TestPendingPresenceAccountsHaveATotalCapacity` drives distinct-account churn under database contention and proves the configured total capacity (4096 in production), bounded refusal latency and preservation of accepted releases.
- `TestDelayedPresenceEmissionReadsTheLatestAggregate`: hold deferred offline emission, reconnect on another API, then release emission; it reads the new aggregate and emits no stale offline. Verify transactional notification order and privacy with the real listener.
- `TestPresenceExpiryCleanupIsBoundedAndPreservesRenewedLeases`: real worker `Tick`, more than one batch, concurrent renewal and account deletion; row count and execution cancellation asserted with the injected scheduler/deadline seam, including a real row-lock wait while business time is frozen. Retain historical last-seen state and avoid FK failures for the rest of a batch after purge.
- Existing S5 authorization, anonymous typing, coalescing-before-DB, frame parser, scheduler, clock, purge and diagnostic tests pass. Cover both Set and Advance: each route flushes only its own API leases before success, even when Set repeats the same instant. The multi-instance test controller sets the same absolute instant on every API and waits for every response before assertions, sends or worker/digest execution; these operations are forbidden during the intermediate interval. A failed flush can leave the clock changed and requires explicit local recovery before continuing. This is a local acknowledgement protocol, not a distributed clock barrier.
- `TestPresenceWaitsOnlyForConflictingUserRowLocks` demonstrates permitted operator/purge waits and passage through `FOR SHARE` and `FOR NO KEY UPDATE`; no operator lock changes.

Tests use real API/gateways, PostgreSQL, the real listener and worker; injected schedulers/clocks and explicit conditions, never mocks, sleeps or artificial database behavior outside repository exceptions. No HTTP endpoint or frame can set an instance identifier.

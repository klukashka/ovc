## Request lifetime rule

1. Before the initial authenticated document navigation, bind the exact three GET targets, including origin and complete query parameters, to the owned account/document generation. Mark only each target's first request as eligible if its start is observed while the initial window is open. Every other request is ineligible.
2. Close that window permanently at the same first WebSocket ready, first successfully completed target response or existing readiness deadline. Closure prevents any new request from becoming eligible; it does not erase the recorded identity of an already eligible first request. No SPA transition, retry, reload or account change rearms it.
3. A cancellation of that recorded first request may be delivered after closure, but must be the engine's explicit cancellation outcome and arrive before the original readiness deadline. Reject every non-cancellation failure, second cancellation, unknown request, ownership/scope transition and failure of any ineligible request. All raw failures remain counted.
4. Require the same target's exact second request, in the same owned document/account generation, to finish fully with status 200 before the original deadline. Its start must follow the first request's start; its callback may precede delivery of the first request's cancellation. No third request can substitute for a failed or missing second request. Missing, failed, late or mismatched replacement is failure. A successful first request never creates a cancellation allowance for a later request.
5. Require actual account validation, visible seeded history, composer and the observed post-ready authoritative refreshes before navigation. Quiescence counts owned HTTP API requests; long-lived gateway/HMR connections remain separately observed rather than being treated as unfinished HTTP bodies. Preserve failure observation for non-API resources and shared production diagnostics. Export bounded pending counts and fixed resource categories to make a timeout diagnosable without raw addresses.

This changes when an already observed request can be classified, not the number of eligible requests or the ownership/window/deadline bounds. It is nevertheless an explicit verification-contract change requiring approval. If an engine cannot provide the necessary exact request identities, cancellation outcome or complete replacement evidence, stop without widening the rule.

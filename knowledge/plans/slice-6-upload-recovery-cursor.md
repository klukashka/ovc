# Separate recovery pass expiry from healthy cursor continuation

Status: approved on 2026-11-01; security planning review passed after redesign; owner approved implementation of this extension on 2026-11-01. This extends the approved recovery-regression correction after its one authorized gate repeat failed a different existing assertion. Implementation base is `bf6ea79d5c999df1a8ad077cc25d172521ff4955`, including the separately merged quota clarification; unmerged change `8c80a6884d3e475f42d8c058a0da564281166726` and both gate reports are retained.

## Failure and intended behavior

The repeat passed 29 commands but failed the backend command in `TestUploadRecoveryRetainsCursorAcrossBudgetAndWraps`; E2E did not run. That unchanged test sets candidate/pass budgets to 50/75 ms and assumes exactly two blocked candidates are attempted in the first pass. It then requires healthy continuation inside the same shortened budgets. The observed first pass retained the first candidate, and the second pass timed out before useful work; the assertion combined both timing assumptions with the cursor contract. The earlier correction intentionally left this test unchanged, so it was not covered by that approval.

Split this test's deadline and cursor-continuation responsibilities, using only existing real-database and cancellation mechanisms:

1. **Outer-pass deadline:** keep the 75 ms recovery pass and the existing production one-second candidate budget. Hold the first ordered intent and require deadline failure, zero processed rows, unchanged durable state/outbox and completion within the same one-second overall bound used by the candidate-deadline regression. The cursor may remain zero if the 75 ms budget expires in candidate selection, or identify the first held intent if it was attempted; neither case is falsely rejected. The separate already-corrected 50/200 ms regression continues to prove the per-candidate deadline. A negative control removing only the outer timeout must fail the overall-bound assertion, rather than being allowed to masquerade as a candidate cancellation.
2. **Cursor retention, continuation and wrap:** use normal production budgets and a cancellable caller context. Hold only the first of three ordered intents, start the real recovery call, and use the existing `awaitDatabaseLock` helper with its bounded observation context to observe that call actually waiting on the owned first row. Only then cancel the caller context. Require `context.Canceled`, zero processed, the first identifier retained and all durable state unchanged. This reaches the same `bounded.Err()` branch as pass expiry without racing the observation against an artificial 75 ms window. Release the lock and call recovery with a fresh context: exactly the second and third intents must be processed and queued, the first unchanged, and the cursor wrapped to zero. A third call must visit all three, including the first, and leave valid durable cleanup ownership. No successful transaction is required to complete within 50 or 75 ms.

No production budget, existing short deadline, global timeout or gate ceiling changes. The observed database wait is the synchronization event; there is no sleep, mocked store, runtime patch or altered database connection. The caller cancellation is a normal production cancellation path, not an injected database failure. Retain the separate outer-deadline test so the cursor test does not substitute cancellation evidence for timing evidence.
Register transaction cleanup immediately after Begin, before any setup statement that could fail. The failure path must not strand the fixture's own row lock. Use explicit transaction completion and real database state; no sleeps, timing retries, mocks, new clock abstraction or database-behavior alteration are proposed.

The fixture must have no other waiting database operation when `awaitDatabaseLock` observes its wait; the existing helper counts all waits in that isolated database. Cleanup cancels and joins the recovery goroutine even if observation fails, before closing the fixture. The observation deadline must precede the normal one-second candidate deadline; it is a bounded liveness check, not a requirement for successful business work inside the short artificial budget.

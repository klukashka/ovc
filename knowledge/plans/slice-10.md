## 1. Problem, outcome and scope

**Problem.** After slice 9 the MVP's homework loop works locally, but four things stand between it and the pilot of [ADR-0013](../../docs/decisions/0013-pilot-deployment.md).

- **The check budget is exceeded.** The last three passing merge gates of slice 9 took 700.3, 639.9 and 716.1 s, a median of 700.3 s, above the 540 s at which the check-budget rule of [ADR-0018](../../docs/decisions/0018-targeted-checks-and-merge-gate.md) then made a consolidation due before further feature work (replaced on 2026-11-17 by the idle-machine rule, see D5). The end-to-end run is the larger part of each gate and grew from 1,859 to 2,102 runs during slice 9. Load from other work on the laptop and sleep on battery made several gates slow or flaky, and the gate does not record its power source or its load at the end.
- **Carried items are open.** The [slice 9 slice review](../reviews/slice-9-slice-review.md#carried-into-slice-10) and its [known limitations](../reviews/slice-9-known-limitations.md) carry 18 rows and three owner decisions into slice 10, and the roadmap entry of slice 10 holds carry-overs from slices 1, 2, 4, 5, 6 and 8 and from the design slice.
- **The product is unfinished.** Today and Home still assemble their panels from several reads, `GET /home` is unbuilt, the first-run checklist cannot be dismissed, the Students list has no open assignments column, Home cannot say that checked feedback is new, and every page below 1024 px uses the interim one-column frame (FR-15, NFR-5.2). Web push (ADR-0015) is unbuilt and has no functional requirement.
- **OVC has no host.** It is local only, with no remote, no CI and no server. Pilot deployment, production serving, public web hygiene and the deployment's measurements need a server the owner does not have yet.

**Outcome.** End to end locally through the real API, worker, PostgreSQL, the local S3-compatible server and the production frontend build:

- the end-to-end suite is consolidated with every behaviour still covered, the merge gate prints its power source and load at its start and end, and the after-fix gate carries evidence that its change addresses the named failure;
- the carried fixes of slice 9 have landed: the tutor-state rule for homework emails, the flaky Firefox notes test, the `popstate` residual, the shared notices' focus, the assignment page's refusal focus tests, the narrower live refetch of homework frames, Upcoming deadlines expiring on an open page, the notification rows' text-load state and the pilot 2 actors' own settings;

### The after-fix evidence (10.1, change T1)

- **D11. After-fix gates carry evidence, without a reviewer (Q6 A).** A gate counts as an after-fix gate only when, in addition to the 2026-11-15 definition, the readiness report quotes the failed assertion or check output of the previous gate, names the diff hunk that addresses it, and shows the failed test or check failing before the fix and passing after it with the same command and exit statuses; for an intermittent failure, the same command run a stated number of times on the unfixed and the fixed tree, with the failure reproduced on the unfixed one. Without that evidence the gate is a rerun and follows the rerun rule. T1 also lands D1's sub-slice rule. The slice review re-verifies each after-fix row. T1 lands the rule in `AGENTS.md`, ADR-0018, `docs/development.md` and ovc-verify (pending owner review) and maps it to T-41. The alternative, a fresh scoped reviewer before every after-fix gate, would have cost about ten reviews in slice 9.

  - `OVC_WEB_PUSH`, `off` (the default) or `on`, read by the API and the worker;
  - `OVC_WEB_PUSH_PUBLIC_KEY`, the VAPID public key as an uncompressed P-256 point in unpadded base64url, required by both processes when push is on;
  - `OVC_WEB_PUSH_PRIVATE_KEY_FILE`, the path of a file outside the repository that holds the VAPID private key, read only by the worker into a `Secret` and required by it when push is on; the worker refuses a file that group or others can read and a key whose public key differs from `OVC_WEB_PUSH_PUBLIC_KEY`. The API never opens it, so `tools/dev-env.sh` can load one environment for the API, the worker and `ovc-admin`; the API refuses to start when key material itself is in its environment (a variable `OVC_WEB_PUSH_PRIVATE_KEY`), so the key never reaches the API's settings. The file is a secret under `AGENTS.md`: never committed, logged or opened by agents. `ovc-admin push generate-keys` creates a new key file exclusively with mode `0600`, refusing an existing file (overwriting it would rotate the key and retire every subscription), a symbolic link and a path inside the repository, and prints only the public key. S4 rewords ADR-0015's key sentence to name the file, pending owner review;
  - `OVC_WEB_PUSH_CONTACT`, the VAPID contact claim, required by the worker when push is on and refused unless it is a `mailto:` address on the domain of OVC's sending address, the From address of its emails, so it is OVC's own address and never a person's mailbox elsewhere (ADR-0015); S4 states the documented generic address. For D59 the owner's development settings name a real OVC domain; if a vendor refuses the claim, the record says so.

  Until a later change lifts it, the API and the worker refuse to start with `OVC_WEB_PUSH=on` unless the database passes the same test-or-development database checks that `OVC_TEST_CONTROL=1` requires (the configured name before connecting and the actual name after, and a loopback host), and a process test proves the refusal for a production database name. That later change is made only after the decision record on minors and the legal assessment are recorded, with the owner's decision; it is not part of slice 10. With `off`, the push routes are not registered, no producer writes a push outbox row, the account read carries no push key, and the page registers no service worker, so no subscription row and no push request can exist. When the worker starts with push off it deletes every stored subscription row, and the page unregisters any OVC service worker as soon as `GET /users/me` answers with `web_push` null, so a switch from `on` to `off` leaves neither rows nor workers behind; that check is a few bytes of the entry chunk, which W4 measures (D61).
- **D53. Subscriptions at rest (Q18 A).** A new table `push_subscriptions` holds one row per session at most: its identifier, `session_id` (a foreign key to `sessions` with `ON DELETE CASCADE`), `user_id` (a foreign key to `users` with `ON DELETE CASCADE`), `endpoint_hash` (the SHA-256 of the endpoint's canonical form, the URL parser's serialisation with a lower-case host and no default port, unique across accounts, so one browser cannot be stored twice), the endpoint, `p256dh` and `auth`, each as its own AES-256-GCM ciphertext under `OVC_FIELD_ENCRYPTION_KEY` with a fresh 12-byte nonce and, as additional data, a fixed ASCII label of its own field with the row's identifier, so no ciphertext can be swapped into another field or row, as invitation tokens are stored ([data model](../specs/data-model.md)), the push service as a value of one enum, the identifier of the VAPID public key it was made for, and `created_at`. A row whose key identifier is not the current key's is never sent to and is deleted by the worker, so rotating the VAPID key retires every subscription, as ADR-0015 says. The rows go with their session and account at every purge and cleanup; the 30-day database backups keep only ciphertext, so reading a backup no longer exposes endpoints and keys without the field key (T-46's residual, T-34). A collision on `endpoint_hash` inside the subscribe transaction is the move of D54, never a `500`. S4 considers a composite foreign key `(session_id, user_id)` so a row cannot name another account's session, writes the table into `data-model.md` and the field key's labels into the configuration section of `detailed.md`.
- **D54. The routes.** Registered only while push is on, each in the audience table and its test, each answer `no-store`; the subscription routes have the audience `user` (a confirmed account only, as lesson emails go only to confirmed addresses):
  - `GET /users/me` always gains `web_push`, `null` while push is off or the caller is unconfirmed, otherwise `{public_key}`, so the page knows whether to show the control without a request that could answer `404`;
  - `PUT /push/subscription` with `{endpoint, keys: {p256dh, auth}}`, at most 4 KiB, subscribes the current session and answers `204`. It takes the account's row lock and the session row `FOR SHARE`, and checks the session again under them, so a concurrent revocation either commits first, and the route answers `401`, or waits for the insert, and its trigger then deletes the new row. It replaces the session's earlier row; an endpoint already held by another session or account moves, its earlier row deleted in the same transaction. More than ten subscriptions of one account are refused with an existing error code that S4 names; subscribing counts against a new per-account limit, `push_subscriptions_hour`, which S4 adds to `data-model.md` and `api.md` (`429` with `Retry-After`);
  - `DELETE /push/subscription` deletes the current session's row, `204`, idempotent;
  - `GET /push/subscription` answers `{subscribed}` for the current session, so the control can show a subscription the worker deleted after a `404` or `410`;
  - `GET /notifications/{id}`, with the audience of `GET /notifications` (`user, unverified ok`), answers one in-app row of the caller in the schema of the list's items, and `404` for a row that is not the caller's, that the list's lifecycle filter would hide, or that is not one of the pushed events of D56, with an entry in the denial table; the page behind a notification's click uses it (D57).

  No response holds an endpoint or a key. The endpoint check at subscription: parsed with the URL parser, scheme `https`, no port or port 443, no user information, at most 2,048 bytes, and a host that is one of the push-service hosts fixed in code (D56); `p256dh` decodes to a valid uncompressed P-256 point and `auth` to 16 bytes, both in unpadded base64url. The order of refusals follows the conventions of `api.md` and S4 states it.
- **D55. The subscription lifecycle.** A subscription is deleted, in the same transaction, on every path ADR-0015 lists, enforced at the data level: a trigger on the revocation of a session (`revoked_at` set) deletes that session's row; a trigger on an account's change to `blocked` or `deleted` deletes the account's rows; the cascades from `sessions` and `users` delete the rest when the session cleanup, the purge or the 7-day cleanup deletes their rows. The paths covered by tests are sign-out, sign out everywhere, refresh token reuse, the same-browser confirmation that revokes other sessions, password reset, password change, reclaim, blocking through `ovc-admin`, account deletion, the purge, the 7-day cleanup of an unconfirmed account and the cleanup of an expired session; an expired session that the cleanup has not reached yet is never sent to (the worker's send-time check). The client also unsubscribes the browser (`PushSubscription.unsubscribe()`) and unregisters the service worker on sign-out and on an account change, and nothing subscribes on sign-in.
- **D56. Kinds, preference, payload and sending (Q19 A).**
  - **Kinds.** Students receive `lesson.reminder_24h`, `lesson.reminder_1h`, `lesson.moved`, `lesson.cancelled` and `lesson.series_changed`; tutors receive `lesson.reminder_24h` and `lesson.reminder_1h`, the only lesson events addressed to them. `group.archived`, `relationship.ended` and every other event are not pushed. The payload's enum has five values, one per pushed event.
  - **Preference.** The device's subscription is the only switch: a subscribed device receives every pushed kind of its account's role, and neither the email preference groups nor a one-click unsubscribe changes push. S4 rewords ADR-0015's "the preference allows the kind" to say so (K24, pending owner review) and keeps per-kind switches as an open question in `detailed.md`, to be answered from the pilot.
  - **Payload.** `{"k": <kind>, "id": <identifier>}` and nothing else, the identifier being the in-app row's or, for `lesson.reminder_24h`, which has no in-app row, the lesson's. Every payload is padded to one fixed length, so its size reveals no kind. The headers the push service reads are the same for every kind: no `Topic`, `Urgency` `normal` and a `TTL` of one hour, so neither reveals the kind or the lesson's start (T-46); a push that cannot be delivered within the hour is dropped by the push service, and email and the in-app row still carry it.
  - **Outbox.** A new lane, `push`, with its own concurrency of 4. The transactions that write the email outbox rows of the pushed events also write, only while push is on, one fan-out row per recipient, keyed by the email row's key with a `push` prefix. The fan-out effect decides the recipient again (the session is neither revoked nor expired, the account is `active`, the audience rule of the event's email holds, the lesson is still due or the change is not obsolete under the email's rules) and inserts one send row per live subscription of the recipient, keyed by the event key and the subscription's identifier, so each subscription's retries are its own. Push outbox rows hold identifiers only (the event's subject, the recipient and, for send rows, the subscription). A per-account cap of 20 pushed events per UTC day, counted per fan-out row so the sends of one event to up to ten subscriptions count once, bounds the metadata the push services see (T-20, T-46).
  - **Sending.** The send effect decides the recipient again as the fan-out did, checks the subscription row again (present, its session live, its key identifier current), validates the decrypted endpoint again with the same function the API uses at subscription (`https`, port 443, no user information, the length and a listed host, D54), drops a row older than the one-hour `TTL` as obsolete; an endpoint the check refuses deletes the subscription and makes the row `dead` with the error code `endpoint_refused`, logged as `push.failed`. It then encrypts the payload as RFC 8291 `aes128gcm`, signs a VAPID token (ES256, `aud` the endpoint's origin, `exp` at most 12 hours ahead, `sub` the contact) and posts it. `201` or `202` completes the row; `404` or `410` deletes the subscription; `403` makes the row `dead` with the error code `vapid_rejected` and deletes nothing, so a misconfigured key cannot wipe every subscription; `429` and `5xx` retry with the outbox's back-off, honouring `Retry-After` within its bounds, and become `dead` after 8 attempts; any other answer is `dead` at once with the error code `permanent`.
  - **The outbound client** lives in a new adapter package that S4 adds to the package layers. Its transport ignores proxy variables (`Proxy: nil`), refuses every redirect, requires TLS 1.2 or later, and bounds the dial, the handshake, the response header and the whole request below the lease (S4 states the values); it reads at most 4 KiB of a response body, discards it and never logs it. Its dialer allows, through `net.Dialer.Control` on the address actually connected and after unmapping IPv4-mapped forms, only port 443 and only global unicast addresses outside every special-purpose range: loopback, private, unique-local, link-local, carrier-grade NAT, `0.0.0.0/8`, `240.0.0.0/4` and broadcast, `192.0.0.0/24`, `198.18.0.0/15`, the documentation ranges (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`), unspecified, multicast, metadata addresses, NAT64 (`64:ff9b::/96` and `64:ff9b:1::/48`), 6to4 (`2002::/16`), Teredo (`2001::/32`) and IPv4-compatible addresses are refused. The whole endpoint is validated again before every request, as above.
  - **The fixed host list** is in code, taken from a dated research note, `knowledge/research/web-push-services-2026-11-<day>.md`, that S4 writes from the vendors' own documentation, because the entries of 2026-10-26 are marked unconfirmed. The expected entries are `fcm.googleapis.com`, `updates.push.services.mozilla.com` and `web.push.apple.com`, matched exactly, and Microsoft's per-endpoint hosts under `notify.windows.com`, matched at a dot boundary; the note records each with its source and date. The list changes only by a code change that updates the note.
- **D57. The web app and the service worker.**
  - **Manifest.** `manifest.webmanifest` with the name OVC, `id`, `start_url` and `scope` `/`, `display` `standalone`, colours from the tokens, icons at 192 and 512 px and a maskable 512 px icon, and an Apple touch icon, linked from `index.html` in every deployment, since installing changes nothing on the server. W1 decides `viewport-fit` and the status bar style for the installed app on iOS and iPadOS, carried from the 10.3 slice review's safe-area finding, and the owner's device check records the result (D59).
  - **Service worker.** `sw.js`, a separate build entry emitted at `/sw.js` without a hash, importing no application chunk, with handlers for `push` and `notificationclick` only: no `fetch` handler and no use of Cache Storage, which is stricter than ADR-0015's "at most precaching". The page registers it only from the settings control, when `web_push` is non-null and the user turns push on; turning push off, signing out and an account change unsubscribe and unregister it and delete any cache, so while push is off no deployment has a service worker. It is served from the built output with `Cache-Control: no-cache`, scope `/` and no `Service-Worker-Allowed` header, and the content security policy gains `worker-src 'self'` and `manifest-src 'self'` (T-37); the served-directory test covers the new files. The pilot deployment slice's reverse proxy must serve `/sw.js` the same way, never with the long cache of hashed assets; section 11 adds that to its production serving.
  - **What it shows.** The worker parses the payload strictly (exactly `k` in the enum and `id` a UUID) and shows the fixed text of its kind (S4 may give several kinds the same wording), or for an unparsable payload a generic "A notification from OVC" that opens Notifications, since browsers require a shown notification for every push. The notification's `tag` is the kind and the identifier, and its `data` member holds only the kind and the identifier. The texts in both languages are built into `sw.js` from the language sources, with a test that they equal those entries. The page registers the worker as `/sw.js?lang=en` or `/sw.js?lang=ru` with the account's language and registers it again with the new value on a language change; the worker reads the value from its own script address and falls back to the browser's language, so it stores nothing, keeping T-37's rule that OVC stores nothing in IndexedDB.
  - **The click** opens or focuses only a same-origin route built from the kind and the identifier, never an address from the payload (T-28): `/lessons/{id}` for `lesson.reminder_24h`, and `/notifications/{id}` for the other kinds, a frontend route, built in W4 on W2's generated client, that reads `GET /notifications/{id}` and replaces itself with the row's link, or shows Notifications with a notice when the row is gone.
- **D58. Tests without a vendor push service (K5).** The backend's integration tests pass the sender a loopback fake push service, an in-process `httptest.Server` over TLS, through its constructor (D33). ## 5. Conflicts and silences (none resolved silently)

- **K1. A local `deploy/` folder against ADR-0017.** Creating `deploy/` makes `pnpm lint` fail while the release age is 3 days, so locally prepared deployment files would force the restore early. Resolved by Q2 A: the folder and the restore belong to the pilot deployment slice. Placing the same files under another folder name to avoid the check would defeat its purpose and is not done.
- **K2. The decision of 2026-11-08 against local work.** That decision deferred the stress readiness check, the diagnosis of WebKit failures under load and the performance measurements until OVC is deployed. Q3 A and Q9 A of 2026-11-16 supersede it for the diagnosis, the stress check and the plan-and-count measurements, which run on the machine where the gate runs; latencies stay with the deployment. Section 11 records this in the roadmap. Since revision 6 the plan-and-count measurements move to the pilot deployment slice again, while the diagnosis and the stress check stay in 10.5 (K23).
- **K3. "Written with the slice 10 plan" against the `docs/` rule.** The roadmap says the web push requirement is written with this plan; `AGENTS.md` lets agents change `docs/` only as part of an approved plan. Resolved by Q5 A: the text is in D31, and S4 lands it, pending owner review.
- **K4. The heap growth measurement's place.** The slice 8 plan placed it "with the deployment's performance measurements", but it measures the browser, not the server. D35 measures it locally in 10.5; the pilot deployment slice may repeat it on a phone against the real host. Since revision 6 the measurement moved with H2 to the pilot deployment slice (K23).
- **K5. A fixed host list against tests.** ADR-0015 fixes the push-service hosts in code, which no production setting can extend, while tests need a fake push service on loopback. D33 injects the list through the worker sender's constructor, which `AGENTS.md` allows for fakes. Whether a browser-level end-to-end subscription test is possible without a vendor push service is open for the 10.4 revision; it may not add a test-control route that extends the list.
- **K6. NFR-2 "on the reference deployment".** NFR-2.1's latencies name the reference deployment, and NFR-2.2 and NFR-2.5 need a realistic host and network. They are measured in the pilot deployment slice; slice 10 measures plans, counts, bundle sizes and memory (D34, D35). Since revision 6 D34 and D35 moved to the pilot deployment slice as well (K23).
- **K7. "All four pilot scenarios in their MVP form".** Scenario 1's recording parts and scenario 2 step 15 are after the MVP, so the MVP form leaves them out; D40 says so in the scenarios file.
- **K8. One `/home` read against the narrower live refetch.** `GET /home` gathers every panel into one read, so a frame that touches one panel refetches all of them, which works against the goal of D18. D22 bounds the cost by fixed list sizes and coalescing; S2 also lists, per frame kind, whether it invalidates `/home` at all, and H1 measures `/home` under a burst of frames (since revision 6 in the pilot deployment slice, D50).
- **K9. A target is not a budget.** ADR-0018 requires a change to a check budget to land as its own change. C0b's 80 % is a measurement target for one change, not a standing budget, and C0a changes no limit; neither changes a check budget.
- **K10. A local run before an after-fix gate.** D11 requires the failed test to fail before the fix and pass after it with the same command before the gate; this goes beyond the wording of the owner's answer to Q6, which named only the passing run, and the owner approves it with this plan. An end-to-end or full backend run is a heavy run, so the coordinator schedules it like the others (D4).
- **K11. Phone layouts against the check budget.** A phone device project would add a fourth configuration to every gate. D29 keeps phone tests inside the existing projects at 360 px; if the 10.3 revision finds a page whose phone behaviour cannot be proven that way, it asks the owner.
- **K12. What slice 9 already delivers for results after a tutor's deletion.** Slice 9's D35 kept the read access; how much of the Past tutors row and its date the interface already shows is not recorded. B4 inventories it first (D26).
- **K13. `PATCH /tutor/settings` in the MVP.** `api.md` says the route is not registered in the MVP because recording retention comes after it and the onboarding dismissal with slice 10. S2 registers it with only the dismissal field and keeps that sentence's recording part.
- **K14. A seen marker against "a `GET` never writes".** Marking feedback as seen when the assignment page loads would make `GET /submissions/{id}` write. D25 uses an explicit `POST` sent by the page instead.
- **K15. Sub-slices and the roadmap's definition of done.** The roadmap's conditions apply to each sub-slice: requirements end to end locally, its pilot scenario segments, its checks, its documents, its merges through the gate and its own slice review, recorded under the slice as "Sub-slice 10.n closed at `<commit>`". Slice 10 closes when 10.5 closes.

D1 and T1 make each sub-slice count as a roadmap slice for that tier, with its scope defined by its list of changes rather than by a commit range, because a sub-slice's contract change may merge while the previous review runs, pending owner review, and 10.5's security reviewer also covers the cumulative diff since `c218028` per trust-boundary family.

## 9. Risks

- **The consolidation misses 20 %, or the median stays high.** Two consolidations of slice 9 saved little (its C1 3 s, its C2 nothing merged), and a 20 % end-to-end saving is about 60 to 100 s against gates of 640 to 716 s. D10 sends both cases to the owner with the measurements instead of merging a weak change, loosening coverage or blocking the carried fixes indefinitely.
- **The budget is crossed again.** Phone layouts, the home pages and web push add end-to-end tests. D5 runs every gate on an idle machine and puts a consolidation to the owner at the earliest unresolved sub-slice review whenever the median passes 540 s; D29 keeps phone tests in the existing projects.
- **Machine load and battery.** The power and load lines make slow gates explicable, not rarer. Heavy runs stay one at a time, measurements run on mains under `caffeinate`, and the owner keeps other projects' load off the machine during gates where possible.
- **`/home` grows expensive.** One read for every panel, refetched on frames. D21's bounds and D22's coalescing contain it; H1's burst measurement moved to the pilot deployment slice (D50), so until then the bound rests on those two and on the code-level review, and a per-panel split stays possible if the measurement shows a problem.
- **Push cryptography.** A home-grown RFC 8291 implementation can be subtly wrong. D32 requires RFC 8291's test vectors and RFC 8292's example, W3a reviews the cryptography apart from the network code, and the owner's interoperability check (D59, Q20 A) runs once against real browsers; iOS stays unverified until the pilot deployment.
- **Web push on by mistake.** A deployment could set `OVC_WEB_PUSH=on` before the decision record on minors and the legal assessment. D52's start-up guard refuses it outside a test or development database, a process test proves it, and only a separate change with the owner's decision lifts it.
- **A volatile host list.** Vendors may change their push-service hosts, which would make subscriptions refused or sends fail. The list comes from a dated research note, refusals are logged with the service enum, and a change of hosts is a code change that updates the note; until push is enabled the cost is nil.
- **Subscriptions outliving their session.** A path that revokes a session without the trigger, or a subscribe racing a revocation, could keep pushing to a shared browser. D55 enforces deletion at the data level, W2 tests every path and the race, and the worker checks the session again at send time.
- **The interface rework moves the settings page.** W4 builds its control on a page the rework may redesign. W4 starts after the phone stage has closed (D49, D63, since revision 7) and builds on the page as the stages leave it; the stage's plan says if it needs a decision of this plan changed.
- **iOS lapses.** Subscriptions of installed web apps on iOS are reported to stop silently. Push never replaces an email or an in-app notification (FR-13.5), the client shows the server's `subscribed` state, and the pilot measures it (`detailed.md`'s open question).
- **Phone layouts expand.** Every page in two roles, three engines and both themes. The design step bounds the scope before implementation, and revision 5 splits the work into five page groups (D42); a group that grows past one reviewable change is split again in its task plan, which says so.
- **Phone tests cost gate time.** Phone tests in three engines add runs to a gate whose median was 591.8 s at the 10.2 record, before traces were turned off. D43's target of about 25 s of wall time, measured from each gate's own output, the sweeps that replace today's per-page 390 px tests, and D5's rules contain it; a change above the target goes to the owner before it merges.
- **The entry chunk is nearly full.** 0.7 KB was left on 2026-11-19 (K21); G0 measures it again and counts the bytes of every new text; page texts that do not fit go to a feature section, while frame labels, needed on every page, could only fit through the owner's separate budget change.
- **Phone behaviour that the existing projects cannot show.** Touch-only behaviour is not emulated in Firefox and only partly in the desktop projects; the `@coarse-pointer` tag covers Chromium and WebKit, and anything beyond it goes to the owner (K11, D29).
- **Manual checks of the audit.** VoiceOver and Safari on iOS need a person and a device; the audit records them as `unverified` when not run, and the 10.3 slice review states what stayed unverified.
- **Flaky browser tests during 10.3's gates.** The assignment, reclaim and WebKit closure flakes of the known limitations may fail 10.3's gates; X4 runs early so their next failure names its cause, and the rerun rule of ADR-0018 applies unchanged.
- **Diagnosis without end.** H3 is bounded by run counts in its record, and a family not reproduced in the stated runs is recorded as such rather than chased indefinitely.
- **Plan revisions add overhead.** Three revisions, each with planning reviews. They replace detail that would otherwise be guessed now and rewritten later.

# Recheck tutor sessions after write serialization

Status: approved by the owner on 2026-11-01 after independent security planning review; both minor clarifications are incorporated. Implementation is authorized within this plan. Inspected baseline: `ecd74d8e165b54f5cde41f45884a48cb122ea8b2`, 2026-11-01. Resolves major S6-SEC-01 and its auth-family integration edges.

## Problem, outcome and decision

The account contract promises that tutor writes authenticated before block/deletion cannot act after the account is restored. Current tutor helpers in files, chat, tutoring and schedule acquire the profile lock and check only the present active state. Block revokes every session; unblock restores active while preserving relevant data. An already authenticated request can therefore resume after both transitions and mutate using a revoked session. Tutoring operations also change slice-6 channel membership, so fixing only upload and messages leaves the same boundary open through their producers.

The proposed correction covers every signed-in tutor write enumerated in the accounts specification's profile-lock rule: card/link/invitation mutations, group mutations, code regeneration, join-request decisions and student unblock, lesson creation/edit/cancellation, chat send/edit/delete and chat upload admission/publication. Carry the authenticated session identity through the service boundary and read the session in a separate statement after the existing tutor profile lock. Require the same account owner, a non-revoked, unexpired session and an active account before mutations, idempotency replay or outcome publication. Obtain a fresh injected-clock instant after acquiring the profile lock for this session-expiry comparison, using the existing `Clock.InstantWithin(ctx, repos.TestClock)` interface so the shared test clock does not acquire a second pooled connection while the transaction holds locks; preserve separately captured business timestamps where their existing contracts require them. Missing or unusable sessions return the existing structured unauthenticated refusal; upload settlement requests durable cleanup instead of publishing.

This intentionally also refuses a tutor operation when logout/password reset has already revoked its session before the recheck. It does not make logout globally linearizable with every in-flight transaction: logout does not acquire the profile lock, and a revocation committed after the recheck can still race that already admitted transaction. State changes serialized by the profile lock retain their existing ordering. This stronger recheck and its precise limit are explicit owner-approval scope, not an inferred change.

Tier: standard; security trigger met (T-2/T-5/T-21/T-29, storage/deletion T-13/T-34, resource bounds T-20 and safe diagnostics T-18). A separate security planning review precedes approval, followed by independent standard and full-security readiness reviews, affected checks and one exact-tree gate.

## Implementation boundaries and files

Inventory all callers of the tutoring/schedule acting-tutor helpers and the profile-lock rule before editing. Replace UserID-only authenticated mutation inputs with precise actor/principal types carrying UserID and SessionID; API routes pass the principal already obtained by authentication. Keep read-only lookups, anonymous invitation/code acceptance, background jobs and operator actions distinct: they do not impersonate a signed-in tutor and must not acquire invented sessions. Preserve existing public request/response schemas, roles, relationship scope, validation/refusal precedence, quota/rate charging and transaction boundaries. Do not add an unchecked legacy overload or optional session bypass for production callers.

Keep lock order unchanged: existing student user rows when required, tutor profiles, relationships/groups/channels/messages and later resources. Read session state after profile acquisition without adding a tutor user-row or session-row lock. Do not acquire a user lock after a profile. Reuse existing repository session reads and local error mapping. A small precise shared domain identity is allowed if useful; no dependency or new package is needed, and no generic architecture-rule exemption is proposed.

Expected production files include `backend/internal/services/files/chat_uploads.go`, `backend/internal/services/chat/release.go`, the tutoring service mutation files and `deletion.go`, schedule creation/edit/cancellation and `schedule.go`, and their API route callers. Existing service/API fixtures must seed real session rows and pass actual identities rather than bypassing the guard. Update `knowledge/specs/accounts.md`, `files.md`, `realtime-and-video.md`, `schedule.md` as needed for the shared contract, `docs/threat-model.md` with pending-owner-review wording, the cumulative security findings and a verification record. Any additional behavior, schema change or lock-policy change returns to approval.

## Checkable acceptance

- A real tutor upload is held in its existing local-S3 request barrier after initial authentication/admission. Real operator block and unblock complete before release. Publication returns 401, creates no pending/bound ownership or reference/charge, and the real worker cleans the known completed object according to the durable protocol. The test proves the previous implementation accepts the restored account through a retained negative-control result.
- Real account authentication captures an actor before block/unblock; each affected mutation family then calls its actual service with that same actor and real PostgreSQL. Send/edit/delete, group membership/archive, relationship ending, card/invitation/code/request decisions and lesson creation/edit/cancellation refuse without changing their business rows, frame/outbox effects or charge state. A refusal before admission reserves no rate slot. Schedule admission and business execution are separate committed transactions: check the session in both, on every retry and before replay, and retain an already committed admission attempt when the later phase refuses. Do not change the existing rate-accounting contract. Existing HTTP tests verify route-to-service identity propagation; where an existing sanctioned request barrier can prove authentication already completed, additionally use the real HTTP path. No mocked repository, patched handler or forbidden transport interception is introduced.
- Missing, foreign-owner, revoked and expired session cases refuse; a deterministic lock-wait test advances the injected clock past expiry before releasing the profile lock and proves the post-lock instant is used; a fresh active tutor session still succeeds. Already-committed logout/reset revocation is covered under the newly approved recheck semantics. The tests do not claim a stronger serialization guarantee for revocation committed after the check.
- Preserve the existing concurrent deletion/block tests and student session/reclaim checks. Account deletion/restore may revoke channel access permanently; test its applicable refusal without pretending restore reconstructs discarded links. Existing lock-order and global student-purge tests remain required.
- Observe safe existing error/outcome diagnostics and no raw session/token/body fields. Refused operations emit no successful business outcome. Rollback retains existing rate-slot semantics.

Use real services, database, local S3 and sanctioned fakes only. Verification includes targeted negative/positive integration runs, full backend race/static/generation checks, relevant existing production browser journeys, docs/scanners and the separate merge gate. All failed runs remain evidence; no timeout, retry, production rate limit or 260-second gate threshold is relaxed.

## Sequence and risks

Review and approve this plan, enumerate the complete signed-in caller matrix, implement precise identity propagation and checks, update real fixtures and regression cases, synchronize contracts/threat mapping, run checks, obtain independent readiness reviews, apply the after-fix rule, gate and finish. The highest risks are missing a caller that still drops SessionID, accidentally requiring sessions for background/anonymous operations, inverse locks, changing refusal precedence or letting idempotency replay bypass the check. The final record lists every covered mutation family and any explicit boundary left unchanged; a two-helper change alone cannot close the general finding.

## Security planning review

An independent full-profile planning review found no blocker/major. Two minor ambiguities were corrected above: both schedule transactions require the guard while retaining a previously committed rate attempt, and session expiry uses a fresh post-lock injected-clock instant. The reviewer confirmed real authenticated actors plus existing S3 barriers can reproduce the relevant state without forbidden mocks. The caller inventory explicitly includes tutoring cards, invitation emails, links, ending, groups, archiving, join requests and code regeneration; target-tutor checks for anonymous or student acceptance remain distinct from acting-tutor session checks. Runtime evidence is pending implementation.

# Slice 7: durable meeting recovery ledger

Status: approved by the owner on 2026-11-05. Security planning review passed; its two minor clarifications are included below. Baseline: main `01c3f8e1e8b78e8316cf1e09718d7cf89e02e11a`. This is the next local-first stage after provider discovery, not approval of API activation or a complete remote recovery guarantee.

## Problem and outcome

`meetings` currently cascades with `lessons`. A failed or cancelled Create can already have created provider state; an absent Inspect snapshot cannot rule out a later Create. Deleting business metadata must not delete the only provider identity and evidence needed for subsequent cleanup. The outbox is not that evidence: its dead rows have finite retention.

Deliver an independent PostgreSQL ledger, atomic business-row/ledger creation, conditional recording of a single create attempt and its acknowledged generation, durable cleanup eligibility on closure or purge, and bounded reads for a future recovery service. No provider calls, new HTTP routes, worker jobs, link issuance or UI are activated. This storage stage is necessary but does not itself clean provider rooms. The next implementation plan must add the bounded coordinator, outbox effects, operator recovery and activation policy before joins can be enabled.

Tier: standard. Security trigger: provider ownership, purge, generation binding and persistence. One independent security planning review before approval; separate standard and security implementation reviews, change checks and ordinary merge gate/finish. Earlier failed-gate exceptions do not apply. General repository check budget remains unchanged; no slice 6 budget tuning is included.

## Contract

### Identity and lifetime

Add `meeting_recovery` with an immutable opaque provider identifier as primary key, provider kind, nullable unique business `meeting_id` referencing meetings with `ON DELETE SET NULL`, and no account/lesson foreign key or retained account identifier. The meeting foreign-key index is explicit. Store no names, participant identities, routing key, credential, provider address or raw error. A fixed internal attempt identifier is concurrency evidence, never an authorization capability.

Store finite creation/update instants; create state `prepared`, `started`, `returned` or `uncertain`; nullable attempt identifier; nullable positive acknowledged create time; monotonic `cleanup_requested`; positive revision. SQL checks enforce valid state/attempt/generation combinations. The primary provider identifier and provider kind never change. Cleanup is required when the flag is set or the business meeting reference is NULL. Orphan detection cannot depend on retained owner identity. Closed business rows cannot be republished.

CreateUnderLessonLock inserts the meeting and ledger atomically, including when its existing caller uses a transaction; no window with a committed business row and no ledger is allowed. Use a single data-modifying SQL statement or an existing transaction-bound repository path that cannot be called in autocommit as two separate statements. Existing scoped identifiers and one-current-meeting constraints remain.

CloseUnderLessonLock sets cleanup_requested in the same statement/transaction as a successful close; a refused stale close must not mark a replacement or unrelated ledger. The existing already-closed result must preserve the cleanup obligation. Lesson/tutor purge sets the nullable meeting reference to NULL by its foreign key action; the ledger survives. Student purge retains tutor-owned meeting history as today. No new database trigger is introduced.

### Single-attempt evidence

- BeginCreate is a conditional prepared-to-started transition with an injected nonzero attempt identifier and expected revision. It requires a still-current creating business meeting, no cleanup request, and the caller's lesson lock. At most one concurrent caller wins. A second dispatch is refused, including after cancellation, timeout or process reconstruction. This stage adds no dispatcher.
- RecordCreateReturned binds the same attempt to one positive provider create time. Repeating exactly that evidence is idempotent; a changed attempt or generation is refused. It accepts late successful evidence from started or uncertain even after close/purge, without clearing cleanup or reopening business state. For an orphan it touches only the ledger and never reacquires a business lock.
- MarkCreateUncertain is conditional on the same attempt and started state. It records missing proof, not provider absence; it cannot overwrite returned evidence. Uncertain-to-prepared and started-to-prepared are forbidden.
- Existing OpenUnderLessonLock requires matching returned ledger evidence and no cleanup/orphan status in addition to its current business-state/generation predicates. It cannot publish a late result after closure or purge. The ledger result is not user authorization; later API scope/session rechecks remain mandatory.
- No settle, delete, retry-Create or operator-forget method is added. No elapsed time, absence observation or database lease is treated as remote fencing. Retained uncertainty is explicit. No automatic or physical erasure deadline is promised.

Lock order remains existing account/profile/lesson locks, then business meeting, then ledger. Any path holding only ledger state must not subsequently acquire business locks. A read of recovery candidates grants no authority to call End; the future coordinator must revalidate identity and generation. Revision versions explicit repository evidence transitions, not every physical row change: foreign-key SET NULL does not increment it. No publication or dispatch decision may rely on revision alone; it must check current business-row identity/state and the actual nullable reference and cleanup flag under the prescribed locks. Tests must hold the old revision across purge and prove refusal.

### Bounded access and migration

Provide typed keyset pagination for cleanup candidates, with repository-enforced batch size 1–100 and deterministic order by the immutable provider identifier. Add a partial index on that key with the complete predicate `cleanup_requested OR meeting_id IS NULL`; use the same predicate and key boundary in the query. Do not order by mutable update times or union two potentially overlapping pages. Invalid limits fail explicitly, never imply unlimited reads. Candidate reads contain only required ledger fields. Cursor tests cover mixed orphan/closed/prepared rows, exact page boundaries and no duplicate rows. Concurrent changes behind a cursor require a later scan from the beginning; there is no snapshot-completeness or starvation guarantee across transactions. The future coordinator must define scan restart/fairness. LIMIT bounds returned records, not wall-clock work; all reads use the caller's context/deadline, and implementation review must confirm the matching indexed access path without turning a planner choice on tiny fixtures into a flaky assertion.

Migration 00024 (or next free number after a base refresh) creates the ledger and backfills all existing meeting rows conservatively: positive persisted create time becomes returned evidence with a migration-specific typed provenance instead of inventing an attempt acknowledgement; a row without a known generation becomes uncertain, not prepared. Closed rows request cleanup. Preserve existing meeting fields unchanged. Final schema must distinguish legacy evidence from new attempt evidence explicitly (for example `origin = legacy | attempt` with appropriate checks); no synthetic attempt token can imply an actual dispatched operation. New rows use attempt origin. The migration never contacts a provider or interprets existing metadata as evidence of remote absence. Up/down/up checks use disposable fixture databases only. Downgrade must refuse while any ledger row exists, rather than destroy recovery obligations; empty-ledger down remains possible for isolated migration fixtures.

The allowed provenance matrix is explicit: attempt/prepared has no attempt ID or create time; attempt/started and attempt/uncertain have a nonzero attempt ID and no create time; attempt/returned has a nonzero attempt ID and positive create time. Legacy/uncertain has neither; legacy/returned has positive create time but no attempt ID. All other combinations fail SQL constraints. BeginCreate, MarkCreateUncertain and RecordCreateReturned refuse legacy origin; legacy returned evidence may only support the existing exact-generation business guards, never imply a newly dispatched call. The downgrade obtains ACCESS EXCLUSIVE on the ledger before the emptiness guard and retains it through DROP in the same migration transaction, so a concurrent insertion cannot pass between them. Use ordinary SQL for the guard, without DO, a new trigger or an unsupported StatementBegin block.

Ledger rows intentionally are not deleted in this stage. There is no process/API producer yet and no claim of a production total-size bound. Before activation, the next plan must specify admission capacity, terminal evidence, retention/operator handling and bounded reconciliation; activation remains blocked until those decisions and implementation are complete. Query page bounds are not a substitute for that requirement.

## Acceptance checks

Use real PostgreSQL with the actual repository and migration runner, not mocked SQL or transport. Named tests may be organized into the existing meeting fixture to avoid redundant setup while retaining distinct assertions:

1. `TestMeetingRecoveryAtomicCreation`: commit yields both rows; rollback yields neither; duplicate/current-lesson failures leave no orphan ledger; migration preserves existing identities.
2. `TestMeetingRecoveryTransitions`: invalid state/zero identifiers/generation/timestamp combinations fail; exactly one concurrent Begin wins using independent pools; mismatched attempts/generations and second dispatch are refused; exact repeated returned evidence is idempotent. Provenance is immutable through every repository operation. Legacy rows refuse Begin and attempt-origin uncertain/completion transitions; migration and transition tests explicitly assert these refusals.
3. `TestMeetingRecoveryLateCompletion`: close/purge before successful evidence retains the evidence and cleanup obligation; attempts to Open remain refused; stale evidence cannot affect a replacement meeting with a different provider ID. Exercise real row-lock barriers and both lock acquisition orders to prove termination without sleeps.
4. `TestMeetingRecoveryPurge`: existing tutor lesson purge and final account purge retain only the specified ledger fields; student purge retains tutor history; another tutor's state is untouched. Explicitly assert foreign-key nulling and continued candidate visibility.
5. `TestMeetingRecoveryPagination`: 0/101 rejected; pages of 1/100 deterministic over more than 100 rows, including overlapping requested/orphan predicates without duplication; retained uncertainty stays visible after store reconstruction.
6. `TestMeetingRecoveryMigration`: populated legacy creating/open/closed fixtures backfill conservatively; nonempty downgrade refuses and leaves obligations intact; empty round trip passes; repeat migration does not alter evidence.
7. Cancellation of a genuine blocked SQL transition returns the context failure, releases resources and does not claim a successful mutation. A subsequent real query observes authoritative state. Commit errors remain potentially uncertain, never rollback assertions without observation.

Negative controls in isolated copies remove the late-publication guard and the purge-preserving foreign-key action; the corresponding real tests must fail. The control copies never enter the final tree. Reuse current real PostgreSQL helpers and observed barriers; no new interception exception or dependencies.

## Coordination and risks

At most three active working sessions total including other projects. At entry another project chat is active; use one planning reviewer at a time, no heavy runs during planning. Before each heavy runtime check refresh other-chat status, actual processes/load, local services and sleep protection; run one heavy workload at a time. Do not alter another session's files, containers or processes. Normal check failures are preserved and handled under the repository after-fix policy, not automatic repeats or blanket historical exceptions.

Main risks are lock inversion through the SET NULL action, accidental false acknowledgement in legacy backfill, bypass through existing open/close helpers, indefinite retained evidence and mistaking a storage foundation for complete cleanup. Tests address the first three; the last two are explicit activation blockers for the next stage. BBB compatibility, media, browser rooms, callbacks and remote deletion guarantees remain unverified.

## Change 1: channel pagination focus

Observed mechanism: `ChannelList.tsx` appends a cursor on Show more but records no pagination focus intent. The existing removed-row hook observes list rows, not the Show more button. When the last page removes the button, focus can be lost. Shared behavior requires the first new visible row, or the last visible row/page heading when no visible row is added and the focused control disappears.

Files: `frontend/src/features/messages/ChannelList.tsx`, `MessagesPage.test.tsx`, `frontend/e2e/messages.spec.ts`, the narrowly approved one-shot channel-list failure in `frontend/src/lib/api/fakeChat.ts` and its structured-refusal/recovery contract check in `fakeTransport.test.ts`, the necessary pending-owner-review mapping in `docs/threat-model.md` for existing cache-scope/fake-fixture boundaries, and `knowledge/reviews/slice-6-frontend-review.md` or its descriptive follow-up evidence record. Reuse `components/ui/liveRows.ts` patterns; change that shared hook only if the focused behavior cannot remain local, with expanded consumer tests and a revised scope assessment first.

Implementation:

1. Record one pagination intent containing the clicked continuation cursor, current search/scope revision and ordered visible channel IDs before requesting the page. Block duplicate activation while that continuation is fetching without removing the focused control merely for a loading state.
2. After that same continuation successfully settles and its rows commit, focus the first newly visible channel link in display order. Deduplication against existing IDs must precede choosing the target. If it contributes no new visible row and Show more remains, keep focus on that control; if it disappears, focus the last visible link or the page heading. Do not focus an older page's first row.
3. A failed continuation retains its intent for an explicit successful Retry, without focus movement during the failure. Search changes, account/channel-list scope eviction, unmount and a superseding request discard the obsolete intent. Never allow a late revoked-page result to acquire focus or restore rows. Ordinary live refetch retains the existing removed-row behavior and does not consume a pagination intent for another revision.

Proposed named component tests: `channel show more focuses its first new link`, `final channel page without a new visible row restores focus to the last link or heading`, `channel continuation retry focuses only its new rows`, and `a superseded channel continuation cannot steal focus`. They assert `document.activeElement`; use the real fake HTTP adapter already governed by its contract, no request patching. Extend the real Messages browser suite with `channel pagination retains keyboard focus through the final page`, asserting `toBeFocused` for intermediate/final pages. Exercise both roles, English/Russian and light/dark across the affected browser matrix; include the narrow list-only route and a wide split layout. Preserve the existing held-continuation revocation test.

Negative control: in an isolated disposable copy/worktree at the recorded baseline, the last-page browser/component focus assertion must fail at the documented missing target. Apply any control patch only in that isolated copy and preserve its diff/evidence; never mutate the implementation worktree to manufacture a baseline. This plan grants no implicit permission for git restore, reset, destructive checkout or history rewriting, and never weakens the assertion. This is functional verification, not a new performance workload. Observability impact: no production diagnostics added; test evidence contains only fixed action/stage labels and counts.

## Change 2: distinguish live incremental history from reconciliation

Observed causal chain: `frames.ts` parses `seq` for message.new, but `RealtimeEvent` drops it. `app/liveRefetch.ts` treats every message and read event as changed(channelId); the coalescer marks both channel detail and history dirty. `Conversation.tsx` refetches every history page down to the oldest displayed sequence for every query invalidation. A displayed 1,000-message history therefore causes at least twenty sequential default-50 history reads for one live signal, before any follow-up read needed for an overlapping request. The architecture instead describes after_seq or the changed message page. This is a source mechanism discrepancy, not an established latency-budget failure.

### Owner decision required before implementation

Recommended decision: incremental reads apply only to known live message frames; first-ready/reconnect and other unclassified or authority-changing invalidations keep full authoritative reconciliation of the displayed history. Clarify the architecture text to name that exception and describe one scheduled coalescing wave per second rather than falsely promising one HTTP request total when a wave needs several changed-item or catch-up pages. The exact existing one-second cadence is unchanged. A reconnect can miss an edit or deletion anywhere in displayed history; after_seq alone cannot recover it. Unknown invalidation, scope change, stale-conflict refresh, signed-address renewal and explicit Retry must not silently become append-only.

Alternative: retain full history reconciliation for every invalidation and record the amplification finding as an owner-accepted limitation with a named future slice. This resolves no performance mechanism and cannot be presented as the architecture's incremental implementation.

Not proposed: append-only reconnect with stale older rows; clearing old displayed history to reduce work; a new change-feed/version endpoint; altered wire frames; relaxed diagnostic checks; new polling. If the owner wants one of those, stop for a separate contract plan. Approval must select the recommended clarification or an explicit alternative; this draft itself makes no normative exception.

### Implementable boundary and algorithm under the recommended decision

Files: `frontend/src/lib/realtime/client.ts` and its contract/tests; `frontend/src/app/liveRefetch.ts` and `.test.ts`; `frontend/src/features/messages/refetch.ts`, `api.ts`, `Conversation.tsx`, and a narrowly scoped `historyRefresh.ts` plus its integration tests if needed; `MessagesPage.test.tsx`; `frontend/e2e/messages.spec.ts`/`realtime.spec.ts`; an opt-in production-path request-wave probe under `frontend/scripts/`; `knowledge/architecture/detailed.md`, relevant realtime specification wording, `docs/development.md`, `docs/threat-model.md`, and descriptive evidence under `knowledge/reviews/`/`knowledge/analysis/`. List a new module in the frontend module map if introduced. No generated API or server route change should be necessary: the current typed endpoint accepts after_seq and limit.

1. Preserve parsed seq in a discriminated internal new-message event; updated/deleted events retain message ID without inventing a sequence. Keep strict frame validation unchanged. Route read.updated only to list/unread work; entity.changed channel retains detail/scope checks and conservative reconciliation. Preserve list first-page/unread and presence behavior.
2. Introduce typed history intents: catch up through observed seq, reread known cached message IDs, and full reconciliation. A per-query-client, per-mounted-channel owner serializes work and retains the existing epoch, channel-query identity, scope revision and cancellation/generation guards. It registers on mount and unregisters/cancels owned work on channel/account change, page suspension and unmount. Inactive conversations are not fetched merely because a frame arrived; their next mount performs authoritative initial/full reads.
3. Keep the default TanStack query function authoritative/full. Route known live intents through the same history owner, not a mutable global query-function mode that could accidentally turn a reconnect/focus/Retry invalidation into incremental work. Full query reads and incremental work share one sequencing barrier: let a running read finish, then reread from the state after that read if an event arrived meanwhile. A full request supersedes incremental intents it covers; events arriving after its start remain queued for a follow-up, preserving FollowingQueryClient's freshness rule. Do not abort the user's existing shared fetch just because a live frame arrives.
4. For new messages, use authorized typed REST after_seq starting at the greatest retained seq, with limit at most 100, and continue from the last returned seq until the captured frame high-water is covered. An empty/gapped result that cannot prove coverage, missing initial cache, a failed request or an unknown intent falls back to authoritative reconciliation or an explicit failure; it must not silently claim success. Handle more than 100 missed/new messages without dropping the tail. Merge REST rows by ID and sequence, preserve the oldest continuation cursor and ascending rendered order, and keep duplicate/out-of-order frames idempotent.
5. For updated/deleted IDs present in the loaded cache, resolve their known seq from that same scoped snapshot and fetch an authorized one-item page with after_seq=seq-1 and limit=1. Validate both ID and seq before replacing the cached REST row, including deleted/erased placeholders and attachment metadata. Never reconstruct message state from a frame. IDs outside loaded history need no fabricated row; list/unread/detail refreshes still run, and full reconciliation remains the safety path for an unknown/inconsistent result. Coalesce duplicate IDs; cap retained dirty metadata at a fixed bounded count and fall back to full reconciliation on overflow, rather than retaining an unbounded set. Choose the internal cap from the endpoint's existing maximum-page size during implementation, record it, and do not treat overflow as dropped work.
6. Cache publication rechecks account epoch, mounted channel/query identity, current scope revision and request generation. A 404 evicts through existing onUnavailable/evictChannel and takes notice focus; no late result can recreate removed history. Failed reads keep the existing safe error/retry behavior, drafts and focus. Read markers continue to derive only from visible rows and current versions, never from a frame or an unfetched seq. Conflict resolution still requires successful fresh channel/history reads and an explicit version-adoption action. Signed-file refresh retains authoritative renewal, and no removed attachment gets an old URL reinstated by a late incremental result.

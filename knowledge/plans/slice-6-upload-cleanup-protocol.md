# Durable chat upload cleanup protocol

Status: approved for implementation by the owner on 2026-11-01 after security planning review and scoped after-fix review. Approval includes the 30-second deadlines, one-second recovery-candidate budget, 4,096-intent capacity with structured 503 refusal, retained uncertainty, finite automatic cleanup and local operator recovery with indexed, paginated uncapped receipts. The owner accepted that ambiguous remote Complete does not guarantee automatic physical deletion. This plan addresses `S6-BE-03`, a major finding identified during the slice 6 backend review; approval does not close the finding or the slice.

The closure-record checkout was at `f9c7450928a17017bc34654159a5d27b9299147c`; the intervening erasure-deadline change does not modify the upload implementation. ## Problem, outcome and verification tier

`services/files/chat_uploads.go` detaches settlement and discard with `context.WithoutCancel` and retains an upload permit until they return. Pool acquisition, business-clock reads, row locks and storage calls can therefore retain an upload indefinitely. Merely adding a timeout is insufficient: account or tutor purge can remove the attachment, and a later completed object can lose its last cleanup owner when settlement cannot write to PostgreSQL. The existing T-34 residual already acknowledges an unreferenced object after settlement fails following purge. This plan must not silently enlarge or erase that residual.

The desired result is bounded request-side settlement with a cleanup owner committed before any storage operation, independent of attachment and account lifetime. The protocol must preserve a successful pending or bound attachment after an uncertain transaction outcome. Automatic cleanup uses the existing bounded outbox, and unresolved provider outcomes remain explicitly recorded rather than falsely reported as deleted.

Tier: **standard**. The security trigger is met by uploads, storage, purge, authorization rechecks, resource bounds, diagnostics and a proposed operator command. A fresh security planning review precedes approval. Implementation requires a fresh standard review and separate full security review, change checks, the exact-tree merge gate and finish. The implementation reviewer must explicitly recheck `S6-BE-03`. No implementation checks have run for this draft.

## Scope and decisions requiring approval

The proposal is limited to new chat multipart uploads, their settlement, expiry, account/tutor purge and storage deletion. Avatars retain their existing flow and existing residual; library and homework upload adoption is deferred to their slices. No browser protocol, file-size limit, membership rule, quota policy, storage provider or dependency changes are proposed.

Approval must explicitly cover all of the following, or require a revised plan before code:

1. One 30-second monotonic budget for detached request settlement/discard, and one 30-second budget for a recovery pass and for each intent-aware storage effect. Each recovery candidate additionally has a proposed one-second monotonic budget, capped by the remaining pass budget, including pool acquisition and every lock/SQL wait. Existing earlier caller or shutdown deadlines win. Both thirty seconds and one second are proposals, not interpretations of the current contract.
2. A global capacity of 4,096 unresolved intents, enforced before creating a new chat upload. Full capacity returns structured `503 service_unavailable`, the existing API error code, without promising a recovery time or automatically replaying the upload. Extend its documented uses to this capacity refusal; do not silently reuse a per-user rate-limit response. Capacity rejection reads no body and creates no storage upload. Existing four-per-user and 32-per-instance concurrent limits remain.
3. Uncertain and failed intents survive normal outbox retention and account purge, consuming capacity until safely resolved. They contain opaque technical identifiers, no account or channel identifier, filename, content or session credential. This retention and the denial of new uploads during a sufficiently large unresolved backlog are explicit availability/privacy trade-offs.
4. A local, audited `ovc-admin uploads` inspection/retry workflow. Receipts of explicit operator attempts have no total count cap and remain for an unresolved intent to prevent replay; the 4,096 limit bounds intents, not all journal bytes. Only privileged deliberate actions can grow these receipts. Automatic retries remain finite. No administrative HTTP route, automatic resurrection of dead work, or arbitrary operator-supplied storage key is introduced.
5. Acknowledgement that finite retries and an ambiguous remote Complete cannot guarantee eventual object removal. The protocol guarantees preservation of cleanup ownership, subject to database durability, and automatic removal in the named recovery scenarios; persistent storage failure or an unresolved remote operation may require operator/provider intervention.

If retaining unresolved intents or the capacity refusal is rejected, this design needs a different approved retention/fencing mechanism. Removing the cap would leave database growth unbounded under repeated failures. Deleting uncertainty records after a time limit would restore the orphan risk.

## Storage semantics and limits of the guarantee

An S3-compatible client timeout cancels local waiting; it is not proof that an accepted storage request cannot finish. A successful Abort, `NoSuchUpload`, an absent object, an expired worker lease, process shutdown and elapsed wall or business time are not by themselves a terminal fence for a previously submitted Complete.

The official [CompleteMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html) describes assembly after the request is received, processing that can take minutes, and errors inside an initially successful HTTP response. The [AbortMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_AbortMultipartUpload.html) warns that concurrent part uploads may still finish and repeated aborts can be needed. These sources do not establish the cross-operation terminal fence this design would need to forget an ambiguous Complete. They also do not certify another S3-compatible provider. Before implementation, record dated provider research separately under `knowledge/research/`; human-facing documentation states the qualitative limitation and links to that evidence.

Use one application Complete invocation per upload and explicitly disable SDK retries for that invocation, so a successful response cannot conceal earlier client retries still awaiting an outcome. The same one-attempt rule applies to Create, whose upload ID must be known before streaming. Confirm the installed SDK's per-operation options from its local source. Part uploads may retain their existing bounded behavior. This proposal does not add automatic Complete replay. A definite successful Complete response, with no other invocation issued, establishes completion for that producer. Errors are conservatively ambiguous unless the adapter can prove that no request was submitted; no new error-text heuristics establish that proof.

The existing bucket lifecycle aborts incomplete multipart uploads. It does not delete completed objects. The Create-before-ID-persistence residual remains: an unknown incomplete multipart upload can require lifecycle cleanup. No part or Complete is permitted before the ID-persistence commit is confirmed, so that window cannot create a completed object through this protocol.

## Persistent model

Add `upload_intents`, a small business cleanup journal owned by the files repository. A separate journal is justified because outbox `done` and `dead` rows are retained for only seven and thirty days, an effect lease must not be held for the duration of an HTTP upload, and a successful Delete can precede a late Complete. The outbox remains the only automatic executor of storage side effects.

| Column | Contract |
|---|---|
| `attachment_id uuid PRIMARY KEY` | No foreign key; survives attachment and user deletion; never reused. |
| `storage_key text UNIQUE NOT NULL` | Exact server-generated chat key, never reused and never returned to a client or logged. |
| `multipart_upload_id text NULL` | Allows exactly one transition from NULL to the returned ID, including after cleanup is requested. A non-NULL value cannot be replaced. No browser exposure or logging. |
| `phase` | Named enum: `opening`, `streaming`, `completing`, `cleanup`, `uncertain`. |
| `completion_started boolean` | Monotonic; set durably before the sole Complete invocation is allowed. |
| `completion_confirmed boolean` | Monotonic; set only from the producer's definite successful Complete response, never from age or an absent object. |
| `cleanup_requested boolean` | Monotonic publication revocation; once true, pending transition is forbidden. |
| `final_cleanup_required boolean` | Set atomically with a definite completion acknowledgement when generation 0 already exists; retained while a manual cycle delays generation 1. Generation 0 cannot retire an intent with this flag. |
| `cleanup_generation smallint NULL` | No generation, initial generation 0, or final generation 1; never wraps or advances further automatically. |
| `cleanup_outbox_id uuid NULL` | The current generation's fixed row ID, no cascading foreign key. |
| `cleanup_result` | Named enum: `none`, `queued`, `deleted`, `failed`; describes the current generation's attempt result, not a provider fence. |
| `created_at`, `updated_at` | Business instants for scheduling and diagnostics, never evidence of remote termination. |
| `error_code` | Nullable finite safe code, no raw error. |

SQL checks enforce valid combinations; conditional repository updates preserve immutable identity and enforce monotonic transitions. Add an index supporting bounded candidate selection. Operator retry receipts use `(attachment_id, attempt_id UUID)` as their unique key, with an immutable outbox ID and cycle status. Retain receipts until that intent is terminally removed, independently of outbox retention; an absent intent cannot be recreated by an operator retry. Receipt insertion requires an explicit operator command and never happens on a scheduler scan. Receipt growth follows explicit operator-authorized cycles, not automatic retries; inspection reports that count. A single capacity row contains `used` and has `0 <= used <= 4096`; every insertion increments it and every terminal removal decrements it in the same transaction. No count-then-insert race is allowed. The capacity row is locked last, with no subsequent account, channel, attachment or intent lock acquisition.

`cleanup_result=deleted` means a specific Delete completed. An intent with `completion_started=true`, `completion_confirmed=false` remains `uncertain` even then. There is no independently expiring intent lease that purports to terminate the storage writer.

## Transaction and request protocol

1. **Admission:** acquire the current user/profile and channel locks and perform existing checks. Create attachment and `opening` intent together, reserve capacity last, then commit. Do not call S3 unless this commit is confirmed. An uncertain commit leaves at most a row with no initiated S3 operation.
2. **Create:** invoke Create outside transactions using the request's bounded context. Record the returned MPU ID in the intent and, if still uploading, in the attachment in a short transaction. Check the affected-row results. The intent permits NULL-to-ID even after cleanup is requested or generation 0 is queued; recording the identical non-NULL ID is idempotent and a different ID is refused. No bytes or Complete may be sent until this commit is confirmed and the same transaction confirms that publication has not been revoked. If purge removed the attachment but the intent remains, retain the ID in the intent, preserve cleanup and return a refusal. If the intent has already been terminally removed while Create was in flight, do not recreate it or reserve capacity again: send no part or Complete, attempt a bounded abort of the returned ID and return a refusal. If that abort or ID persistence cannot complete, the remaining object is an incomplete MPU subject to the existing lifecycle residual, never an authorized completed object. A missing intent therefore prohibits creation, parts and Complete, but permits this bounded abort of the just-returned ID.
3. **Streaming:** preserve current limits, checksums, filtering, no-spooling rule and transport deadlines. Parts use the recorded ID. No database transaction spans storage streaming.
4. **Authorize Complete:** lock the existing attachment, then its intent; recheck uploading state, matching key/ID, `cleanup_requested=false` and `phase=streaming`. Atomically set `completion_started=true`, `phase=completing`. Only a confirmed commit authorizes the single Complete invocation. A commit error never triggers Complete. Later purge can revoke publication, but cannot revoke a request already authorized in this way.
5. **Complete and inspect:** perform the single storage Complete. On definite success, carry that acknowledgement in the producer's local state; persist `completion_confirmed` within the shared settlement budget. A container inspection can still refuse publication. Storage success does not bypass any existing inspection or authorization check.
6. **Publish:** under the existing account/session, channel and attachment checks, lock the intent and require matching identity and no cleanup request. Atomically change the attachment to pending, with all metadata and expiry, and remove its intent/release capacity. This transfers ownership to the existing pending/bound/reference lifecycle. The producer cannot issue any later write or Complete for that key.
7. **Uncertain publish commit:** do not run unconditional MarkDeleted. Reconciliation rereads the durable state under locks. A pending or bound attachment with the matching key and no intent means ownership was transferred; never delete it. An uploading attachment with an intent can be revoked for cleanup. A missing attachment with an intent requires cleanup. Database unavailability returns uncertainty without issuing a destructive guess. A missing attachment and missing intent permits no new storage write or Complete; ordinary successful deletion may already have completed. The late-Create bounded abort exception is limited to the just-returned ID as specified above.
8. **Failure/disconnect:** request cleanup in one short transaction where possible. Do not reset the deadline between settlement, acknowledgement persistence and discard. When the deadline ends, return and release the permit; no goroutine continues holding the permit or 8 MiB buffer. Persisted intent, not process memory, is the recovery owner.

Account/tutor purge, failed upload and expiry change the attachment and intent together where the intent exists, requesting cleanup before removing the attachment. Generic storage-delete producers for an upload with an intent must route through that intent; they must not create a second independent job that can delete after publication. Existing pending/bound uploads, for which the intent was atomically removed, retain the ordinary deletion and purge retry contracts.

## Cleanup generations, recovery and operator work

Creating initial generation 0 is atomic with publication revocation, using `storage_delete:<attachment>:intent:0`. Its immutable payload contains only attachment/intent ID, exact storage key and cleanup generation (or the fixed operator attempt UUID for manual work); it does not snapshot MPU ID. Under attachment-then-intent locks, workers validate immutable identity and read the journal's current MPU ID before each attempt. NULL-to-ID after enqueue is valid and must not become a malformed-payload or key-mismatch failure. No caller can replace the key or a recorded non-NULL MPU ID. Generation 1 is allowed exactly once after a definite Complete acknowledgement if initial cleanup was already scheduled; the acknowledgement atomically sets `final_cleanup_required` so deferring enqueue behind an active manual cycle cannot lose that obligation; it uses `storage_delete:<attachment>:intent:1`. Creating final work in advance of initial completion is safe because cleanup is irreversible and neither generation can publish. A late initial finisher cannot overwrite the journal's generation-1 result.

Each storage effect uses a bounded context, aborts the currently observed MPU where applicable and deletes the object outside a database transaction. Its final transaction locks attachment then intent, rechecks immutable identity, current generation and current MPU ID, and records its result. If the worker read NULL but a late Create recorded an ID before this final check, it must not report terminal success or remove the intent: release the transaction, read and abort that ID and repeat Delete within the same effect deadline, then recheck again. There can be only one NULL-to-ID change, so this reconciliation loop is bounded to one additional storage sequence. If its remaining budget is exhausted, the existing job follows ordinary retry/failure handling and retains the intent. A different non-NULL ID is a protocol violation, not a retargeting instruction. If the final locked check still sees NULL, no Complete was authorized and cleanup is irrevocable, the worker may remove the intent and release capacity; a Create that returns afterwards follows the bounded-abort/lifecycle rule above. Removal otherwise requires either that no Complete was authorized and the latest recorded MPU was handled, or that completion was definitely confirmed and this deletion generation was selected after that confirmation. A producer that authorized Complete but never sent it is conservatively uncertain; a time threshold cannot distinguish it from an in-flight remote request.

Eight attempts and existing backoff apply to each generation, including expired claims. An effect or finalization timeout retains the intent. A dead row causes a durable failed result where the worker can record it; if that recording fails, recovery reconciles against the fixed outbox ID. It never invents a fresh ID because an old row disappeared. Preserve the journal result independently of outbox retention. Scheduler scans do not resurrect failed work. Two automatic generations are the maximum, not two generations per scheduler tick or purge.

Add `uploads.recover` to the existing scheduler, once per minute, with one proposed 30-second monotonic pass budget including SQL waits, at most 200 candidates per batch and 20 batches per pass. Both selection and cursor advancement are bounded by that same pass deadline; its in-memory cursor consumes constant space. Select by indexed due state and stable attachment-ID keyset order, without locking candidate rows early. For each candidate create a child context with the lesser of one second and the remaining pass budget, then acquire attachment and intent locks in the business order and recheck state. Cancellation rolls back only that candidate; after the transaction has ended, advance the scan cursor past its ID on both success and failure so a locked first candidate cannot consume the whole pass. Preserve the scan cursor in the worker service between passes and wrap only after exhausting the keyspace; a restart starts a fresh scan and repeated restarts can delay progress, which is not claimed as starvation freedom. Two workers may inspect the same candidate; conditional journal/outbox updates remain idempotent. Do not use early `FOR UPDATE SKIP LOCKED` on intents to bypass the business lock order. A pass reports partial failure when any candidate failed, while continuing later candidates within its overall budget. It handles missing attachments, expired uploading attachments, unqueued cleanup and outbox-result reconciliation. It does not repeatedly enqueue for `uncertain/deleted`, run S3 inside a transaction, add a scheduler goroutine or claim unbounded outbox work. Current business-age rules may revoke an active upload when the test clock advances; this cannot establish completion or remove its uncertain journal.

The known regression is recovered automatically when cleanup could not be queued or dispatched until after the late successful Complete: the durable intent supplies the key after purge and generation 0 deletes the actual object after database recovery. If initial cleanup already completed, a later confirmed producer acknowledgement creates generation 1. If acknowledgement itself is lost and a remote Complete can still arrive after the final bounded attempts, the journal remains uncertain and automatic deletion is not guaranteed. This is an explicit proposed residual requiring owner approval, not a passed version of the stronger guarantee.

Proposed local commands are `ovc-admin uploads inspect <attachment-id>` and `ovc-admin uploads retry-cleanup <attachment-id> --attempt <uuid>`. The caller supplies and reuses that UUID when retrying an uncertain CLI result; the command never silently generates a new attempt UUID. Inspection reports state, existing attempt UUID/outbox status and safe identifiers, not storage credentials, keys or file metadata. Attempt history uses stable keyset pagination with at most 100 receipts per response; UUID deduplication is indexed. No query under the intent lock scans all historical receipts. Under attachment-then-intent locks, one transaction first looks up the receipt for this UUID: if it exists, return that exact cycle/status without granting another eight attempts, even after its outbox row has expired. If the intent has been removed, return already resolved/not found and create nothing. For a new UUID, use an indexed active-cycle lookup under the intent lock, rather than scanning receipt history, to atomically check automatic and manual cleanup for that intent; any pending or in-progress cycle refuses the new request and returns its identity. Only with no active cycle may the transaction insert the unique receipt and one fixed outbox row, granting eight bounded attempts using the existing policy. All producers of automatic/manual work serialize on the same intent lock, and automatic generation 1 must defer creation while a manual cycle is active; its required generation remains recorded for recovery after that cycle ends. A manual retry never resets automatic generations or another receipt. An old UUID cannot acquire new attempts after a newer cycle or ordinary outbox retention. Manual retries may remove an object but do not clear unproven completion uncertainty. Do not implement a generic force-forget or a flag that asserts a provider fence without evidence. Provider-specific terminal reconciliation and any later exceptional removal of an uncertain record require a separately documented operational decision. Filling capacity while uncertainty cannot be resolved is a possible fail-closed outcome, not an automatic reason to discard evidence.

## Locks, clocks and shutdown

Preserve the global account/profile, relationship/group, channel, message and attachment order. Append intents after all attachments in sorted attachment-ID order, and the capacity row last. A path must not lock one intent and subsequently acquire another attachment, channel or account lock. Purge first stabilizes and locks its affected attachments in order before locking their intents; recover selects candidate identifiers without premature intent row locks, then locks attachment if present and intent. Outbox bookkeeping is last and must not call back into earlier business locks. Claims commit before the effect obtains these locks. All transactions remain free of S3 calls.

The request's detached phase uses the lesser of the remaining process drain and its single 30-second budget. Shutdown cancels it when the existing 40-second drain ends; cleanup must not extend shutdown to 70 seconds. The monotonic deadline also covers business-clock reads and pool waits. The cancellation source must be provided by process lifetime wiring, not just a detached HTTP context. A constructor timing setting enables short deterministic test deadlines; production constants remain the approved values. No new environment variable is presumed necessary.

Business time controls daily quota, attachment expiry and scheduler due times. System monotonic time controls network, settlement and recovery execution bounds. Advancing the shared business clock neither cancels an already authorized remote request nor certifies storage absence.

## Observability, risks and check evidence

Add structured lifecycle events for cleanup requested, settlement deadline, completion uncertainty, recovery failed/completed, capacity rejection and explicit operator retry. Use safe error kinds, attachment/intent and outbox identifiers, phase/generation and bounded counts. Do not log storage keys, MPU IDs, filenames, credentials, contents or raw errors. `upload.accepted` requires confirmed publication; a successful Delete with uncertain Complete is not `cleanup.completed`. Keep uncertainty visible after ordinary outbox retention. Repeated scheduler scans of unchanged uncertain/dead state do not emit an ERROR every minute; emit transitions and operator inspection provides current state.

Threat mapping: T-20 covers bounded permits, batches, queue attempts and the capacity trade-off; T-34 covers purge-independent ownership, delayed retention and explicit unresolved outcomes; T-18/T-19 cover safe diagnostics and retained technical identifiers; T-22 covers local operator authority. Recheck T-13 and relationship/session authorization threats for publication and stale deletion. No new test-policy exception is proposed; if one becomes necessary, T-41 and ADR-0009 require their own approved change.

The highest risks are false terminal evidence, deleting an already published attachment, inverse purge/intent/capacity locks, lost failure evidence when outbox rows expire, and migration alongside old writers. The cap deliberately turns indefinite uncertainty into visible admission failure rather than silent growth. Global capacity serialization adds a short database lock; measure contention with the approved 32-upload workload instead of assuming it is free. Retained technical keys still require data-minimization review. Existing finite-retry dead-object residuals remain, and uncertainty must not be described as physical erasure.

## Proposed boundaries

1. Arm exactly once before the owned authenticated document navigation with the existing exact origin/method/path/full-query targets: unread, initial list and initial current channel. Keep the original absolute readiness deadline of 30 seconds.
2. Enroll only the first request identity of each target, at its start, before that absolute deadline and before initial settlement is sealed, while the same owned document/account/scope remains valid. WebSocket ready and another target's completed response no longer prevent enrollment of an initial target that has not yet mounted. They remain observed readiness/completion evidence. They never rearm an enrolled target.
3. A successful complete first response permanently prevents a cancellation allowance for a later request of its target. Only the enrolled first identity can have one explicit engine cancellation. Its exact second identity must complete its entire response with status 200 before the same original deadline; a third request cannot repair it. Preserve callback-reordering support and all raw failure counts. Reject unknown/repeated/non-cancellation failures and late or missing/failed replacements.
4. Close all remaining enrollment irrevocably at the first completed initial settlement, deadline, document navigation, SPA scope transition, account transition or scope loss. Initial settlement retains actual account validation, WebSocket ready, completed authoritative after-ready reads for all three targets plus history, seeded visible history and composer, and owned HTTP quiescence. The observer explicitly seals before allowing the journey to leave the initial page. No retry, reload, reconnect or channel revisit rearms it.
5. After sealing, cancellations fail even if the absolute deadline has time remaining. All non-target failures, HTTP failures, console warnings/errors and page errors retain their existing strict rules. The shared production collector gets no cancellation allowance. Bounded diagnostics report categories/counts only.

## Alternatives and risks

Removing StrictMode, changing production QueryClient cancellation/defaults, forcing requests to start together, holding unrelated requests to fit the global cutoff, suppressing browser events or broadening the shared collector would change the workload or hide failures and are not proposed. Per-target initial enrollment is a verification-contract change and needs explicit owner approval after security planning review. It does not prove that every arbitrary early cancellation is caused by StrictMode: acceptance still requires the declared all-target producer and browser counterfactual controls. If exact identity, lifecycle causality or sealing cannot be established, stop without widening the rule.

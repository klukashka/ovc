# Parsed-document capture for browser readiness evidence

Status: approved by the project owner on 2026-11-04, including bounded cleanup and one seven-case execution. Standard tier; security trigger T-18/T-19/T-41. No production change or diagnostic exemption.

## Evidence

The previous approved follow-up passed 883 component tests, all eight frontend check commands and 18 strict native controls. Its single eight-case execution passed Chromium account switching and failed the six Firefox cases and WebKit reset. The Firefox warnings persisted with a plain Document wrapper. ## Scope and implementation

Change only frontend/e2e/realtime.ts, existing native/state controls and English verification/contract documentation (docs/development.md and docs/threat-model.md wording pending owner review). Retain the ordinary wrapper containing the real Document reference. For a committed document, directly await public page.waitForLoadState('domcontentloaded', { timeout: 5000 }) before obtaining that reference. Track and join that actual promise; never use Promise.race or timeout:0. Keep all request/response/socket/navigation listeners active from their original installation, and keep recording their exact ownership and generation throughout the wait. This is not a sleep, timeout extension or exclusion of in-flight requests.

Capture binds to the generation that requested it. Check generation/disposed status after the lifecycle wait and before evaluateHandle; a superseded wait cannot capture a newer document as the old owner. Check ownership again after handle creation and dispose any superseded handle. A current owner's lifecycle or evaluation failure fails closed. Readiness requires completed current-document capture, not just socket ready; release/navigation resets that eligibility synchronously. Same-document identity checks await the same capture promise, preserve the actual Document comparison and cannot revive a failed owner. Disposal joins the actual lifecycle waiter before returning and may therefore take up to five seconds while a document remains blocked. This bounded cleanup delay requires explicit owner approval; immediate disposal is not claimed. A superseded/disposed wait resolves without installing a handle only after the actual waiter has settled. A current-owner timeout remains a failure. The five-second wait is not a restart or extension of the existing overall readiness assertion deadline; repeated generations and late capture cannot prolong that assertion. Keep the existing page/action limits for the synchronous reference evaluation, track it separately, and join/dispose its returned handle. Never close a borrowed page to force cleanup.

Add a real local entry-module hold-and-forward control (not a stylesheet-only assumption): directly observe that DOMContentLoaded has not fired while the existing module is held, and readiness cannot pass. Record request/response/socket ownership from the same original installation. Release the module unchanged, then require the actual DOMContentLoaded event, successful current-document capture and normal readiness. Add a superseded-document/disposal control across the same hold: disposal must settle after the real bounded waiter ends while the module remains unreleased, no old waiter may install a new-document handle, and every listener/handle/hold must be released. Use only permitted route hold plus unchanged fallback/continue and condition deadlines. No synthetic response, browser event or sleep. These controls explicitly test the added maximum cleanup delay, not a larger readiness or application timeout.

## Risks

DOM lifecycle waiting must not assign a later navigation to an earlier generation or leave disposal waiting indefinitely. Delayed capture must not delay network enrollment or let a pending API request escape readiness. DOMContentLoaded may not eliminate the warning; that outcome is a failure, not grounds for a broad warning allowance. Browser-level early page actions outside this observer remain visible to diagnostics.

## Planning review

Initial security planning review found two majors: cancellation was unspecified for a public waiter without AbortSignal, and a held stylesheet did not itself prove delayed DOMContentLoaded. The revised design directly joins the bounded public waiter and explicitly requests up-to-five-second cleanup; the control holds the real entry module and asserts lifecycle ordering directly. Planning recheck accepted this alternative with unchanged overall readiness deadlines. No implementation or browser execution followed.

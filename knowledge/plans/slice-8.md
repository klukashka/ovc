## 1. Problem, outcome and scope

**Problem.** A tutor can schedule lessons, talk and share files in chat and meet in a video room, but cannot keep teaching materials or build an assignment. FR-6 (library) and FR-7 (builder) are unbuilt: no folder, material or template table exists, the upload route refuses the `library` and `prompt_image` contexts, lessons cannot carry materials, and the room gets no presentation. Slice 9 (issuing, completing, checking) snapshots templates, so it cannot start before them. Pilot scenario 2 stops at step 5.

**Outcome.** End to end through the real API, worker, PostgreSQL, the local S3-compatible server and the production frontend build:

- a tutor keeps materials (an uploaded file with a title) and assignment templates in folders nested at most three levels deep, finds any item by a substring of its title across all folders, and renames, moves and deletes them;
- a tutor builds a template from the eight block types in the builder, with autosave, a stale-edit notice that keeps unsaved text, reordering by drag and by keyboard, up to three images per prompt, and library materials as blocks;
- the preview shows the template as a student will see it, without any answer key, explanation or points;
- a tutor duplicates a template, which shares its files through new references, and deletes it, which releases files used only by it;
- a tutor attaches library materials to a lesson at any status and to a series, and the lesson's audience downloads them from the lesson page;
- when a lesson has an attached PDF, the meeting is created with the first one as its presentation, proven against the fake provider;
- every library file counts once against the tutor's quota, every download is authorized through a reference the caller can see, and the purges remove the library with its files;
- Today's first-run checklist shows "Create an assignment".

**In scope:**

- FR-6.1, FR-6.2 and FR-6.3 for templates (the "never changes issued work" half is proven in slice 9, which creates issues); FR-7.1 to FR-7.5 for building and previewing (automatic checking itself runs in slice 9, on submission);

## 3. Decisions the plan proposes

Each names the alternative and the reason. S1 lands them in the specifications; `docs/` changes in S1 are marked pending owner review.

### Library

- **D1. One service, `internal/services/library`,** owns folders, materials, templates and the template's student projection; it is already in the [module map](../architecture/detailed.md#backend-backend) and is covered by the existing `internal/services` row of the package-layer table; no layer row changes for it. *Alternative:* folding it into `homework`, which would mix tutor-only content with student-facing submissions.
- **D2. Library writes take the tutor's profile lock first** and answer `401 unauthenticated` unless the tutor is `active` or `unverified` under it, as lesson and chat writes do ([locks and the session re-check](../specs/accounts.md#locks-and-the-session-re-check)); every write that creates or removes a quota charge then follows the charge lock order. This also serialises folder moves, so the cycle and depth checks of D3 cannot race.
- **D3. Folders.** A name of 1 to 100 code points without control or format characters, unique among siblings by its normalised form (`422 validation_failed`, `body.name: taken`). Moving a folder into itself or a descendant, or so that any folder ends deeper than three levels, is refused with `validation_failed` (`body.parent_id: invalid`). Only an empty folder is deleted (`409 not_editable`, K5): one with no child folder and no non-deleted material or template; soft-deleting a material or template sets its `folder_id` to null, so a deleted item never blocks or breaks a folder deletion. Deleted folders leave the table directly, as the data model's pure-link rule allows. `GET /library/folders` answers every folder of the tutor unpaginated (bounded by D4), for the folder tree and the Move dialog's destination picker.
- **D4. Per-tutor caps** (T-20): 1,000 folders, 10,000 non-deleted materials and 2,000 non-deleted templates, plus 50,000 material and template rows in all, deleted ones included until the purge, refused with `validation_failed` (`too_many`); the caps are constructor settings, so tests use small ones. *Reason:* the file quota bounds bytes but not rows, and D5's search scans one tutor's rows. *Alternative:* no caps, leaving rows unbounded.
- **D5. Listing and search.** `GET /library?folder=&q=&limit=&cursor=` answers the current folder (`null` at the root) with its path of at most three ancestors, its child folders unpaginated (bounded by D4), and its materials and templates keyset paginated by `(normalised_title COLLATE "C", kind, id)`; with `q`, it answers every matching material and template across all folders instead, each with its folder path. `q` is normalised by text normalisation version 1 and matched as a substring with `%`, `_` and `\` escaped; a `q` that normalises to empty is refused (`query.q: required`). Search scans the tutor's rows through `(tutor_id, normalised_title, id)` indexes, without `pg_trgm`; D4 bounds the scan. The answer carries `template_count`, the tutor's non-deleted templates, which the checklist reads (D33). *Alternative:* a trigram index, which adds a database extension for a bounded scan. `GET /library` is fetched by Today only for the checklist (D33), with `limit=1`.
- **D6. Text normalisation version 1** lives in `internal/domain` as a pure function with unit tests for every step, idempotence and the Russian cases, using `golang.org/x/text/unicode/norm` for NFKC and `golang.org/x/text/cases` for case folding; `golang.org/x/text`, the Go team's package already present as an indirect dependency, becomes direct and gains a stack-table row; the package-layer row of `internal/domain` changes from "standard library only" to "standard library and `golang.org/x/text`", and a depguard rule in `backend/.golangci.yml` keeps `golang.org/x/text` inside `internal/domain`. Number parsing version 1 lives beside it, parsing into `math/big` rationals, so slice 9 needs no new parser. *Alternative:* hand-written folding tables, which would drift from Unicode.
- **D7. Materials.** `POST /library/materials {attachment_id, title, folder_id}` binds the caller's own unexpired `pending` upload of the `library` context, creating its `material` reference and, when needed, the tutor's charge (`507 quota_exceeded`); any other identifier answers `404`. A title holds 1 to 200 code points, as a template title. `PATCH` renames and moves; the file is never replaced. `DELETE` sets `deleted_at` and removes the material's own reference; templates, lessons and series that use it keep theirs ([library](../specs/homework.md#library)).
- **D8. Library rows are tutor-only.** Every library route resolves identifiers within the caller's own library and answers `404` otherwise; students reach no library route (`404` for the role, as every tutor route). Library routes are `tutor, unverified ok`, as the API table already says, because an unconfirmed tutor shares nothing with anyone; uploads of the library's two contexts are the exception (D20, Q9), because they consume storage.

### Templates and blocks

- **D9. Block shape.** One `TemplateBlock` struct with `id`, `type` and the optional fields of every type; the service refuses a field that does not belong to the block's type (`not_allowed`). The frontend parses blocks into a discriminated union at the boundary in `features/builder`. *Alternative:* an OpenAPI `oneOf`, which huma and openapi-typescript handle poorly for this shape.
- **D10. Identifiers.** Block and option identifiers are version 4 UUIDs generated by the client (`crypto.randomUUID`), checked for format and uniqueness within the template; duplicating keeps them, because they are unique only within a template. S1 also decides now that a slice 9 snapshot issues fresh random option identifiers, so two issues of one template under different answer policies never share them ([answer visibility](../specs/homework.md#answer-visibility)).
- **D11. Field limits** that the specification leaves open (K2): a prompt and an explanation hold up to 10,000 code points, as an instruction; each accepted answer up to 500; a `long_text` block's maximum length is 1 to 20,000; a `file` block's allowed kinds are a non-empty subset of `images`, `pdf`, `office`, `audio`.
- **D12. Two levels of validation** (Q2 A). Structural rules always refuse a save with `422 validation_failed` and field paths: types, identifiers, the upper bounds of every count and length, points from 0 to 100, at most 100 blocks, attachments that may be bound (D14). Completeness rules never refuse a save: they are answered as `problems: [{block_id, code}]` beside the template, and the template's `ready` is true only when there are none. This re-classes the specification's refusal of an accepted answer that normalises to empty as a completeness problem (K13). Completeness covers a missing prompt, fewer than two options, a single choice without exactly one correct option, a multiple choice without a correct option, a short text without an accepted answer or with one that normalises to empty, a value or tolerance that is not a decimal of at most 6 fractional digits or a negative tolerance, and a template without blocks (K3). Slice 9 refuses to issue a template that is not ready. *Alternative (Q2 B):* refuse incomplete saves, as the specification says today, which makes autosave fail while the tutor types.
- **D13. Autosave.** `PUT /library/templates/{id} {title, blocks, version, save_id}` replaces the template conditionally on `version`; a replayed `save_id` equal to the stored `last_save_id` answers the current state instead of `conflict`, as submission autosave does ([submission lifecycle](../specs/homework.md#submission-lifecycle)). The client saves one second after the last change, with one request in flight; the server accepts at most two `PUT`s per second per template and 3,600 template `PUT`s per tutor per hour, and separately 600 other library writes per tutor per hour (`429 rate_limited` with `Retry-After`); autosave never counts toward the second limit. A stale `version` answers `409 conflict`; the builder shows "This changed elsewhere" with "Reload" and keeps the unsaved blocks visible ([shared behavior](../design/web/pages.md#shared-behavior)). `POST /library/templates` takes an `Idempotency-Key`, stored per tutor as `create_key`.
- **D14. Template references.** A template holds one `template` reference per distinct attachment its blocks show. A save computes the new set: an attachment may appear when the template already references it, when it is the caller's own unexpired `pending` upload of the `prompt_image` context, or, in a `material` block, when it is the attachment of a non-deleted material of the tutor named by the block's `material_id` (a block naming a deleted material is kept only if the template already referenced that file). Anything else answers `404`, like a random identifier. The save then adds and removes references and charges in the same transaction, under D2's locks; a removed last reference queues the file's `storage_delete`. A prompt holds at most 3 images.
- **D15. Size.** A template's request body stays within the 1 MiB JSON limit of the [API conventions](../specs/api.md#conventions); a larger one answers `413 payload_too_large`, which the builder shows as "This assignment is too large to save". The per-block limits alone would allow more than 1 MiB (K4). *Alternative:* a larger limit for this route, which raises memory per request for a rare case.
- **D16. Stored summary columns.** `template` gains `question_count`, `max_points`, `ready`, `last_save_id`, `create_key` and `updated_at`, written by every save, so the library list never parses block JSON.
- **D17. Duplicate and delete.** `POST /library/templates/{id}/duplicate {title, folder_id}` copies blocks and adds new references for every attachment (no bytes copied; a charge already exists for the tutor); the client proposes the localised title "{title} (copy)" cut to 200 code points. `DELETE` sets `deleted_at` and removes the template's references. Both count toward the 600 other library writes of D13. The builder's per-block Duplicate copies a block in the client with fresh block and option identifiers.
- **D18. The preview is the student projection** (Q3 A). `GET /library/templates/{id}/student-view` answers the template through the student content schema that slice 9 reuses for issued work: prompts, option identifiers and texts, block settings a student needs (maximum length, allowed kinds, file count), material titles and prompt images with download addresses, and nothing else. The schema is a separate Go struct with no field for correctness, accepted answers, value, tolerance, explanations, points, `max_points`, `ready`, `problems` or the `multiple_choice` scoring mode, which is points data under ADR-0009. The builder flushes autosave before it opens the preview. The test is an allowlist, not a denylist: for a seeded template holding every block type, it asserts the exact set of keys of every object in the response (the top level, each block per type, each option, each material entry and each prompt-image entry), failing on any other key, and asserts that no string in the response contains any of the distinctive sentinel accepted answers, numeric values, tolerances or explanations seeded in that template. It decodes the response recursively into `map[string]json.RawMessage`, without `any` or `reflect`, and its allowed key sets are literals taken from S1's schema, not derived from the struct. It starts the answer-key contract test of slice 9. *Alternative (Q3 B):* a client-side projection, which keeps keys in the code path that renders the student view and cannot be proven by a server test.

### Uploads and downloads

- **D19. The `library` and `prompt_image` contexts adopt the general upload pipeline** of slice 6 ([upload flow](../specs/files.md#upload-flow)): streaming in 8 MiB parts, content detection, the durable cleanup intent of [ADR-0019](../../docs/decisions/0019-durable-upload-cleanup.md) (whose adoption for new contexts needs the owner's decision, Q10), the uploading, pending and bound states and the 24-hour expiry. Under Q10 A the library contexts get their own capacity row of 1,024 unresolved intents, so slow 100 MB library uploads never make chat uploads answer `503`. The current code is chat-specific (`BeginChatUpload`, `ChatUploadAdmission`, scope rechecks and partial indexes `WHERE context = 'chat'`), so B2a first generalises it with no behaviour change. The scope is the caller's own library (no `scope` parameter; one given is refused with `422`). Admission counts the tutor's charged usage plus non-expired `uploading` and `pending` rows of every context charged to the tutor (K6), through a new partial index on `quota_tutor_id` where the state is `uploading` or `pending`. The daily byte cap stays chat-only.
- **D20. Limits.** `library`: 100 MB per file, images, PDF, office documents, audio and MP4; `prompt_image`: 5 MB, JPEG, PNG, WebP and GIF. Every JPEG, PNG, WebP and GIF of either context passes the [picture metadata filter](../specs/files.md#pictures) and gets recorded dimensions, because library pictures reach students as lesson materials. Uploads of both contexts require a confirmed email (Q9 A): an unconfirmed tutor gets `403 email_not_verified` before the body is read, as chat does, while folders and templates without images stay `unverified ok`. Per tutor, across both contexts: at most 20 open uploads and 60 starts per hour; the general 4 concurrent uploads per user and 32 per instance apply. A 100 MB library file has the read deadline's 10-minute ceiling, which requires about 170 KB/s for its upload, and the download route's 10-minute streaming ceiling requires the same of a student downloading it on a phone; both are recorded as residuals.
- **D21. MP4 detection** requires the file to start with a box of type `ftyp` whose declared size is between 16 and 4,096 bytes and lies inside the first part. The major brand decides: it must be one of `isom`, `iso2`, `mp41`, `mp42`, `avc1` and `M4V` followed by a space; an M4A major brand stays M4A, the QuickTime brand `qt` (followed by two spaces) is refused, whatever the compatible brands say; extension `.mp4` only. Unit tests cover each brand, each disguise, each precedence case and each size boundary.
- **D22. Download addresses for references other than messages** (Q7 A).
  - **Token version 2** binds the attachment, a reference kind byte, the referencing item's identifier, the expiry and the disposition, under the same HKDF key, lifetime (5 to 10 minutes), refusals and `Referrer-Policy: no-referrer` as version 1. The kind bytes are fixed now: 1 `material`, 2 `template`, 3 `lesson`, and for slice 9 4 `issue_snapshot`, 5 `answer`, 6 `review_item`. The parser picks the layout by the version byte and requires that version's exact length; version 2 refuses `message` and every unknown kind byte; version 1 only ever serves message references.
  - **Staging:** B2 ships token version 2, the `ref` parser and the kind enum only; each kind's authorization, with its audience and denial rows, lands in the change that creates its table (B3 material, B4 template, B5 lesson).
  - **Minting:** `GET /attachments/{id}?ref=<kind>:<id>&disposition=` mints only when a live reference row (attachment, kind, item) exists and the caller can see that item: the tutor for their own non-deleted materials, non-deleted templates and lessons; a student for a lesson they can see, decided by `GetStudentLessonView`, the visibility copy the [visibility rule](../specs/schedule.md#visibility) already tests. The refusal order: (1) whether the caller can see some item holding a live reference to the attachment, `404` otherwise; (2) a missing `ref` for a non-chat attachment, or any `ref` on a chat attachment, `404`; (3) the `ref` format, one value, a known kind and a UUID, `422 validation_failed` at `ref`; (4) whether `ref` names a visible item holding a live reference, `404`; (5) `disposition`, `422` at `disposition`. S1 records this order in the `api.md` row. Chat attachments are minted without `ref`, as today.
  - **Serving:** `GET /files/{id}` re-checks that the attachment is `bound`, that the named reference row still exists and, for a material, that it is not deleted. Residual: an address keeps working until its expiry after the student loses sight of the lesson, because the token is a bearer credential, as for chat.
  - **Disposition:** pictures with recorded dimensions may be `inline`, and `inline` for any other kind answers `422` at `disposition`; every other kind is an `attachment` download, so PDFs, audio and video open outside the page.
  - **Responses** that list materials or prompt images (the library, the template, its student view, the lesson detail) carry addresses minted per response, as message pages do, and send `Cache-Control: no-store`.

### Lessons and the room

- **D23. Lesson materials.** `POST /lessons/{id}/materials {material_ids, version}` replaces the ordered list of one lesson's materials, at most 20, with the tutor's non-deleted materials (a material already attached may stay after its deletion); it works at any lesson status, as the [schedule](../specs/schedule.md#rules-for-all-edits) allows, records `materials` in `overridden_fields` for a series occurrence, takes the lesson write limit and, because removing a file's last reference releases a charge, the charge lock order of [accounts](../specs/accounts.md#locks-and-the-session-re-check): the tutor's profile lock first, then the lesson edit's existing relationship, group, series and lesson locks, with a re-check after locking (series edits with `material_ids` under D24 do the same, before the series lock); emits `entity.changed lesson` to the lesson's audience and roster (S1 adds materials to that frame's roster-signalling fields in `realtime-and-video.md`), and answers the tutor's lesson detail. It conditions on `version` and increments it. `PATCH /lessons/{id}` with scope `this` and `material_ids` is refused with `422 validation_failed` (`body.material_ids: not_allowed`), because this route is the one place a single lesson's materials change (K12).
- **D24. Series materials.** `POST /lessons` and `PATCH /lessons/{id}` with scope `following` take an optional `material_ids`, which sets `series_material` and the materials of the covered occurrences that have not overridden them, under the existing split rules; new occurrences copy the series' materials as they are materialised. Horizon extension and split copying are part of B5: they insert lesson-material rows and `lesson` references, and create no charge, because each copied file already carries the tutor's charge through its `series` reference; they take the charged tutor's profile lock before the series lock only when a charge must change, keeping the charge lock order. Per occurrence this adds at most 20 rows and references inside the extension job's existing 2-minute budget (a risk in section 9). Horizon extension reads `series_material` and inserts the new lessons' references under the series row lock that a series edit takes, so an edit removing a file's last reference cannot queue its `storage_delete` while extension adds a new one; a race test proves it.
- **D25. Lessons and series hold their own references.** Each lesson material has a `lesson` reference and each series material a new `series` reference kind (K7), charged to the tutor, so a material deleted from the library stays downloadable from lessons and is still copied into new occurrences; removing the last reference releases the file.
- **D26. The lesson detail** gains `materials` in attachment order: for the tutor `[{material_id, attachment_id, title, filename, media_type, size_bytes, width, height, url, expires_at}]`, for students the same without `material_id`. The title is the material's current title, kept after deletion, so a library rename shows on the lesson page. A student sees a lesson's materials exactly when they can see the lesson (Q4 A).
- **D27. The presentation** (Q5 A).
  - **Contract:** the meeting provider contract gains an optional presentation: a 5-minute signed storage `GET` URL of the first attached PDF, which [ADR-0009](../../docs/decisions/0009-owner-approved-exceptions-and-visibility.md) item 1 already allows. The storage adapter's new presign operation mints it for each create attempt. The URL is never stored, logged, placed in `meta_*` values, the meeting recovery ledger, the outbox or any retry state ([ADR-0020](../../docs/decisions/0020-durable-meeting-recovery.md), [ADR-0021](../../docs/decisions/0021-quiet-window-meeting-settlement.md)), or returned to a client.
  - **Setting:** presigning uses a new typed setting, the storage endpoint the conferencing server can reach, documented in `.env.example`, under the storage endpoint's rule (an `https` origin, or `http` on a loopback host), tightened so that `http` also requires the `fake` provider and, under `OVC_TEST_CONTROL=1`, a loopback IP address, as the storage endpoint requires there; start-up refuses anything else.
  - **BigBlueButton:** the adapter sends the document in the `create` call's `POST` XML body (`<modules><module name="presentation"><document url=…/>`), never in the query string, tested against the local protocol server.
  - **Fake:** the shared fake fetches the URL once, only from the fixture-validated local storage host (any other host is refused), and records only the fetched size and SHA-256, so a test proves the bytes arrive.
  - **Signing failure:** the meeting is created without a presentation and `meeting.presentation.offered` is not logged; the failure is logged as `meeting.presentation.unavailable` (WARNING), so a storage hiccup never blocks a lesson. The conferencing server must reach the storage host the presign names (a risk in section 9). The shared fake's recorded size and SHA-256 are columns of its own infrastructure tables, added by a migration in B6.
  - **Error paths:** a failed signing, a provider error or a timeout never puts the URL or a signed-query fragment into a record, an error kind or a safe failure description; a `*url.Error` is reduced to its kind before logging.
  - **Residuals:** the conferencing server keeps its converted copy of the presentation while it keeps the meeting; a live fetch stays `unverified` until the remote probe.

### Frontend

- **D28. The restricted Markdown renderer** (Q1 A) is OVC's own small parser in `frontend/src/lib/markdown/`, producing React elements and never an HTML string, so the existing lint rules against unsafe DOM sinks stay unweakened. It supports exactly the subset of [restricted Markdown](../specs/homework.md#restricted-markdown); links are kept only when the URL parser yields `https:` with a host and no user information, open with `target="_blank"` and `rel="noopener noreferrer"`, and anything else renders as text. Unit tests run an injection corpus (raw HTML, `javascript:` and `data:` links, nested emphasis, unbalanced markers) and count the parser's steps on 10,000-character adversarial inputs, which must stay within a fixed multiple of the input length; no wall-clock bound. *Alternative (Q1 B):* a parser library with a sanitiser, a dependency whose output is an HTML string.
- **D29. Reordering** (Q8 A) uses the browser's own drag events for the pointer and "Move up" and "Move down" buttons for the keyboard and touch, with no dependency; after a keyboard move, focus stays on the moved button, and a test asserts it. *Alternative (Q8 B):* a drag-and-drop library, which is then the builder's vendor chunk.
- **D30. The builder's code** stays in its own lazily loaded route chunk; `pnpm check:bundle` gains an assertion that no module reachable only from the builder appears in the entry or in any student page chunk, and records the builder chunk's size. This is the roadmap's "builder vendor code in its own chunk" item; with D28 and D29 there is no builder vendor code to split, and if Q1 or Q8 is answered B, the library goes into the builder chunk and the same assertion covers it.
- **D31. Navigation.** The tutor's Homework section opens `/homework/library` with the Library tab only and no count; the Issued and Needs checking tabs and the count arrive in slice 9. The builder is `/homework/templates/{id}`; "New assignment" creates a template titled with the localised "New assignment" and opens it ([navigation](../design/web/navigation.md)).
- **D32. Pages.** The library and builder follow [pages](../design/web/pages.md#library) and the desktop layout standard: on a computer, the folder tree in the side column and items as a table; below 1024 px the interim one-column frame. Focus rules for every new dialog, notice and removal are defined in S1's `pages.md` changes and each has a `toBeFocused` test.
- **D33. The first-run checklist** shows "Create an assignment", done when `template_count` is above zero, read through `GET /library?limit=1`. As with the existing steps, the step follows current data: a tutor who had finished the three earlier steps sees the checklist again with this one step until they create a template, and deleting every template makes it undone again.
- **D34. Live data.** No new frame kind: library data belongs to one tutor, whose other tabs meet a stale edit as `conflict`. Lesson materials reuse `entity.changed lesson`, already mapped to the lesson page.

### Purge, logging and tests

- **D35. Purges.** The tutor purge's batch kinds gain, before lessons and series, lesson materials and series materials with their references and charges; then template references and charges, material references and charges, templates, materials, and folders deepest first, 500 rows per batch inside the round-robin budget. ### 6.2 Data

## 9. Risks

- **The design slice is still closing.** S1 edits `pages.md`, `navigation.md`, `states.md` and the roadmap, which its last changes also touch, so S1 starts after it closes (wave 1).
- **The template body is the largest JSON OVC accepts.** Validation and reference computation on every autosave cost CPU and a transaction holding the profile lock; standard reviewers check the per-save cost, and measurements wait for the deployment as the owner decided on 2026-11-08.
- **Autosave and conflicts are subtle.** A save answering after newer typing must never overwrite it, as for the student card's notes; F3's tests cover it.
- **Search by substring** scans a tutor's rows; D4's caps bound it, and a slow scan would show only for very large libraries.
- **The check budget.** Two new end-to-end specs and scenario 2's first steps add to the full local run, which must stay under 10 minutes; proposal 0004's techniques apply from the start, and the merge gate's duration is reported per change.
- **Migrations in parallel branches** collide on numbers; section 7's merge order handles it.
- **Generalising the upload pipeline** touches slice 6's most intricate code (intents, recovery, settlement); B2a does it alone, with no behaviour change and every existing test unchanged, before any new context.
- **Series materials in the worker** add up to 20 rows and references per new occurrence to horizon extension, whose 2-minute budget already fills near 50,000 series ([slice 5 known limitations](../reviews/slice-5-known-limitations.md)); standard reviewers check the per-occurrence cost, and the budget is measured with the deployment.
- **The conferencing server must reach the storage host** the presign names; in local tests the fake reaches the local storage server, and the deployment's network path is checked by the remote probe.
- **The language chunk grows** with the library and builder texts, and counts against the entry limit in `frontend/scripts/bundle-budget.ts`; F2 and F3 report its size, and builder-only texts may move into the builder chunk if it nears the limit.
- **A removed prompt image is released at once**, so undoing its removal after a save cannot restore it; the builder keeps the picked file in memory until the page closes and uploads it again on undo.
- **Expected check growth:** about two new end-to-end specs of a few minutes in all and a few hundred backend integration tests; each change reports its gate duration, and consolidation follows proposal 0004 if the full run nears 10 minutes.
- **Q7 amends `AGENTS.md`.** If the owner answers B instead, D22 is replaced by signed storage URLs and T-35's headers are lost for library files; the plan is rewritten before S1.
- **No real BigBlueButton fetch** proves the presentation; it stays `unverified` until the remote probe.
- **Flaky tests** stop gates; a failed assertion is never rerun without the owner's decision.

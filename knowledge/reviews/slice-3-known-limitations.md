# Slice 3 known limitations

Minor findings accepted during slice 3 instead of starting another review round ([ADR-0011](../../docs/decisions/0011-tiered-verification.md)). The slice review re-verifies each entry; each is fixed, accepted by the owner or carried into a named later slice.

| Finding | Severity | Change | Why it was accepted |
|---|---|---|---|
| The student list and its search read and sort all of a tutor's matching cards for every page, because the `state = ANY(...)` filter keeps PostgreSQL from using `relationships_tutor_list_idx` for the ordering | minor | Student cards and invitation links | The work is bounded by one tutor's cards; the slice review's performance pass measures the query plan on 50,000 relationships, and an index on `(tutor_id, created_at DESC, id DESC) WHERE state <> 'discarded'` is the likely fix |
| Signed-in acceptance reads the account email used for the card's email binding before its transaction, outside the account's row lock | minor | Signed-in acceptance and My tutors | Safe while no account email change exists (email change is outside the MVP); when one lands, the binding check moves under the account's row lock |
| Two endings of the same relationship in the same microsecond, with a reactivation between them, share the `relationship.ended` idempotency key `(relationship.ended, relationship, ended_at)`, so the second email is not queued | minor | Ending relationships | Practically unreachable: an ending, a reactivation and a second ending cannot all commit within one microsecond on the system clock; it shows only with the fake test clock, whose tests advance it between endings |
| The ending services read `now` before their transaction, so a second ending that waited on the relationship lock while a reactivation committed can record an `ended_at` earlier than that reactivation | minor | Ending relationships | Practically unreachable and harmless: the window is the lock wait of one request; the ended state, the email and its obsolescence check all use the stored `ended_at`, so only the recorded time is slightly early |
| The Node runtime pinned by `frontend/.node-version` (26.0.0) bundles undici 8.0.2, which the advisories accepted in `frontend/osv-scanner.toml` also affect; no lockfile scan sees it, and the end-to-end harness's built-in fetch uses it against the local deployment only | minor | Undici advisories in the test tools | Node does not run in production, where the frontend ships as static files; the slice review checks for a Node 26 release bundling a fixed undici. Closed on 2026-10-26: Node 26.12.1, pinned in `frontend/.node-version`, bundles undici 8.12.2, which fixes those advisories. |
| One large tutor purge can take a whole run's budget of 100 batch transactions, so the accounts behind it in that run wait for the next hourly run (head-of-line delay) | minor | Deletion effects on tutoring | The delay is bounded: each run moves the large purge forward by 50,000 rows, and the accounts behind it are purged once it finishes; the slice review's performance pass measures it, and a per-account share of the budget is the likely fix |
| A tutor's deletion through `DELETE /users/me` runs its discard, ending, revocation and expiry statements over all of the tutor's relationships, invitations and requests in one transaction, without a bound | minor | Deletion effects on tutoring | The work grows only with the tutor's own cards, which grow by at most 50 a day plus the cards that removals give. Measured on 2026-10-24 with 60% active, 20% ended and 20% invited relationships with open links and 200 groups, on a shared development machine (load average 2 to 4): `DELETE /users/me` took 1.0 s, 4.3 s and 10.2 s at 5,000, 20,000 and 50,000 relationships while each `tutor.deleted` email was queued with its own statement; since the ending returns only the identifiers it logs and all `tutor.deleted` rows are queued with one statement, it takes 0.12 s, 0.41 s and 0.95 s (about 19 µs per relationship). The transaction stays unbounded and still writes one `relationship.ended` record per ended relationship (10.4 MB of logs at 50,000), as the observability specification requires. The figures are indicative: they come from one run each on a machine that was not idle, with a harness that is not committed; the next slice review's performance pass measures the request on an idle machine |
| The group dialogs' `not_found` refusal (a chosen student's card left the tutor's scope meanwhile, so the choice is emptied) has no test: a chosen active card leaves the scope only through a student purge, which needs the shared clock moved 31 days and ends the tutor's browser session | minor | Groups pages and ending | The `relationship_not_active` refusal, which shares the dialog's refusal handling, is tested end to end; the slice review's frontend pass decides whether a component test through the fake transport covers the emptied choice |
| Tutor deletion builds `repositories.Relationship` values with only the identifier, tutor and student set for the discarded and ended cards it logs, so a later reader of another field of those values would get zero values silently | minor | Tutor deletion batching | The values are read only by the logging and email queueing of the same function today; a narrow type for them is the fix when that code next changes |
| The ESLint rule that enforces the ban on the `Reflect` API catches the global, member access by name, string or template key, and destructuring, but not a lookup such as `Object.getOwnPropertyDescriptor(globalThis, 'Reflect')`; a selector on the bare `'Reflect'` string would also flag the lint configuration that names the global | minor | Agent configuration after the slice 3 review | Such a lookup is a deliberate evasion that the reviews catch, and AGENTS.md already forbids building identifiers to dodge a check; a narrow configuration exclusion for the lint configuration file is the fix if the pattern ever appears |
| `git checkout` asks the owner for every form, so the confirmation rules guard its path forms, but the rules match the command text only: an alias, a wrapper such as `bash -c` or `env git`, or an unlisted spelling of another destructive command runs without confirmation | minor | Agent configuration after the slice 3 review | Recorded as the T-41 residual; the rules guard against accidental use, and the reviews and the owner's plan approval catch deliberate evasion. Because the rules match text, a routine command whose free text contains a guarded word or option (a commit message naming `git checkout`, `reset` or `--force`) also asks, which fails safe. Combined short flags in other letter orders (for example `-qD` or `-qf`) are among the unlisted spellings |
| Three end-to-end runs starting at once over a stale run lock can race: a run that read the stale holder moves aside the lock another run just took, and if a third run links its own lock in that moment, the second run's lock is lost; the second run's re-check before removing earlier outputs or deleting the shared bucket then fails loudly, but when the loss happens after its check before removing earlier outputs, it is caught only at teardown, after both runs shared the deployment files, the binaries and the bucket for the whole suite and the other run removed the second run's output folder | minor | End-to-end harness after the slice 3 review | It needs a stale lock and three starts within microseconds, and the clash is detected rather than silent; preventing it needs an operating-system advisory lock, which Node offers only through a new dependency |
| The consolidated full local check run (152.5 s, against 208.4 s before; [check-budget record](../analysis/check-budget-2026-10-25-consolidated.md)) was measured once on a loaded machine, with load averages from 1.9 to 15.2 and another project's processes running, not on an idle machine as the slice plan asked | minor | Suite consolidation before slice 4 | The run is 27 s under the 180-second threshold and about a quarter of the 10-minute budget, and the end-to-end time repeated within seconds; the next slice review's performance pass measures the full check run on an idle machine |

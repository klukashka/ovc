# Slice 5 known limitations

Minor findings accepted during slice 5 instead of starting another review round ([ADR-0011](../../docs/decisions/0011-tiered-verification.md)). The slice review re-verifies each entry; each is fixed, accepted by the owner or carried into a named later slice.

| Finding | Severity | Change | Why it was accepted |
|---|---|---|---|
| No test proves that the stale-template cleanup of the integration-test fixture keeps a template-named database owned by another role, or that a wait for the template lock ends after one minute; the age and name rules, the process's own template and clone independence are tested | minor | Test database template | The owner filter is one condition in the query that lists the candidates, and the bound is a context deadline on the lock statement; a test of either would need a second login role on the shared local server or a lock held for a minute, which would disturb other test processes and worktrees sharing that server |
| The frontend unit test that every zone of `Intl.supportedValuesOf('timeZone')` has an entry in `frontend/src/lib/time/timezone-cities.json` does not exist yet; the table covers all 418 zones Node's ICU lists and 19 common aliases, and the byte-for-byte comparison with the backend copy is tested | minor | Schedule core | The test imports the JSON table, which needs the frontend's TypeScript configuration to accept JSON modules; the lesson page change, which first loads the table, adds the test with that configuration |
| `TestLessonWritesRacingATutorDeletionOrBlockAnswer401` races only lesson creation (a one-off lesson and a series) against a tutor deletion and an operator block | minor | Schedule core | `PATCH /lessons/{id}` and `POST /lessons/{id}/cancel` do not exist yet; the lesson edits and cancellation change extends the test to both. Fixed by that change: the test also races an edit of following lessons and a cancellation, each leaving the lessons unchanged |
| The answer `409 conflict` after a group's members changed twice under the lock has no test yet; the retry and the answer's position after the body and the caps are implemented | minor | Schedule core | Its named test, `TestAGroupLessonWriteWhoseMembersChangedAnswersConflict`, belongs to the lesson edits and cancellation change, which exercises the same path for creations and edits. Fixed by that change: the test changes the members during both attempts, through a held group row and a held member card, for a creation and an edit, and proves nothing changed |
| The field code `too_many` is not among the frontend's field codes and has no translation | minor | Schedule core | No page sends `POST /lessons` before the Schedule pages change, which adds the code and both translations with the New lesson dialog |
| The student purge deletes the account's roster rows in one statement of the transaction that deletes the user row, not in bounded batches; the data model now says so | minor | Schedule core | A student's roster rows are bounded by the lessons the student attended or was expecting, as the student's notification rows, which the same transaction deletes the same way; a tutor's rows, which can be many, are deleted in batches |
| A NUL byte in a card's notes reaches PostgreSQL and answers `500 internal` instead of `422`; lesson titles and descriptions, card display names and group names refuse control characters at validation | minor | Schedule core | Found while checking the lesson text rules; only the tutor can write their own card's notes, nothing is stored, and the fix belongs to the card routes, outside this change |
| A `POST /lessons` that repeats the `Idempotency-Key` of a first request still running uses a slot of the hourly write limit, because its admission finds no committed row to replay; it then waits for the first request's profile lock and returns the first result | minor | Schedule core | Only the tutor's own concurrent retries reach this, each costs at most one slot of 120 per hour, and the answer stays the first result |
| The sign-out-everywhere realtime test waits for the Students page's queries by a hand-kept list of their paths; a query the page gains later is covered only by the test's check that no API request is in flight, so an unlisted request that started only after every listed one finished could still race the revocation | minor | Wait for the post-ready refetch before signing out everywhere in the realtime test | Such a late request would fail the test as an unexpected `401`, never pass it falsely; the refetch wave starts from one synchronous invalidation, so its requests start before any of them is answered |
| The realtime test that shows a join request on Students and Today without reloading waits for two sockets through the server's presence count, which can pass before either page handled `ready` | minor | Wait for the post-ready refetch before signing out everywhere in the realtime test | The test does not revoke the session, so a late refetch after `ready` is harmless to it; it predates the change |
| The dispatcher reads each claimed email's recipient, preferences and subject with queries of its own, row by row, not in a few batched queries per claimed batch; notifications.md now says so | minor | Lesson jobs and optional emails | Accepted by the owner on 2026-10-27; the slice 4 dispatcher already builds each row on its own, and a measurement at the slice review (NFR-4.5 with a burst of reminders) decides whether batching is needed |
| Until the lesson effects of tutoring land, the reminder job reminds the current members of an archived group and the status job ends that group's lessons with those members on the roster; horizon extension already skips archived groups | minor | Lesson jobs and optional emails | Carried into the lesson effects of tutoring change, which cancels an archived group's future lessons in the archiving transaction, so no scheduled lesson of an archived group remains |
| `GET /students`, `GET /students/{id}`, `GET /groups` and `GET /groups/{id}` read the card or the group in one read transaction and its lessons in a second one, so a lesson written between the two can pair a card or a group with a lesson state that is newer than the card's own fields | minor | Lessons on the tutoring routes | Both reads are scoped to the calling tutor, the lesson read checks the card's or the group's scope again inside its own transaction, and the page refetches on the `entity.changed` frame that every lesson write sends; the schedule service owns the lesson reads and labels, and a service never imports another, so one transaction would need the tutoring service to duplicate the tutor-side label rules |
| `PATCH /students/{id}` and the other card and group write routes answer `StudentCard` and `Group` without `next_lessons`, `future_lesson_count` and `has_open_series`, which only `GET /students/{id}` and `GET /groups/{id}` carry; a client that writes a write route's answer into the detail cache drops those fields | minor | Lessons on the tutoring routes | No page shows the fields before the frontend change for lessons on the tutoring pages, which must refetch the card or the group detail after a write instead of writing the answer into its cache |
| A split or a "cancel following" of up to 100 lessons issues one `UPDATE` per changed lesson and one roster insert per cancelled lesson inside its transaction, not one statement per operation | minor | Lesson edits and cancellation | Each row can take different values (its overridden fields and its own date), and the count is bounded by the series rules (at most 100 counted occurrences, or the 12-week horizon); the split of a 100-lesson series is measured at the slice review, which decides whether batched statements are needed |

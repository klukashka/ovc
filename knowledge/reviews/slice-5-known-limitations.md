# Slice 5 known limitations

Minor findings accepted during slice 5 instead of starting another review round ([ADR-0011](../../docs/decisions/0011-tiered-verification.md)). The slice review re-verifies each entry; each is fixed, accepted by the owner or carried into a named later slice.

| Finding | Severity | Change | Why it was accepted |
|---|---|---|---|
| No test proves that the stale-template cleanup of the integration-test fixture keeps a template-named database owned by another role, or that a wait for the template lock ends after one minute; the age and name rules, the process's own template and clone independence are tested | minor | Test database template | The owner filter is one condition in the query that lists the candidates, and the bound is a context deadline on the lock statement; a test of either would need a second login role on the shared local server or a lock held for a minute, which would disturb other test processes and worktrees sharing that server |
| The frontend unit test that every zone of `Intl.supportedValuesOf('timeZone')` has an entry in `frontend/src/lib/time/timezone-cities.json` does not exist yet; the table covers all 418 zones Node's ICU lists and 19 common aliases, and the byte-for-byte comparison with the backend copy is tested | minor | Schedule core | The test imports the JSON table, which needs the frontend's TypeScript configuration to accept JSON modules; the lesson page change, which first loads the table, adds the test with that configuration. Resolved by the lesson page change: `tsconfig.app.json` accepts JSON modules, the lesson page loads the table through `frontend/src/lib/time/timezoneCities.ts`, and `timezone city table › every zone the engine reports has an English and a Russian city` checks every zone of `Intl.supportedValuesOf('timeZone')` |
| `TestLessonWritesRacingATutorDeletionOrBlockAnswer401` races only lesson creation (a one-off lesson and a series) against a tutor deletion and an operator block | minor | Schedule core | `PATCH /lessons/{id}` and `POST /lessons/{id}/cancel` do not exist yet; the lesson edits and cancellation change extends the test to both. Fixed by that change: the test also races an edit of following lessons and a cancellation, each leaving the lessons unchanged |
| The answer `409 conflict` after a group's members changed twice under the lock has no test yet; the retry and the answer's position after the body and the caps are implemented | minor | Schedule core | Its named test, `TestAGroupLessonWriteWhoseMembersChangedAnswersConflict`, belongs to the lesson edits and cancellation change, which exercises the same path for creations and edits. Fixed by that change: the test changes the members during both attempts, through a held group row and a held member card, for a creation and an edit, and proves nothing changed |
| The field code `too_many` is not among the frontend's field codes and has no translation | minor | Schedule core | No page sends `POST /lessons` before the Schedule pages change, which adds the code and both translations with the New lesson dialog. Resolved by the frontend Schedule change: `too_many` is a frontend field code with a generic translation in both languages, and the New lesson dialog shows the cap refusal in its own words |
| The student purge deletes the account's roster rows in one statement of the transaction that deletes the user row, not in bounded batches; the data model now says so | minor | Schedule core | A student's roster rows are bounded by the lessons the student attended or was expecting, as the student's notification rows, which the same transaction deletes the same way; a tutor's rows, which can be many, are deleted in batches |
| A NUL byte in a card's notes reaches PostgreSQL and answers `500 internal` instead of `422`; lesson titles and descriptions, card display names and group names refuse control characters at validation | minor | Schedule core | Found while checking the lesson text rules; only the tutor can write their own card's notes, nothing is stored, and the fix belongs to the card routes, outside this change |
| A `POST /lessons` that repeats the `Idempotency-Key` of a first request still running uses a slot of the hourly write limit, because its admission finds no committed row to replay; it then waits for the first request's profile lock and returns the first result | minor | Schedule core | Only the tutor's own concurrent retries reach this, each costs at most one slot of 120 per hour, and the answer stays the first result |
| The sign-out-everywhere realtime test waits for the Students page's queries by a hand-kept list of their paths; a query the page gains later is covered only by the test's check that no API request is in flight, so an unlisted request that started only after every listed one finished could still race the revocation | minor | Wait for the post-ready refetch before signing out everywhere in the realtime test | Such a late request would fail the test as an unexpected `401`, never pass it falsely; the refetch wave starts from one synchronous invalidation, so its requests start before any of them is answered |
| The realtime test that shows a join request on Students and Today without reloading waits for two sockets through the server's presence count, which can pass before either page handled `ready` | minor | Wait for the post-ready refetch before signing out everywhere in the realtime test | The test does not revoke the session, so a late refetch after `ready` is harmless to it; it predates the change |
| The dispatcher reads each claimed email's recipient, preferences and subject with queries of its own, row by row, not in a few batched queries per claimed batch; notifications.md now says so | minor | Lesson jobs and optional emails | Accepted by the owner on 2026-10-27; the slice 4 dispatcher already builds each row on its own, and a measurement at the slice review (NFR-4.5 with a burst of reminders) decides whether batching is needed |
| Until the lesson effects of tutoring land, the reminder job reminds the current members of an archived group and the status job ends that group's lessons with those members on the roster; horizon extension already skips archived groups | minor | Lesson jobs and optional emails | Carried into the lesson effects of tutoring change, which cancels an archived group's future lessons in the archiving transaction, so no scheduled lesson of an archived group remains. Fixed by that change: archiving and a tutor's deletion cancel every lesson of the group that starts after the archiving, with the members at archiving frozen on the roster, so the reminder job finds no scheduled lesson of an archived group ahead of it; a lesson already under way when the group is archived stays scheduled and is ended by the status job with the members as its roster, as for any lesson under way (`TestArchivingCancelsAndEndsAndSendsOneEmailPerMember`, `TestUnarchivingRestoresNothingScheduled`) |
| `GET /students`, `GET /students/{id}`, `GET /groups` and `GET /groups/{id}` read the card or the group in one read transaction and its lessons in a second one, so a lesson written between the two can pair a card or a group with a lesson state that is newer than the card's own fields | minor | Lessons on the tutoring routes | Both reads are scoped to the calling tutor, the lesson read checks the card's or the group's scope again inside its own transaction, and the page refetches on the `entity.changed` frame that every lesson write sends; the schedule service owns the lesson reads and labels, and a service never imports another, so one transaction would need the tutoring service to duplicate the tutor-side label rules |
| `PATCH /students/{id}` and the other card and group write routes answer `StudentCard` and `Group` without `next_lessons`, `future_lesson_count` and `has_open_series`, which only `GET /students/{id}` and `GET /groups/{id}` carry; a client that writes a write route's answer into the detail cache drops those fields | minor | Lessons on the tutoring routes | No page shows the fields before the frontend change for lessons on the tutoring pages, which must refetch the card or the group detail after a write instead of writing the answer into its cache. Handled by that change: the card and group pages keep the detail fields of their cached detail when they store a write's answer and fetch the detail again, and an `entity.changed` frame of kind `lesson` also refetches the student lists, the cards and the groups |
| Neither `GET /calendar` items nor `GET /lessons/{id}` carry whether an `ended` lesson took place (`live_at`), so the Schedule shows every `ended` lesson as "Did not take place", which is true in slice 5 because nobody can join before slice 7 | minor | Frontend Schedule | Every ended lesson of slice 5 did not take place ([schedule](../specs/schedule.md#lesson-status-and-join-window)); carried into slice 7, whose joining change adds the field that tells "Ended" from "Did not take place" and changes the Schedule's status word with it |
| A split or a "cancel following" of up to 100 lessons issues one `UPDATE` per changed lesson and one roster insert per cancelled lesson inside its transaction, not one statement per operation | minor | Lesson edits and cancellation | Each row can take different values (its overridden fields and its own date), and the count is bounded by the series rules (at most 100 counted occurrences, or the 12-week horizon); the split of a 100-lesson series is measured at the slice review, which decides whether batched statements are needed |
| Each `tutor.deleted` email reads its listed lessons with one query on the cause, the tutor and the deletion instant, filtered by the recipient's roster; at a deletion near the per-tutor bound it may plan as a scan of the `(cancel_cause, cancelled_at)` index over every lesson that deletion cancelled, once per recipient | minor | Lesson effects of tutoring | The cost is one read per queued email in the worker, never in a request; the slice review measures the dispatch of a tutor deletion's emails at the bound of the per-tutor caps and decides whether the query needs an index leading with the tutor |
| The lesson page derives "Starting soon", "Room opens at", "Did not take place" for a scheduled lesson whose end has passed, and whether Edit and Cancel show from the browser's clock, so a browser clock that differs from the server's shows these states early or late | minor | Lesson page | Accepted by the owner on 2026-10-28; the server stays authoritative: an edit or cancellation after the start answers `not_editable`, which closes the dialog onto the changed-meanwhile notice, and the status word of every lesson that is not `scheduled` comes from the server |
| No test asserts the focus when an open edit or cancel dialog closes because its lesson's start passed by the browser's clock; the rule that closes it (`dialogOutdated`) has unit tests at the start, and the move onto the changed-meanwhile notice is tested for a live change | minor | Lesson page | `LessonPage` reads the browser's clock directly through `useLessonClock`, and the end-to-end harness moves only the server's clock; injecting a clock into the page would need a new injection point for one focus move whose notice and focus path are the ones the live-change test already proves |
| The frontend's fake transport can seed an unverified account but still answers every route it serves, where the API answers `403 email_not_verified` outside the routes marked "unverified ok", so a component test of an unverified account on such a route would pass against behavior the server refuses | minor | Signed-in frame test harness | No current test opens such a route for an unverified account: the unverified frame tests render routes the fake does not serve, so both roles get `404`; gating the fake's routes on the account state belongs with the first test that needs it. |
| A split or a "cancel following" sends up to about 100 `lesson` frames, and each now invalidates the Students lists, every student card with its Lessons pages and every group query, so an open tutoring page may refetch many times in a burst; the cost is not measured | minor | Lessons on the tutoring pages | Every refetch stays within the tutor's own scope and reads bounded pages; the slice review's measurements decide whether the live refetch needs batching for bursts |
| The lesson page decides that "End this series and create a new one" ended the series from the date of the lesson's start in the series timezone, because the lesson detail carries no occurrence date; an occurrence moved on its own to an earlier date reports "changed meanwhile" although its series ended | minor | End a series and create a new one | It fails safe: the page shows the notice, refetches and opens no New lesson dialog; exposing the occurrence date on the lesson detail fixes both directions and is left to the slice review. |
| The same derived date can open New lesson for nothing: when an occurrence of a series with an end date and no count was moved on its own past that end date and then cancelled alone in another tab, a stale "End the series" answers the current state and the page opens a prefilled New lesson although nothing ended | minor | End a series and create a new one | The window needs a moved occurrence beyond the series' end and a concurrent single cancellation; the tutor gets only a prefilled dialog to dismiss, and exposing the occurrence date on the lesson detail closes it. |

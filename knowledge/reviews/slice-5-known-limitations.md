# Slice 5 known limitations

Minor findings accepted during slice 5 instead of starting another review round ([ADR-0011](../../docs/decisions/0011-tiered-verification.md)). The slice review re-verifies each entry; each is fixed, accepted by the owner or carried into a named later slice.

| Finding | Severity | Change | Why it was accepted |
|---|---|---|---|
| No test proves that the stale-template cleanup of the integration-test fixture keeps a template-named database owned by another role, or that a wait for the template lock ends after one minute; the age and name rules, the process's own template and clone independence are tested | minor | Test database template | The owner filter is one condition in the query that lists the candidates, and the bound is a context deadline on the lock statement; a test of either would need a second login role on the shared local server or a lock held for a minute, which would disturb other test processes and worktrees sharing that server. Slice review (2026-10-28): accepted. |
| The student purge deletes the account's roster rows in one statement of the transaction that deletes the user row, not in bounded batches; the data model now says so | minor | Schedule core | A student's roster rows are bounded by the lessons the student attended or was expecting, as the student's notification rows, which the same transaction deletes the same way; a tutor's rows, which can be many, are deleted in batches. Slice review (2026-10-28): accepted. |
| A NUL byte in a card's notes reaches PostgreSQL and answers `500 internal` instead of `422`; lesson titles and descriptions, card display names and group names refuse control characters at validation | minor | Schedule core | Found while checking the lesson text rules; only the tutor can write their own card's notes, nothing is stored, and the fix belongs to the card routes, outside this change. Slice review (2026-10-28): no layer report covered this entry; the owner decided to fix it now in `fix/lesson-effects-follow-ups`, where card notes refuse control characters other than line feed and tab with `422`, which removes this row. |
| A `POST /lessons` that repeats the `Idempotency-Key` of a first request still running uses a slot of the hourly write limit, because its admission finds no committed row to replay; it then waits for the first request's profile lock and returns the first result | minor | Schedule core | Only the tutor's own concurrent retries reach this, each costs at most one slot of 120 per hour, and the answer stays the first result. Slice review (2026-10-28): accepted. |
| The sign-out-everywhere realtime test waits for the Students page's queries by a hand-kept list of their paths; a query the page gains later is covered only by the test's check that no API request is in flight, so an unlisted request that started only after every listed one finished could still race the revocation | minor | Wait for the post-ready refetch before signing out everywhere in the realtime test | Such a late request would fail the test as an unexpected `401`, never pass it falsely; the refetch wave starts from one synchronous invalidation, so its requests start before any of them is answered. Slice review (2026-10-28): accepted. |
| The realtime test that shows a join request on Students and Today without reloading waits for two sockets through the server's presence count, which can pass before either page handled `ready` | minor | Wait for the post-ready refetch before signing out everywhere in the realtime test | The test does not revoke the session, so a late refetch after `ready` is harmless to it; it predates the change. Slice review (2026-10-28): accepted. |
| The dispatcher reads each claimed email's recipient, preferences and subject with queries of its own, row by row, not in a few batched queries per claimed batch; notifications.md now says so | minor | Lesson jobs and optional emails | Accepted by the owner on 2026-10-27; the slice 4 dispatcher already builds each row on its own, and a measurement at the slice review (NFR-4.5 with a burst of reminders) decides whether batching is needed. Slice review (2026-10-28): accepted pending the NFR-4.5 measurement with a burst of reminders; if that measurement shows batching is needed and the slice 5 follow-ups do not add it, carried into slice 10. |
| `GET /students`, `GET /students/{id}`, `GET /groups` and `GET /groups/{id}` read the card or the group in one read transaction and its lessons in a second one, so a lesson written between the two can pair a card or a group with a lesson state that is newer than the card's own fields | minor | Lessons on the tutoring routes | Both reads are scoped to the calling tutor, the lesson read checks the card's or the group's scope again inside its own transaction, and the page refetches on the `entity.changed` frame that every lesson write sends; the schedule service owns the lesson reads and labels, and a service never imports another, so one transaction would need the tutoring service to duplicate the tutor-side label rules. Slice review (2026-10-28): accepted. |
| Neither `GET /calendar` items nor `GET /lessons/{id}` carry whether an `ended` lesson took place (`live_at`), so the Schedule shows every `ended` lesson as "Did not take place", which is true in slice 5 because nobody can join before slice 7 | minor | Frontend Schedule | Every ended lesson of slice 5 did not take place ([schedule](../specs/schedule.md#lesson-status-and-join-window)); carried into slice 7, whose joining change adds the field that tells "Ended" from "Did not take place" and changes the Schedule's status word with it. | A split or a "cancel following" of up to 100 lessons issues one `UPDATE` per changed lesson and one roster insert per cancelled lesson inside its transaction, not one statement per operation | minor | Lesson edits and cancellation | Each row can take different values (its overridden fields and its own date), and the count is bounded by the series rules (at most 100 counted occurrences, or the 12-week horizon); the split of a 100-lesson series is measured at the slice review, which decides whether batched statements are needed. Slice review (2026-10-28): accepted pending the measurement of a split of a 100-lesson series, which decides whether batched statements are needed. |
| Each `tutor.deleted` email reads its listed lessons with one query on the cause, the tutor and the deletion instant, filtered by the recipient's roster; at a deletion near the per-tutor bound it may plan as a scan of the `(cancel_cause, cancelled_at)` index over every lesson that deletion cancelled, once per recipient | minor | Lesson effects of tutoring | The cost is one read per queued email in the worker, never in a request; the slice review measures the dispatch of a tutor deletion's emails at the bound of the per-tutor caps and decides whether the query needs an index leading with the tutor.

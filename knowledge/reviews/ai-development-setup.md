# AI development verification

Active policy for how coding agents verify OVC changes. [AGENTS.md](../../AGENTS.md) requires the checkpoints; [ovc-verify](../../.claude/skills/ovc-verify/SKILL.md) owns routing and evidence. Product behavior remains in the specifications and their cited decisions. This file is the exception in `reviews/`: it is current policy, not a historical record.

## Minimal inventory

- `AGENTS.md` at the repository root holds every rule; `CLAUDE.md` imports it so Claude Code loads the same text.
- One skill, `.claude/skills/ovc-verify`, with three verification tiers ([ADR-0011](../../docs/decisions/0011-tiered-verification.md)), a standard checklist for routine changes, and four full review profiles for slice reviews and security reviews: correctness, security, browser and performance.
- `.claude/settings.json` sets permissions and two hooks.
  - **Permissions:** secrets, private keys and credential directories are unreadable, and system directories are not editable. Commits and merges run without confirmation; the settings ask before agents push, rebase, reset, clean, force-delete branches, discard work with destructive checkouts, restores or stash drops, or rewrite history (amend, filter-branch, update-ref, reflog expiry). Absolute paths in rules use the `//` prefix, because a single leading `/` is relative to the settings file.
  - **Secret guard hook** (`guard_secrets.py`, before file, search and shell tools). It refuses calls that name an environment file other than `.env.example`, `.envrc`, a private key or certificate, or a credential directory, and the common forms of shell commands that print the environment or interpolated container credentials: `docker compose config` or `convert` (except with only read-only listing flags), `docker inspect` (except for images, volumes and networks), `docker buildx bake --print`, environment dumps inside `docker exec` or `run`, `/proc/*/environ`, `env` without a command, `printenv`, `export`, `declare`, `typeset` or `compgen` with only flags, bare `set`, `ps` with environment flags, `launchctl getenv` and `export`, interpreter code that reads the environment (in `-c` or `-e` arguments and in heredocs fed to an interpreter), `echo`, `printf`, `cat` or `tee` of a credential variable, and unquoted heredocs that expand a credential variable. It sees through leading assignments, wrappers (`command`, `nohup`, `time`, `nice`, `timeout`, `xargs`, `watch`, `arch`, `uv run`, `pnpm`, `npm`, `npx` and `pnpx` with their `-c`, `--call` and `--shell-mode` scripts and every word after the runner, `env`, `eval`, and the local settings wrapper `tools/dev-env.sh`, also when it runs as a shell script or is sourced, refusing the common traced-shell forms around or inside it and trace or startup-file variable assignments (`SHELLOPTS`, `BASHOPTS`, `BASH_ENV`, `BASH_XTRACEFD`, `ENV`, `ZDOTDIR`, `HOME`) anywhere in the same simple command, which also refuses harmless arguments that start with those names, such as `docker compose run -e HOME=/tmp`), grouping, shell `-c` in any flag cluster, command substitution and heredocs fed to a shell, and it leaves `git commit`, `log` and `status` arguments, single-quoted text and heredoc bodies fed to other programs alone. `.claude/hooks/check_guard_secrets.py` lists the refused and allowed forms and fails on any regression. Limitations: it matches command text, so it guards against accidental disclosure rather than a determined agent; forms it does not recognise include other programs that dump the environment (for example `jq -n env`, `make -p`, `find -exec env`, `su -c`, a command or heredoc piped into a shell or an interpreter, `declare -p NAME`, nested command substitutions), environment reads in interpreter code it cannot see, and scripts written to a file first; through `tools/dev-env.sh` in particular, `jq -n env`, `make -p`, programs that print their own environment, commands piped into `xargs tools/dev-env.sh`, and `sh -c` commands that send a loaded value elsewhere (for example `curl -v` or `psql "$OVC_DATABASE_URL"`) are not recognised, a variable name such as `OVC_SMTP_USERNAME` is not treated as a credential by the printer check, trace settings exported earlier in the command (`export BASH_ENV=…; …`; the wrapper clears inherited traps, unsets `BASH_ENV`, `ENV` and `ZDOTDIR` and stops exporting `BASH_XTRACEFD` (unsetting it would close the descriptor it names in bash 4.1 and later) before it runs its command, but an exported `BASH_ENV` still runs in the wrapper's own shell before it can protect itself, and the user's own `~/.zshenv` still runs for zsh commands), functions exported before the call and inner traces such as `make SHELL='bash -x'`, `env -S 'bash -x' tools/dev-env.sh …` and zsh's underscore option spellings (`x_trace`) and `setopt -x` are not recognised, while an exported `unset` function replaces the wrapper's own `unset`, so no exported function is removed and it runs again after the files load (bash 4 and later), and exported `set` and `[` functions run before the files load; an assignment to an already exported variable such as `HOME=…;` in an earlier statement of the same call is not recognised; and an inner interactive or login shell (`bash -i`, `bash -l`, `bash --rcfile`) reads its startup files from the user's home directory; the scan of every word after a package runner also refuses ordinary commands whose arguments end with a printer's name, such as `pnpm exec vitest run -t set` or `pnpm add env`; variable names containing `TOKEN`, `SECRET` or `PASSWORD` are refused in printers even when harmless; and it fails open when `python3` itself is missing, because the harness treats only exit code 2 as a refusal.
    - Matching is case-insensitive, follows symlinks for file tools, and treats glob patterns that could match such files as matches.
    - It also scans unquoted heredoc bodies, and the file-access lines of quoted heredocs fed to interpreters.
    - It fails closed on malformed input. Commit messages, `git status`, `git log` and `git check-ignore` are not inspected.
    - **Recorded limitations:** names built at runtime, programs that open such files by themselves, and wrappers that hide `git` from the permission rules are not caught.
  - **Post-edit hook:** reports Python syntax errors, and Go files that `gofmt` cannot parse or would reformat, back to the agent; when `gofmt` is missing it reports that the file was not checked.

There are no permanent specialist agents. Correctness spans every component contract, so separate architect, API, database, test-writing or frontend agents would duplicate ownership and drift from `AGENTS.md`. Browser and performance stay separate profiles because performance needs an uncontended machine and an explicit measured conclusion beyond successful interactions, even when one layer reviewer applies both. Security owns threat-based reasoning beyond correctness. Routine changes get one fresh general-purpose reviewer applying the standard checklist, plus a fresh security reviewer when the change meets the security trigger defined in [AGENTS.md](../../AGENTS.md#development-verification); slice reviews run one fresh general-purpose subagent per changed layer (backend, frontend, security, tooling and agent configuration), each applying the profiles its components need, and after fixes at most one reviewer looks again ([ADR-0011](../../docs/decisions/0011-tiered-verification.md)). Reviewers never inherit the implementation conversation.

The repository is local only: no remote, no CI service and no automated pull-request review. An implementing agent runs the change checks of its diff from the [change-check table](../../docs/development.md#change-checks-and-the-merge-gate) and reports every other check as `deferred to the merge gate`; the coordinating agent runs the full local check run once per merge in the merge gate, `main`'s copy of `tools/merge-gate.sh` run from a scratch folder, on a clean tree under a per-user lock, bound to the base commit and the tested tree, and merges only when it passes ([ADR-0018](../../docs/decisions/0018-targeted-checks-and-merge-gate.md)). The readiness report carries the change checks, and the merge report the gate's commands, exit codes and hashes. When a remote and CI are adopted, the same commands become required CI jobs.

## Component checklist

Use [the knowledge index](../README.md) for exact contracts. This checklist names navigation families, not indivisible review assignments: split a family into the actual affected components when they own distinct contracts, state or failure boundaries. At a slice review, every affected component receives correctness review and the skill selects other profiles from its effects; a standard reviewer uses the same families to decide what to read. The last column selects measurements under the performance profile's [resource lifetime method](../../.claude/skills/ovc-verify/references/performance.md#resource-lifetime-measurements); runtime checks activate with the implementation, not because this table names them.

| Component family | Check focus | Performance and resource-lifetime workload |
|---|---|---|
| Accounts and sessions | Registration with consent, verification, enumeration resistance, hashing, throttling, refresh rotation and reuse detection, reset and change, deletion and purge, `ovc-admin` | Repeat sign-up, login, refresh and logout cycles; hashing latency, query count per request, session and token rows retained versus revoked |
| Relationship and group guards | Relationship-scoped resolution on every route and frame, `not_found` outside scope, ended and removed participants | Extra queries per guarded request; guards never load whole collections |
| Relationships, invitations, join requests | Card states, email-bound acceptance, code throttling and regeneration, ending and reactivation effects in one transaction | Tutors with many students and requests; list query count and payload size |
| Groups | Membership changes and their effects on chat, rosters and issues; archiving | Groups at the 30-member limit; membership change cost |
| Schedule and series | Local-to-UTC conversion across daylight-saving changes, materialisation horizon, scoped edits and splits, overlap warnings, status and join window | Long series and range queries; index use, horizon extension cost |
| Meetings, recordings and provider adapters | Join authorization and link handling, callback verification, reconciliation, copy, retention, playback authorization, shared contract tests for BigBlueButton and fake | Repeated join, end and recording cycles; streaming copy memory, outbound connections closed, provider timeouts bounded |
| Chat and WebSocket gateway | Persist-then-fan-out, membership and writability, pagination stability, read markers, reconnect recovery, close paths | Many connected members and idle sockets; fan-out latency, memory and tasks per connection, registry cleanup after error and abrupt close |
| In-app notifications and broadcaster | Recipient selection, hint-only payloads, tutor labels, idempotent rows; slow consumers are closed with `4429` and refetch, which replaces any lost-frame guarantee | Burst publishing; queue sizes and cleanup |
| Library and builder | Folder depth, block schema validation, restricted Markdown sanitising, normalisation version | Templates at the 100-block limit; validation and render cost |
| Issuing, submissions and review | Snapshots, answer visibility and the key-leak contract test, autosave versions, state machine, scoring and overrides, corrected files | Group issues at the size limit; autosave write rate; review queue query count |
| Analytics | Final scores after overrides, per-question aggregates, purge effects | NFR-2.6 workload: 50 submissions × 100 questions |
| Email, outbox and worker | Transactional outbox writes, `SKIP LOCKED` claiming, backoff and dead rows, idempotency keys, reminders from current state, digests, unsubscribe tokens, `Tick(now)` determinism | Backlogs of thousands of rows; batch duration, connection use, no growth across repeated ticks |
| Uploads, storage and downloads | Streaming size limits, content-based type detection, random keys, binding rules, quotas, unbound cleanup, signed URLs | Large and concurrent uploads and downloads; memory independent of file size, temporary objects and descriptors released on success, rejection and disconnect |
| HTTP API routers, schemas and error mapping | Route paths and callers match the API specification, the error-code catalogue and status codes, separate student and tutor schemas, pagination, security headers | Payload size per route; query count per request |
| Domain rules (`internal/domain`) | Normalisation, number parsing, scoring arithmetic, recurrence expansion, state transitions, with the unit tests `AGENTS.md` allows | Expansion of 100-lesson series; normalisation of 20,000-character answers |
| End-to-end test harness | Control routes exist only under `OVC_TEST_CONTROL=1`, shared clock across processes, mail sink readable, fake room and signed fake callbacks | Suite isolation and parallel run time within the 10-minute budget |
| Data model and migrations | Constraints, check constraints for exclusive pairs, indexes, migration up and down on a populated database | Migration time on representative data |
| Configuration and processes | Settings validation, startup refusal on invalid configuration, logging bootstrap, graceful shutdown of the API and worker | Startup time; connections and tasks closed on shutdown |
| Frontend realtime client (`lib/realtime`) | Reconnect with jitter, refetch on reconnect, close-code handling (`4401`, `4429`), subscription cleanup | Reconnect storms; listeners and timers after unmount |
| Adapters: storage, mail, clock, meeting provider, PostgreSQL listener | Contract tests shared by production implementations and fakes; the PostgreSQL listener has no fake and is tested against the test database, through the byte-relaying forwarder only in its liveness tests; the shared test clock and mail sink only under test control | Adapter call latency and resource release |
| Frontend shell, routing, i18n, shared UI components and API client | Thin client, translated error codes, token refresh, role guards, both languages and themes, loading, empty and error states | Bundle size per role, loading milestones, query cache bounds |
| Frontend features (auth, home, notifications, schedule, lessons and embed, students and groups, library and builder, homework and review, chat, settings) | Pilot scenario journeys for both roles, tutor labels, untrusted content rendering, accessibility, responsive layout | Long message lists, calendar navigation, large builders, embed mount and dispose cycles; listeners, subscriptions, timers and heap after unmount |
| Development configuration and agent setup | Rule consistency, routing completeness, permissions, preserved checks | Check run duration; instruction-only edits need methodology review, not fabricated runtime samples |

## Activation

Checks activate with the capability they verify, following the [roadmap](../../docs/roadmap.md):

- **Now (documentation only):** Markdown lint, offline link and anchor check, and Mermaid parsing over all Markdown are active and required.
- **Backend scaffold (slice 1):** `go mod tidy -diff`, `gofmt`, `go vet`, golangci-lint, `govulncheck`, `sqlc diff` (active since the accounts schema of slice 2), and `go test -race` including the package-layer architecture test and the integration test database container activate. Security scanning tools are selected and registered here.
- **Frontend scaffold (slice 1):** pnpm frozen install, TypeScript check, ESLint, Prettier check and production build activate. The first runnable shell activates Playwright boot, diagnostics and accessibility smoke and loading-performance measurement.
- **Each later slice:** adds its integration tests, its Playwright journeys, its observability assertions and its performance workloads from the table above, registered as commands in the development guide in the same change.

Unimplemented capabilities are `pending implementation` with the slice that activates them; an existing capability that cannot be checked is `blocked`. Missing tools are never silently installed or counted as passing; dependency adoption follows `AGENTS.md`.

Prompt routing is procedural, not enforced by tooling. Reviewers inspect source and actual command output; an implementation-authored report alone does not prove independent review.

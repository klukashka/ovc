# API specification

REST under `/api/v1` (omitted from the paths below), JSON in and out except uploads. Authentication is `Authorization: Bearer <access token>` unless marked otherwise. The WebSocket surface is in [realtime and video](realtime-and-video.md#connection); its route is listed under [realtime](#realtime). The frontend is a thin client over this API and holds no rules of its own. Behavior is defined in the domain specifications linked from each section; this file fixes paths, callers, codes and conventions.

In the MVP the recordings routes and the recording-ready callback, `GET /students/{id}/progress` and `GET /issues/{id}/analytics` are not registered, and `/tutor/settings` returns and accepts no recording retention or recording quota and usage; they come [after the MVP](../../docs/roadmap.md#after-the-mvp) by the owner's decision of 2026-10-22.

**Who:**

| Value | Meaning |
|---|---|
| `public` | needs no session |
| `user` | any signed-in account |
| `unverified ok` | also open to accounts whose email is not confirmed; every other authenticated route requires a confirmed email and answers `403 email_not_verified` otherwise |
| `tutor` | a tutor acting on their own resources |
| `student` | a student acting on their own resources |
| `role check` | open to both roles at the audience level; the service refuses the other role with `409 role_mismatch` ([FR-1.3](../../docs/requirements/functional.md#fr-1-accounts)) |
| `audience` | the lesson's tutor, or a student in its current audience, resolved by the [visibility rule](schedule.md#visibility) |
| `roster` | the lesson's tutor, or a student in its frozen roster, resolved likewise |
| `member` | an active member of the channel: a member row that is not suspended, of a channel that is neither discarded nor pending erasure ([channels](realtime-and-video.md#channels)) |
| `author` | the author of the message, while an active member of its channel |
| `provider` | the meeting provider, authenticated as described under [callbacks](realtime-and-video.md#callbacks) |

- **Refusal order:** audience refusals come first and depend only on the caller: the other role gets `404 not_found`, with the same body and headers as an unknown route, then an unconfirmed email gets `403 email_not_verified`. Both are checked before the body is read, so a caller of the other role gets `404` whatever the body holds: missing required fields, wrong lengths, types or formats, an unexpected property, another content type, or JSON that is not well formed. Then comes the request itself: a body that is not well-formed JSON answers `400`, and the operation's schema checks answer `422 validation_failed` (required fields, lengths, patterns, types, `unexpected_property`). These checks depend only on the request and reveal nothing about other accounts' data. A malformed path identifier answers `404`. Then every identifier in a path or a body is resolved within the caller's scope, and anything outside it is `not_found`, with the same body as a random identifier. Then come `409 role_mismatch` and state refusals (`409`), then the remaining validation the service performs (`422`), so a state refusal never confirms that an out-of-scope identifier exists. Routes whose order differs say so in their row and in the per-route orders of the [accounts specification](accounts.md#invitations), for example the new-account path of `POST /invitations/{token}/accept` and `POST /join-requests`, which answers `422 tutor_code_invalid` before `409 already_linked`.
- A student calling a tutor route, or the reverse, gets `not_found`; the only role-specific refusal is `409 role_mismatch` on invitation acceptance and code entry, which both roles reach.
- Every authenticated request checks the session and account state ([roles and accounts](accounts.md#roles-and-accounts)).

## Conventions

- **Errors:** every non-2xx response has the body
  `{"error": {"code": "<stable_snake_case>", "message": "<English fallback>", "request_id": "<id>", "fields": [...], "details": {...}}}`.
  - `code` values are an enum in `internal/domain`. The frontend translates them; `message` is a developer fallback, never shown as is.
  - `fields` lists `{"path", "code"}` for validation errors.
  - `details` carries structured data for a few codes, for example the conflicting lessons of `lesson_overlap`.
  - No stack traces, SQL or internal identifiers appear in an error, and no submitted value is echoed back: huma's default problem-details error is replaced through `huma.NewError` with this shape, and `fields` carries paths and codes only.
- **Error codes:**

  | Status | Codes |
  |---|---|
  | 400 | `bad_request` |
  | 401 | `unauthenticated`, `token_expired`, `invalid_signature` (provider callbacks), `invalid_credentials` (a wrong password, an unknown email or a deleted account, with one identical answer) |
  | 403 | `email_not_verified`, `account_blocked` (only after the correct password, or for an existing session), `forbidden` (allowed to see, not to change; also a missing, foreign or repeated `Origin` where a route requires the exact one) |
  | 404 | `not_found` |
  | 405 | `method_not_allowed` |
  | 409 | `conflict` (stale version), `lesson_overlap`, `lesson_not_live`, `outside_join_window`, `not_editable`, `answer_frozen`, `already_linked`, `student_exists`, `relationship_not_active`, `audience_not_active`, `role_mismatch`, `invitation_invalid`, `invitation_email_mismatch`, `relationship_not_provisional` (removal of a card that is not `provisional` or `reclaim_pending`), `return_not_allowed`, `issue_has_submissions`, `channel_read_only`, `edit_window_passed` |
  | 410 | `gone` (provider callbacks only) |
  | 413 | `payload_too_large` |
  | 415 | `unsupported_media_type` |
  | 422 | `validation_failed`, `lesson_in_past`, `tutor_code_invalid`, `token_invalid` (an invalid, expired, used or superseded confirmation or reset token, or an account in a state the token does not apply to; an invalid, expired, forged or malformed unsubscribe token, or one of an account that no longer exists or is `deleted` or `blocked`; one identical answer for every cause) |
  | 429 | `rate_limited`, `tutor_unavailable`, with `Retry-After` |
  | 500 | `internal` |
  | 503 | `provider_unavailable`, `service_unavailable` (readiness, a saturated password-hashing limiter, a full avatar decoding budget, a full budget of unauthenticated WebSocket connections, or from slice 6 an instance serving its limit of 64 downloads at once or the global chat upload intent capacity being full, and from slice 8 the global library upload intent capacity being full) |
  | 507 | `quota_exceeded` |

  Every code is an `ErrorCode` constant in `internal/domain`, listed by `AllErrorCodes` with its status and message, and published as the enum of `ErrorBody.code` in the OpenAPI document; the frontend derives its `ErrorCode` type from that enum and must translate every code in both languages. A conventions test requires `AllErrorCodes` to list exactly the declared constants, and an unlisted value is sent as `internal`. A client that receives a code it does not know shows a generic message with the request identifier.

- **Pagination:** every list route except `/calendar`, `/home`, `/tutors`, `/groups` and `/library/folders` is keyset paginated (`?limit=&cursor=`, default 30, maximum 100), except that a channel's message history defaults to 50 per page ([messages](realtime-and-video.md#messages)). Responses include `next_cursor`, which is `null` at the end. `/tutors` is bounded by the relationships tutors create for the student, and `/groups` by the limit of 200 groups per tutor ([groups](accounts.md#groups)). From slice 8 `/library/folders` and the child folders of `GET /library` are unpaginated too, bounded by the limit of 1,000 folders per tutor, while the items of `GET /library` are keyset paginated ([library](homework.md#library)).
- **Identifiers** are UUIDs. **Timestamps** are ISO-8601 in UTC; the client converts them for display.
- **Idempotency:** `PUT` routes and the submit, check, return, accept, decline, end, cancel, archive, unarchive and withdraw routes are safe to retry; repeating one in the same state returns the current state, and a repeated withdrawal of a student card (`DELETE /students/{id}`) answers `204`. Removal of a provisional student is not retry-safe: a repeat names a discarded card and answers `not_found`. Create routes (`POST /lessons`, `/students`, `/groups`, `/issues`, `/library/templates`) accept an `Idempotency-Key` header, and a repeated key returns the first result; for cards, groups, lessons, series and templates the key is stored per tutor with the created row (`lesson.create_key` for a one-off lesson, `lesson_series.create_key` for a series, from slice 8 `template.create_key`), and it is never logged. From slice 6 `POST /channels/{id}/messages` accepts an `Idempotency-Key` too, stored as `message.client_key` per sender and channel and re-authorized on a repeat ([messages](realtime-and-video.md#messages)).
- **Request identity:** every response carries `X-Request-ID`, which also appears in error bodies and diagnostics ([observability](observability.md#correlation)). An incoming `X-Request-ID` is kept only when it appears once and matches `^[A-Za-z0-9._-]{1,64}$`; otherwise the server generates a new one and never rejects the request.
- **Schemas** are the Go structs in `internal/schemas`, validated by huma and published as OpenAPI JSON at `/api/docs/openapi.json` only when `OVC_API_DOCS_ENABLED=true` (off by default and in production), with no documentation UI; `api openapi` prints the same document without reading any setting. Student-facing and tutor-facing structs are separate wherever their content differs ([answer visibility](homework.md#answer-visibility)).
- **Server limits:** the HTTP server sets `ReadHeaderTimeout` (10 s), `IdleTimeout` (120 s) and `MaxHeaderBytes` (16 KiB). Every request has a default read deadline of 30 s and a write deadline of 35 s, set per request through `http.ResponseController`, so a request whose body stalls until the read deadline still receives its structured error; JSON bodies are limited to 1 MiB and must arrive within 30 s (both also set on every huma operation, whose own defaults are 1 MiB and 5 s). A body that does not arrive in time is answered with `400 bad_request`. The API process waits up to 40 s for in-flight requests on shutdown, longer than any request may last. Upload routes raise the body limit and the read deadline to the [file limits](files.md) and stream the body instead of buffering it; from slice 6 a streamed upload's read deadline is the context's per-file limit at 128 KiB per second, at least 60 seconds and at most 10 minutes, a body that delivers less than 16 KiB in any 30-second window is aborted as stalled, and a download from `GET /files/{id}` has a write deadline computed the same way from the file's size ([upload flow](files.md#upload-flow)); an upload still running when the 40-second shutdown drain ends is aborted and the client retries; the WebSocket route clears the deadlines after the upgrade, and on shutdown the gateway closes every socket with `1001` before that 40-second drain.
- **Paths:** a request whose path is not in canonical form (a repeated `/`, a `.` or `..` segment, or a trailing `/`) receives `404 not_found` instead of the standard library's redirect, so every non-2xx response keeps the error body.
- **Validation fields:** `fields` appears only on `422 validation_failed`. A field path never repeats a property name the client invented: an unexpected property is reported at `body` with the code `unexpected_property`.
- **Exceptions:** responses that Go's HTTP server writes before any handler runs (`431` for oversized headers, `400` for a malformed request line or URL, `501` for an unsupported transfer encoding) are plain text without the error body or the headers below; the deployment's reverse proxy answers or filters these first. Go also allows about 4 KiB beyond `MaxHeaderBytes` before refusing.
- **SQL:** every business query is written in `backend/queries/` and compiled by sqlc (from slice 2), with `sqlc.narg` and `sqlc.slice` for optional filters and lists. Infrastructure statements (the readiness ping, `current_database()`, the test clock, migration bookkeeping, test database creation) are named constants with bound parameters in the package that owns them; test database names are generated and quoted with `pgx.Identifier`. No SQL is built from client input, and `NOTIFY` is sent as `pg_notify($1, $2)` for notification and heartbeat signals and as `pg_notify($1, payload)` over `unnest($2::text[])` for entity signals, with bound parameters.
- **Headers:**
  - every response, including the static frontend, sends `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`;
  - every API response with a status of 400 or above sends `Cache-Control: no-store`;
  - pages send a Content Security Policy with `default-src 'self'`, `script-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `frame-src` limited to the conferencing subdomain, and `connect-src`, `img-src` and `media-src` limited to the OVC origin; `style-src`, `font-src` and `form-action` are `'self'`, and until the conferencing subdomain exists (slice 7) `frame-src` is `'none'`; the policy is defined once in `frontend/security-headers.ts`. Attachments are served by the OVC download route `GET /api/v1/files/{id}` on the OVC origin ([downloads](files.md#downloads)), so no storage host enters the policy; recording playback, after the MVP, decides its own source with its plan (slice 6, pending owner review);
  - the fake test room is the only exception, and only under `OVC_TEST_CONTROL=1`.

## Accounts

Behavior: [accounts](accounts.md). Every operation declares its audience in code (`public`, `user`, `user, unverified ok`, `tutor`, `tutor, unverified ok`, `student`, `student, unverified ok`, or the refresh cookie), and a test sends each non-public operation a request without a token and expects `401 unauthenticated`. A role audience refuses the other role with `404 not_found` first; then `user`, `tutor` and `student` operations answer `403 email_not_verified` to an unverified account. `POST /auth/login`, `POST /auth/refresh` and `POST /auth/verify-email` (which can sign a browser in) require exactly one `Origin` header, equal to `OVC_PUBLIC_URL` (`403 forbidden` otherwise, also for two `Origin` headers of which one is correct), compared by the same plain `net/http` function as the WebSocket upgrade; every route with a body requires `Content-Type: application/json` (`415 unsupported_media_type` otherwise), with one exception: `POST /unsubscribe` accepts no body, or the form and multipart bodies that RFC 8058 mail clients send ([preferences and unsubscribe](notifications.md#preferences-and-unsubscribe)); and the authentication routes and `/users/me` answer with `Cache-Control: no-store`. Routes marked "public, optional bearer" authenticate a bearer token when one is sent, answering `401` or `403` like any authenticated route when it is not valid, and otherwise run anonymously. Validation refusals name the field as `body.<property>`; the account routes use the field codes `invalid`, `required`, `not_allowed`, `too_short`, `too_long` and `incorrect`. Login and refresh set `__Host-ovc_refresh` with `Path=/`, `Secure`, `HttpOnly`, `SameSite=Strict` and no `Domain`; a refused refresh and both sign-outs clear it.

## Students and groups

Behavior: [relationships](accounts.md#tutorstudent-relationships), [invitations](accounts.md#invitations), [provisional links and reclaim](accounts.md#provisional-links-and-reclaim), [tutor code and join requests](accounts.md#tutor-code-and-join-requests), [ending](accounts.md#ending-a-relationship), [groups](accounts.md#groups).

- **Student card** (`StudentCard`, tutor-facing): `{id, state, display_name, email, account: {name, email, avatar_id, email_confirmed} | null, groups: [{id, name, colour}], notes, invitation: {url, expires_at, status: open | expired | revoked_after_mismatches} | null, linked_at, ended_at, ended_by, created_at}`. `account` is `null` while the card is `invited` or `reclaim_pending`, and while the linked student account is `deleted`. `groups` lists the card's groups that are not archived. `invitation` describes the card's open invitation, or, when it has none, its latest invitation if that was revoked after repeated wrong emails, and is `null` otherwise and for every card that is not `invited` or `ended`; `url` is set only while the status is `open`, so a link is shown again only while it can be used (`null` also when the stored ciphertext cannot be opened, which `invitation.unreadable` records). From slice 6 the card that `GET /students/{id}` answers also carries `channel_id`, the relationship's direct channel while the tutor is an active member of it, otherwise `null` ([chat](#chat)); `StudentCardSummary` and the cards other routes answer omit it. `StudentCardSummary` omits `notes` and `invitation`.
- **Error details:** `student_exists` carries `details.student_id`, the identifier of the tutor's existing card with that email; `relationship_not_active` from the group routes carries `details.relationship_ids`, the named relationships that are not `active`, in identifier order.
- **The student's tutor** (`MyTutor`, student-facing): `{relationship_id, state: active | provisional | ended, colour, tutor: {name, avatar_id, subjects, bio}, ended_at, ended_by, account_closed_until}`, and from slice 6 `channel_id`, the relationship's direct channel while the student is an active member of it, otherwise `null` ([chat](#chat)). `account_closed_until` is set while the tutor's account is `deleted`, to the deletion time plus 30 days (the purge), and is `null` otherwise. Student-facing structs never contain the card's display name, notes or email, or other students.
- **Responses that carry or accept an invitation link** send `Cache-Control: no-store`.
- **Refusal order:** as in the [conventions above](#api-specification): role (`404`) and email confirmation (`403`) before the body is read, then parsing and schema validation (`400`, `422`), scope (`404`), `role_mismatch` and state (`409`), then the service's remaining validation (`422`), except where a row says otherwise.

## Schedule

Behavior: [schedule](schedule.md). Slice 5 registers the first five routes below; the materials route, `material_ids` on creation and edits and the lesson detail's `materials` arrive with the library in slice 8 ([lesson materials](schedule.md#lesson-materials)), the join, end and restart-room routes with video in slice 7, and the recording routes and callbacks after the MVP and with slice 7.

- **Refusal order:** as in the [conventions above](#api-specification), with the per-route order of `POST /lessons` fixed in [scheduling limits](schedule.md#scheduling-limits): `403 email_not_verified`, the schema checks (`400`, `422`), the replay of a repeated `Idempotency-Key`, `429 rate_limited`, the audience's scope (`404`) and state (`409 audience_not_active`), the body (`422`), the caps (`422`, `too_many`), `409 conflict`, then `409 lesson_overlap`. `PATCH /lessons/{id}` and `POST /lessons/{id}/cancel` resolve the lesson within the tutor's scope (`404`) before any other answer. A test asserts the order.
- **Join admission:** after the audience, the path identifier and the scope (`401`, `404`, none of which uses a slot), a committed step under the tutor's profile lock or the student's user row lock, with the session re-check, reserves one `meeting_join_minute` slot. - **The denial table** gains every lesson route with a second tutor sharing the student, a removed group member, an ended relationship and, for `GET /lessons/{id}`, a former provisional account; the audience test lists every new operation. ## Homework

Behavior: [homework](homework.md). Slice 8 registers the library routes ([slice 8 plan](../plans/slice-8.md#61-routes)); the issue, assignment, submission and review routes arrive with slice 9.

- **Library routes** are tutor routes, open to an unconfirmed tutor (`tutor, unverified ok`); a student gets `404` for the role. Every identifier in a path, the query or a body is resolved within the caller's own library and answers `404` otherwise, with the same body as a random identifier ([library](homework.md#library)).
- **Refusal order:** as in the [conventions above](#api-specification): the role (`404`), parsing and schema validation (`400`, `413` for a body over 1 MiB, `422`), the replay of a repeated `Idempotency-Key` on `POST /library/templates`, the session and state under the profile lock (`401`), `429 rate_limited`, the identifiers' scope (`404`), the state refusals (`409`), the service's remaining validation (`422`, `too_many` and `taken` included), then the quota (`507`).
- **Writes** take the tutor's profile lock first and answer `401 unauthenticated`, changing nothing, unless the tutor is `active` or `unverified` under it; every write except a template save counts toward 600 library writes per tutor per hour, and template saves toward 2 per second per template and 3,600 per tutor per hour (`429 rate_limited` with `Retry-After`).
- **Caching:** every library route answers with `Cache-Control: no-store`, because its responses carry answer keys or download addresses.
- **The denial table** gains every library route with a second tutor's identifiers (folders, materials, templates, prompt images and material blocks), a student, a provisional account and a deleted material or template; the audience test lists every new operation.

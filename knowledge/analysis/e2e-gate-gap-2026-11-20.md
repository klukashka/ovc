# Why the merge gate's end-to-end phase is slower than the suite: measurements before a second consolidation

Recorded on 2026-11-20 for the end-to-end consolidation that the owner inserted into sub-slice 10.2 at its slice review, before the feature work of 10.3. Its aim was a merge gate median at or below 540 s without dropping coverage.

In a reused worktree the suite itself runs at 311 to 345 s. The gates' longer end-to-end phase has two measured candidates, each about 40 s in single runs and neither isolated: the gate's Playwright trace setting, and the freshly created worktree that gates are run from. Other work on the machine is not excluded either: processes of other projects ran during both decisive runs.

The owner decided on 2026-11-20 that this change records the measurements and changes no test, and that turning traces off in the gate's end-to-end run is planned as a separate change (wording pending owner review).

- **Summed test time** is the sum of the per-test durations that Playwright's list reporter prints, read from each gate's end-to-end command log (`~/Library/Caches/ovc-e2e/logs.*/26.log`).
- **The end-to-end phase is about two thirds of each gate.** With lanes of about 190 s, a gate of 540 s leaves about 350 s for the end-to-end phase.
- **The phase is close to the summed test time divided by the 6 workers, plus about 40 s.** That gap first suggested that worker restarts were a lever, since each worker starts its own deployment.

## Method

- **Tree:** `main` at `f347b78`.
- **Command:** `pnpm e2e` with the list and JSON reporters (`--reporter=list,json`, `PLAYWRIGHT_JSON_OUTPUT_NAME`). The JSON report gives each test's worker, start time and duration.
  - Every run but the last passed `--trace=off`.
  - The last ran the gate's end-to-end arguments, `pnpm e2e --max-failures=10`, which uses the configuration's `trace: 'retain-on-failure'`. That setting records a trace for every test and keeps it only when the test fails.
  - Three differences from the gate remain: the added reporters, the main checkout's `tools/dev-env.sh` in place of the tested tree's `../tools/dev-env.sh` (for lane A of the gate-like runs as well), and no gate run lock.
  - `test-results` was deleted after each run.
- **Batches:** each batch started on AC power once the one-minute and five-minute load averages were both below 6. No merge gate, other end-to-end run or full backend run of this repository was started during a batch.
  - Within a batch, the end-to-end run followed its preceding load directly, so it started at the load shown in the table.
  - Power and load were checked before every batch, but the meta files record the power line only for the first five runs.
  - No batch was checked for work of other projects; the samples of the two fresh-tree batches found some.
- **Wall time:** from the start of `pnpm e2e` to its exit, including the global setup that builds the binaries and the frontend.
- **`caffeinate`:** the first six runs used `caffeinate -dis`, except the run marked without it. The three gate-like runs used `caffeinate -i`.
- **Gate-like runs** ran each lane's commands from the full check list of `tools/merge-gate.sh` in their order, in parallel as the gate does, then the end-to-end run with `--max-failures=10`. The pre-phase tool check was left out.
- **Raw data:** the per-run JSON reports, logs and process samples were kept in a temporary folder outside the repository and are not kept.

- **Reused and fresh worktrees.**
  - The first seven runs reused one warm worktree that had no `bin/`, so the pinned tools came from the main checkout's `bin/`. In both of its runs that included lane A, lane A failed only `TestProjectLintRulesFire`, which needs the pinned linter in the worktree's `bin/`.
  - The two fresh-tree runs followed how gates are run, from a worktree created for the gate rather than by `tools/merge-gate.sh` itself: a new detached worktree created with `git worktree add` seconds before, `bin/` copied into it, and dependencies installed by the lanes. The worktree was removed with `git worktree remove` afterwards.
  - Lane A passed in the first fresh-tree run. In the second it failed only `TestUploadRecoveryBoundsCandidateAndPassDeadlines`, recorded as a flaky test in the [slice 10 known limitations](../reviews/slice-10-known-limitations.md). A lane A failure does not change the end-to-end run that follows.
- **Process samples** were taken every 15 s during both fresh-tree batches only, as the twelve processes using the most processor time. Besides the browsers, Docker's virtual machine, `node` and the deployments' own processes, they show work outside this repository:
  - **Fresh tree, traces off.**
    - A Homebrew Python 3.11 process of unknown origin used up to one full core (100 %), above 20 % in 28 samples, from 12:03:42 to 12:10:28. That covers all the lanes and the first three minutes of the end-to-end run.
    - Another project's Python test harness used up to 94 %, above 20 % in 11 samples, from 12:09:28 to 12:11:59, inside the end-to-end run.
  - **Fresh tree, the gate's arguments.** That harness used up to 73.6 %, above 20 % in 13 samples, from 12:20:42 to 12:27:14: during the lanes and the first three and a half minutes of the end-to-end run. A second process of that project used 94.3 % at 12:23:43, just before the end-to-end start.
  - The reused-tree runs have no samples, so similar outside work cannot be ruled out there either.
- **Worker restarts are not the lever.** Every run started 60 workers, 54 of them as replacements.
  - The median pause between a slot's old worker ending and its new worker's first test was 0.94 to 1.08 s with traces off and 1.34 s with traces on.
  - The pauses add up to 54 to 65 s across the six slots with traces off (84 s with traces on), about 10 s of wall time.
  - A deployment kept per slot for the whole run could save at most that much.

## Findings

- **The suite runs at 311 to 345 s in a reused worktree.** The preceding lane A, a processor load without the database, running without `caffeinate`, and the gate's three lanes all left it in that range.
- **Traces and the fresh worktree each measured about 40 s, in single runs.**
  - In the fresh tree, traces raised the end-to-end run from 363 s to 403 s, and the summed test time by 203 s.
  - With traces off, the fresh tree took 363 s against 311 to 345 s in the reused tree, 46 s above that range's median of 317 s, and 272 s more summed.
  - The engines did not move consistently between the two fresh-tree runs. Firefox fell from 954 s to 834 s summed while WebKit rose from 568 s to 809 s, so the fresh tree's Firefox excess did not recur.
  - Each cause rests on one pair under the outside work described above, so neither is isolated and they cannot be ranked.
- **The fresh-tree run with the gate's arguments reached the gates' range.** It took 190 s of lanes and 403 s of end-to-end, about 593 s, with 2144 s summed; the mains gates took 583.0 to 674.8 s, with 2054 to 2394 s summed. It ran beside another project's harness, so it does not show that the gates were free of outside work.
- **A gate without traces is estimated at about 550 s, from one run under outside work.** The fresh-tree run without traces gives 206 s of lanes and 363 s of end-to-end, about 569 s; with the about 190 s of lanes of the gates above, about 553 s. If the estimate holds, a test consolidation would still have to find roughly 10 to 15 s more. The levers that keep coverage are small: the earlier consolidation's [measurements](e2e-consolidation-2026-11-16.md#measurements) saved 28 to 41 s with every option it found, and this record found worker restarts worth about 10 s.

## Decision

The owner decided on 2026-11-20 that this change only records these measurements: no test, fixture, configuration or gate script changes, and coverage is unchanged.

Turning traces off in the gate's end-to-end command (`tools/merge-gate.sh` and its self-test, leaving local `pnpm e2e` unchanged) follows as its own change. That change needs its own task plan, the security-profile review that a verification-policy change needs (T-41), and alternating paired measurements on a machine checked for outside work (wording pending owner review).

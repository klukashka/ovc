# End-to-end speed-up of slice 9's first change: measurements and coverage record

Recorded on 2026-11-11 for change C0 of the [slice 9 plan](../plans/slice-9.md) (decisions D1 to D4, the owner's answers Q5 A and Q6 A), which applies option 1 of the [end-to-end timing analysis](e2e-speed-2026-11-11.md), fresh Firefox and WebKit browsers more often, and option 5, `maxFailures` in the gate's run. This record holds the before-and-after measurement the analysis requires and the coverage record D3 requires.

## The change

- `frontend/playwright.config.ts` reads every `*.spec.ts` under `e2e/` (recursively) at load, leaves out the three browserless suites by file name, sorts the rest and deals them round-robin into four groups. Firefox and WebKit each run as four projects, `firefox-1` to `firefox-4` and `webkit-1` to `webkit-4`, one per group, each matching its specs by their full path, with the same device settings and, for Firefox, the same `@coarse-pointer` exclusion as before. Chromium stays one project with every spec.
- Playwright starts a new worker when the next test belongs to another project, so a Firefox or WebKit worker's life now ends with its spec group, which holds a fifth to a third of its engine's tests (Firefox 121, 158, 182 and 118 runs, WebKit 121, 158, 184 and 118, since whole specs are dealt round-robin) and is shared by several workers at once; its successor starts with a new browser and a new deployment (a new database, migrations, API, worker and preview). The number of concurrent workers stays at Playwright's default of 6, so the PostgreSQL connection peak is unchanged.
- The gate's end-to-end entry in `tools/merge-gate.sh` becomes `../tools/dev-env.sh pnpm e2e --max-failures=10`, and the expected list in `tools/check-merge-gate.sh` follows. A passing run is unchanged; a failing run stops after its tenth failed test and reports the rest as not run. Local `pnpm e2e` keeps its full run. The gate always runs `main`'s copy of the script, so the setting applies from the first gate after this change merges.
- `e2e/database-measurement.config.ts` spreads the default projects, so it inherits the split (`firefox-1-on` and so on); its `--list` with `--project='*-on'` and with `--project='*-off'` each list 1788 tests.

## Method

- Machine: 12 logical cores, macOS, Playwright 1.63.0, 6 workers in every run. Each run was `tools/dev-env.sh pnpm e2e --trace=off` from the change's `frontend/`, with `test-results` deleted after each run. The coordinating session confirmed that no merge gate, other end-to-end run or full backend run was on the machine during each batch of three.
- Before: three back-to-back runs of `main` at `e130813`. After: three back-to-back runs of the same tree with this change. The one-minute load average was read at each start. A run that follows another starts at a load average near 20, left by the previous run's own browsers; it was the same for both batches.
- Wall time: from just before `pnpm e2e` started to the end of its output (the "before" runs: from the recorded start to the log file's last write; the "after" runs: `date +%s` before and after). Both include the global setup that builds the binaries and the frontend.
- Summed test time per engine and the ratio of each Firefox or WebKit test to the same test in Chromium by quarter of that engine's runs (in completion order) come from the list reporter's per-test durations, as in the analysis.

- **Wall time:** mean 313 s before (285 to 342 s) and 259 s after (257 to 261 s), 54 s or 17 % less, and the run-to-run spread fell from 57 s to 4 s. The slowest "after" run is 24 s faster than the fastest "before" run.
- **Firefox:** summed time fell from 965 s to 579 s on average (40 % less). Its ratio to Chromium by quarter went from 1.53–1.68, 2.15–2.39, 2.52–3.43 and 4.20–5.77 before to 1.67–1.76, 1.73–1.84, 1.50–1.74 and 1.91–2.15 after: the late-run slowdown the analysis found is mostly gone, as its answer 3 bounded (Firefox at about 590 s if it stayed at its first-quarter ratio).
- **WebKit:** its ratios were 1.20 to 1.46 in every quarter before and 1.27 to 1.65 after, so these runs showed no WebKit slowdown to remove, unlike the gates the analysis read (where it rose from about 1.35 to about 2.4 under the lanes' preceding load). Its summed time is unchanged within the spread (443 s before, 459 s after); the split is kept for WebKit because the analysis's gates showed the slowdown there and the extra worker starts cost no measurable wall time in these runs.
- **Chromium** is unchanged (334 s and 329 s summed), as expected.
- **The failure in "before 3"** is the Firefox test `student card › notes corrected after a refusal are saved` (`students.spec.ts:508`) on `main` before any change; it is recorded in the [slice 9 known limitations](../reviews/slice-9-known-limitations.md) and is not caused by this change.

D2's target, three consecutive merge gates of this change's tree at no more than 480 s each, is measured by the coordinating session's gates, not here. With the analysis's median lane A of 131 s (164 s at most), an end-to-end run of about 260 s gives a gate of about 390 to 425 s.

## Coverage record

This change merges, moves and removes no test and changes no spec file, fixture or assertion. Evidence:

- `pnpm exec playwright test --list` prints `Total: 1788 tests in 34 files` on `main` and with the change, and the sorted list of its `[project] › file:line › title` lines, after mapping `firefox-1` to `firefox-4` back to `firefox` and `webkit-1` to `webkit-4` back to `webkit`, is identical line for line (628 Chromium, 579 Firefox, 581 WebKit runs).
- Every measured run with the change reports `1788 passed`, the same totals as the passing baseline runs.
- The measured runs used a first version of the configuration whose patterns matched a spec by its file name instead of its full path and left out the browserless suites by relative path instead of file name; after the review fixes the inventory is again identical line for line to `main`'s, so the measured runs ran the same tests as the final configuration.
- `git diff main -- frontend/e2e` is empty, and `git diff main -- frontend/playwright.config.ts` adds no `timeout` or `retries` line.

## Threat model mapping

The change meets the security trigger as an end-to-end harness and verification-policy change. T-41 (verification policy weakened): examined; the gate's end-to-end entry gains `--max-failures=10`, decided by the owner as Q6 A; a stopped run exits non-zero, so the gate still fails closed, and `docs/development.md` limits what a stopped run proves for the infrastructure-rerun rule; no check, timeout, retry or worker count is loosened and no test leaves any engine; the T-41 row needs no amendment. T-19 (secret disclosure): not affected; the gate still runs the end-to-end suite only through `tools/dev-env.sh`, and the configuration reads only file names under `e2e/`. T-36 (the test control surface): not affected; no route or test-control setting changes.

## What this record does not cover

- Three runs per side on one machine; the gate runs `pnpm e2e` after lane A has loaded the machine, so its savings may differ from these.
- Each of the 6 worker slots now starts 9 deployments in a run instead of 3, so the teardown residual in the development guide (a process that misses both deadlines may still hold its address, and the next deployment's address check on that port then fails loudly) has three times as many chances to occur; the six measured runs did not hit it.
- No check asserts that the Firefox and WebKit inventory equals Chromium's minus the browserless suites; it holds by construction (every group is dealt from the same discovered list) and was verified with `--list` for this change.
- The group count of four was not tuned: the first measurement already removed most of the Firefox slowdown, so no exploratory run with three or six groups was made.
- The remaining options of the analysis (moving browser-independent checks to Go, shortening lane A) are left for a later consolidation if D4's 540 s rule calls for one.

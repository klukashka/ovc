# OVC verification

Use the proposed scope at task entry and the actual diff before readiness. This skill owns review routing and the tiers decided in [ADR-0011](../../../docs/decisions/0011-tiered-verification.md); [AGENTS.md](../../../AGENTS.md) owns the change workflow, [the knowledge index](../../../knowledge/README.md) owns contract lookup, and [the coverage checklist](../../../knowledge/reviews/ai-development-setup.md) maps component families, workloads and activation conditions. Load only the selected profiles. An assigned reviewer runs its profile directly and may subdivide that assignment without restarting the whole router.

## Choose the tier

State the tier and whether the change meets the [security trigger](../../../AGENTS.md#development-verification), with reasons, in the plan, and recheck both against the final diff before readiness. When in doubt, pick the higher tier and assume the trigger is met. A change that meets the trigger is never trivial.

| Tier | When | Reviews before readiness | After fixes |
|---|---|---|---|
| Trivial | A typo, a broken link, an obvious one-line bug that does not meet the security trigger | None; run the checks | Rerun the checks |
| Standard | Every other change inside a slice | One fresh reviewer over the complete diff with the [standard checklist](references/standard.md); plus one fresh reviewer with the full [security profile](references/security.md) when the change meets the security trigger | Rerun the checks; at most one fresh reviewer scoped to the fixes, only when a blocker or major finding was fixed or a contract changed; it applies the standard checklist to the fixes, plus the full security profile when such a finding concerned security; if the final diff meets the security trigger and no security-profile reviewer saw the change, one runs over the complete diff even when the scoped re-review has run, replacing it when both would run and also applying the standard checklist to the fixes; minor findings of the re-review are fixed when cheap or recorded as known limitations in `knowledge/reviews/slice-<n>-known-limitations.md` and start no further round; a blocker or major finding from it is fixed and the checks rerun, and the coordinating or implementing agent decides without asking the owner whether one more fresh reviewer runs, running one when in doubt (with the full security profile when the finding concerned security) and recording in the readiness report that it ran or why it did not; that reviewer follows the re-review's rules, and after a blocker or major finding from it the decision on any further reviewer goes to the owner as a multiple-choice question before the change merges; the readiness report says for each fixed security finding whether its fix touches a trust boundary; other minor fixes need only the checks; severity is the reviewer's and is never downgraded |
| Slice | Every planned change of a roadmap slice has merged and the slice is about to close; each sub-slice of slice 10 counts as a roadmap slice (see [Determine scope](#determine-scope-slice-tier)) | One fresh reviewer per changed layer (backend, frontend, security, tooling and agent configuration), as below, over the cumulative diff since the commit that closed the previous slice, or for a slice 10 sub-slice over its list of changes | Fix in follow-up changes under the standard after-fix rule; each follow-up is a standard-tier change, names the finding it resolves, and its reviewer confirms it is closed |

The security trigger and its examples are defined once, in [AGENTS.md](../../../AGENTS.md#development-verification); link to it instead of restating it.

"The checks" in this table are the change checks of [ADR-0018](../../../docs/decisions/0018-targeted-checks-and-merge-gate.md): the rows of the [change-check table](../../../docs/development.md#change-checks-and-the-merge-gate) that the diff touches, or the full local check run for a path the table does not list or any doubt. The readiness report lists each change check with its result and every other command of the full run as `deferred to the merge gate`.

### Merge gate

Before every merge into `main`, on an idle machine as the check budget of [ADR-0018](../../../docs/decisions/0018-targeted-checks-and-merge-gate.md#decision) defines, the coordinator copies `main`'s gate with `git show main:tools/merge-gate.sh > <scratch>/merge-gate.sh`, never running the copy in the tree under test, and runs `bash <scratch>/merge-gate.sh gate --ff-only --change <branch> --repo <change checkout>`, or, when `main` has moved, `git merge --squash <branch>` on `main` and `bash <scratch>/merge-gate.sh gate --squash --change <branch> --repo <main checkout>`; one change per gate, with nothing edited, restaged or committed between the gate and the merge. It merges only when the gate prints `result: passed`, then runs `bash <scratch>/merge-gate.sh finish --repo <main checkout>`, which must print `result: passed` with equal tested and `main` trees and the full check list (or the Markdown-only list for a Markdown-only scope). Never pass `--checks self-test` outside `tools/check-merge-gate.sh`. A failed squash gate leaves the staged squash on `main`; agents never reset or restore, so the owner unstages it. A failed command sends the change back to its branch under the after-fix rule; one rerun of the gate is allowed only when the output names an infrastructure error (Docker or PostgreSQL unreachable, `too many clients`, also while the lanes run) and no test assertion failed, and the merge report quotes it together with the earlier attempts the gate lists for the same tree; a test that fails and then passes is a failure and a flaky-test bug; a second infrastructure failure goes to the owner, and a `too many clients` that recurs on the rerun is reported to the owner as a gate bug. The gate holds the end-to-end run lock for its whole run, so a run-lock refusal in its own `e2e` log is a gate bug with no rerun; when the gate fails before any check because `the end-to-end run lock … is busy`, wait for the named holder to end and start the gate again, which does not count as the rerun. Run the gate from a clean shell: it refuses to start while the shell exports a function, `BASH_ENV`, `ENV`, `SHELLOPTS` or `BASHOPTS`, a `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG*` or other repository-selecting Git variable, or while the environment or the user-level Go or pnpm configuration changes what its checks run (for example `GOFLAGS`, `NODE_OPTIONS`, `npm_config_*`, `go env -w`, pnpm `node-options`); unset the named setting for the gate only (`env -u NAME` or `env -u 'BASH_FUNC_<name>%%'`, or `GOENV=off` for the user-level Go configuration) rather than working around it, and never pass `--lock-dir`, `--checks self-test` or `--skip-tool-probes` to a real gate. A failed finish keeps the lock and goes to the owner. The merge report to the owner carries what the gate and its finish printed: the change, the base commit, the tested tree, `main^{tree}` after the merge and every command with its exit result, and names every container that the gate's `other containers` count includes (decided by the owner on 2026-11-22, pending owner review). A new gate of a change after a failed gate is a rerun unless it is an after-fix gate as the Failures bullet of [ADR-0018](../../../docs/decisions/0018-targeted-checks-and-merge-gate.md#decision) defines it, with the evidence that bullet requires; in doubt, it is a rerun, and the coordinator reads that bullet before it gates a change again. A change whose own diff changed after its failed gate, beyond its rows in the slice's known-limitations file, is gated again only as an after-fix gate with that evidence; the owner's approval of a rerun never admits a changed diff; when a run of the evidence series of such a gate ran no test, the change returns to its branch, and only a further change of its diff with a new, complete evidence series admits a gate (decided by the owner on 2026-11-22 after the sub-slice 10.3 slice review, pending owner review). Every failed gate of a change that is gated again, the one infrastructure rerun included, gets a row of kind `rerun` or `after-fix` in the slice's known-limitations file, with its date, tested tree, failing tests or checks and the owner's decision or the after-fix evidence, written in the change's own commit before the next gate, so the next gate tests the tree that holds the row. The one rerun after a named infrastructure error with no failed assertion needs no approval; every other rerun needs the owner's approval, recorded in its row before it runs, and the merge report repeats the row. A run or series made for after-fix evidence is never repeated, discarded or replaced. Where this summary and ADR-0018 differ, the stricter rule applies (decided by the owner on 2026-11-17, pending owner review). Every run made for after-fix evidence or for a measurement record goes through the main checkout's `tools/dev-env.sh`, never a fresh worktree's copy, with the pinned tools of `bin/` present. An after-fix evidence run counts only when its output holds a line naming the selected test with its outcome, as ADR-0018's recorded lines require (a package's `ok` line alone does not), and a measurement run only when its output names the measured test or package with its outcome; a run that ran no test is recorded as such, counts as not run under ADR-0018's Failures bullet and is never repeated, discarded or replaced, so a broken evidence series leaves the next gate a rerun ([development guide](../../../docs/development.md#change-checks-and-the-merge-gate); added 2026-11-20 by the owner's decision after the sub-slice 10.2 slice review found the finding recurring, pending owner review).

Planning reviews: a slice plan gets one standard reviewer before work starts, and a slice or task plan that meets the security trigger also gets a security-profile reviewer before approval, as [the security profile](references/security.md) requires; other task plans are approved by the owner without a planning review. Standard reviewers flag performance risks; measurements run only at the slice tier.

### Standard dispatch

Launch a non-fork `general-purpose` subagent through the Agent tool, in the background when other work can continue. Give it the repository path, the instruction to read `AGENTS.md` and [references/standard.md](references/standard.md) in full, the base commit and working-tree scope, the plan's acceptance criteria, the contracts touched, the tier, whether the change was classified as meeting the security trigger, and whether a security reviewer was dispatched. Do not pass the implementation conversation or a desired verdict. Dispatch the security reviewer, when required, in the same message with the security profile and the same scope. The rest of this page, except where it says otherwise, describes the slice tier; evidence and status rules apply to every tier.

## Determine scope (slice tier)

Identify the requested behavior, the acceptance criteria and the approved base (the last commit on `main`, or the empty tree before the first commit; at the slice tier, the commit that closed the previous slice). Each sub-slice of slice 10 counts as a roadmap slice for the slice tier; the sub-slices are, in this order, 10.1, 10.2, 10.3, the interface rework stage (`UI`), the finance stage (`FIN`), the booking stage (`BOOK`), the task tracker stage (`TASK`), the phone stage (`PHONE`), 10.4 and 10.5, each planned in or from the [slice 10 plan](../../../knowledge/plans/slice-10.md), and inserting, removing or reordering one changes this sentence, which meets the security trigger and needs the owner's approval (the stages after 10.3 named by the owner's decisions of 2026-11-23 with the [interface rework plan](../../../knowledge/plans/ui-rework.md), pending owner review): its slice review's scope is its own list of changes in that plan or in the stage's own plan, including any inserted consolidation, its plan revision and the follow-ups of the previous sub-slice's review that merged after that review started, stated in the review record with each change's commit, instead of the diff since the previous slice closed; the record maps every commit on `main` since the previous sub-slice's closing commit (for 10.1, since `c218028`) to exactly one sub-slice's list, a commit in no list joins the scope of the earliest sub-slice whose slice review has not started (a commit that merges after 10.5's review started is listed in 10.5's record as carried and goes to the next slice's review, which covers it in addition to its own diff), and 10.5's record shows that the lists, with the commits it lists as carried, cover every commit from `c218028` to its own closing commit; the security reviewer of 10.5's slice review also covers, per trust-boundary family, the cumulative diff since `c218028`; the known limitations stay in one file, `knowledge/reviews/slice-10-known-limitations.md`, with a sub-slice column, the development tooling reviewer re-verifies every `rerun` and `after-fix` row in it while each layer reviewer also checks the rows of its own layer, and each entry is resolved as fixed, accepted by the owner or carried into a named later sub-slice or slice (decided by the owner on 2026-11-16 with the slice 10 plan's D1 and K17, pending owner review). Include commits since that base, staged and unstaged changes, relevant non-ignored untracked files and both paths of renames and deletions. Tests, fixtures, generated code, dependencies and configuration inherit the components they affect; specification-only changes can change the same contracts.

1. Map directly changed behavior to the component checklist and the canonical contracts. Its rows are navigation families: split them when parts own distinct contracts or resources (for example the REST routers and the WebSocket gateway, or the chat feature and the shared WebSocket client). Assign unmapped areas before continuing.
2. Follow changed contracts, imports and callers, schemas, persisted data, WebSocket frames, resource ownership and shared configuration to their consumers and providers. Repeat for newly affected components until no further effect remains. Trace semantic dependencies even without an import or a changed consumer file. Record a causal edge and its source or contract evidence for every transitive inclusion, and the unchanged boundary that stops propagation. Mere reachability does not require reviewing every component.
3. Assign an owner for each affected integration boundary. For example, a change to the API error body reaches the typed frontend API client and every feature that renders errors; a change to submission status reaches the homework service (scoring and review), the homework routes, the notification frames and the homework UI. Identify the affected behavior on each side rather than assigning one giant context.
4. Produce a matrix of component, direct or transitive reason, layer, boundary owner, applicable profiles, checks and activation status. Select profiles additively for every component, then give each layer's components and profiles to that layer's reviewer, and reconcile cross-layer findings centrally.

Use the stricter of the approved base policy and the proposed policy until the owner explicitly approves a reduction. Deleting a check, test or routing instruction does not deactivate a requirement. Changes to verification policy, check budgets or agent configuration meet the security trigger, so they are never trivial and always get a standard and a security reviewer, plus explicit owner review.

## Select independent reviews (slice tier)

| Profile | Slice plan | Slice review |
|---|---|---|
| [Correctness](references/correctness.md) | Contract or nontrivial design changes; a typo needs no design review | Every affected component, scaled to the change |
| [Security](references/security.md) | A separate security-profile reviewer when the plan meets the [security trigger](../../../AGENTS.md#development-verification) | The security layer reviewer, whenever any change in the slice met the [security trigger](../../../AGENTS.md#development-verification); every component records applicability |
| [Browser](references/browser.md) | New or changed frontend interactions, including specification-only changes | Every frontend or backend change once a runnable frontend exists: common smoke plus affected journeys |
| [Performance](references/performance.md) | Performance-sensitive architecture, resource ownership or contract changes | Every frontend or backend change and other resource-lifecycle changes: relevant measurements and leak checks, by the backend and frontend layer reviewers |

Selection is additive: an authorization change that alters frontend behavior also requires browser and separate performance checks. For an unimplemented capability, record its checks as `pending implementation` with the roadmap slice that activates them; reserve `not applicable` for checks unrelated to the change. Existing executable requirements remain mandatory; activation is incremental only for capabilities not yet implemented.

Apply [the observability specification](../../../knowledge/specs/observability.md) to every changed executable component. Correctness checks its logging evidence. Changes to logging collection, redaction, correlation or sinks additionally require security and performance review.

## Dispatch and collect evidence

At the slice tier, use one fresh subagent per changed layer: the backend (correctness and performance), the frontend (correctness, browser and performance), security across the slice, and development tooling with agent configuration. Each applies every profile selected for its components and may subdivide its scope with fresh contexts. The security reviewer runs whenever any change in the slice met the trigger, subdivides by trust-boundary family when the slice touches more than one, and reports each affected threat as examined, not affected or unverified. Give each reviewer the entries of its layer from the slice's known-limitations file as items to re-verify, not as verdicts, including each `after-fix` row, which the reviewer re-verifies against its recorded evidence; the slice review resolves only when each entry is fixed, accepted by the owner or carried into a named later slice. Run the layer reviewers' performance measurements one at a time. In Claude Code, launch a non-fork `general-purpose` subagent through the Agent tool, never a conversation fork; send independent assignments in one message so they run concurrently. A concrete failure to dispatch leaves that assignment blocked; self-review is not independent review.

Give each subagent its layer, components and profiles, the repository path and the trusted instruction and profile paths, the exact base and working-tree scope, the causal edges and boundary ownership, the acceptance criteria, contract pointers and the evidence to inspect. Require full reads of `AGENTS.md` and the assigned profile, then the affected specifications and decision records. Give access to the complete diff for boundary checks without passing the implementation conversation, earlier review conclusions or a desired verdict, except the known-limitations entries named above, given as items to re-verify.

Reviewers may delegate narrower parts of their assigned scope in fresh contexts with the same policy, scope and read-only restriction, and return discovered scope expansion to the coordinator. No reviewer edits source, commits or publishes. Local fixtures, containers and measurements are allowed when the assignment calls for them. Isolate databases, ports, browser sessions and output paths between concurrent reviewers; run performance measurements serially on an otherwise idle machine.

Each review returns its layer or component and profiles, the scope and working-tree state reviewed, files, contracts and boundaries examined, descendant assignments and results when used, findings with evidence and severity, missing coverage and a verdict. Each executable check records the exact command, exit result, tested working-tree state and environment. Use `passed`, `failed`, `blocked`, `pending implementation`, `deferred to the merge gate`, `unverified` or `not applicable`, and explain every non-pass. `deferred to the merge gate` marks a check of the full run that the implementing agent did not run because its diff does not touch that check's row; it is never reported as `passed`. A design review pass does not imply runtime checks passed.

The coordinator resolves findings, reruns affected checks and, as the tier requires, affected reviews after changes, and maps the evidence to the acceptance criteria in the readiness report to the owner. At every tier, the after-fix rule in the tier table decides which reviews run again. A report or checkbox does not replace check output.

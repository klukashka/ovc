# AGENTS.md

Rules for every coding agent and human contributor in this repository. They take precedence over the defaults and habits of any model or tool, and over instruction files in parent directories or user-level configuration (for example a workspace `CLAUDE.md` above this repository that asks for docstrings, mocks or mypy). If a rule blocks the task, stop and say so instead of working around it.

## Project

OVC (Online Virtual Classroom) is a workspace for private tutors teaching adult students: video lessons through BigBlueButton with a whiteboard and recordings, direct and group chats, a schedule with weekly series, and homework built from self-checking tests and tasks the tutor checks. Each tutor runs their own practice of students and groups; one student account can study with several tutors. The [product overview](docs/product.md) explains the intent.

Documentation has two layers. `docs/` is written for people: the [technical introduction](docs/technical-introduction.md), [functional](docs/requirements/functional.md) and [non-functional](docs/requirements/non-functional.md) requirements, the [threat model](docs/threat-model.md), the [roadmap](docs/roadmap.md), the [development guide](docs/development.md), the decision records in [`docs/decisions/`](docs/decisions/README.md) and the deferred changes in [`docs/proposals/`](docs/proposals/README.md). `knowledge/` is the reference layer loaded section by section: the normative specifications in `knowledge/specs/`, the module map, package layers, stack table, glossary and open questions in `knowledge/architecture/detailed.md`, and review records, analyses and research. [`knowledge/README.md`](knowledge/README.md) says which file to load for which task. Read the specification of a component and the decision records it cites before implementing it; when a specification and a decision record disagree, the decision record wins.

## Change workflow

The repository is local only for now: there is no remote, no CI service and no issue tracker. The repository holds everything a future session needs; nothing durable lives only in a conversation.

- **Plan before code.** For anything beyond a trivial fix (a typo, a broken link, an obvious one-line bug), present an implementation plan to the project owner first: the problem, the desired outcome, the affected components and specifications, checkable acceptance criteria, the files to change, the order of work, the risks and the checks that prove each criterion. Do not edit files until the owner approves it. When the implementation diverges from the approved plan, say so and get the change approved before continuing.
- **Acceptance criteria are checkable without asking a person**: a named test passes, a command prints a given result, an endpoint returns a given field.
- **Decisions never live only in a conversation.** Once decided, a decision lands in the repository as a decision record, a requirement or a specification change. Large or uncertain changes start as a proposal in `docs/proposals/`.
- **One change per branch, one commit per branch.** Work on a branch named `feat/…`, `fix/…`, `chore/…` or `docs/…`, holding one coherent change as one commit whose subject names the change on its own. Once its change checks pass, its readiness reviews are resolved and the merge gate passes, the agent merges it with `git merge --ff-only` and deletes it with `git branch -d`. If `main` has moved, the agent runs `git merge --squash`, gates the staged tree and commits; deleting that branch then needs `git branch -D`, which asks the owner.
- **Agents commit and merge their own work without asking** ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md)), once its change checks pass, its readiness reviews are resolved and the merge gate passes: stage only the files the change touches, review the staged diff, and write a message whose subject names the change on its own. Commit messages carry no AI attribution or co-author trailers. Agents create and switch branches only with `git switch` and `git switch -c`; `git checkout` always asks the owner, because its path forms overwrite files. Agents never push, rebase, reset, clean, force-delete branches, discard work with destructive checkouts, restores or stash drops, or rewrite history (amend, filter-branch, update-ref, reflog expiry) without the owner; `.claude/settings.json` requires confirmation for each of these.
- **Questions to the owner** are asked as multiple-choice questions with a recommended option, never left open in prose.
- On macOS the filesystem ignores case, so after a case-only rename reset the index (`git rm -r -f --cached . && git add -A`) and confirm the new spelling with `git ls-files` before committing.
- When a hosted remote and CI are adopted, add the issue form, pull request template, labels and CI workflow in one change and amend this section.

## Development verification

- **Pick a tier** ([ADR-0011](docs/decisions/0011-tiered-verification.md)). At task entry, before the implementation plan, the coordinating agent reads [ovc-verify](.claude/skills/ovc-verify/SKILL.md), picks the verification tier, decides whether the change meets the security trigger, and states both with reasons in the plan (for a trivial fix, in the readiness report). When in doubt, pick the higher tier and assume the trigger is met.
  - **Trivial** (a typo, a broken link, an obvious one-line bug) runs the checks. A change that meets the security trigger is never trivial.
  - **Standard** (every other change inside a slice) runs the checks and one fresh independent reviewer over the complete diff with the standard checklist, plus a separate fresh reviewer with the full security profile when the change meets the security trigger.
  - **Slice** (every planned change of a roadmap slice has merged, before the slice closes) runs the slice review below over the cumulative diff since the previous slice closed.
- **Change checks and the merge gate** ([ADR-0018](docs/decisions/0018-targeted-checks-and-merge-gate.md)). "The checks" of every tier and of the after-fix rule are the change checks: the checks of what the diff touches, from the table in [the development guide](docs/development.md#change-checks-and-the-merge-gate); a path the table does not list, or any doubt, means the full local check run. Before every merge into `main`, the coordinating agent runs the merge gate, `main`'s copy of `tools/merge-gate.sh` from a scratch folder with `gate`, on the exact tree `main` will hold, one change per gate, merges only when it passes, then runs its `finish`, which must confirm that `main` advanced only by this merge and that `main^{tree}` equals the tested tree. The gate runs the full local check run, or, for a change of Markdown under `docs/` and `knowledge/` that no test or script reads, the documentation checks and Gitleaks. A failed gate sends the change back to its branch under the after-fix rule; one rerun is allowed only for a named infrastructure error with no failed assertion, quoted in the merge report. Every rerun beyond the one infrastructure rerun, which needs the owner's approval, is recorded before that rerun, with its date, tested tree, failing test and the owner's decision, in the slice's known-limitations file as part of the change's own commit (so the rerun gates the tree that holds the record), and the merge report repeats it (decided by the owner on 2026-11-11, pending owner review). After each merge the coordinator gives the owner the merge report: the change, the base commit, the tested tree, `main^{tree}` and every command with its exit result.
- **Security trigger.** A change meets it, even when it changes only specifications, if it touches a trust boundary or maps to a threat in [the threat model](docs/threat-model.md). Examples, not a complete list:
  - authentication, sessions, and tokens in links (invitation, confirmation, reset, unsubscribe);
  - authorization and relationship scope on routes and WebSocket frames, and answer-key and score visibility;
  - uploads, downloads, rendering of untrusted content, the content security policy and framing;
  - secrets, the meeting provider and its callbacks, email content and the SMTP channel, outbound network calls;
  - logging, redaction and correlation; purge and deletion; rate limits; redirects;
  - `ovc-admin`, the end-to-end test control surface, dependencies;
  - agent configuration and verification policy (`AGENTS.md`, `.claude/`), and the threat model itself.
- **After fixes**, rerun the checks. At most one fresh reviewer, scoped to the fixes, runs, and only when a blocker or major finding was fixed or a contract changed; it applies the standard checklist to the fixes, and the full security profile as well when such a finding concerned security. If the recheck before readiness finds that the final diff meets the security trigger and no security-profile reviewer has reviewed the change, one runs over the complete diff even when the scoped re-review has already run; when both would run, it replaces the scoped re-review and also applies the standard checklist to the fixes. Minor findings of the re-review are fixed when cheap or recorded as known limitations in the slice's known-limitations file (`knowledge/reviews/slice-<n>-known-limitations.md`, with the finding, its severity, the change and why it was accepted), and start no further review round; a blocker or major finding of the re-review is fixed, the checks rerun, and the change does not merge until the owner answers a multiple-choice question on whether another reviewer runs (recommending a security-profile reviewer when the finding concerned security). The readiness report says, for each fixed security finding, whether its fix touches a trust boundary. Other fixes to minor findings need only the checks. Severity is the reviewer's; the coordinator never downgrades it. Before readiness, recheck the tier and the security trigger against the final diff.
- **Plans.** A slice plan gets one standard reviewer before work starts. A slice plan or task plan that meets the security trigger also gets a security-profile reviewer before approval. Other task plans need the owner's approval, not a planning review.
- **Slice review.** Assign one fresh reviewer per layer the slice changed: the backend (correctness and performance), the frontend (correctness, browser and performance), security across the whole slice, and development tooling with agent configuration; each reviewer applies every relevant profile to the components of its layer, follows their contract, data-flow and resource-lifecycle consequences, and may subdivide its scope with fresh contexts; the security reviewer runs whenever any change in the slice met the security trigger, subdivides into fresh contexts when the slice touches more than one family of trust boundaries (for example authentication, uploads, agent configuration), and reports each affected threat as examined, not affected or unverified; each reviewer also re-verifies the entries of its layer in the slice's known-limitations file, given to it as items to check rather than as verdicts, and the slice review is resolved only when each entry is fixed, accepted by the owner or carried into a named later slice; performance measurements run one reviewer at a time on an otherwise idle machine. Record which components each reviewer covers and why, and who reviews each integration boundary; a layer with no directly or transitively affected component gets no reviewer. Reviewers do not restart the whole review or grant themselves implementation authority. The coordinator collects every result and fixes findings in follow-up changes under the after-fix rule. Each follow-up change is a standard-tier change with its own reviews, names the slice review finding it resolves, and its reviewer confirms that finding is closed. Once OVC is deployed, a slice is not deployed before its slice review is resolved.
- **Report** review scope, reviewed working-tree state, command results and evidence to the owner at every tier. Distinguish passed, failed, blocked, pending implementation, deferred to the merge gate, unverified and not applicable, with a reason for every non-pass; a check the implementing agent did not run is deferred to the merge gate, never passed. Missing tools or unimplemented components are never passing checks. Self-review is never an independent review.

## Code

- **No comments and no docstrings** in hand-written source code: Go, TypeScript, SQL (queries and migrations), shell, configuration scripts. Code documents itself through names, types, small functions and explicit data structures. When a comment feels necessary, rename, extract a function, or introduce a type or an enum instead.
- Tool directives count as comments and are forbidden too: no `//nolint`, `//lint:ignore`, `// eslint-disable`, `// @ts-ignore`, `// @ts-expect-error`, `-- noqa`. Fix the code, or disable the rule in the tool's configuration, for the whole project or narrowly as the next rule allows. The only allowed comment-like lines are a shebang in an executable script and the Go compiler directives `//go:embed` and `//go:build`, used only where the language offers no other way.
- Never split, concatenate or rename a literal or an identifier only so that a linter or a scanner stops seeing it, without changing what the code does. Fix the finding, or exclude that rule for named files in the tool's configuration with the reason recorded in the [development guide](docs/development.md).
- Generated files (lockfiles, `go.sum`, sqlc output, a generated OpenAPI TypeScript client) are exempt because nobody edits them by hand. Configure generators and templates (for example the goose migration template) so they do not emit comments into files that are then edited by hand; goose's `-- +goose Up` and `-- +goose Down` markers are part of the migration format and allowed in `backend/migrations/*.sql`, as are `-- +goose StatementBegin` and `-- +goose StatementEnd`, paired and only around one `CREATE FUNCTION` or `CREATE OR REPLACE FUNCTION` statement whose dollar-quoted body holds at least one semicolon at which goose would otherwise split it ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md), item 8); sqlc's `-- name: <Name> :one|:many|:exec|:execrows` line is part of the query format and allowed above each query in `backend/queries/*.sql` (not in subdirectories); each stands alone on its line, with nothing before or after it.
- **Types are precise and safe.** No `any` or `interface{}` in hand-written Go except as a generic constraint, and no `unsafe` or `reflect` in hand-written Go and no `Reflect` API in hand-written TypeScript and JavaScript, tests and end-to-end page scripts included: parse untyped data at the boundary into structs or precise types, and keep JSON payloads as typed structs. Domain values (identifiers, statuses, roles) get named types instead of bare strings and integers.
- **Static checks are strict and mandatory**: `gofmt`, `go vet`, golangci-lint with the project configuration (including at least errcheck, gosec, staticcheck, bodyclose, noctx, errorlint and depguard or forbidigo for the forbidden packages and for environment reads outside `internal/core`; none of them may be disabled project-wide) and `govulncheck` over all Go; TypeScript with `strict: true`, ESLint and Prettier over `frontend/`. Code that does not pass them is not finished.
- **Fail fast.** Never discard an error (`_ =` on an error, an unchecked return): handle it meaningfully or return it wrapped with `%w`; log the error kind and correlation fields, never the raw error text ([observability](knowledge/specs/observability.md#safe-content)). No logging-and-continuing, no placeholder results, no silent fallback values that hide a failure. A bare `return` after an error is never handling it: every error branch returns or wraps the error, or panics for an impossible state; only where an error cannot be returned, such as a failed write of a response, is its kind logged instead. `panic` is reserved for impossible states and invalid configuration at start-up; a recovery middleware turns an unexpected panic in a request into a structured internal error, and every other goroutine starts through one recovering helper. Every error that leaves the HTTP API or the WebSocket gateway is a structured error as specified in [the API specification](knowledge/specs/api.md#conventions).
- **The HTTP API is the single implementation.** The web frontend is a thin client over the typed API client and contains no business rules or authorization decisions of its own; it may hide what the API would refuse, never grant what the API would refuse.
- **Focus is never lost.** A route's loading, error and refetching states render inside that route's `Page`, never in place of it, so the page and its heading survive a change of its own data state and focus never stays on a removed element; a route change remounts the page, and an account change clears the loaded data and passes through the signed-out state ([navigation](knowledge/design/web/navigation.md)). Every state change and action of a page either moves focus as the shared behavior or its own specification defines, or keeps it where it was; the focus rules are in [shared behavior](knowledge/design/web/pages.md#shared-behavior) and [navigation](knowledge/design/web/navigation.md). Each focus move a specification defines has a test that asserts the focused element: `toBeFocused` in Playwright, `document.activeElement` in component tests.
- **Layers are explicit.** Backend code is layered as routers and WebSocket handlers → services → repositories, with external systems behind adapters, as tabled in [package layers](knowledge/architecture/detailed.md#package-layers). Only repositories touch business data in the database; the infrastructure adapters listed under package layers keep only their own state there. Only adapters touch storage, the meeting provider and outbound notifications. A new package enters the table in the change that creates it, and an architecture test enforces the table from the first backend scaffold onward.
- **Configuration** is read once from the environment into one typed settings object; no scattered environment reads. Secret settings use a dedicated type whose `String`, `Format`, `GoString` and `LogValue` methods redact the value, so no print or log of the settings can expose it. Every variable is documented in `.env.example`. Constants such as roles, statuses and WebSocket frame types are enums in one place, not inline literals.
- **Dependencies are deliberate.** Add one only when the standard library or an existing dependency cannot reasonably do the job, and record it with its reason in the [stack table](knowledge/architecture/detailed.md#stack-per-component); a dependency that changes a decided row of [ADR-0002](docs/decisions/0002-implementation-stack.md) needs a new decision record. Go dependencies are managed only with `go get` and `go mod tidy`, and frontend dependencies only with `pnpm`; `go.mod`, `go.sum` and `pnpm-lock.yaml` are committed and change only through those tools.

## Security

- **Authorization is enforced server-side on every route and every WebSocket frame**, by role (`tutor` or `student`) and by relationship scope ([ADR-0005](docs/decisions/0005-tutor-centric-domain.md)):
  - a tutor reaches a student's data only through their own relationship with that student, never through another tutor's;
  - a student reaches only their own work and the resources of tutors they have a relationship with;
  - students never reach each other's work.

  Resolve every client-supplied identifier within the caller's scope, and return `not_found` outside it.
- **Answer keys stay on the server** until the answer visibility policy allows them, and **points and scores never reach students** at all ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md)). Student-facing schemas contain no key, points or score fields ([answer visibility](knowledge/specs/homework.md#answer-visibility)).
- **Credentials in URLs** are allowed only where the specifications define them, as approved in [ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md): invitation, email confirmation, password reset and unsubscribe links; per-request conferencing join links; 5-minute signed storage URLs for authorized downloads, recordings and the lesson presentation fetched by the conferencing server; and OVC-signed download addresses for authorized attachment downloads, valid for at most 10 minutes and bound to the attachment, its referencing item (its message, or from slice 8 a material, template or lesson, together with the reference kind) and the disposition, and refused once that reference is removed (approved 2026-10-29; the referencing item approved 2026-11-10; pending owner review). Each is bounded in lifetime and scope, never signs anyone in to OVC, and is never logged; pages that carry one send `Referrer-Policy: no-referrer`. Access and refresh tokens never appear in URLs. Every other credential travels in headers, bodies or `HttpOnly` cookies. Provider callback routing keys are not credentials and never authenticate anything on their own.
- **Uploads** are bounded in size, checked against a content-type allowlist and stored under random keys. A download is authorized against the resource that owns the attachment, and no filesystem path is ever built from client input.
- **Content that no request may receive** (for example build manifests, source maps of private code, reports, test output, keys, environment files and server or build configuration) stays outside every directory from which built output is served: the preview server, a reverse proxy and any static serving by the backend. Never protect it there by filtering request paths, which percent-encoding, case, duplicate slashes, symbolic links and URL parsing bypass; no symbolic link in it reaches outside it, and a test proves the served directory does not contain such content. The development server (`pnpm dev`) serves the frontend sources by design and listens only on loopback; its own file denial rules keep keys and environment files from it, and everything else under `frontend/` is reachable there. Authorized downloads and signed storage URLs are protected by authorization and signatures, not by this rule.
- **Secrets**, including environment files other than `.env.example`, private keys, signing and encryption keys, the conferencing shared secret, storage and SMTP credentials and any other credential, are never committed, logged, sent to the browser or placed in URLs or provider `meta_*` values. Environment files (`.env`, `.env.local` and the other ignored variants) are ignored by Git; agents never open, print, copy or edit them with file tools or shell commands. Until OVC has hosting, the only sanctioned use ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md), item 7) is `tools/dev-env.sh <command>`, which loads the owner's root `.env` and `backend/.env` into that one command's environment without printing them; `backend/.env.local` and other environment files are never loaded and stay owner-only. The wrapper and the secret guard hook refuse the common ways of printing the loaded settings, which guards against accidental disclosure only ([T-19](docs/threat-model.md)).
- **Operator actions** exist only in the local `ovc-admin` command; there is no administrative HTTP surface.
- **The end-to-end test control surface** (`/__test__/` routes, the shared test clock, the database mail sink viewer) exists only when `OVC_TEST_CONTROL=1`. The processes refuse that setting unless the meeting provider is `fake`, mail is the database sink, and the database is a test or development database. A test proves the routes are absent without it.
- **Personal data is minimal and stays in Russia.** Collect only the personal data a feature needs, and keep it out of logs, URLs and third-party requests. As participant data the conferencing provider receives only a display name, an opaque participant identifier and a role; it also receives the lesson presentation, a PDF the tutor chose as lesson material, passed unfiltered, which may contain personal data such as student names or document metadata like its author: OVC sends a signed storage URL that only the self-hosted conferencing server in Russia fetches, and its retention there is recorded in T-11 of [the threat model](docs/threat-model.md) (amended 2026-11-11, pending owner review). Never add a service outside Russia that receives user data ([ADR-0008](docs/decisions/0008-hosting-and-data-residency.md)).
- Every change that touches a trust boundary maps itself to the [threat model](docs/threat-model.md) and updates it in the same change.

## Observability

- **Every executable component ships with structured, leveled diagnostics from its first implementation.** Follow [the observability specification](knowledge/specs/observability.md) for event ownership, correlation, levels, safe fields and failure behavior. Process entry points configure logging; libraries use bound loggers.
- Never log secrets, tokens, passwords, message bodies, submission contents or uploaded file contents. DEBUG does not relax this.
- Component behavior changes include their observability impact and evidence in the plan and in the readiness report.

## Documentation

- Everything committed to the repository is in English.
- Write every specification, design document, decision record and commit message for a reader who never saw the session that produced it. Never reference session-local context: subagent names, review rounds, ad-hoc labels such as "item K2" or "question 5", "as discussed above", "the user asked". Give hypotheses, decisions, files and folders descriptive names.
- Identifiers defined inside the repository and resolving there (for example `FR-3.2`, `NFR-2.1`, `T-4`, `ADR-0003`) are allowed; labels that exist only in a conversation are not.
- **Documents and code change together.** A change that alters behavior described in a specification, decision record or requirement updates that document in the same change. When code and its specification disagree and the task does not say which one is right, stop and ask instead of silently following either.
- **`docs/` is human-validated.** Every statement in `docs/` is reviewed and accepted by the project owner, and each file records its review status. Agents change `docs/` only as an explicit part of an approved plan, mark new or changed wording as pending owner review, and never place unreviewed findings there. Research, analyses, review records and drafts produced by agents go to `knowledge/`, which may hold agent-only material and is cited from `docs/` as evidence, never as a decision.
- **Volatile external facts** (versions, prices, release dates, provider limits) live in `knowledge/research/` with the date they were checked; `docs/` states them qualitatively and links there.
- **No organisation-specific names** in examples: use neutral terms ("a school", "a language tutor", "a self-hosted conferencing server").

## Testing

- **Use Arrange–Act–Assert.** Write each test in three distinct, sequential phases separated by blank lines, made clear through descriptive names or extracted helpers, never comments. The one exception is a step test of a [pilot scenario](knowledge/design/web/pilot-scenarios.md) suite, whose title starts with `pilot-<n> › step <k>` or `pilot-<n> › steps <k>–<m>` and names the scenario steps it proves (a `pilot-<n> › seed` test is not one), whose intermediate states are the step's acceptance criteria: it may act and assert in turns; every other test keeps three phases.
- **No mocks.** Forbidden: gomock, mockery, `testify/mock`, runtime function patching (gomonkey and similar), swapping package-level variables or environment variables in tests, stubbing HTTP clients at the transport level (custom `RoundTripper`s, httpmock), `vi.mock`, mocked `fetch`, and any other technique that replaces behavior behind the code's back. One exception: in a Playwright end-to-end test, a `page.route` or `context.route` handler may only hold a request and then pass it on unchanged with `route.continue()` or `route.fallback()` called without arguments, to observe an in-flight state, and may call `route.abort()` without arguments only in the language-chunk load failure test, `frontend/e2e/language.spec.ts`; `route.fulfill()`, `route.fetch()`, a changed URL, method, headers or body, `routeFromHAR`, `routeWebSocket` and any other interception stay forbidden, and the frontend lint configuration enforces the listed forms ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md), item 9). The separate local-wrapper self-test `tools/check-dev-env.sh` may remove inherited `OVC_*` variables from its own process before creating synthetic fixture files, without reading or printing their values; it then runs the real wrapper and every assertion, including explicit caller-variable precedence ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md), item 10, approved 2026-10-31). This permits no environment replacement in application tests.
- **Fakes are the only test doubles.** A fake is a real implementation of an adapter interface or of an interface a service defines for a core component (the password hasher) (a fake meeting provider, which may run as an in-process `httptest.Server`; a mail sink; a fake clock; a fake password hasher, `internal/testhasher`, that counts, fails or pauses verifications; an in-memory storage for unit and contract tests only; there is no in-process broadcaster, so tests use the real PostgreSQL listener), selected through configuration or constructor injection and checked by the same contract tests as the production implementation. If code cannot be tested without patching, change its design so the dependency is injected. One exception: to prove that a worker job isolates the failure of one item, a test may create, through its own connection to the test database created for it, database objects (for example a trigger) whose only effect is to raise a real database error for that item, never through application code, migrations or the end-to-end test control surface; no other database object created by a test changes how the database behaves, and the only other changes to the database connection in a test are the listener forwarder under integration tests below ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md), item 8) and the cancellation that follows. To make one database write fail at a chosen point, a test may cancel with `pg_cancel_backend`, through its own connection to the test database created for it, only statements of that database that wait directly on a row lock the test itself holds, found through `pg_locks`, never through application code, migrations or the end-to-end test control surface, so that the write fails with PostgreSQL's real cancellation error ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md), item 12, decided by the owner on 2026-11-10).
- **Unit tests are rare.** Write them only for intricate logic where a bug hides easily: scoring arithmetic, short-answer normalisation, recurrence and timezone conversion, permission rules, state machines (submission, lesson and relationship status). Do not unit-test glue code, data mapping, trivial accessors or framework behavior.
- **Integration tests are the bulk.** Exercise real components together:
  - the real API server over HTTP and WebSocket;
  - the real worker through `Tick(now)`;
  - the real PostgreSQL database and a local S3-compatible server in containers.

  Use fakes only where BigBlueButton, the SMTP provider, the clock or the password hasher would otherwise be involved; a test that needs to pause a storage write puts an in-process `httptest.Server` in front of the local S3-compatible server that forwards every request and response unchanged and only holds a request, instead of a storage fake. Likewise, and only in tests of the database listener's liveness (its heartbeat and the detection of a silent connection), a test may put an in-process TCP forwarder in front of the test PostgreSQL. `internal/testdb/forwarder` builds it from the database endpoint the integration-test fixture has already checked; it listens only on `127.0.0.1` on an ephemeral port, dials only that checked host and port, and relays every byte unchanged in both directions; when one side ends its stream (end of file or a read error), it passes that end on to the other side by half-closing the same direction and does nothing else to that connection, which is part of a faithful relay (a reset reaches the other side as an ordinary end of stream); its only other behavior is to stop relaying in both directions at once and permanently, after which it passes nothing on, not even an end of stream, and may close both connections; it never resumes, delays or drops individual bytes. Nothing else alters the database connection's behavior in a test, apart from the cancellation of a statement waiting on a row lock the test holds, described under fakes above ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md), items 8 and 12).
Only in chat download lifecycle integration tests, a transparent HTTP forwarder may hold the real local S3 response body at an explicit barrier, including its stream end where the transport permits it. It uses the fixture-validated local endpoint, listens on loopback at an ephemeral port, and preserves status, headers and bytes. Cancellation closes upstream and ends forwarding; cleanup releases every resource. It never fabricates responses, changes data or targets external or owner services. This narrow exception was approved on 2026-11-01 ([ADR-0009](docs/decisions/0009-owner-approved-exceptions-and-visibility.md), item 11); it does not permit other response interception.

- **Tests are deterministic.** No `sleep` for synchronisation: wait on an explicit condition with a deadline. No real network beyond local containers and in-process servers. Time and randomness come from injected sources, and tests pass fake ones. A flaky test is a bug: fix its cause, never hide it with retries or longer timeouts.
- **End-to-end tests are targeted.** The four [pilot scenarios](knowledge/design/web/pilot-scenarios.md) run as Playwright suites. They drive the production frontend build against the real backend, worker and database, with the fake meeting provider, the database mail sink and the shared fake clock. They cover the main journeys of both roles and the key refusals.
- **The full local check run finishes in under 10 minutes.** Write tests so they can run in parallel. When a change threatens the budget, make tests faster or consolidate them; never drop coverage silently.

## Platforms

- Supported development platforms: **Linux and macOS**. No Windows code paths, shims or path handling. POSIX assumptions are fine.
- Supported browsers for the frontend: current Chromium, Firefox and Safari, on desktop and on phones (Safari on iOS, Chrome on Android). The conferencing client inherits BigBlueButton's own browser support, and "open in a new tab" is always available.
- BigBlueButton runs only on a dedicated Ubuntu server; local development and automated tests use the fake meeting provider ([development guide](docs/development.md#local-services)).

## Definition of done

- Before reporting a change as ready, run its change checks and see them pass. A change is done when it has merged through the merge gate, which runs every check in [the development guide](docs/development.md) that exists for the current scaffold (format, lint, type check, tests, documentation checks), or, for a Markdown-only change, the documentation checks and Gitleaks, on the tree `main` holds after the merge. Report failures as they are. The manual live conferencing checks are the only exception: report them as passed or `unverified`.
- Never make checks green by weakening them: no `skip` or `xfail` on failing tests, no deleted or loosened assertions, no relaxed linter, type-checker or test settings, no raised timeouts or budgets, unless changing that check is the approved task itself.
- When the same review finding recurs, add the rule that prevents it to this file.

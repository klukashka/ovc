## Tool setup

Use Linux or macOS with Git, Bash, Docker with Compose v2 (Docker Desktop, Colima or OrbStack all work), Node and pnpm (see below), a system `python3` (3.9 or newer, for the agent hooks in `.claude/hooks/`), a C compiler (for `go test -race`, which needs cgo) and the pinned toolchain:

- Go: the version in [`tools/go.mod`](../tools/go.mod) (`go` and `toolchain` lines, matched by `backend/go.mod`), installed from [the official downloads](https://go.dev/dl/) or a package manager; the `toolchain` line lets newer Go installations fetch the pinned release.
- Repository tools (Gitleaks, OSV-Scanner, govulncheck, golangci-lint, and sqlc, which generates `backend/internal/dbgen` from `backend/queries/` and `backend/migrations/`): pinned as Go `tool` dependencies in `tools/go.mod`, with checksums in `tools/go.sum`, and built once per tools upgrade from those pinned versions into the ignored `bin/` directory with the command below, so no check compiles them again; no separate installation is needed (pending owner review).
- Node and pnpm: Node from `frontend/.node-version` and pnpm from the `packageManager` field of `frontend/package.json` ([versions](../knowledge/research/frontend-toolchain-2026-10-21.md)). Playwright's browsers are installed once with `pnpm --dir frontend exec playwright install chromium firefox webkit`.
- lychee for link checks: installed with its [official instructions](https://lychee.cli.rs/installation/).

Exact versions are recorded with their check dates in `knowledge/research/` when the scaffold pins them.

The full local check run that NFR-6.2 bounds to 10 minutes is every command of the documentation checks, the security scanning (Gitleaks over history and over staged changes, and the four OSV-Scanner lockfile scans of `tools/go.mod`, `backend/go.mod`, `frontend/pnpm-lock.yaml` and `tools/docs/pnpm-lock.yaml`), the backend checks, the frontend checks with the end-to-end suites, the secret guard hook and local settings wrapper checks, and `tools/check-tool-binaries.sh`; a check-budget record in `knowledge/analysis/` times each of them (pending owner review). It also runs `tools/check-merge-gate.sh`, the merge gate's own test. The full run executes once per merge, in the [merge gate](#change-checks-and-the-merge-gate); an implementing agent runs the change checks of its diff (amended 2026-10-27, pending owner review). The gate runs the full run in five slots: `tools/check-tool-binaries.sh` alone first; then three concurrent lanes, lane A with `go test -race`, lane B with the two Gitleaks scans, the backend checks other than `go test` and `tools/check-merge-gate.sh`, and lane C with the documentation checks, the four OSV-Scanner scans, the frontend checks other than the end-to-end suites, the secret guard hook check and `tools/check-dev-env.sh` (amended 2026-10-27, and 2026-10-28, when the OSV-Scanner scans moved from lane B to lane C because the longer `tools/check-merge-gate.sh` made lane B the longest of the lanes B and C, pending owner review); and `pnpm e2e` alone last. From 2026-10-27 the budget figures of the full run are the gate's wall time, measured cold on an idle machine; every check-budget record also reports the summed command seconds, comparable with earlier records, the wall time of each lane, the machine's core count and what the cold measurement emptied (amended 2026-10-27, pending owner review).

## Security scanning

Run from the repository root; each must pass in the [merge gate](#change-checks-and-the-merge-gate) before a change merges, and before readiness a change runs the scans of the change-check rows its diff touches: Gitleaks over staged changes always, Gitleaks over history for agent configuration, the wrapper and the Gitleaks configuration, and OSV-Scanner over each module or lockfile it changes (amended 2026-10-27, pending owner review). The scanners run from `bin/`, built as [the backend checks](#backend-checks) describe; `tools/check-tool-binaries.sh` must print `bin/ matches tools/go.mod` first (pending owner review).

- **Secrets in history:** `bin/gitleaks git --redact --no-banner --config .gitleaks.toml .` reports no leaks.
- **Secrets about to be committed:** `bin/gitleaks git --staged --redact --no-banner --config .gitleaks.toml .` reports no leaks. Gitleaks never scans the working directory, so ignored environment files are never read.
- **Gitleaks configuration:** `.gitleaks.toml` at the repository root extends the default rules and adds one allowlist: the `generic-api-key` rule does not report a match in `backend/cmd/internal/startup/settings_process_test.go` whose matched value is exactly `OVC_UNSUBSCRIBE_SIGNING_SECRET=`, because its start-up refusal cases put that variable name beside values each test run generates, which the rule mistakes for a hard-coded key; the path and the value must both match (`condition = "AND"`), so any other generic-shaped value in that file is still reported, every other rule still scans it, and the configuration adds no exclusion beyond this one and the default rules' own allowlists (narrowed from the whole file on 2026-10-26, pending owner review). The commands pass `--config` so an ambient `GITLEAKS_CONFIG` cannot replace it (pending owner review).
- **Known vulnerabilities in dependencies:** OSV-Scanner over each module and lockfile with an explicit path, starting with `bin/osv-scanner scan source --no-call-analysis=go --lockfile=tools/go.mod` (the tools module has no packages of its own to call-analyse) and `bin/osv-scanner scan source --no-call-analysis=go --lockfile=backend/go.mod` (the backend gets call analysis from `govulncheck` in the backend checks); `bin/osv-scanner scan source --lockfile=frontend/pnpm-lock.yaml`, and `bin/osv-scanner scan source --lockfile=tools/docs/pnpm-lock.yaml`. A pass is exit code 0. Accepted findings are listed in the `osv-scanner.toml` next to the scanned file, each with a reason and an `ignoreUntil` date, and explained in a dated triage table ([Go tools](../knowledge/research/local-s3-2026-10-21.md#repository-tool-scan-triage), [documentation tools](../knowledge/research/toolchain-2026-10-21.md#documentation-tools), [frontend](../knowledge/research/frontend-toolchain-2026-10-21.md#accepted-findings) (pending owner review), [backend](../knowledge/research/backend-libraries-2026-10-21.md#notes)).

## Backend checks

Build the pinned tools from the repository root after cloning and after any change to `tools/go.mod` or `tools/go.sum`, including one brought by a pull, a merge or a branch switch; every git worktree has its own ignored `bin/`. `tools/check-tool-binaries.sh` compares the build information embedded in each binary with the tools module: the Go toolchain, the tool's own module and every dependency must have the versions of the tools build list and the checksums of `tools/go.sum`, and no module may be replaced; a missing binary or any difference fails it, because Gitleaks compiles its rules into the binary and cannot report its own version. It detects a stale binary, not a forged one; the build command pins `GOTOOLCHAIN` to the `toolchain` line, because a newer local Go would otherwise build the tools and the check would refuse them (pending owner review):

```bash
GOTOOLCHAIN="$(awk '$1 == "toolchain" { print $2 }' tools/go.mod)" go -C tools build -o ../bin/ github.com/golangci/golangci-lint/v2/cmd/golangci-lint golang.org/x/vuln/cmd/govulncheck github.com/zricethezav/gitleaks/v8 github.com/google/osv-scanner/v2/cmd/osv-scanner github.com/sqlc-dev/sqlc/cmd/sqlc
```

Then, from `backend/`, with Docker Compose running and `OVC_TEST_DATABASE_ADMIN_URL` set to a PostgreSQL URL that may create databases (for example the `ovc` user on `ovc_dev`); the test fixture refuses a URL whose hosts are not loopback addresses or Unix sockets:

```bash
go mod tidy -diff
unformatted="$(gofmt -l .)" && test -z "$unformatted"
go vet ./...
../bin/golangci-lint run ./...
../bin/govulncheck ./...
../tools/dev-env.sh go test -race -count=1 ./...
../bin/sqlc -f sqlc.yaml diff
```

After changing a query or a migration, regenerate the query package from `backend/` with `../bin/sqlc -f sqlc.yaml generate` and commit the result; `sqlc diff` fails while `internal/dbgen` is out of date.

Every command must exit 0. The tests include the package-layer architecture test (it parses the [package layers table](../knowledge/architecture/detailed.md#package-layers)), the no-comments and no-`any` conventions test (whose check of shell, YAML, TOML, Python and ignore files reads only the files `git ls-files --cached --others --exclude-standard` lists, as the documentation checks do, so it never reads ignored output, other worktrees under `.claude/worktrees/` or files deleted from the working tree; amended 2026-10-28, pending owner review), integration tests that each create and drop their own `ovc_<random>_test` database (cloned from the test process's template database, described below), and process tests that build the `api` and `worker` binaries and run them with an explicit environment. The storage tests use the local SeaweedFS bucket `ovc-test`, created when missing, with the keys from the root `.env` (`OVC_DEV_STORAGE_ACCESS_KEY`, `OVC_DEV_STORAGE_SECRET_KEY` and `OVC_DEV_STORAGE_PORT`), so `go test` runs through `tools/dev-env.sh`; the storage contract test runs against both SeaweedFS and the in-memory store. A missing or unreachable test database or storage server, or missing storage keys, fails the run; nothing is skipped. (Pending owner review.) The fixture creates and drops the test databases through one administrative connection pool per test process, and connects without TLS (`sslmode=disable`) unless `OVC_TEST_DATABASE_ADMIN_URL` sets `sslmode` or names a `service`, or `PGSSLMODE` or `PGSERVICE` is set; a loopback port that forwards to a remote PostgreSQL server therefore needs an explicit `sslmode` in the URL (pending owner review). Each test process (`go test` runs one per package) migrates one template database, `ovc_template_<Unix seconds>_<random>_test`, the first time a test asks for a migrated database, only after the host check has passed; it then closes the template to connections, and every migrated test database is a clone of that template (`CREATE DATABASE … TEMPLATE`), never of a database the process did not create. Clones take a PostgreSQL advisory lock in shared mode on the administrative database, so the lock coordinates only runs whose `OVC_TEST_DATABASE_ADMIN_URL` names the same database, and each wait for it is bounded to one minute. Each test database opens a pool of at most 4 connections; a test that holds a row lock while several requests wait on it asks for the one larger pool, of 6 connections, through `testdb.NewForLockContention`, as the two API tests that hold a row lock while three or four requests wait on it do and, from M4, the chat search test that holds the messages table while four searches wait on it (pending owner review), while the API tests' authentication harness otherwise opens the pool of 4 (amended 2026-11-07, pending owner review); the template database is migrated through a pool of 2; and the administrative pool of each test process closes a connection after about one second idle. The bound keeps `go test -race ./...`, which runs up to one package per core side by side and in each package up to one test per core, under PostgreSQL's default `max_connections` of 100: three full runs sampled on 2026-10-27 peaked at 75 client connections, against 98 before the bound ([plan](../knowledge/plans/merge-gate-critical-path.md)) (amended 2026-10-27, pending owner review). Measured on 2026-11-07 on a machine running no other tests, a full run peaked at 67 client connections in 105.8 s, the API package taking 84.6 s; capping the administrative pool at 4 or 3 lowered the peak to 55 or 46 but lengthened a full run to about 200 s, so the administrative pool stays uncapped ([plan](../knowledge/plans/merge-gate-critical-path.md)) (amended 2026-11-07, pending owner review). Heavy runs (the merge gate, full backend runs, end-to-end suites and measurements) never run concurrently on one machine, because they share the local PostgreSQL's limit of 100 connections: the end-to-end processes of one session held about 44 connections while a full backend run peaks at 67, and the merge gate failed with SQLSTATE 53300 (too many clients) on 2026-11-07 (amended 2026-11-07, pending owner review). The process tests in `cmd/internal/startup` run at most three at a time: each counts its own test database's pool at `testdb.DefaultPoolConnections` (4), the child process's pool of 5 and its listener connection, 10 connections and 30 for the three slots, the count the sampled peak already included; the start-up refusal test holds one slot for its 32 child processes, one per case and binary, which are refused while their settings are loaded or before their database pool opens, so they open no connection to the test server (amended 2026-10-29, pending owner review). Before creating its template, a process takes the same lock exclusively and drops, without `FORCE`, the databases its own role owns whose names match the template pattern and carry a creation time more than an hour before the server's clock, because a test process has no end hook that could drop its own template. A full `go test ./...` therefore leaves one template (about 9 MB) per package that asks for a migrated database, and each stays for at least an hour, until a later run removes it. A test process that runs longer than an hour can lose its template to another run's cleanup; a stale template-named database with a live connection fails the cleanup and every migrated test of the run until it is dropped by hand. `NewMigratedTo` and unmigrated test databases still start empty and migrate from scratch (pending owner review). The lint configuration excludes gosec's G204 (subprocess with variable arguments) and G304 (file path from a variable) for `_test.go` files only, because the process tests run the binaries they have just built and the convention tests read the repository's own files; production code keeps both rules. It also excludes G101 (hard-coded credentials) only for the lines of `internal/core/settings.go` and `internal/core/storage_settings.go` that assign an `OVC_…` setting name, because the names of secret settings such as `OVC_SMTP_PASSWORD` look like credentials to it, while their values are only ever read from the environment; any other literal in those files is still checked (pending owner review). The lint configuration sets `run.allow-serial-runners: true`, because the merge gate runs `go test`, whose lint rule test in `internal/conventions` runs `bin/golangci-lint` on a fixture, at the same time as golangci-lint over `./...`, and golangci-lint refuses a second concurrent run by default; with the setting a second run waits for the first instead of failing. It changes no linter, rule or setting that decides findings (amended 2026-10-27, pending owner review). The wait for that lock, a file lock in the user's temporary folder shared by every session of the account, has no bound of its own in golangci-lint, so the configuration also sets `run.timeout: 5m`, which bounds every run under this configuration, the gate's lint and the lint rule test's alike, and so bounds how long one waiting run can be held by another; a run that reaches the timeout fails with golangci-lint's timeout exit code, which fails its check. Residual: a golangci-lint run with another configuration, for example of another project of the same account, or a run that is stopped rather than hung, can still hold the lock without a bound, and a waiting run's own wait for the lock is not counted against its timeout (amended 2026-10-29, pending owner review).

## Frontend checks

From `frontend/`:

```bash
pnpm install --frozen-lockfile
pnpm typecheck
pnpm lint
pnpm format:check
pnpm test
pnpm build
pnpm check:classes
pnpm check:bundle
pnpm api:check
pnpm audit --audit-level high
../tools/dev-env.sh pnpm e2e
```

Every command must exit 0.

- `lint` runs ESLint and the comment check, which rejects comments in every hand-written frontend file (scripts, styles, markup and configuration); the generated `src/lib/api/schema.ts` is exempt from both and from Prettier. The lint configuration forbids importing `vi` or `vitest` from Vitest at all, the test-double methods on them (`mock`, `doMock`, `importMock`, `mockObject`, `spyOn`, `fn`, `stubGlobal`, `stubEnv`, `useFakeTimers`, `setSystemTime`), importing `vitest` or its subpaths dynamically, replacing `fetch` by assignment, `Object.defineProperty`, `Object.defineProperties`, `Reflect.set` or `Object.assign`, the mocking libraries `msw`, `nock`, `sinon`, `testdouble`, `tinyspy` and any module named `*mock*`, lint and TypeScript directives and explicit `any`; a Vitest suite proves each rule fires. The list names known techniques and is not exhaustive: the rule in AGENTS.md still applies to anything it misses. ## End-to-end test harness

Started in slice 1 (the clock and tick routes), extended by each slice. The [pilot scenarios](../knowledge/design/web/pilot-scenarios.md) run against local test deployments: the real API, worker, database and storage in local containers, configured with `OVC_TEST_CONTROL=1` and `OVC_CLOCK=test`.

- **Safety:**
  - the API, the worker and `ovc-admin` refuse to start with `OVC_TEST_CONTROL=1` unless the meeting provider is `fake`, mail is the database sink, `OVC_HTTP_ADDR` is a loopback IP literal, the storage endpoint of the API and the worker is a loopback IP literal, every database host is a loopback IP literal, `localhost` resolving only to loopback, or a Unix socket (checked before connecting), and `SELECT current_database()` matches `^[a-z0-9_]+_(test|dev)$`; they also refuse `OVC_CLOCK=test` without `OVC_TEST_CONTROL=1`;
  - the control routes require `Content-Type: application/json`, bodies of at most 4 KiB and a loopback `Host` header, so a page in the developer's browser or a rebinding host name cannot drive them; `localhost` is accepted beside the loopback IP literals because the check compares the header as a string and never resolves it, a rebinding page sends its own host name, and a page served from another local origin is stopped by the JSON content-type preflight, which the routes do not answer;
  - without the setting, none of the routes below exist, and a test proves it;
  - the worker also refuses `OVC_MAIL_BACKEND=sink`, the default, unless the database passes the same local host and name checks, so a production database never accumulates emails that carry tokens; a deployment sets `OVC_MAIL_BACKEND=smtp` with the SMTP settings.
- **Worker:** with `OVC_CLOCK=test` the worker's own loops are paused, so only harness ticks run jobs. Local development keeps `OVC_CLOCK=system`, so its worker loops run normally while the mail route stays available; the clock and tick routes exist only with `OVC_CLOCK=test`.
- **Clock:** the fake clock reads its current instant from a single test-clock row, so the API and the worker of one deployment share one time; each deployment starts it at the real current time. Suites that move the server clock and depend on the browser's own time install `page.clock` at the same instant (from the first suite that needs it; pending owner review). Tests that wait for an answer, review draft or template save may also install `page.clock` without a fixed time, so the page's time keeps flowing, and advance the 1-second save delay with `page.clock.fastForward` instead of waiting for it in real time, through `frontend/e2e/save-delay.ts`; the component tests of each autosave pin the delay at 1000 milliseconds (decided by the owner on 2026-11-16, pending owner review). The calls a test may make are listed in [ADR-0009](decisions/0009-owner-approved-exceptions-and-visibility.md) item 13 (recorded 2026-11-17, pending owner review).
- **Parallelism:** each Playwright worker gets its own deployment (own database, API and worker processes, and `vite preview`, on ports derived from the worker's index), so suites that move the clock never interfere. Suites assigned to one worker run serially. Firefox and WebKit each run as four projects (`firefox-1` to `firefox-4`, `webkit-1` to `webkit-4`), each holding a group of the browser specs that `playwright.config.ts` deals round-robin from every `*.spec.ts` under `e2e/` in sorted order, so every browser spec runs in every engine; Playwright starts a new worker when the next test belongs to another project, so a Firefox or WebKit worker's life ends with its spec group (about a fifth to a third of its engine's tests, several workers sharing a group) and its successor starts with a new browser and a new deployment, which keeps the late-run slowdown of those engines in check while the number of concurrent workers stays the same. Select an engine with `--project='firefox*'` (added 2026-11-11, pending owner review). A deployment stops its API, worker and preview processes with TERM, and after 20 seconds with KILL, after which it waits up to 5 more seconds for the process to exit; a process that misses the first deadline fails the teardown with an error naming it (`api`, `worker` or `preview`), and one that misses the second too names its pid and says that its address may still be held, so the next deployment's address check on that port can fail (amended 2026-10-29, pending owner review). The global setup builds the binaries and the frontend once; every deployment shares the storage bucket `ovc-e2e`, because SeaweedFS allocates volumes per bucket and objects carry random keys anyway (pending owner review).
- **HTTPS preview:** WebKit refuses the `Secure` refresh cookie over plain `http://127.0.0.1`, so each deployment's preview is served over HTTPS with a self-signed certificate for `127.0.0.1` that the global setup creates with `openssl` for every run in the ignored `frontend/test-results/deployment/tls/`. `vite preview` reads it from `OVC_FRONTEND_PREVIEW_CERTIFICATE` and `OVC_FRONTEND_PREVIEW_PRIVATE_KEY` (both or neither; listed in `frontend/.env.example`, empty by default), and the private key is kept at mode 0600 in a 0700 folder. Playwright accepts it with `ignoreHTTPSErrors`; it is never installed into any trust store, and the cookie's `__Host-` prefix and `Secure` flag are never relaxed. `OVC_PUBLIC_URL` is that HTTPS origin, and a probe in every browser checks that confirmation sets the refresh cookie and a refresh then succeeds (pending owner review).
- **One run at a time:** the global setup takes an exclusive run lock before it builds anything: it creates one per-user lock file shared by every checkout of that account, outside every checkout, `~/Library/Caches/ovc-e2e/run.lock` on macOS and `~/.cache/ovc-e2e/run.lock` on Linux, under the home folder of the user's account record and independent of environment variables such as `XDG_CACHE_HOME`, with exclusive-create semantics, holding the runner's pid, start time and repository checkout path; the `ovc-e2e` folder is created readable only by its owner (mode 0700, narrowed if it already exists) and the lock file with mode 0600. Because the per-worker ports and the `ovc-e2e` bucket are shared by every checkout on the machine, the lock serialises runs across all git worktrees of that account, not only within one checkout; runs under different operating-system accounts are not serialised although they share the ports and the bucket. The lock folder must be a real folder owned by the user and the lock a regular file owned by the user, or the run refuses (pending owner review). A second run started while one holds the lock, from the same or another checkout, fails at once with a message naming the holding checkout, the holding pid and the lock file, which can be removed by hand when that pid is not an end-to-end run, and its global teardown leaves the shared bucket alone; a lock whose pid is no longer running, or is the runner's own pid left by an earlier run, is reclaimed with a notice on standard error. The run checks after taking the lock and again in its global teardown that the lock still holds its pid, start time and checkout (pending owner review), and fails instead of touching the shared files and bucket when it does not. The lock is released by the global teardown, after the bucket is deleted, and on the runner's exit. The [merge gate](#change-checks-and-the-merge-gate) takes the same lock for its whole run, with a record that adds `"kind": "merge-gate"`, so every run started while a gate runs, from any checkout and also from a command of the gate's own lanes, fails at once with a message naming the gate, its checkout and its pid, and asks to wait for the gate instead of removing the lock; the gate's own `pnpm e2e` instead adopts the lock: the gate passes it the lock file open on descriptor 7 together with `E2E_HARNESS_GATE_RUN_LOCK_FD=7`, a harness-internal variable that is not a setting, and the global setup adopts the lock only when the variable names a descriptor of 3 or more, the lock names a merge gate, the gate tests this run's own repository checkout, that gate's pid is an ancestor of the runner process (from `ps`), and the descriptor is the lock file itself (same device and inode); an adopting run neither reclaims nor releases the lock, which the gate removes after its last check (amended 2026-10-28, pending owner review). Playwright clears its output folder before the global setup runs, so each run writes its traces to its own `frontend/test-results/playwright/run-<pid>/`, which the configuration passes to the Playwright workers in `E2E_HARNESS_RUN_OUTPUT`; that variable is harness-internal, not a setting, and the configuration refuses any value other than a `run-<positive integer>` folder directly inside `frontend/test-results/playwright/`, because Playwright clears that folder before the lock is taken; and only the run that holds the lock removes the folders of earlier runs, and only inside its own checkout's `frontend/test-results/playwright/`, never another worktree's (pending owner review); a refused run therefore touches neither the deployment folder, the built frontend nor the bucket, and the output of the run in progress only if the caller deliberately names that run's folder in the variable; the removal of earlier outputs also refuses to run when `frontend/test-results/` or its `playwright/` folder is a link (pending owner review).

The coordinating agent runs the **merge gate** before every merge into `main`, one change per gate, never batched. The gate always runs `main`'s copy of the script, never the copy in the tree it tests, so a change to the gate is gated by the gate it replaces; the copy lives in the coordinator's scratch folder and reaches the checkout only through `--repo`:

```bash
git show main:tools/merge-gate.sh > <scratch>/merge-gate.sh
bash <scratch>/merge-gate.sh gate --ff-only --change <branch> --repo <change checkout>
git merge --ff-only <branch>
bash <scratch>/merge-gate.sh finish --repo <main checkout>
```

The gate runs in the change's checkout on its branch, and the merge and `finish` in the checkout of `main`. When `main` has moved, the coordinator runs `git merge --squash <branch>` on `main`, then `bash <scratch>/merge-gate.sh gate --squash --change <branch> --repo <main checkout>`, commits the squash without changing the index and runs `finish`. A squash gate that fails leaves the staged squash on `main`; agents never reset or restore, so only the owner unstages it (pending owner review).

- **Lock:** the gate takes a per-user lock built like the [end-to-end run lock](#end-to-end-test-harness), `merge-gate.lock` in the same `ovc-e2e` cache folder (mode 0700, the lock file 0600, both owned by the user, the lock a regular file and not a link), created exclusively and holding the gate's pid, start time, checkout, mode, change, base commit, gated head, tested tree, check list and scope. A second gate fails at once naming the holding checkout and pid. A lock left by a gate whose pid is no longer running while its checks ran is reclaimed: the gate moves it to a private name, reads it again and removes it only when it still names the same stale pid and start time, and otherwise puts it back and fails. A gate that passed keeps the lock until `finish` releases it, and an abandoned one is released with `merge-gate.sh release`.
- **End-to-end run lock:** a gate that runs a laned list (the full run, or `self-test-lanes`) also takes the per-user [end-to-end run lock](#end-to-end-test-harness), `run.lock` in its lock folder, right after its own lock and before its first check, and holds it until after its last check, so no end-to-end run of another session or of its own lanes starts its deployments, about 70 PostgreSQL connections, beside the lanes' `go test`. The record is the harness's JSON with the gate's pid, start time and checkout and `"kind": "merge-gate"`, created exclusively from a private candidate file (mode 0600). When the lock is held by a live process (checked with `ps`, so a process of another account counts as live), the gate fails before any check with `the end-to-end run lock <path> is busy: <an end-to-end run or another merge gate> from <checkout> (pid, started) holds it; the gate ran no check`, logs the attempt as `e2e-run-lock-busy` and releases its own lock; a lock whose pid no longer runs is reclaimed the way the harness reclaims it (moved to a private name, read again and removed only when it still names the same pid and start time), with a notice; a link, a file of another owner or an unreadable record fails the gate. The gate keeps the lock file open on descriptor 7; every lane other than `e2e` closes it, and only the `e2e` entry inherits it, with `E2E_HARNESS_GATE_RUN_LOCK_FD=7`, so the harness adopts the lock as that section describes. Before the `e2e` phase and before it passes, the gate checks that the lock still names it, and fails otherwise; on a failure or an interruption it removes the lock with its own lock, and keeps both while a lane process group still runs. Because the harness always uses the account's cache folder, the full check list refuses a `--lock-dir` other than the default one (amended 2026-10-28, pending owner review). Residual: the run lock records only the gate's pid, not its lane process groups, because rewriting it would change the file that the `e2e` entry's inherited descriptor names; when the gate dies by SIGKILL, or exits while a lane process group survived KILL, the next end-to-end run or gate reclaims the run lock as stale and can start beside the orphaned processes, whereas the merge-gate lock, which records the groups, stays held (amended 2026-10-28, pending owner review).
- **Clean tree:** a fast-forward gate refuses any line of `git status --porcelain --untracked-files=all`; a squash gate refuses unstaged and untracked files and an empty index. Both refuse, by name and without reading them, ignored files that would change what the checks run: Compose override files, `go.work` at the root, in `backend/` and in `tools/`, and `.npmrc` and pnpmfiles at the root, in `frontend/` and in `tools/docs/`. Other ignored files stay outside the tested tree and can still change what the checks run; the gate never inspects environment files, which `tools/dev-env.sh` loads for the backend and the end-to-end commands and which Vite's `loadEnv` in `frontend/vite.config.ts` reads for `OVC_FRONTEND_` variables during the frontend build and the preview server. The gate checks the clean tree, `main`, the head and the tested tree again after its checks and fails with its report when any changed.
- **Environment:** the gate refuses to start, for every subcommand and before it runs any other command, naming the setting but never printing its value, when the shell exports a function (an exported `go` or `git` would shadow that command in every check and in the gate's own probes; found with `declare -Fx` and by any environment name holding `BASH_FUNC`, `%` or a parenthesis; the message names each function and its unset form for the gate only, `env -u 'BASH_FUNC_<name>%%'`, since some login shells export functions such as `which` or `module`), when the environment, read through its names, exports one of the shell start-up variables `BASH_ENV` and `ENV` (a start-up file that exits 0 makes every `bash -c` check pass without running), `SHELLOPTS` or `BASHOPTS`; a Git variable that selects another repository, index or configuration (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, `GIT_SHALLOW_FILE`, `GIT_REPLACE_REF_BASE` and `GIT_NO_REPLACE_OBJECTS`, which can narrow Gitleaks' history scan or change which objects are read, or any variable whose name starts with `GIT_CONFIG`), which would also change the file list of the conventions tests; `GOFLAGS` (for example `-run=^$` would make `go test` run no test and pass), `GOWORK`, `GOTOOLCHAIN`, `GOPACKAGESDRIVER` (which replaces the package loading golangci-lint relies on), `GOENV` with any value other than `off`, `NODE_OPTIONS` or `E2E_HARNESS_GATE_RUN_LOCK_FD`, also when exported empty, or any variable whose name starts with `npm_config_` or `pnpm_config_` in any case; the message says to unset it for the gate only, with `env -u` or from a clean shell. A gate then refuses to start when `go env -changed`, run in the checkout's root, `backend/` and `tools/`, reports a setting changed from its default, through the environment or `go env -w`, other than `GOPATH`, `GOMODCACHE`, `GOCACHE`, `GOTMPDIR` and `GOBIN` (where files are kept; no check installs a binary), `GOTELEMETRY` (whether usage counters are kept), `GOPROXY` (where modules are fetched from, while `go.sum` still pins every module's hash) and `GOAMD64` and `GOARM64` (the instruction-set level, which selects instructions of the same meaning, and a level the machine lacks fails closed), so `CGO_ENABLED`, `GOOS`, `GOEXPERIMENT`, `GODEBUG`, `GOSUMDB`, `GOINSECURE`, `GOPRIVATE`, `GONOSUMDB` (both of which skip the checksum database) and every other setting that changes what is built or verified are refused; its message says to run the gate with `GOENV=off`, which ignores the user-level Go configuration, or to unset the variables for the gate only; and when pnpm's effective `node-options`, `script-shell` or `shell-emulator`, from its user, global or project configuration (`pnpm config list --json`), is set. The report prints, for each of those folders, the effective `GOVERSION`, `GOTOOLCHAIN`, `GOFLAGS`, `GOWORK` and `GOENV`, whether `GOENV=off` ignored the user-level configuration, and the names of the changed allowlisted settings, and the Node and pnpm versions. `tools/check-merge-gate.sh` passes `--skip-tool-probes` to the gates whose tests do not exercise the Go and pnpm probes, which the gate accepts only with a self-test check list; the shell, Git and variable refusals still run there. Residual: the gate cannot tell a tool shadowed on `PATH` (`go`, `node`, `pnpm`, `git`, `ps`, `python3`, `bash`, `docker`) from the real one, and it does not check runtime variables that `go env` does not report, such as `GOMAXPROCS` and `GORACE`, other user-level pnpm settings outside the tested tree, as under [T-39](threat-model.md), or the variables other tools read, such as `PLAYWRIGHT_` or `VITEST_` variables (amended 2026-10-28, pending owner review).
- **Hashes:** the gate records `main`'s commit and the tested tree, `HEAD^{tree}` of the branch for `--ff-only` (which also needs `main` to be an ancestor of the branch) or `git write-tree` for `--squash`, which must equal `git merge-tree --write-tree main <branch>`, the tree of the branch merged into `main`. `finish` checks that `main` is the gated head (fast-forward) or a single-parent commit on the recorded base (squash), that `main^{tree}` equals the tested tree, and that the gate ran the full run, or the Markdown-only list for a Markdown-only scope; it prints both trees, the check list and the scope. `finish` detects a `main` that moved or whose tree differs only after the merge and cannot prevent it; on any mismatch it fails and keeps the lock for the owner.
- **Checks:** the gate runs every command of the full local check run from the sections above, `go test` and `pnpm e2e` through `tools/dev-env.sh`, from the checkout named by `--repo`; its end-to-end entry is `pnpm e2e --max-failures=10 --trace=off`, so a failing run stops after its tenth failed test (added 2026-11-11, pending owner review) and records no Playwright trace (amended 2026-11-20, pending owner review). Its script keeps one ordered list of the full run, each entry tagged with its slot (`pre`, `A`, `B`, `C` or `e2e`, as listed under [tool setup](#tool-setup)); the gate refuses a list with an unknown slot or a repeated command. `pre` runs alone, then lanes A, B and C at the same time, each in its own process group, each running its commands in list order and stopping at its own first failure; a failing lane lets the other lanes finish. `e2e` runs alone, only after `pre` and all three lanes passed and every process of their process groups has ended, and after the clean tree, `main`, the head and the tested tree have been checked again. After each command the lane's leader process, the shell that runs the lane, writes one record, its slot, the command's list index, exit status and seconds, and at its end one record with its own wall time, to an anonymous pipe: a named pipe the gate opens and unlinks at once, so no file holds a record and, once unlinked, no path in the file system reaches the pipe. Every command runs with that descriptor closed, so on macOS neither a command nor a process it starts can write or read a record. On Linux a command can still open the pipe through `/proc/<pid>/fd/` of its lane's leader (for example `/proc/$PPID/fd/9`), read a failed record away and write consistent forged ones, so there the gate guards only against accidental writes, not against a command that sets out to forge its result (T-41). After the leaders have ended, the gate writes an end marker into the pipe and reads every record into memory. The gate passes only when every `pre`, `A`, `B` and `C` entry has exactly one record with a numeric exit status of 0 reported by the leader of the lane its tag names, every lane reported its end once, every lane's `wait` returned 0, and the `e2e` entry has such a record too; a missing, malformed or duplicate record, a record for an entry of another lane or a non-zero `wait` fails the gate. Processes a lane leaves behind get up to 30 seconds to end after its leader ended; the gate prints that it waits for them, and fails naming the lane when any still runs (amended 2026-10-27, pending owner review). On INT, TERM or exit the gate sends TERM to every running lane's process group, waits up to 20 seconds for each group to end, sends KILL to what remains and waits up to 10 more seconds, and only then releases the lock; if a group still runs, the lock stays held and the gate names the group. An interrupted or stopped gate prints its command log folder and appends its attempt to `merge-gate.log` with the result `interrupted` or `stopped`. Once it holds the lock, every gate prints `gate start: power: <mains|battery|unknown>; load: <1 min> <5 min> <15 min>` and appends it to `merge-gate.log`; when its checks end, passed or failed, it appends `gate end: power: …; load: …; battery-during-run: <yes|no|unknown>; sleep: <yes|no|unknown>` before the attempt's result line, and its report repeats both lines after the check list. On macOS the power source comes from `pmset -g batt`, the load from `sysctl -n vm.loadavg`, and battery during the run and sleep from the `pmset -g log` entries between the gate's start and end, compared in the system time zone; on Linux the power source comes from `/sys/class/power_supply/*/online`, the load from `/proc/loadavg`, and battery during the run and sleep are `unknown`; a source the gate cannot read gives `unknown`, and an interrupted or stopped gate, or one refused by a busy end-to-end run lock, logs no end line. Reading the power log takes about a second, so `tools/check-merge-gate.sh` passes `--skip-power-log`, which the gate accepts only with a self-test check list, to every gate except one passing and one failing self-test gate; such a gate reports battery during the run and sleep as `unknown` (added 2026-11-16, pending owner review). Residual: Playwright starts every browser in a process group of its own, outside the `e2e` entry's group, so the gate's TERM and KILL never reach a browser directly, and the gate neither waits for nor names browser processes; Playwright closes its browsers itself when it handles TERM and kills each browser's group when its process exits normally, but when a Playwright process is killed with KILL its browsers survive the gate and are left for the owner to end (amended 2026-10-29, pending owner review). `--lane-grace SECONDS` replaces the three waits with one shorter wait for the self-tests; the gate refuses it with any other check list (amended 2026-10-27, pending owner review). The lock records the process groups of the running lanes, and a running lock counts as stale only when neither the gate's pid nor any recorded lane group is alive; `release` refuses such a lock as well (amended 2026-10-27, pending owner review). `--checks self-test` replaces the list with harmless commands run one after another, and `--checks self-test-lanes` with harmless tagged commands run in lanes, both for `tools/check-merge-gate.sh`; the gate refuses them without an explicit `--lock-dir` outside the default lock folder and on the repository the script belongs to or any repository holding `tools/merge-gate.sh`, and `finish` refuses a gate that ran them. The Markdown-only list and the self-test list run their commands one after another, stop at the first failure and list the remaining commands as not run, as before; both use the same sequential code path, which `tools/check-merge-gate.sh` proves through the self-test list, because the Markdown-only list runs the real documentation tools and cannot run against its temporary repository.

## Upload cleanup operations

Added 2026-11-01; protocol approved, wording pending owner review. Before adopting [ADR-0019](decisions/0019-durable-upload-cleanup.md), stop admission and drain/stop every older API writer, then apply migrations. Old writers do not consult the journal. Migration conservatively retains unresolved legacy uploads and refuses a backlog above 4,096; never delete records or raise the cap to force adoption. Start only the new API/worker after migration succeeds.

An upload-capacity 503 means all durable intent slots are occupied, possibly by uncertain remote completion. It promises no recovery time. Investigate safe lifecycle diagnostics and the local administration command; do not enable automatic browser replay or clear the journal by hand.

Run `ovc-admin uploads inspect <attachment-id>` to see state, current outbox identity and receipt history; `--after <attempt-uuid>` continues its keyset pages of at most 100. The command prints no storage key, multipart identifier or file metadata. To grant another bounded cycle, run `ovc-admin uploads retry-cleanup <attachment-id> --attempt <uuid>` with an operator-chosen UUID. Record and reuse that UUID if the command outcome is uncertain. Replaying it returns the original cycle; a different UUID while a cycle is active refuses with that cycle's identity. The worker, not this command, performs storage I/O. Use personal system accounts so the audit identifies the operator; local commands use `tools/dev-env.sh` without printing settings.

Successful Delete does not resolve an ambiguous Complete. Unresolved intents and explicit attempt receipts remain until safe terminal removal, independently of ordinary outbox retention. Receipts have no global count cap, so deliberate repeated operator actions can grow storage. Inspection and indexed lookup do not scan all receipt history under the intent lock. Permanent uncertainty may need provider investigation; there is no force-forget command and no automatic resurrection of dead attempts. The [dated storage evidence](../knowledge/research/s3-multipart-cleanup-2026-11-01.md) does not certify another compatible provider.

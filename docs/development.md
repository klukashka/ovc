## Tool setup

Use Linux or macOS with Git, Bash, Docker with Compose v2 (Docker Desktop, Colima or OrbStack all work), Node and pnpm (see below), a system `python3` (3.9 or newer, for the agent hooks in `.claude/hooks/`), a C compiler (for `go test -race`, which needs cgo) and the pinned toolchain:

- Go: the version in [`tools/go.mod`](../tools/go.mod) (`go` and `toolchain` lines, matched by `backend/go.mod`), installed from [the official downloads](https://go.dev/dl/) or a package manager; the `toolchain` line lets newer Go installations fetch the pinned release.
- Repository tools (Gitleaks, OSV-Scanner, govulncheck, golangci-lint, and sqlc, which generates `backend/internal/dbgen` from `backend/queries/` and `backend/migrations/`): pinned as Go `tool` dependencies in `tools/go.mod`, with checksums in `tools/go.sum`, and built once per tools upgrade from those pinned versions into the ignored `bin/` directory with the command below, so no check compiles them again; no separate installation is needed (pending owner review).
- Node and pnpm: Node from `frontend/.node-version` and pnpm from the `packageManager` field of `frontend/package.json` ([versions](../knowledge/research/frontend-toolchain-2026-10-21.md)). Playwright's browsers are installed once with `pnpm --dir frontend exec playwright install chromium firefox webkit`.
- lychee for link checks: installed with its [official instructions](https://lychee.cli.rs/installation/).

Exact versions are recorded with their check dates in `knowledge/research/` when the scaffold pins them.

The full local check run that NFR-6.2 bounds to 10 minutes is every command of the documentation checks, the security scanning (Gitleaks over history and over staged changes, and the four OSV-Scanner lockfile scans of `tools/go.mod`, `backend/go.mod`, `frontend/pnpm-lock.yaml` and `tools/docs/pnpm-lock.yaml`), the backend checks, the frontend checks with the end-to-end suites, the secret guard hook and local settings wrapper checks, and `tools/check-tool-binaries.sh`; a check-budget record in `knowledge/analysis/` times each of them (pending owner review). It also runs `tools/check-merge-gate.sh`, the merge gate's own test. The full run executes once per merge, in the [merge gate](#change-checks-and-the-merge-gate); an implementing agent runs the change checks of its diff (amended 2026-10-27, pending owner review).

## Security scanning

Run from the repository root; each must pass in the [merge gate](#change-checks-and-the-merge-gate) before a change merges, and before readiness a change runs the scans of the change-check rows its diff touches: Gitleaks over staged changes always, Gitleaks over history for agent configuration, the wrapper and the Gitleaks configuration, and OSV-Scanner over each module or lockfile it changes (amended 2026-10-27, pending owner review). The scanners run from `bin/`, built as [the backend checks](#backend-checks) describe; `tools/check-tool-binaries.sh` must print `bin/ matches tools/go.mod` first (pending owner review).

- **Secrets in history:** `bin/gitleaks git --redact --no-banner --config .gitleaks.toml .` reports no leaks.
- **Secrets about to be committed:** `bin/gitleaks git --staged --redact --no-banner --config .gitleaks.toml .` reports no leaks. Gitleaks never scans the working directory, so ignored environment files are never read.
- **Gitleaks configuration:** `.gitleaks.toml` at the repository root extends the default rules and adds one allowlist: the `generic-api-key` rule does not report a match in `backend/cmd/internal/startup/settings_process_test.go` whose matched value is exactly `OVC_UNSUBSCRIBE_SIGNING_SECRET=`, because its start-up refusal cases put that variable name beside values each test run generates, which the rule mistakes for a hard-coded key; the path and the value must both match (`condition = "AND"`), so any other generic-shaped value in that file is still reported, every other rule still scans it, and the configuration adds no exclusion beyond this one and the default rules' own allowlists (narrowed from the whole file on 2026-10-26, pending owner review). The commands pass `--config` so an ambient `GITLEAKS_CONFIG` cannot replace it (pending owner review).
- **Known vulnerabilities in dependencies:** OSV-Scanner over each module and lockfile with an explicit path, starting with `bin/osv-scanner scan source --no-call-analysis=go --lockfile=tools/go.mod` (the tools module has no packages of its own to call-analyse) and `bin/osv-scanner scan source --no-call-analysis=go --lockfile=backend/go.mod` (the backend gets call analysis from `govulncheck` in the backend checks); `bin/osv-scanner scan source --lockfile=frontend/pnpm-lock.yaml`, and `bin/osv-scanner scan source --lockfile=tools/docs/pnpm-lock.yaml`. A pass is exit code 0. Accepted findings are listed in the `osv-scanner.toml` next to the scanned file, each with a reason and an `ignoreUntil` date, and explained in a dated triage table ([Go tools](../knowledge/research/local-s3-2026-10-21.md#repository-tool-scan-triage), [documentation tools](../knowledge/research/toolchain-2026-10-21.md#documentation-tools), [frontend](../knowledge/research/frontend-toolchain-2026-10-21.md#accepted-findings) (pending owner review), [backend](../knowledge/research/backend-libraries-2026-10-21.md#notes)).

## Backend checks

Build the pinned tools from the repository root after cloning and after any change to `tools/go.mod` or `tools/go.sum`, including one brought by a pull, a merge or a branch switch; every git worktree has its own ignored `bin/`. `tools/check-tool-binaries.sh` compares the build information embedded in each binary with the tools module: the Go toolchain, the tool's own module and every dependency must have the versions of the tools build list and the checksums of `tools/go.sum`, and no module may be replaced; a missing binary or any difference fails it, because Gitleaks compiles its rules into the binary and cannot report its own version. It detects a stale binary, not a forged one; the build command pins `GOTOOLCHAIN` to the `toolchain` line, because a newer local Go would otherwise build the tools and the check would refuse them (pending owner review):

```bash
GOTOOLCHAIN="$(awk '$1 == "toolchain" { print $2 }' tools/go.mod)" go -C tools build -o ../bin/ github.com/golangci/golangci-lint/v2/cmd/golangci-lint golang.org/x/vuln/cmd/govulncheck github.com/zricethezav/gitleaks/v8 github.com/google/osv-scanner/v2/cmd/osv-scanner github.com/sqlc-dev/sqlc/cmd/sqlc
```

Then, from `backend/`, with Docker Compose running and `OVC_TEST_DATABASE_ADMIN_URL` set to a PostgreSQL URL that may create databases (for example the `ovc` user on `ovc_dev`); the test fixture refuses a URL whose hosts are not loopback addresses or Unix sockets:

```bash
go mod tidy -diff
unformatted="$(gofmt -l .)" && test -z "$unformatted"
go vet ./...
../bin/golangci-lint run ./...
../bin/govulncheck ./...
../tools/dev-env.sh go test -race -count=1 ./...
../bin/sqlc -f sqlc.yaml diff
```

After changing a query or a migration, regenerate the query package from `backend/` with `../bin/sqlc -f sqlc.yaml generate` and commit the result; `sqlc diff` fails while `internal/dbgen` is out of date.

Every command must exit 0. The tests include the package-layer architecture test (it parses the [package layers table](../knowledge/architecture/detailed.md#package-layers)), the no-comments and no-`any` conventions test, integration tests that each create and drop their own `ovc_<random>_test` database (cloned from the test process's template database, described below), and process tests that build the `api` and `worker` binaries and run them with an explicit environment. The storage tests use the local SeaweedFS bucket `ovc-test`, created when missing, with the keys from the root `.env` (`OVC_DEV_STORAGE_ACCESS_KEY`, `OVC_DEV_STORAGE_SECRET_KEY` and `OVC_DEV_STORAGE_PORT`), so `go test` runs through `tools/dev-env.sh`; the storage contract test runs against both SeaweedFS and the in-memory store. A missing or unreachable test database or storage server, or missing storage keys, fails the run; nothing is skipped. (Pending owner review.) The fixture creates and drops the test databases through one administrative connection pool per test process, and connects without TLS (`sslmode=disable`) unless `OVC_TEST_DATABASE_ADMIN_URL` sets `sslmode` or names a `service`, or `PGSSLMODE` or `PGSERVICE` is set; a loopback port that forwards to a remote PostgreSQL server therefore needs an explicit `sslmode` in the URL (pending owner review). Each test process (`go test` runs one per package) migrates one template database, `ovc_template_<Unix seconds>_<random>_test`, the first time a test asks for a migrated database, only after the host check has passed; it then closes the template to connections, and every migrated test database is a clone of that template (`CREATE DATABASE … TEMPLATE`), never of a database the process did not create. Clones take a PostgreSQL advisory lock in shared mode on the administrative database, so the lock coordinates only runs whose `OVC_TEST_DATABASE_ADMIN_URL` names the same database, and each wait for it is bounded to one minute. Before creating its template, a process takes the same lock exclusively and drops, without `FORCE`, the databases its own role owns whose names match the template pattern and carry a creation time more than an hour before the server's clock, because a test process has no end hook that could drop its own template. A full `go test ./...` therefore leaves one template (about 9 MB) per package that asks for a migrated database, and each stays for at least an hour, until a later run removes it. A test process that runs longer than an hour can lose its template to another run's cleanup; a stale template-named database with a live connection fails the cleanup and every migrated test of the run until it is dropped by hand. `NewMigratedTo` and unmigrated test databases still start empty and migrate from scratch (pending owner review). The lint configuration excludes gosec's G204 (subprocess with variable arguments) and G304 (file path from a variable) for `_test.go` files only, because the process tests run the binaries they have just built and the convention tests read the repository's own files; production code keeps both rules. It also excludes G101 (hard-coded credentials) only for the lines of `internal/core/settings.go` and `internal/core/storage_settings.go` that assign an `OVC_…` setting name, because the names of secret settings such as `OVC_SMTP_PASSWORD` look like credentials to it, while their values are only ever read from the environment; any other literal in those files is still checked (pending owner review).

## Frontend checks

From `frontend/`:

```bash
pnpm install --frozen-lockfile
pnpm typecheck
pnpm lint
pnpm format:check
pnpm test
pnpm build
pnpm check:classes
pnpm check:bundle
pnpm api:check
pnpm audit --audit-level high
../tools/dev-env.sh pnpm e2e
```

Every command must exit 0.

- `lint` runs ESLint and the comment check, which rejects comments in every hand-written frontend file (scripts, styles, markup and configuration); the generated `src/lib/api/schema.ts` is exempt from both and from Prettier. The lint configuration forbids importing `vi` or `vitest` from Vitest at all, the test-double methods on them (`mock`, `doMock`, `importMock`, `mockObject`, `spyOn`, `fn`, `stubGlobal`, `stubEnv`, `useFakeTimers`, `setSystemTime`), importing `vitest` or its subpaths dynamically, replacing `fetch` by assignment, `Object.defineProperty`, `Object.defineProperties`, `Reflect.set` or `Object.assign`, the mocking libraries `msw`, `nock`, `sinon`, `testdouble`, `tinyspy` and any module named `*mock*`, lint and TypeScript directives and explicit `any`; a Vitest suite proves each rule fires. The list names known techniques and is not exhaustive: the rule in AGENTS.md still applies to anything it misses. Shell, YAML, TOML and Python files, ignore files, `.editorconfig` and `.env.example` files anywhere in the repository are covered by the backend conventions test.
- `lint` refuses the `Reflect` API in every hand-written TypeScript and JavaScript file, end-to-end page scripts included, as AGENTS.md's rule on precise types requires (pending owner review).
- `lint` also runs `scripts/check-ignored-advisories.ts`, which fails when an advisory in `auditConfig.ignoreGhsas` of `pnpm-workspace.yaml` has no `[[IgnoredVulns]]` entry in `osv-scanner.toml` or that entry's `ignoreUntil` has passed, so `pnpm audit` never keeps ignoring an advisory after its triage expires (pending owner review).
- `lint` also refuses, in `src/` and `public/`, HTML sinks, code from strings, script-readable cookies, IndexedDB and Web Storage outside the preference store, and any file under `src/` other than `.ts`, `.tsx` and `.css` (pending owner review).
- `check:classes` runs after `build`: it collects the class names written in `className` attributes (string and template literals, conditionals, and constants they name, including imported ones) with the TypeScript compiler and fails on any class that has no selector in the built CSS, so a mistyped or unregistered Tailwind class cannot pass silently. Class names are written as whole literal words; a fragment joined at run time (`` `pl-${size}` ``) and the arguments of a function call inside `className` are skipped, so class names belong in literals and constants, not in call arguments (pending owner review).
- `check:bundle` runs after `build`: it reads the build manifest, which the build moves out of `dist/` into the ignored `build-report/manifest.json`, and gzips the built files. It fails when the JavaScript of the entry and all its static imports, which every route loads before it renders, exceeds 180 KB, when the first load of a student's Home (the entry with its static imports, the stylesheet and the Home page's chunk with its imports, fonts excluded) exceeds the 250 KB student budget of NFR-2.4, when the first load of a tutor's Today exceeds the 400 KB tutor budget, when a page module under `src/features/` (a `*Page.tsx` or `*Pages.tsx` file) is not a chunk loaded on demand, or when the access rule (`Gate.tsx`, `access.ts`) or a token holder (`AddressToken.tsx`, `InvitationToken.tsx`) is not part of the first load: the build gives each of them a named chunk (`access-gate`, `access-rule`, `address-token`, `invitation-token`), and the check requires exactly one chunk of each name in the build, among the entry's static imports and not loaded on demand. The manifest lists source module paths, so nothing under `dist/` holds it (the check fails when `dist/.vite/` exists); the check also walks `dist/` without following links and fails on any symbolic link, on any entry whose name or folder starts with a dot, and on any entry other than `index.html`, the files of `public/` that are committed as regular files (listed with `git ls-files -s -v`, mode `100644` or `100755`, without the assume-unchanged or skip-worktree flag, and still regular files in the working tree, so no link that Git tracks and no link that replaced a tracked file; the check fails while `git status` shows any uncommitted or untracked change under `public/`) and the `.js`, `.css`, `.woff` and `.woff2` files directly in `assets/` that the build manifest names as a chunk's file, stylesheet or asset, so no source map, report, key, configuration, untracked file or leftover asset can reach the served build (pending owner review), and the smoke checks that the preview server serves no manifest, also under `//.vite/` and percent-encoded addresses. Each route's page module loads on demand and the libraries from `node_modules` share one `vendor` chunk; the frames, the access rule and the token pages' address replacement stay in the entry's static imports, so a token leaves the address before any page chunk is requested (pending owner review).
- `api:check` regenerates the typed client from `go run ./cmd/api openapi`, which reads no settings, and fails when the committed `src/lib/api/schema.ts` differs; `pnpm api:generate` rewrites it after an API change.
- `pnpm install` runs no dependency install scripts: `allowBuilds` in `pnpm-workspace.yaml` is empty and `strictDepBuilds` fails an install that would need one. `minimumReleaseAge` is 3 days (4320 minutes) until the first deployment and 14 days (20160 minutes) from then on ([ADR-0017](decisions/0017-dependency-release-age.md)): pnpm refuses any direct or transitive version published less than that before resolution, and `pnpm install --frozen-lockfile` re-verifies the lockfile against it. Restoring 14 days does not re-check versions resolved while the delay was 3 days, so the deployment preparation reviews them as ADR-0017 describes. `pnpm lint` runs `scripts/check-release-age.ts`, which parses `frontend/pnpm-workspace.yaml` and `tools/docs/pnpm-workspace.yaml` with js-yaml and fails when either is not one YAML mapping, repeats a key (also under another quoting), or sets the release age under another spelling or below the top level, when the two workspaces disagree, when either sets a value other than 4320 or 20160, or when a `deploy/` folder exists at the repository root while the delay is below 14 days; it also refuses any `minimumReleaseAgeExclude` at 3 days, an exclusion that is not a list, and any entry that names no exact version at 14 days, whatever YAML style writes the list, and it refuses the setting in a `.npmrc` (and any `.npmrc` key that is quoted, escaped or substituted) or in the `pnpm` field of `package.json` of either folder, and a pnpmfile or the `pnpmfile`, `globalPnpmfile` and `configDependencies` settings, through which configuration hooks could change the value (pending owner review).
- `e2e` is the Playwright smoke in Chromium, Firefox and WebKit. It needs Docker Compose running with the root `.env` in place (the harness calls `docker compose exec`, which interpolates the Compose file and so needs the `OVC_DEV_*` variables) and `OVC_TEST_DATABASE_ADMIN_URL` set as for the backend checks, and runs through `tools/dev-env.sh` so that the API and worker receive the local storage keys; the harness creates the bucket `ovc-e2e` through the storage container's shell when it is missing (pending owner review), pointing at the Compose PostgreSQL on a loopback host (the harness refuses any other host, because it creates and drops the database inside the Compose container). Its global setup builds the `api` and `worker` binaries and the frontend, creates the preview certificate and the storage bucket; then each Playwright worker creates an `ovc_e2e_<random>_test` database with `createdb` inside the PostgreSQL container (the password travels in the environment, never in arguments), runs `api migrate`, starts the API and the worker with an explicit environment (`OVC_TEST_CONTROL=1`, `OVC_CLOCK=test`, the shared clock set to the current time, and `OVC_TRUSTED_PROXY_CIDRS=127.0.0.1/32`, so a test that seeds accounts directly sends its own `X-Forwarded-For` from the TEST-NET range and never exhausts the per-IP limits) on `127.0.0.1:18800` plus its index, waits for `/api/v1/health/ready` with a deadline, and serves the production build with `vite preview` over HTTPS on `127.0.0.1:4300` plus its index. Teardown stops the processes and drops the database; a process that exited before teardown, or did not exit cleanly after `SIGTERM` (exit code 0 for the API and the worker; the preview server may also end by the signal itself), fails the run. Process output goes to `frontend/test-results/deployment/`, one log per process and Playwright worker, named with the worker's index so that a worker replaced after a failure keeps the failed deployment's logs (pending owner review). The global teardown deletes the shared `ovc-e2e` bucket, so uploaded objects do not accumulate across runs; the next run's setup creates it again (pending owner review). Each later slice adds its parts of the pilot scenario suites. Three suites drive the real backend without a browser and run in the Chromium project only: the authentication transport contract, the API contracts and, from slice 4, the realtime contract, which drives every server frame type and every close code the harness can cause (all but `1001` and `1013`, which need a server shutdown or a lost listener) through the real gateway, parses each frame with the client's parser and runs the same scenarios against the fake gateway in the unit tests (pending owner review).
- The end-to-end harness fails a test on any uncaught page error, on any browser console error other than the browser's own report of a failed status, on any response of status 400 or higher from the deployment's origin that the test did not declare, on any declared failure that does not occur, and on any request that failed without a response, except a cancelled request whose document was left: it is forgiven only when a navigation of the page started between the request and its failure, or follows the failure with no other request between them (pending owner review).

The development server (`pnpm dev`, `127.0.0.1:5173`) and the preview server (`127.0.0.1:4173`) listen on loopback only and proxy `/api` to `OVC_FRONTEND_API_TARGET` (default `http://127.0.0.1:8000`, documented in `frontend/.env.example`), so the browser talks to one origin as it will behind the production reverse proxy. Only `/api/v1/ws` is proxied as a WebSocket upgrade; the proxy keeps the browser's `Origin` and `Host`, so the gateway's exact-origin check sees the page's own origin, and every other `/api` path is proxied as plain HTTP; the end-to-end harness uses the same preview server, so every Playwright suite runs the realtime client through the proxy (pending owner review). Vite's own CORS handling is turned off on both servers (`cors: false`; by default Vite answers cross-origin requests from any `localhost` origin), and the smoke asserts on the preview server that neither a preflight nor a simple request from another local origin gets `Access-Control-Allow-Origin` (the development server shares the setting but is not exercised by the smoke). Both send `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`; the preview server also sends the page Content Security Policy. The headers are defined once in [`frontend/security-headers.ts`](../frontend/security-headers.ts), which the production reverse-proxy configuration must reproduce. The development server sends no CSP because the React refresh runtime injects an inline script. Plain `/api` requests share keep-alive connections to the API, closed after 60 seconds of idleness, which is under the API's 120-second idle timeout; this is safe only because the API binds no identity or authority to a TCP connection, and a WebSocket upgrade never reuses a pooled connection (pending owner review).

## Local services

The local environment has:

- **Docker Compose** with PostgreSQL 18 and SeaweedFS as the local S3-compatible server ([research](../knowledge/research/local-s3-2026-10-21.md)), both images pinned by digest in [`docker-compose.yml`](../docker-compose.yml).
  - Every port is published on `127.0.0.1` only; check with `docker compose ps --format '{{.Service}} {{.Ports}}'`, which must show `127.0.0.1:` before every published port.
  - The development credentials are required variables listed in [`.env.example`](../.env.example); copy it to the git-ignored `.env` next to it and fill in your own values. There are no default passwords, and PostgreSQL uses SCRAM authentication for every connection.
  - Host ports default to 55432 (PostgreSQL) and 58333 (storage), away from a PostgreSQL that may already run on 5432; `OVC_DEV_POSTGRES_PORT` and `OVC_DEV_STORAGE_PORT` change them.
  - SeaweedFS also runs its master, volume and filer services inside the container without authentication; they are not published to the host, and on Linux they are reachable from the host and other containers only on the Compose network. Development data only.
  - Agents never run commands that print the interpolated credentials or the environment. The secret guard hook refuses the common forms, including through wrappers, `sh -c` and container `exec`; it guards against accidental disclosure and is not a security boundary ([AI development verification](../knowledge/reviews/ai-development-setup.md#minimal-inventory)). After changing the hook, run `python3 .claude/hooks/check_guard_secrets.py`, which must report no failures.
  - The development database is `ovc_dev`. `docker compose up -d` starts both services; `docker compose ps` shows them `healthy` within a minute; `docker compose down` stops them and keeps the data volumes.
- **Local settings:** the owner keeps the Compose credentials in the root `.env` and the backend settings in `backend/.env`, copied from `backend/.env.example`. `tools/dev-env.sh <command>` runs one command with both loaded ([ADR-0009](decisions/0009-owner-approved-exceptions-and-visibility.md), item 7, until hosting exists). It accepts only plain `OVC_KEY=VALUE` lines and loads them literally, with no shell expansion; it refuses any other key, a quoted value and a key repeated within or across the files, naming only the file and line; a missing file is skipped; it never overrides a variable already set in the environment; it turns shell tracing off before reading, prints no value, and refuses to start `env`, `printenv`, `set`, `export`, `declare`, `typeset` or `compgen`, while the secret guard hook refuses the other printing forms it recognises. A value a command needs in its own arguments must be read inside it, for example with `sh -c '…'`, because the calling shell expands arguments before the wrapper loads anything. After changing the wrapper, run `tools/check-dev-env.sh`, which must exit 0; it checks every rule above on a temporary copy with made-up values. For example, `tools/dev-env.sh go -C backend run ./cmd/api` serves the API with the local settings.
- **Field encryption key:** the API and the worker, `api migrate` included, refuse to start without `OVC_FIELD_ENCRYPTION_KEY`, the AES-256-GCM key for stored invitation links: exactly 32 random bytes in standard base64. Generate it with `openssl rand -base64 32` and write the output into `backend/.env` as the unquoted value; a checkout from before the key existed needs this before its next local start of the API or the worker. Agents never open or edit that file: `tools/dev-env.sh go -C backend run ./cmd/api check-settings` and `tools/dev-env.sh go -C backend run ./cmd/worker check-settings` load the settings without connecting to anything and print only `ok` (exit 0) or the settings error, which names the variable and the problem and never a value. The key is not rotated in the MVP, because a new key makes every open invitation link unreadable and tutors then regenerate them. The process tests and the end-to-end harness generate their own key for every run and pass it to the processes in their environment, never in arguments, so no check depends on `backend/.env` (pending owner review).
- **Unsubscribe signing secret:** the API and the worker, `api migrate` included, refuse to start without `OVC_UNSUBSCRIBE_SIGNING_SECRET`, the secret from which HKDF derives the key that signs unsubscribe links: at least 32 bytes, and different from `OVC_JWT_SECRET` and `OVC_FIELD_ENCRYPTION_KEY`. Generate it with `openssl rand -base64 32` and write the output into `backend/.env` as the unquoted value; a checkout from before the secret existed needs this before its next local start of the API or the worker, and `check-settings` confirms it as for the field encryption key. Changing it makes every unsubscribe link already sent invalid. The process tests and the end-to-end harness generate their own secret for every run and pass it in the environment, so no check depends on `backend/.env` (pending owner review).
- **The administration command** `go run ./cmd/ovc-admin users list` (and the other subcommands in the [accounts specification](../knowledge/specs/accounts.md#administration-command)) needs only `OVC_DATABASE_URL`; locally, run it through `tools/dev-env.sh`. Operators run it under their own personal system accounts, never a shared one, because the audit record names the system user (pending owner review).
- **Three commands**, all reading the same settings from the environment (through `tools/dev-env.sh`, or set by hand): `go run ./cmd/api migrate` applies the migrations with a role that may change the schema; `go run ./cmd/api` serves on `OVC_HTTP_ADDR` and refuses to start while migrations are pending; `go run ./cmd/worker` runs the per-lane loops and the scheduler that the [notifications specification](../knowledge/specs/notifications.md) describes; tests drive the same work through one `Tick(now)` pass (pending owner review). Restart them by hand after a change. The API and the worker need the bucket named in `OVC_STORAGE_BUCKET` (`ovc-dev` in `backend/.env.example`) on the local SeaweedFS server, with `OVC_STORAGE_ACCESS_KEY` and `OVC_STORAGE_SECRET_KEY` equal to the root `.env`'s `OVC_DEV_STORAGE_ACCESS_KEY` and `OVC_DEV_STORAGE_SECRET_KEY`; until the bucket exists, readiness reports storage unavailable. Create it once with `printf 's3.bucket.create -name ovc-dev\n' | docker compose exec -T storage weed shell` (pending owner review).
- **Fakes**:
  - the meeting provider is `fake`, because BigBlueButton runs only on a dedicated Ubuntu server and not on developer machines ([research](../knowledge/research/bigbluebutton-2026-10-20.md#server));
  - mail goes to the database sink. Development runs with `OVC_TEST_CONTROL=1` against a development database, so the sink is readable only through the harness route below.
- **Live conferencing checks**, from slice 7 on, use a remote BigBlueButton test server configured through `OVC_BBB_URL` and `OVC_BBB_SECRET` in `backend/.env.local`, which is git-ignored and unreadable by agents. They are manual: the opt-in command runs the BigBlueButton adapter's contract tests. A readiness report lists the result, or `unverified` when the check was not run. The definition of done does not require them.

Automated tests never call a real BigBlueButton server, SMTP provider or production storage.

## End-to-end test harness

Started in slice 1 (the clock and tick routes), extended by each slice. The [pilot scenarios](../knowledge/design/web/pilot-scenarios.md) run against local test deployments: the real API, worker, database and storage in local containers, configured with `OVC_TEST_CONTROL=1` and `OVC_CLOCK=test`.

- **Safety:**
  - the API, the worker and `ovc-admin` refuse to start with `OVC_TEST_CONTROL=1` unless the meeting provider is `fake`, mail is the database sink, `OVC_HTTP_ADDR` is a loopback IP literal, the storage endpoint of the API and the worker is a loopback IP literal, every database host is a loopback IP literal, `localhost` resolving only to loopback, or a Unix socket (checked before connecting), and `SELECT current_database()` matches `^[a-z0-9_]+_(test|dev)$`; they also refuse `OVC_CLOCK=test` without `OVC_TEST_CONTROL=1`;
  - the control routes require `Content-Type: application/json`, bodies of at most 4 KiB and a loopback `Host` header, so a page in the developer's browser or a rebinding host name cannot drive them; `localhost` is accepted beside the loopback IP literals because the check compares the header as a string and never resolves it, a rebinding page sends its own host name, and a page served from another local origin is stopped by the JSON content-type preflight, which the routes do not answer;
  - without the setting, none of the routes below exist, and a test proves it;
  - the worker also refuses `OVC_MAIL_BACKEND=sink`, the default, unless the database passes the same local host and name checks, so a production database never accumulates emails that carry tokens; a deployment sets `OVC_MAIL_BACKEND=smtp` with the SMTP settings.
- **Worker:** with `OVC_CLOCK=test` the worker's own loops are paused, so only harness ticks run jobs. Local development keeps `OVC_CLOCK=system`, so its worker loops run normally while the mail route stays available; the clock and tick routes exist only with `OVC_CLOCK=test`.
- **Clock:** the fake clock reads its current instant from a single test-clock row, so the API and the worker of one deployment share one time; each deployment starts it at the real current time. Suites that move the server clock and depend on the browser's own time install `page.clock` at the same instant (from the first suite that needs it; pending owner review).
- **Parallelism:** each Playwright worker gets its own deployment (own database, API and worker processes, and `vite preview`, on ports derived from the worker's index), so suites that move the clock never interfere. Suites assigned to one worker run serially. The global setup builds the binaries and the frontend once; every deployment shares the storage bucket `ovc-e2e`, because SeaweedFS allocates volumes per bucket and objects carry random keys anyway (pending owner review).
- **HTTPS preview:** WebKit refuses the `Secure` refresh cookie over plain `http://127.0.0.1`, so each deployment's preview is served over HTTPS with a self-signed certificate for `127.0.0.1` that the global setup creates with `openssl` for every run in the ignored `frontend/test-results/deployment/tls/`. `vite preview` reads it from `OVC_FRONTEND_PREVIEW_CERTIFICATE` and `OVC_FRONTEND_PREVIEW_PRIVATE_KEY` (both or neither; listed in `frontend/.env.example`, empty by default), and the private key is kept at mode 0600 in a 0700 folder. Playwright accepts it with `ignoreHTTPSErrors`; it is never installed into any trust store, and the cookie's `__Host-` prefix and `Secure` flag are never relaxed. `OVC_PUBLIC_URL` is that HTTPS origin, and a probe in every browser checks that confirmation sets the refresh cookie and a refresh then succeeds (pending owner review).
- **One run at a time:** the global setup takes an exclusive run lock before it builds anything: it creates one per-user lock file shared by every checkout of that account, outside every checkout, `~/Library/Caches/ovc-e2e/run.lock` on macOS and `~/.cache/ovc-e2e/run.lock` on Linux, under the home folder of the user's account record and independent of environment variables such as `XDG_CACHE_HOME`, with exclusive-create semantics, holding the runner's pid, start time and repository checkout path; the `ovc-e2e` folder is created readable only by its owner (mode 0700, narrowed if it already exists) and the lock file with mode 0600. Because the per-worker ports and the `ovc-e2e` bucket are shared by every checkout on the machine, the lock serialises runs across all git worktrees of that account, not only within one checkout; runs under different operating-system accounts are not serialised although they share the ports and the bucket. The lock folder must be a real folder owned by the user and the lock a regular file owned by the user, or the run refuses (pending owner review). A second run started while one holds the lock, from the same or another checkout, fails at once with a message naming the holding checkout, the holding pid and the lock file, which can be removed by hand when that pid is not an end-to-end run, and its global teardown leaves the shared bucket alone; a lock whose pid is no longer running, or is the runner's own pid left by an earlier run, is reclaimed with a notice on standard error. The run checks after taking the lock and again in its global teardown that the lock still holds its pid, start time and checkout (pending owner review), and fails instead of touching the shared files and bucket when it does not. The lock is released by the global teardown, after the bucket is deleted, and on the runner's exit. Playwright clears its output folder before the global setup runs, so each run writes its traces to its own `frontend/test-results/playwright/run-<pid>/`, which the configuration passes to the Playwright workers in `E2E_HARNESS_RUN_OUTPUT`; that variable is harness-internal, not a setting, and the configuration refuses any value other than a `run-<positive integer>` folder directly inside `frontend/test-results/playwright/`, because Playwright clears that folder before the lock is taken; and only the run that holds the lock removes the folders of earlier runs, and only inside its own checkout's `frontend/test-results/playwright/`, never another worktree's (pending owner review); a refused run therefore touches neither the deployment folder, the built frontend nor the bucket, and the output of the run in progress only if the caller deliberately names that run's folder in the variable; the removal of earlier outputs also refuses to run when `frontend/test-results/` or its `playwright/` folder is a link (pending owner review).
- **Traces:** Playwright keeps a trace only for a failed test (`retain-on-failure`) in the ignored `frontend/test-results/playwright/run-<pid>/` of its run; traces hold only generated test accounts and are never shared (pending owner review).
- **Control routes:** `/__test__/` routes, absent from every other configuration and from OpenAPI:

  | Route | Effect |
  |---|---|
  | `POST /__test__/clock` | Set or advance the shared clock; only with `OVC_CLOCK=test` |
  | `POST /__test__/tick` | Run one worker `Tick(now)` to completion at the shared clock's instant; only with `OVC_CLOCK=test` |
  | `POST /__test__/mail` with `{to}` in the body | Read messages from the database mail sink, with their links |
  | `POST /__test__/presence` with `{user}` | Report `{online, sockets}` from this API instance's connection registry (persisted presence arrives with slice 6), so tests can wait for a socket close (from slice 4, pending owner review) |
  | `POST /__test__/realtime/close` with `{user, code}` | Close the user's sockets on this instance with `4429` or `1012` through the real gateway, so the client's handling of codes the browser cannot provoke deterministically is tested end to end (from slice 4, pending owner review) |
  | `POST /__test__/unsubscribe-token` with `{user, group}` | Mint an unsubscribe token through the real signer, until slice 5 emails carry the links (from slice 4, pending owner review) |
  | `POST /__test__/accounts` with `{role, name, email, language, timezone}` | Create a confirmed tutor (with its tutor profile) or student whose password is this API process's seeding password, and sign it in; answers `{user, password, access_token, expires_in}` with the real refresh cookie, `409 conflict` for a taken email and `422` for invalid fields (pending owner review) |
  | `POST /__test__/session` with `{email}` | Sign in again an account that this API process seeded and whose password is still the seeding password, without verifying the password; answers `{access_token, expires_in}` with the real refresh cookie, and `404 not_found` for every other account (pending owner review) |
  | `POST /__test__/settings/embed` | Override `embed_allowed` for this deployment, until the next override |
  | `POST /__test__/fake-provider/lessons/{lesson}/recording` | After the MVP: start or stop recording in the lesson's latest fake meeting; not registered until recordings land |
  | `POST /__test__/fake-provider/lessons/{lesson}/ready` | After the MVP: make the fake provider send a correctly signed recording-ready callback for the lesson's latest fake meeting; not registered until recordings land |

- **Fake room:** the fake meeting provider's join link opens `/__test__/fake-room`, which shows the meeting, participant name, role and, after the MVP, recording state, refreshing every second. In the MVP the fake meeting provider has no way to start a recording at all (pending owner review). Under `OVC_TEST_CONTROL=1` it is served with framing allowed from the OVC origin, so both the embedded and the new-tab paths can be asserted.
- **Isolation:** each suite seeds its own tutors and students with unique emails.
- **Account seeding:** tests that only need a confirmed account as setup create it with `POST /__test__/accounts` and sign it in with `POST /__test__/session` instead of the real sign-up, confirmation and sign-in, which cost one Argon2id hash each. Each API process generates a random seeding password when it starts with `OVC_TEST_CONTROL=1`, returns it in every successful answer of `POST /__test__/accounts` and hashes it once, on first use, through the production hasher with the production parameters, and stores that hash for every account it seeds; the session route compares the stored hash with it in constant time and then starts the session through the accounts service's own session code, which rechecks the hash and the account state under the account's lock and writes the same session row, access token and refresh cookie as a real sign-in, so a blocked account is refused with `account_blocked` and a deleted one, or one whose password was changed, with `not_found`. Seeded accounts sign in through the real `POST /api/v1/auth/login` with the seeding password as well. Relationships and join requests of seeded students go through the real routes (signed-in acceptance of an invitation, code entry). The sign-up, confirmation, invitation sign-up and sign-in journeys, and every test that asserts their behaviour, keep the real flows; in the browser the harness stores the returned refresh cookie with Playwright's `addCookies` for the preview origin, with the attributes of OVC's refresh cookie (`Path=/`, `Secure`, `HttpOnly`, `SameSite=Strict` and the lifetime from `Max-Age`). The step and seed tests of the [pilot scenarios](../knowledge/design/web/pilot-scenarios.md) keep seeding their accounts through the operations their steps name (pending owner review).

## Change checks and the merge gate

Decided in [ADR-0018](decisions/0018-targeted-checks-and-merge-gate.md) (pending owner review). An implementing agent runs the **change checks**: every row of the table below that its diff touches, and reports them as its readiness evidence; every other command of the [full local check run](#tool-setup) is reported as `deferred to the merge gate`, never as `passed`. A path the table does not list, or any doubt, means the full run. Before any row that runs a scanner from `bin/`, `tools/check-tool-binaries.sh` runs.

| The diff touches | Change checks |
|---|---|
| Anything | Gitleaks over staged changes; `tools/docs/check-docs.sh` when any Markdown file, `.markdownlint.json`, `.markdownlintignore` or the link-checker configuration changes |
| `backend/` Go code | `gofmt`, `go vet ./...`, golangci-lint `./...`, and `go test -race` (through `tools/dev-env.sh`) of the changed packages, every package that imports them directly or transitively (from `go list`), `internal/conventions` and every `cmd/` package's tests; `api:check` and the affected end-to-end specs when routes, schemas or behaviour a page uses change |
| `backend/migrations/`, `backend/queries/`, `backend/sqlc.yaml`, `internal/testdb` | `sqlc diff` and the whole `go test -race ./...` |
| `backend/go.mod`, `go.sum`, `backend/osv-scanner.toml` | `go mod tidy -diff`, `govulncheck`, OSV over `backend/go.mod` |
| Shell, YAML, TOML or Python files anywhere, ignore files, `.env.example`, `knowledge/architecture/detailed.md` | `internal/conventions` tests, plus the rows of the folder they live in |
| `frontend/` source | `typecheck`, `lint`, `format:check`, `test`, `build`, `check:classes`, `check:bundle`, and the end-to-end specs the change affects, named in its plan |
| The generated OpenAPI document or the generated client | `api:check` and the whole `pnpm e2e` |
| `frontend/pnpm-lock.yaml`, `pnpm-workspace.yaml`, `package.json`, `auditConfig.ignoreGhsas` | `pnpm install --frozen-lockfile`, `audit`, `lint` (release-age and ignored-advisory checks), OSV over the lockfile |
| `tools/docs/` lockfile, workspace or `package.json` | the documentation tools' install, `tools/docs/check-docs.sh`, frontend `lint` (release-age check), OSV over `tools/docs/pnpm-lock.yaml` |
| `frontend/e2e/`, the Playwright configuration, `/__test__/` routes and the test-control settings, the Compose file, `frontend/security-headers.ts`, the Vite configuration, `frontend/public/` | `build`, `check:bundle`, the whole `pnpm e2e`, and the backend tests of the test-control start-up refusals and of the routes' absence without `OVC_TEST_CONTROL=1` |
| `tools/`, `tools/go.mod`, `tools/osv-scanner.toml`, the `bin/` build | `tools/check-tool-binaries.sh`, OSV over `tools/go.mod`, every changed check script under `tools/` and every check that reads a changed configuration there, and the checks that use any rebuilt tool |
| `.claude/`, `tools/dev-env.sh`, `.gitleaks.toml`, `tools/merge-gate.sh` | the secret guard hook check, `tools/check-dev-env.sh`, `tools/check-merge-gate.sh`, Gitleaks over history |

The coordinating agent runs the **merge gate** before every merge into `main`, one change per gate, never batched. The gate always runs `main`'s copy of the script, never the copy in the tree it tests, so a change to the gate is gated by the gate it replaces; the copy lives in the coordinator's scratch folder and reaches the checkout only through `--repo`:

```bash
git show main:tools/merge-gate.sh > <scratch>/merge-gate.sh
bash <scratch>/merge-gate.sh gate --ff-only --change <branch> --repo <change checkout>
git merge --ff-only <branch>
bash <scratch>/merge-gate.sh finish --repo <main checkout>
```

The gate runs in the change's checkout on its branch, and the merge and `finish` in the checkout of `main`. When `main` has moved, the coordinator runs `git merge --squash <branch>` on `main`, then `bash <scratch>/merge-gate.sh gate --squash --change <branch> --repo <main checkout>`, commits the squash without changing the index and runs `finish`. A squash gate that fails leaves the staged squash on `main`; agents never reset or restore, so only the owner unstages it (pending owner review).

- **Lock:** the gate takes a per-user lock built like the [end-to-end run lock](#end-to-end-test-harness), `merge-gate.lock` in the same `ovc-e2e` cache folder (mode 0700, the lock file 0600, both owned by the user, the lock a regular file and not a link), created exclusively and holding the gate's pid, start time, checkout, mode, change, base commit, gated head, tested tree, check list and scope. A second gate fails at once naming the holding checkout and pid. A lock left by a gate whose pid is no longer running while its checks ran is reclaimed: the gate moves it to a private name, reads it again and removes it only when it still names the same stale pid and start time, and otherwise puts it back and fails. A gate that passed keeps the lock until `finish` releases it, and an abandoned one is released with `merge-gate.sh release`.
- **Clean tree:** a fast-forward gate refuses any line of `git status --porcelain --untracked-files=all`; a squash gate refuses unstaged and untracked files and an empty index. Both refuse, by name and without reading them, ignored files that would change what the checks run: Compose override files, `go.work` at the root, in `backend/` and in `tools/`, and `.npmrc` and pnpmfiles at the root, in `frontend/` and in `tools/docs/`. Other ignored files stay outside the tested tree and can still change what the checks run; the gate never inspects environment files, which `tools/dev-env.sh` loads for the backend and the end-to-end commands and which Vite's `loadEnv` in `frontend/vite.config.ts` reads for `OVC_FRONTEND_` variables during the frontend build and the preview server. The gate checks the clean tree, `main`, the head and the tested tree again after its checks and fails with its report when any changed.
- **Hashes:** the gate records `main`'s commit and the tested tree, `HEAD^{tree}` of the branch for `--ff-only` (which also needs `main` to be an ancestor of the branch) or `git write-tree` for `--squash`, which must equal `git merge-tree --write-tree main <branch>`, the tree of the branch merged into `main`. `finish` checks that `main` is the gated head (fast-forward) or a single-parent commit on the recorded base (squash), that `main^{tree}` equals the tested tree, and that the gate ran the full run, or the Markdown-only list for a Markdown-only scope; it prints both trees, the check list and the scope. `finish` detects a `main` that moved or whose tree differs only after the merge and cannot prevent it; on any mismatch it fails and keeps the lock for the owner.
- **Checks:** the gate runs every command of the full local check run from the sections above, in order, `tools/check-tool-binaries.sh` first, `go test` and `pnpm e2e` through `tools/dev-env.sh`, from the checkout named by `--repo`, and stops at the first failure, listing the remaining commands as not run. `--checks self-test` replaces the list with harmless commands for `tools/check-merge-gate.sh`; the gate refuses it without an explicit `--lock-dir` outside the default lock folder and on the repository the script belongs to or any repository holding `tools/merge-gate.sh`, and `finish` refuses a gate that ran it.
- **Markdown-only changes:** when every entry of `git diff --raw --no-renames main...HEAD` (or `git diff --cached --raw --no-renames` for a squash) is a regular file of mode 100644 on both sides (000000 for an addition or a deletion), a Markdown file under `docs/` or `knowledge/` other than `knowledge/architecture/detailed.md`, which the package-layer architecture test parses, and no file of the repository that is not Markdown names its file name (`git grep --cached -F`), the gate runs only the documentation checks and Gitleaks over history and staged changes, with the same lock, clean tree and hashes, and prints `scope: docs-only`. A symbolic link, a submodule or a mode change means the full run. A test or script that reads Markdown by walking folders or by a pattern, without naming the file, is not detected.
- **Failures:** a failed command blocks the merge and sends the change back to its branch under the after-fix rule. One rerun is allowed only when the output shows a named infrastructure error and no test assertion failed (Docker or PostgreSQL unreachable, `too many clients`), quoted in the merge report; a test that fails and then passes is reported as failed and fixed as a flaky-test bug; a second infrastructure failure goes to the owner. Each gate appends its time, base, tested tree, check list, scope and result to `merge-gate.log` in the lock folder (mode 0600), and the report lists the earlier attempts for the same tree.
- **Merge report:** the coordinator gives the owner what the gate and `finish` printed: the change, the base commit, the tested tree, the earlier attempts for it, `main` and `main^{tree}` after the merge, the check list, the scope and every command with its exit code.

After changing `tools/merge-gate.sh`, run `tools/check-merge-gate.sh`, which must exit 0; it runs a copy of the script from outside any repository against a temporary repository and lock folder and proves that a second gate is refused while the lock is held; that dirty, untracked and influential ignored files are refused; that `finish` passes after a fast-forward and a squash merge, refuses a moved `main`, a differing tree and a self-test gate; that a staged squash that is not the branch merged into `main`, an empty index and a squash off `main` are refused; that `finish` refuses a merge commit after a squash gate; that the Markdown-only scope excludes files a script names, the package layers document, symbolic links, mode changes and submodules; that a linked or non-regular attempt log fails the gate and leaves no lock; that a tree changed during the checks fails with a report; that reruns list earlier attempts; that the self-test list is refused outside a test lock folder and repository; that a stale lock is reclaimed and that a link or a folder in the lock's place is refused (pending owner review).

## Changes and commits

Every nontrivial change starts with an owner-approved plan and lives on its own branch as one commit. Once its change checks pass and its readiness reviews are resolved, the agent merges it into `main` through the [merge gate](#change-checks-and-the-merge-gate) with `git merge --ff-only` and deletes the branch, as [AGENTS.md](../AGENTS.md#change-workflow) describes (amended 2026-10-27, pending owner review). Agents never push, rebase, reset, clean, force-delete branches, discard work with destructive checkouts, restores or stash drops, or rewrite history (amend, filter-branch, update-ref, reflog expiry) without the owner. A change that alters a contract updates its specification, requirement or decision record in the same change. New dependencies enter only with an implemented consumer and a recorded reason in the [stack table](../knowledge/architecture/detailed.md#stack-per-component).

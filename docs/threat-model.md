The assets OVC protects, the actors who might threaten them, the trust boundaries, and the control that answers each threat, with a link to the specification that defines it. Every change that touches a trust boundary maps itself to the identifiers here and updates this file in the same change ([AGENTS.md](../AGENTS.md#security)).

## Assets

- **Accounts and sessions:** credentials, refresh tokens, email and reset tokens.
- **Personal data** of adults: names, emails, avatars, presence, voices and faces in recordings.
- **A tutor's practice:** student cards and private notes, groups, schedule, library, answer keys.
- **Student work:** answers, files, scores, feedback, corrected files.
- **Conversations:** direct and group chats with attachments.
- **Live lessons:** who can see and hear them, and who can moderate.
- **Platform secrets:** token signing keys, the BigBlueButton shared secret, storage and SMTP credentials.

## Actors

- **Anonymous internet user** without an account.
- **Student** of one tutor reaching another student's work, another tutor's data, or answer keys.
- **Tutor** reaching another tutor's relationships with a shared student.
- **Former participant:** an ended relationship, a removed group member, or a stale or stolen token.
- **Holder of a leaked link:** an invitation, a join link, a playback URL, an unsubscribe link, a tutor code or, from slice 6, an attachment's download address (pending owner review).
- **Forger of provider traffic:** someone who fakes BigBlueButton callbacks.
- **Malicious uploader or author** using files or text against other users.
- **Hostile web page or network peer** reaching a developer's local services.
- **Compromised dependency author or registry** shipping malicious or vulnerable code, images or tools.
- **Operator of a foreign push service**, curious or compelled, who sees web push metadata (from slice 10, pending owner review).

## Trust boundaries

1. Browser ↔ API (REST and WebSocket): all client input is untrusted, including identifiers.
2. API ↔ BigBlueButton: only the API creates meetings and join links; callbacks into the API are untrusted until verified. From slice 8 the `create` call's body may carry the lesson presentation's 5-minute signed storage URL, which the conferencing server fetches from object storage (pending owner review).
3. API and worker ↔ object storage: storage keys are internal; browsers reach objects only through short-lived signed URLs issued after authorization, or, from slice 6 for attachments, through OVC's own download route, which streams the object after checking an OVC-signed address bound to the attachment and its message, or from slice 8 to the attachment, the reference kind and its material, template or lesson (pending owner review), or from slice 9 its issue snapshot, submission answers or review revision (pending owner review); the conferencing server fetches a lesson presentation through a 5-minute signed storage URL sent in the `create` body (slice 8, pending owner review).
4. Browser ↔ BigBlueButton: media flows outside OVC; access depends on join links bound to the meeting's create time.
5. Worker ↔ SMTP provider and recipients' mailboxes: email content leaves OVC, and in the pilot bounce and complaint events come back through the provider's Data Streams stream.
6. Operator ↔ database through `ovc-admin`.
7. Developer machine ↔ local network and browser: local services and test control routes must not be reachable from outside the machine.
8. Repository ↔ supply chain: dependencies, container images and tools enter only pinned; lockfile dependencies are also scanned.
9. Coding agent ↔ repository and developer machine: agents act with the developer's shell; their configuration and the verification policy decide what they may run and what review a change gets.
10. Browser and worker ↔ the browser vendors' push services (from slice 10, [ADR-0015](decisions/0015-web-push.md)): the browser registers with its vendor's service outside Russia, the endpoint it returns is client input to OVC, and the worker sends encrypted payloads to that service (pending owner review).

## Threats and controls

| ID | Threat | Controls |
|---|---|---|
| T-1 | Credential stuffing and brute-force sign-in | Argon2id with the OWASP parameters and a bounded hashing limiter, per-email and per-IP throttling reserved atomically before any hashing (the per-IP slot first, so requests already over that limit add no per-email rows), generic failure messages ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). Residual risk: anyone who knows an email can keep it throttled with five wrong attempts every 15 minutes, so its owner gets `429` even with the right password until the window ends; an attempt refused by a limit returns its reserved slots, so many correct sign-ins in flight from one address cannot lock it out; the current-password check has its own per-account counter with the same numbers, one counter shared by every current-password check (password change and account deletion), so wrong guesses on one route spend the budget of the other and an integration test proves it ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords), [account deletion](../knowledge/specs/accounts.md#account-deletion)); residuals: a stolen access token adds five guesses per fixed 15-minute window to the sign-in budget, up to ten within a few seconds across a window boundary, and it can keep the owner's own password change and deletion throttled for the window, while sign out everywhere needs no password and a reset revokes every session (pending owner review) |
| T-2 | Stolen or replayed refresh token | Rotation by compare-and-swap, reuse detection revoking the session, sign out everywhere (which asks for confirmation in the interface, design slice step L2, pending owner review), `HttpOnly` cookie, an absolute 30-day expiry; the cookie carries a MAC over its session and generation, so only a cookie the server issued can trigger reuse detection and a forged stale cookie cannot sign anyone out ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). The frontend serialises refreshes across the tabs of one browser with the Web Locks API, so a waiting tab sends the already-rotated cookie; a Playwright test reloads two tabs at once and requires the session to survive, and fails when the lock is removed. Sign out everywhere ends the tab that asks at once; other tabs and browsers end at their next request, because every request is checked against the revoked session, and a Playwright test proves another browser's session ends. Residual risk: a refresh whose response is lost after rotation, including one aborted by a reload or a closed tab while it is in flight, leaves the browser with the old cookie, and its next refresh counts as reuse and signs that browser out; from slice 4, sign-out, sign out everywhere and refresh-token reuse also close the session's live connections with `4401` within 5 seconds, through the revocation trigger on the session row ([authentication and revocation](../knowledge/specs/realtime-and-video.md#authentication-and-revocation)) (pending owner review); the realtime client answers a `4401` with one refresh, so a connected tab whose session was revoked elsewhere signs out at once with "You were signed out on this device" instead of at its next request (a tab that is waiting to reconnect signs out at its next reconnect or request), and a Playwright test proves it for sign out everywhere in another browser (pending owner review); the session decides whether its access token is still valid by wall-clock time read through its injected scheduler, not by a monotonic clock that may pause while the system sleeps, so the realtime client of a tab that wakes after its token expired renews the token before it sends `auth`, while REST requests send the current token and renew it after the server answers `token_expired`; a wall clock set back only makes the frontend send an expired token, which the server refuses with `token_expired` or `4401` and the frontend answers with one refresh; a unit test proves the renewal across a suspended monotonic clock (pending owner review); ## Limitations and out of scope

- Uploaded files are not scanned for malware in the MVP; risky kinds (archives, executables) are refused instead.
- The hardening of the BigBlueButton host itself, whether its client loads external assets such as STUN servers (to be checked in the slice 7 probe for residency), and what participants record with their own devices.
- The object-storage bucket policy and the operator's credentials, which are deployment obligations.
- Message logs kept by the SMTP provider (limited to 30 days by the provider choice, which for the pilot's Postbox is a condition still to be confirmed) and raw recording data on the conferencing host after the MVP (deleted with the provider copy, to be confirmed by the recordings probe; in the MVP no recording is made).
- What the browser vendors' push services do with web push metadata beyond delivery, which OVC cannot control; it is bounded by the payload rules and the gate of T-46 (pending owner review).
- Compromise of hosts or the database by an operator.
- Academic integrity: students sharing answers with each other outside OVC.

## Slice 7 cumulative review residuals

Recorded 2026-11-07 from the [slice 7 slice review](../knowledge/reviews/slice-7-slice-review.md); wording pending owner review. Each residual is minor, carried into the [remote-activation checklist](../knowledge/plans/slice-7-remote-activation-checklist.md) where it depends on a real provider, and listed in the [slice 7 known limitations](../knowledge/reviews/slice-7-known-limitations.md#slice-review-residuals).

- **T-12/T-20, ended-hint permit exhaustion.** The unauthenticated ended-hint route takes one of 4 process-wide permits for every well-formed routing key and holds it for up to 2 seconds of database work, with no per-client limit. Once a real provider is active, anonymous floods can decline genuine hints, so rooms the provider ended stay recorded as open until a join's provider read or cleanup notices. No access is gained and no lesson ends, because the hint carries no authority and joins recheck the provider. A declined hint is logged only at DEBUG as `meeting.hint.declined`, so a flood does not show at the production INFO level. Today the route is a no-op outside test control. Before activation it needs an INFO-level or counted signal for declined hints and a per-address limit using the client address of OVC's own reverse proxy, or a proxy that admits it only from the conferencing host.
- **T-10/T-20/T-25, an intermediary retrying `create`.** The quiet-window settlement of [ADR-0021](decisions/0021-quiet-window-meeting-settlement.md) relies on no replay of a dispatched Create, which OVC's adapter guarantees only for its own transport by disabling connection reuse. A retried `create` landing after OVC recorded an uncertain outcome as absent, or confirmed End, creates a room OVC believes absent or ended, possibly on another server, and reopens the cleanup and revocation branches recorded as unreachable. OVC never issues join links for such a room, but the premise holds only with a single upstream that never retries or replays provider API requests, which the deployment must confirm before activation.
- **T-21/T-36, fake room presence is not authoritative.** The navigable fake room learns of a leave only from the room page, and closing a tab or removing a frame sends none, so it reports a participant present until the room ends. No decision uses presence today. A future authorization or cleanup decision that relies on presence, for example ending a room nobody attends, must not treat fake presence as evidence, and its change must restate this residual.

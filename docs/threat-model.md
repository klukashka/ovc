The assets OVC protects, the actors who might threaten them, the trust boundaries, and the control that answers each threat, with a link to the specification that defines it. Every change that touches a trust boundary maps itself to the identifiers here and updates this file in the same change ([AGENTS.md](../AGENTS.md#security)).

## Assets

- **Accounts and sessions:** credentials, refresh tokens, email and reset tokens.
- **Personal data** of adults: names, emails, avatars, presence, voices and faces in recordings.
- **A tutor's practice:** student cards and private notes, groups, schedule, library, answer keys.
- **Student work:** answers, files, scores, feedback, corrected files.
- **Conversations:** direct and group chats with attachments.
- **Live lessons:** who can see and hear them, and who can moderate.
- **Platform secrets:** token signing keys, the BigBlueButton shared secret, storage and SMTP credentials.

## Actors

- **Anonymous internet user** without an account.
- **Student** of one tutor reaching another student's work, another tutor's data, or answer keys.
- **Tutor** reaching another tutor's relationships with a shared student.
- **Former participant:** an ended relationship, a removed group member, or a stale or stolen token.
- **Holder of a leaked link:** an invitation, a join link, a playback URL, an unsubscribe link or a tutor code.
- **Forger of provider traffic:** someone who fakes BigBlueButton callbacks.
- **Malicious uploader or author** using files or text against other users.
- **Hostile web page or network peer** reaching a developer's local services.
- **Compromised dependency author or registry** shipping malicious or vulnerable code, images or tools.
- **Operator of a foreign push service**, curious or compelled, who sees web push metadata (from slice 10, pending owner review).

## Trust boundaries

1. Browser ↔ API (REST and WebSocket): all client input is untrusted, including identifiers.
2. API ↔ BigBlueButton: only the API creates meetings and join links; callbacks into the API are untrusted until verified.
3. API and worker ↔ object storage: storage keys are internal; browsers reach objects only through short-lived signed URLs issued after authorization.
4. Browser ↔ BigBlueButton: media flows outside OVC; access depends on join links bound to the meeting's create time.
5. Worker ↔ SMTP provider and recipients' mailboxes: email content leaves OVC, and in the pilot bounce and complaint events come back through the provider's Data Streams stream.
6. Operator ↔ database through `ovc-admin`.
7. Developer machine ↔ local network and browser: local services and test control routes must not be reachable from outside the machine.
8. Repository ↔ supply chain: dependencies, container images and tools enter only pinned; lockfile dependencies are also scanned.
9. Coding agent ↔ repository and developer machine: agents act with the developer's shell; their configuration and the verification policy decide what they may run and what review a change gets.
10. Browser and worker ↔ the browser vendors' push services (from slice 10, [ADR-0015](decisions/0015-web-push.md)): the browser registers with its vendor's service outside Russia, the endpoint it returns is client input to OVC, and the worker sends encrypted payloads to that service (pending owner review).

## Threats and controls

| ID | Threat | Controls |
|---|---|---|
| T-1 | Credential stuffing and brute-force sign-in | Argon2id with the OWASP parameters and a bounded hashing limiter, per-email and per-IP throttling reserved atomically before any hashing (the per-IP slot first, so requests already over that limit add no per-email rows), generic failure messages ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). Residual risk: anyone who knows an email can keep it throttled with five wrong attempts every 15 minutes, so its owner gets `429` even with the right password until the window ends; an attempt refused by a limit returns its reserved slots, so many correct sign-ins in flight from one address cannot lock it out; the current-password check on change and deletion has its own per-account counter with the same numbers, so a stolen access token adds five guesses per 15 minutes to the sign-in budget (residual) |
| T-2 | Stolen or replayed refresh token | Rotation by compare-and-swap, reuse detection revoking the session, sign out everywhere, `HttpOnly` cookie, an absolute 30-day expiry; the cookie carries a MAC over its session and generation, so only a cookie the server issued can trigger reuse detection and a forged stale cookie cannot sign anyone out ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). The frontend serialises refreshes across the tabs of one browser with the Web Locks API, so a waiting tab sends the already-rotated cookie; a Playwright test reloads two tabs at once and requires the session to survive, and fails when the lock is removed. Sign out everywhere ends the tab that asks at once; other tabs and browsers end at their next request, because every request is checked against the revoked session, and a Playwright test proves another browser's session ends. Residual risk: a refresh whose response is lost after rotation, including one aborted by a reload or a closed tab while it is in flight, leaves the browser with the old cookie, and its next refresh counts as reuse and signs that browser out; from slice 4, sign-out, sign out everywhere and refresh-token reuse also close the session's live connections with `4401` within 5 seconds, through the revocation trigger on the session row ([authentication and revocation](../knowledge/specs/realtime-and-video.md#authentication-and-revocation)) (pending owner review); the realtime client answers a `4401` with one refresh, so a connected tab whose session was revoked elsewhere signs out at once with "You were signed out on this device" instead of at its next request (a tab that is waiting to reconnect signs out at its next reconnect or request), and a Playwright test proves it for sign out everywhere in another browser (pending owner review); the session decides whether its access token is still valid by wall-clock time read through its injected scheduler, not by a monotonic clock that may pause while the system sleeps, so the realtime client of a tab that wakes after its token expired renews the token before it sends `auth`, while REST requests send the current token and renew it after the server answers `token_expired`; a wall clock set back only makes the frontend send an expired token, which the server refuses with `token_expired` or `4401` and the frontend answers with one refresh; a unit test proves the renewal across a suspended monotonic clock (pending owner review) |
| T-3 | Account enumeration through sign-up, sign-in, reset or invitation pages | Sign-in answers `invalid_credentials` alike for an unknown email, a wrong password and a deleted account, verifies a placeholder hash for an unknown email and reveals a block only after the correct password (residual: after the hashing parameters change, accounts not yet rehashed verify at the old cost while unknown emails verify at the new one, so timing can tell them apart until those accounts sign in once); `202` with no session for every sign-up, with the same body and headers for a new and a taken email and a password hashed in both cases; identical `202` answers from forgot and the public resend for any email, with per-account sending limits counted per email and silent on those routes and on sign-up, which creates the account and answers `202` even over a limit (residual: a known email adds two small inserts to the same transaction, a timing difference far below network noise and slowed by the per-IP limit; and whoever signs up with a free email can sign in to the new unverified account with the password they chose, while for a taken email they cannot, which the 7-day cleanup and the per-IP limit bound but do not remove), invitation pages that always offer both paths, notice to the existing owner, card-creation limits per tutor ([registration](../knowledge/specs/accounts.md#registration-and-email-verification), [invitations](../knowledge/specs/accounts.md#invitations)); the forgot-password page shows the same "if an account exists" message for every email, and the sign-up page always continues to "Check your email"; residual: sign-up does more database work for a new email (the account, its profile, the sending-limit counters, the request and the outbox row in one transaction) than for a taken one (a lookup and the notice), so timing can hint whether an email is registered; since [ADR-0014](decisions/0014-students-join-through-their-tutor.md), sign-up on an invitation page answers the same `202 {}` with no session for a new and a taken email, with the password hashed in both cases, and leaves the invitation usable after a taken-email answer (a link holder who tries a taken email and later sees the link still valid learns nothing new, because the page offers sign-in either way); a new-email sign-up whose link stops being usable while it waits inside its transaction creates no account and answers the same `202 {}` (pending owner review); the page then signs in automatically with the chosen password and otherwise shows "Check your email, or sign in to accept" (residual: that the automatic sign-in works only for a new account, and that the tutor's card then shows "Email not confirmed", are the same kind of signal as ordinary sign-up followed by sign-in); a student sign-up with a code checks the code behind the per-IP request slot and before hashing, so an invalid code costs a slot and says nothing about the email; the automatic sign-in after a sign-up on the invitation page lands on the account's own home page, or stays on the invitation page with Accept when the account that signed in is already confirmed; if the email was taken and the person typed that account's real password, the existing account signs in without being linked unless the person then accepts, which reveals nothing new because the person knows that password (pending owner review); the student sign-up page with a code shows the same message under the code field for every `tutor_code_invalid`, whatever email was typed, and continues to "Check your email" on every `202`, so the page itself adds no signal about the email (pending owner review) ([invitations](../knowledge/specs/accounts.md#invitations), [registration](../knowledge/specs/accounts.md#registration-and-email-verification)) |
| T-4 | Theft or reuse of confirmation and reset tokens | Minted by the worker only when the email is sent, 32 random bytes stored only as a hash and never in an outbox payload; single-use through one conditional update under the account's row lock; 24 hours for confirmation and 1 hour for reset; invalidated by a newer email of the same purpose and by confirmation, reset and an active account's password change, which also drop queued emails that have not been sent; minted under the account's row lock after checking its state again, so a change that commits first is never undone by a later mint; bound to the account state, so a blocked or deleted account's token is refused with the same `token_invalid` as an unknown one; reset revokes all sessions, and a sign-in that races a reset creates no session because it starts only while the verified password hash is unchanged ([registration](../knowledge/specs/accounts.md#registration-and-email-verification)); confirmation and reset tokens also confirm a provisional link and release held join requests, but on a reclaim (a confirmation with a new password from a browser not signed in to the account, or a reset of an unverified account) only through the mailbox owner's explicit keep of each link and request, so whoever holds such a token chooses nothing a tutor will see without that choice ([provisional links and reclaim](../knowledge/specs/accounts.md#provisional-links-and-reclaim)) |
| T-5 | A tutor reaches another tutor's work with a shared student | Relationship-scoped resolution of every identifier, `not_found` outside scope ([ADR-0005](decisions/0005-tutor-centric-domain.md), [relationships](../knowledge/specs/accounts.md#tutorstudent-relationships), [API](../knowledge/specs/api.md)); every scoped route resolves path, query and body identifiers (for example the group filter of the student list) within the caller's relationships before any role or state refusal, so a `409` never confirms that an out-of-scope identifier exists, and the integration denial suite gives every operation with a path identifier a denial case and fails when one is missing ([API](../knowledge/specs/api.md#students-and-groups)); role and email confirmation are checked before the body is read, and the other role gets the unknown-route `404` with the same body and headers ([API](../knowledge/specs/api.md#api-specification)) (residual: response timing, an anonymous `401` against an unknown route's `404`, and a `405` with `Allow` for a wrong method reveal that a route exists, which the published OpenAPI document already does) (pending owner review); the web interface passes path and query group identifiers (the group page address and the student list's group filter) only to the API and renders its `not_found` as "This group is not available." or Not found, showing nothing of the group (pending owner review); from slice 4, frame recipients are decided in the producer's transaction from relationship rows held at least `FOR SHARE`, within relationship scope and never another tutor of the same student; notification rows, their labels and their links are scoped to the recipient and resolved at read time, a link outside the caller's current scope is `null`, `POST /notifications/read` answers `404` for another account's row like a random one, and denial tests connect a second tutor who shares the student and cover the notification routes ([authorization of frames](../knowledge/specs/realtime-and-video.md#authorization-of-frames), [notification routes](../knowledge/specs/notifications.md#notification-routes)) (pending owner review); from slice 5, lessons, rosters, `entity.changed lesson` frames and the notification rows that name lessons are resolved through one visibility query per role within relationship scope [visibility](../knowledge/specs/schedule.md#visibility); a second tutor sharing a student reaches none of the first tutor's lessons, overlap checks read only the tutor's own lessons and never reveal a student's lessons with other tutors, and the denial table covers every lesson route (pending owner review); the lessons on the tutoring pages (a card's next lessons and history, the next lesson on the student and group lists, a group's next lessons, future lesson count and open series) are read only within the card's or the group's own tutor, a card's group lessons only through that card's own membership and its student's roster rows of that tutor's lessons, and `GET /students/{id}/lessons` answers `not_found` for another tutor's card like a random one, also when the tutors share the student ([lessons on the tutoring pages](../knowledge/specs/schedule.md#lessons-on-the-tutoring-pages)) (pending owner review); the tutor's lesson detail carries the lesson's own `relationship_id` or `group_id`, read from the lesson row with the tutor's identifier and bound to that tutor by the lesson's composite foreign keys, so a second tutor sharing the student gets only its own card's identifier and never the first tutor's, while student answers, calendar items and the items on the tutoring pages carry neither ([lesson detail](../knowledge/specs/schedule.md#lesson-detail)) (pending owner review) |
| T-6 | A student reaches another student's submission, or a group they left | Submissions resolved by owner; group access follows current membership ([groups](../knowledge/specs/accounts.md#groups), [pilot scenario 2](../knowledge/design/web/pilot-scenarios.md#scenario-2-group-homework-from-the-library)); a provisional or reclaim-pending student can never join a group, so group chats, group lessons and other students' work stay out of reach before confirmation; a removed, dropped or cleaned-up provisional link is discarded and never reactivated, and its data never passes to another account: the tutor's new card carries only the tutor's own display name, email and notes, and a card without an email never takes the account's email ([provisional links and reclaim](../knowledge/specs/accounts.md#provisional-links-and-reclaim)); from slice 5, a former group member reaches no scheduled lesson of the group and keeps only the lessons whose roster froze while they were a member, shown with their `group.archived` row and their lines in emails under the neutral label "Group lesson", never the group's current name; students never see a group lesson's member list [label table](../knowledge/specs/schedule.md#labels-per-role) (pending owner review) |
| T-7 | A forwarded invitation link is accepted by the wrong person | Email-bound invitations accept only the matching account; single use; 14-day expiry; regeneration revokes ([invitations](../knowledge/specs/accounts.md#invitations)); the card's email binds sign-up and signed-in acceptance, compared after the sign-up normalisation; the link of an ended card is bound to its linked account and refuses every sign-up on its page; every mismatch is counted in one atomic update and the fifth revokes the link, which the card shows (residual: a link holder can revoke a leaked link on purpose, and can test up to four guesses of the bound email before the link is revoked); a link accepted before confirmation is only provisional and the tutor can remove it ([invitations](../knowledge/specs/accounts.md#invitations)); a link revoked after repeated wrong emails, and the revoked link of an ended card, are replaced with a fresh one only by the tutor's deliberate regeneration or send by email, counted against the regeneration limit of 50 per UTC day, and a sent link goes only to the card's own email; an email change on an invited card also issues a fresh link, under its own limit of 50 email changes per UTC day (pending owner review) |
| T-8 | Tutor codes are guessed or spammed | 8 characters from an unambiguous alphabet, per-student throttling, tutor approval of every request, regeneration ([tutor code](../knowledge/specs/accounts.md#tutor-code-and-join-requests)); codes are 8 characters from a 31-character alphabet without 0, 1, I, L and O, matched with case, spaces and hyphens ignored; entries are throttled to 10 per student per hour, held entries included, and a sign-up with a code also uses the per-IP counter of 10 per hour; regeneration is limited to 10 per tutor per UTC calendar day, and refused attempts are not counted (pending owner review); a code works only while its tutor's account is `active` ([tutor code](../knowledge/specs/accounts.md#tutor-code-and-join-requests)); Today shows the tutor their own code, which the browser holds only in the query cache that is cleared when the signed-in account changes, never in storage or the address (pending owner review) |
| T-9 | Answer keys leak to students before release | Separate student schemas, reveal rules on the server, random option identifiers, a contract test ([answer visibility](../knowledge/specs/homework.md#answer-visibility)) |
| T-10 | An uninvited person joins a lesson | Authorization by roster or audience, join window and status; only a tutor join creates a meeting ([join flow](../knowledge/specs/realtime-and-video.md#join-flow)); in slice 5 nobody can join a lesson, because joining arrives with slice 7, and the lesson page is visible only under the [visibility](../knowledge/specs/schedule.md#visibility) rule (pending owner review) |

## Limitations and out of scope

- Uploaded files are not scanned for malware in the MVP; risky kinds (archives, executables) are refused instead.
- The hardening of the BigBlueButton host itself, whether its client loads external assets such as STUN servers (to be checked in the slice 7 probe for residency), and what participants record with their own devices.
- The object-storage bucket policy and the operator's credentials, which are deployment obligations.
- Message logs kept by the SMTP provider (limited to 30 days by the provider choice, which for the pilot's Postbox is a condition still to be confirmed) and raw recording data on the conferencing host after the MVP (deleted with the provider copy, to be confirmed by the recordings probe; in the MVP no recording is made).
- What the browser vendors' push services do with web push metadata beyond delivery, which OVC cannot control; it is bounded by the payload rules and the gate of T-46 (pending owner review).
- Compromise of hosts or the database by an operator.
- Academic integrity: students sharing answers with each other outside OVC.

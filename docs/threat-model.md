The assets OVC protects, the actors who might threaten them, the trust boundaries, and the control that answers each threat, with a link to the specification that defines it. Every change that touches a trust boundary maps itself to the identifiers here and updates this file in the same change ([AGENTS.md](../AGENTS.md#security)).

## Assets

- **Accounts and sessions:** credentials, refresh tokens, email and reset tokens.
- **Personal data** of adults: names, emails, avatars, presence, voices and faces in recordings.
- **A tutor's practice:** student cards and private notes, groups, schedule, library, answer keys.
- **Student work:** answers, files, scores, feedback, corrected files.
- **Conversations:** direct and group chats with attachments.
- **Live lessons:** who can see and hear them, and who can moderate.
- **Platform secrets:** token signing keys, the BigBlueButton shared secret, storage and SMTP credentials.

## Actors

- **Anonymous internet user** without an account.
- **Student** of one tutor reaching another student's work, another tutor's data, or answer keys.
- **Tutor** reaching another tutor's relationships with a shared student.
- **Former participant:** an ended relationship, a removed group member, or a stale or stolen token.
- **Holder of a leaked link:** an invitation, a join link, a playback URL, an unsubscribe link or a tutor code.
- **Forger of provider traffic:** someone who fakes BigBlueButton callbacks.
- **Malicious uploader or author** using files or text against other users.
- **Hostile web page or network peer** reaching a developer's local services.
- **Compromised dependency author or registry** shipping malicious or vulnerable code, images or tools.

## Trust boundaries

1. Browser ↔ API (REST and WebSocket): all client input is untrusted, including identifiers.
2. API ↔ BigBlueButton: only the API creates meetings and join links; callbacks into the API are untrusted until verified.
3. API and worker ↔ object storage: storage keys are internal; browsers reach objects only through short-lived signed URLs issued after authorization.
4. Browser ↔ BigBlueButton: media flows outside OVC; access depends on join links bound to the meeting's create time.
5. Worker ↔ SMTP provider and recipients' mailboxes: email content leaves OVC.
6. Operator ↔ database through `ovc-admin`.
7. Developer machine ↔ local network and browser: local services and test control routes must not be reachable from outside the machine.
8. Repository ↔ supply chain: dependencies, container images and tools enter only pinned; lockfile dependencies are also scanned.
9. Coding agent ↔ repository and developer machine: agents act with the developer's shell; their configuration and the verification policy decide what they may run and what review a change gets.

## Threats and controls

| ID | Threat | Controls |
|---|---|---|
| T-1 | Credential stuffing and brute-force sign-in | Argon2id with the OWASP parameters and a bounded hashing limiter, per-email and per-IP throttling reserved atomically before any hashing (the per-IP slot first, so requests already over that limit add no per-email rows), generic failure messages ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). Residual risk: anyone who knows an email can keep it throttled with five wrong attempts every 15 minutes, so its owner gets `429` even with the right password until the window ends |
| T-2 | Stolen or replayed refresh token | Rotation by compare-and-swap, reuse detection revoking the session, sign out everywhere, `HttpOnly` cookie, an absolute 30-day expiry; the cookie carries a MAC over its session and generation, so only a cookie the server issued can trigger reuse detection and a forged stale cookie cannot sign anyone out ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). The frontend serialises refreshes across the tabs of one browser with the Web Locks API, so a waiting tab sends the already-rotated cookie; a Playwright test reloads two tabs at once and requires the session to survive, and fails when the lock is removed. Sign out everywhere ends the tab that asks at once; other tabs and browsers end at their next request, because every request is checked against the revoked session, and a Playwright test proves another browser's session ends. Residual risk: a refresh whose response is lost after rotation, including one aborted by a reload or a closed tab while it is in flight, leaves the browser with the old cookie, and its next refresh counts as reuse and signs that browser out |
| T-3 | Account enumeration through sign-up, sign-in, reset or invitation pages | Sign-in answers `invalid_credentials` alike for an unknown email, a wrong password and a deleted account, verifies a placeholder hash for an unknown email and reveals a block only after the correct password (residual: after the hashing parameters change, accounts not yet rehashed verify at the old cost while unknown emails verify at the new one, so timing can tell them apart until those accounts sign in once); `202` with no session for every sign-up, with the same body and headers for a new and a taken email and a password hashed in both cases; identical `202` answers from forgot and the public resend for any email, with per-account sending limits counted per email and silent on those routes and on sign-up, which creates the account and answers `202` even over a limit (residual: a known email adds two small inserts to the same transaction, a timing difference far below network noise and slowed by the per-IP limit; and whoever signs up with a free email can sign in to the new unverified account with the password they chose, while for a taken email they cannot, which the 7-day cleanup and the per-IP limit bound but do not remove), invitation pages that always offer both paths, notice to the existing owner, card-creation limits per tutor ([registration](../knowledge/specs/accounts.md#registration-and-email-verification), [invitations](../knowledge/specs/accounts.md#invitations)); the forgot-password page shows the same "if an account exists" message for every email, and the sign-up page always continues to "Check your email" |
| T-4 | Theft or reuse of confirmation and reset tokens | Minted by the worker only when the email is sent, 32 random bytes stored only as a hash and never in an outbox payload; single-use through one conditional update under the account's row lock; 24 hours for confirmation and 1 hour for reset; invalidated by a newer email of the same purpose and by confirmation, reset and an active account's password change, which also drop queued emails that have not been sent; minted under the account's row lock after checking its state again, so a change that commits first is never undone by a later mint; bound to the account state, so a blocked or deleted account's token is refused with the same `token_invalid` as an unknown one; reset revokes all sessions, and a sign-in that races a reset creates no session because it starts only while the verified password hash is unchanged ([registration](../knowledge/specs/accounts.md#registration-and-email-verification)) |
| T-5 | A tutor reaches another tutor's work with a shared student | Relationship-scoped resolution of every identifier, `not_found` outside scope ([ADR-0005](decisions/0005-tutor-centric-domain.md), [relationships](../knowledge/specs/accounts.md#tutorstudent-relationships), [API](../knowledge/specs/api.md)) |
| T-6 | A student reaches another student's submission, or a group they left | Submissions resolved by owner; group access follows current membership ([groups](../knowledge/specs/accounts.md#groups), [pilot scenario 2](../knowledge/design/web/pilot-scenarios.md#scenario-2-group-homework-from-the-library)) |
| T-7 | A forwarded invitation link is accepted by the wrong person | Email-bound invitations accept only the matching account; single use; 14-day expiry; regeneration revokes ([invitations](../knowledge/specs/accounts.md#invitations)) |
| T-8 | Tutor codes are guessed or spammed | 8 characters from an unambiguous alphabet, per-student throttling, tutor approval of every request, regeneration ([tutor code](../knowledge/specs/accounts.md#tutor-code-and-join-requests)) |
| T-9 | Answer keys leak to students before release | Separate student schemas, reveal rules on the server, random option identifiers, a contract test ([answer visibility](../knowledge/specs/homework.md#answer-visibility)) |
| T-10 | An uninvited person joins a lesson | Authorization by roster or audience, join window and status; only a tutor join creates a meeting ([join flow](../knowledge/specs/realtime-and-video.md#join-flow)) |
| T-11 | Recordings exposed through public playback links | Media copied into OVC storage and served only after authorization through 5-minute signed URLs; provider copies deleted after copying, on deletion in any state and after holds expire; the conferencing host serves playback paths to the worker only ([recordings](../knowledge/specs/realtime-and-video.md#recordings)) |
| T-12 | Forged recording-ready or meeting-ended callbacks | Recording-ready accepted only with an `HS256` JWT signed by the shared secret whose `meeting_id` matches the routing key's meeting; the unsigned meeting-ended hint is confirmed with the provider, never ends a lesson, and its `recordingmarks` never settles reconciliation; idempotent upserts ([callbacks](../knowledge/specs/realtime-and-video.md#callbacks)) |
| T-13 | Malicious uploads: oversized files, disguised types, path traversal | Streaming size limits, content-based type allowlists, random keys, no archives or executables, `nosniff`; avatars are read up to 5 MB, checked by magic bytes, extension and decoded format, limited to 4096 × 4096 pixels before decoding, decoded and encoded again so no metadata or appended data survives, stored under 32 random bytes with a fixed file name, limited to 3 pending (checked again under the user's row lock) and 20 per hour per user, and refused when 16-bit or CMYK ([files](../knowledge/specs/files.md#contexts-and-limits), [avatars](../knowledge/specs/files.md#avatars)); the profile page's file filter and size check are conveniences, the server's detection is the control, its refusal is shown inline, and a Playwright test proves a file that is not an image is refused |
| T-14 | Script injection through messages, names, file names, prompts or feedback | Chat as plain text; one sanitising restricted-Markdown renderer; no raw HTML ([restricted Markdown](../knowledge/specs/homework.md#restricted-markdown)) |
| T-15 | Cross-site request forgery against the refresh cookie | `__Host-` cookie with `SameSite=Strict`, exact `Origin` equality on the refresh route (a same-site subdomain does not qualify), refresh is the only cookie-authenticated route, and sign-in, which sets the cookie, requires the same exact `Origin` and a JSON content type ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)) |
| T-16 | Clickjacking of OVC pages | OVC pages send `frame-ancestors 'none'` ([API conventions](../knowledge/specs/api.md#conventions)); only the BigBlueButton subdomain admits framing, and only by the OVC origin ([embedding](../knowledge/specs/realtime-and-video.md#embedding)). The page headers are defined once in `frontend/security-headers.ts`, sent by the preview server and asserted by the Playwright smoke; the production reverse proxy must reproduce them ([frontend checks](development.md#frontend-checks)) |
| T-17 | Unsubscribe or email links used to act as the user | Unsubscribe tokens change one preference and never sign in; email links point only to OVC pages ([preferences](../knowledge/specs/notifications.md#preferences-and-unsubscribe)) |
| T-18 | Personal data leaks to logs, emails, the provider or foreign services | Safe-content rules, digest without message text, participant data limited to display names, all processors in Russia ([observability](../knowledge/specs/observability.md#safe-content), [email](../knowledge/specs/notifications.md#email), [ADR-0008](decisions/0008-hosting-and-data-residency.md)); diagnostics and start-up messages never carry the text of library errors, panic values, SQL or query arguments (only stable kinds and OVC's own settings and refusal messages), rate-limit subjects are HMAC-SHA-256 values keyed from `OVC_JWT_SECRET` through HKDF, so no email or IP address is stored in counters, and sign-in records carry the user identifier and a reason, never an email; access records carry route templates or `unmatched` instead of paths ([observability](../knowledge/specs/observability.md#safe-content)); `X-Request-ID` values are accepted only in a safe form ([API conventions](../knowledge/specs/api.md#conventions)); request records name the authenticated account only by its UUID and role, bound after authentication succeeds, so a refused token adds nothing ([correlation](../knowledge/specs/observability.md#correlation)) |
| T-19 | Secret disclosure, including through agent tooling | Settings from the environment; environment files and keys ignored by Git, denied to agent file tools and refused by the `guard_secrets.py` hook for file tools and shell commands (heredoc bodies count as data unless they are fed to a shell or an interpreter, or expand variables); the same hook refuses the common forms of shell commands that print the environment or interpolated container credentials, checked by `check_guard_secrets.py`; until hosting exists, agents run local commands with the owner's development settings only through `tools/dev-env.sh` ([ADR-0009](decisions/0009-owner-approved-exceptions-and-visibility.md), item 7), which loads the root `.env` and `backend/.env` into one command without printing them, accepts only `OVC_` keys, turns shell tracing off and refuses to start the common environment printers; the hook unwraps it, including when it runs as a shell script or is sourced, and refuses the common traced-shell forms around or inside it, so the common printing forms are refused through it too; checked by `tools/check-dev-env.sh` and `check_guard_secrets.py`. Residual risk: every command run through the wrapper holds those settings, and a program that prints its own environment is not recognised, so the files hold development values only and real provider secrets stay in `backend/.env.local`, which the wrapper never loads. Residual risk: the hook matches command text, so it guards against accidental disclosure, not against a determined agent; the forms it does not recognise are listed in [AI development verification](../knowledge/reviews/ai-development-setup.md#minimal-inventory); secrets absent from diagnostics and `meta_*` values, and secret settings held in a type that redacts itself in every format, log and JSON encoding, inside a function value, which formatting prints only as an address, so no format verb can print it even through a struct that holds it in an unexported field; a database URL whose user name or password is not percent-encoded is refused, so it cannot be misparsed into a logged host or database name, and the processes refuse the driver's own `PG*` environment variables so no credential bypasses the settings, while the integration-test fixture still reads them and the driver defaults, its host checked like any other; the fixture prints only error kinds and the names of the databases it creates, never driver error text (the driver still reads `~/.pgpass`, `~/.pg_service.conf` or another service file when the URL names a service, and the client certificate, key and root certificate files under `~/.postgresql/` from the process user's home directory) ([ADR-0004](decisions/0004-bigbluebutton-primary-provider.md)); local development credentials are required Compose variables with no defaults, and Gitleaks scans history and staged changes with redaction but never the working directory ([security scanning](development.md#security-scanning)); the storage keys are `Secret` settings, the S3 client is built from them alone and never takes credentials, an endpoint or a region from `AWS_*` variables, shared AWS files or instance metadata (depguard bans the packages that would; the SDK still reads a few `AWS_*` variables for its user agent and retry defaults), ignores proxy variables, and the integration and end-to-end tests take the local server's keys only through `tools/dev-env.sh`; Playwright traces are kept only for failed tests in the ignored `frontend/test-results/`, hold only generated test accounts and are never shared, and the per-run preview certificate's private key stays in that ignored folder |
| T-20 | Resource exhaustion through connections, uploads, messages or emails | WebSocket authentication timeout, inbound frame limits, bounded outbound queues and ping timeout ([connection](../knowledge/specs/realtime-and-video.md#connection)); message rate limits and a daily per-student chat attachment cap, with the tutor able to delete attachments in their channels ([messages](../knowledge/specs/realtime-and-video.md#messages)); upload concurrency, limits and quotas ([upload flow](../knowledge/specs/files.md#upload-flow)); bounded pagination; digest frequency limits. Per-IP limits use the client address set by OVC's own reverse proxy, never a client-supplied header; the HTTP server's header timeout, idle timeout, header size limit and per-request read and write deadlines, the 1 MiB JSON body limit on every operation, and a readiness ping bounded to 1 s and shared by concurrent requests, so readiness floods hold at most one database connection; database connections time out after 5 s unless the URL sets its own timeout ([API conventions](../knowledge/specs/api.md#conventions)); password hashing runs at most `GOMAXPROCS` Argon2id hashes at once and answers `503` after waiting 5 s for a slot; the client address for per-IP limits is the TCP peer, or, only when the peer is inside `OVC_TRUSTED_PROXY_CIDRS`, the right-most `X-Forwarded-For` entry outside those ranges, and the settings refuse `0.0.0.0/0` and `::/0`; avatar uploads are bounded per user and per instance, and their decoding shares a 256 MiB budget per instance with at most one decode per user, charged by pixels and format, with a fixed allowance for WebP's lossless tables (residual: a slow upload holds one of the 32 instance upload slots for up to its 60-second read deadline, so a few accounts can keep uploads busy, though nothing else) ([avatars](../knowledge/specs/files.md#avatars)); transport deadlines always use the system clock, never the shared test clock ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). Deployment obligation: OVC's reverse proxy must append the client address to `X-Forwarded-For` or overwrite the header; a proxy that passes a client's header through lets the client choose its own per-IP bucket, and a proxy that writes entries OVC cannot parse (with ports or brackets) puts every client behind it into the proxy's own bucket |
| T-21 | A removed participant keeps access | Ending a relationship and removing a group member update channel membership, future audiences and writability in one transaction; message edits and deletes require current membership; the [join rule](../knowledge/specs/schedule.md#join-rule) refuses their further joins, including to live lessons. Residual risk: someone already connected or holding an earlier link stays until the meeting ends; the tutor's "Restart the room" cuts them off ([ending a relationship](../knowledge/specs/accounts.md#ending-a-relationship), [join flow](../knowledge/specs/realtime-and-video.md#join-flow)) |
| T-22 | Operator misuse | `ovc-admin` actions are audited with the operator's system user name and numeric identifier, the subcommand, the target account identifier and the outcome, never the email; refusals and failures, including failures before the command runs, are audited too; operators use personal system accounts; the command needs only database and logging settings and has no network listener; there is no operator HTTP surface (residual: the audit record goes to the command's standard error, which an operator holding the database credentials can discard; blocked accounts are never purged automatically, so removing a blocked squatter is the operator's decision, and each unblock into `unverified` restarts its 7-day clock) ([administration command](../knowledge/specs/accounts.md#administration-command)) |
| T-23 | Email squatting: someone signs up with another person's email, directly or through a forwarded invitation link; acceptance races | Only an emailed invitation confirms an email on sign-up; other sign-ups stay unverified and are removed after 7 days; confirming from a browser without that account's session (including one signed in to another account) requires setting a new password and revokes every session, so the mailbox owner takes the account; the confirmation route checks the exact `Origin` because it can set the refresh cookie; a password change on an unverified account keeps the emailed links, so the squatter cannot cancel them (residual: the squatter's name and language stay on the account until the owner edits them); a password reset confirms the email; invitations are reserved and consumed atomically ([registration](../knowledge/specs/accounts.md#registration-and-email-verification), [invitations](../knowledge/specs/accounts.md#invitations)); in a browser signed in to another account, the confirmation page names that account, warns that confirming switches accounts, and signs it out before sending the new password, so its server session is revoked; a refreshed token is checked against the account the tab shows before the tab uses it, so a token for a different account ends that tab's session, which a Playwright test proves with two tabs; a failed check leaves the token unused and fails the request that needed it. Residual: when another tab has already replaced the refresh cookie, the sign-out before confirming cannot revoke the first account's server session, which then has no cookie left |
| T-24 | Same-site attacks from the conferencing subdomain: refresh forgery, cookie tossing | Exact-origin refresh and sign-in checks (the origin is `OVC_PUBLIC_URL` normalised to lower case without a default port), `__Host-` cookie that subdomains cannot overwrite, conferencing origin excluded from CORS ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). Until a separate frontend origin needs it, no CORS is configured at all: the development and preview servers proxy `/api` so the browser sees one origin, and their own CORS handling is turned off in `vite.config.ts`; the smoke asserts its absence on the preview server ([frontend checks](development.md#frontend-checks)) |
| T-25 | A leaked join link, especially a moderator link, is reused during the meeting | Links only in `POST` bodies, never stored or logged by OVC or kept by the client, bound to one meeting's create time; the slice 7 probe evaluates session-token joins. Residual risk: the link appears in the conferencing host's access logs and in new-tab history until that meeting ends ([join flow](../knowledge/specs/realtime-and-video.md#join-flow)) |
| T-26 | Callback routing keys read from `meta_*` values | Routing keys are not secrets; only the JWT authenticates recording-ready, and meeting-ended is confirmed with the provider ([callbacks](../knowledge/specs/realtime-and-video.md#callbacks)) |
| T-27 | Tokens leak through `Referer`, browser history or access logs | One rule for every token page (invitation, confirmation, reset, unsubscribe): `Referrer-Policy: no-referrer`, token removed from the address bar after reading, no third-party loads; token segments redacted in proxy logs ([token pages](../knowledge/design/web/navigation.md#token-pages), [observability](../knowledge/specs/observability.md#safe-content)). The confirmation and reset pages read the token once, remove it from the address with a router replace before sending it, and send it only in the request body; a component test proves the address no longer carries it. Residual: `replaceState` does not remove the visited token URL from the browser's own history list, so someone with the device can see a recently opened link until it expires or is used, and the token pages go live before the production proxy redacts its logs in slice 10; the token also stays in the address bar until the start-up session has loaded, which the refresh and account-check timeouts bound, including those of another tab holding the refresh lock, and while the server is unreachable |
| T-28 | Open redirect through the `next` parameter | Only a path starting with a single `/` (not `//` or `/\`) and without control characters, resolved with the URL parser and compared to the OVC origin; the client navigates to the parsed path, query and fragment, never the raw value, and honours `next` only on the sign-in address ([navigation rules](../knowledge/design/web/navigation.md#rules)). A unit test covers protocol-relative, backslash, absolute, `javascript:`, tab and newline values, and a Playwright test signs in with a foreign `next` and lands on Today |
| T-29 | Stale WebSocket access after logout, blocking, ending or removal | Session and account checks on every frame, membership resolved at publish time, sockets closed on revocation ([connection](../knowledge/specs/realtime-and-video.md#connection)) |
| T-30 | Inferring the answer key from scores | Students never receive points, totals or scores; explanations carry no files; a contract test checks every student surface ([answer visibility](../knowledge/specs/homework.md#answer-visibility)) |
| T-31 | Email abuse: invitation spam or phishing relay, mail bombing through resets or sign-ups, header or body injection | Smaller invitation budget for new tutors, per-recipient daily invitation caps, per-account confirmation and reset caps (1 per minute, 5 per hour, 10 per day, counted together), one per-IP counter of 10 sign-up, reset and resend requests per hour, one duplicate-sign-up notice per day; account emails carry no user-written text and link only to `OVC_PUBLIC_URL`; user text HTML-escaped in email bodies and CR/LF-stripped and encoded in headers; the mail adapter composes every message itself, refuses a recipient that is not one plain address and a malformed message identifier, and the SMTP connection uses STARTTLS or implicit TLS with TLS 1.2 or newer and a verified certificate. Residual risk: anyone who knows an email can spend its owner's daily confirmation and reset budget, delaying a genuine reset until the next day ([registration](../knowledge/specs/accounts.md#registration-and-email-verification), [invitations](../knowledge/specs/accounts.md#invitations), [email](../knowledge/specs/notifications.md#email)) |
| T-32 | Unsubscribe tokens used beyond their purpose | Dedicated signing key, purpose, group and 90-day expiry claims, never signs in, nothing changes on `GET` ([preferences](../knowledge/specs/notifications.md#preferences-and-unsubscribe)) |
| T-33 | Harassment through repeated join requests | Code-entry throttling, per-tutor cap on pending requests, decline and block ([tutor code](../knowledge/specs/accounts.md#tutor-code-and-join-requests)) |
| T-34 | Personal data retained after deletion | Deletion revokes every session and discards pending email requests and tokens at once; slice 2 purges the account's own rows and uploads 30 days later (an unverified account at once when its owner deletes it, and 7 days after sign-up when never confirmed), each object deleted through an outbox row that carries its key, so no object outlives its row (residual: if the database fails at the moment an upload is settled after its account was purged, that one object stays in storage unreferenced); message bodies erased at purge, tutor purge covers cards and notes, recordings bounded by retention, backups retained 30 days, conferencing host logs retained 14 days ([account deletion](../knowledge/specs/accounts.md#account-deletion), [ADR-0008](decisions/0008-hosting-and-data-residency.md)); the account settings page asks for the password in a dialog that names the consequence and starts empty each time it opens, ends the tab that asks at once while other tabs end at their next request, and a Playwright test proves the account no longer signs in |
| T-36 | The end-to-end test control surface (clock, worker, mail sink) reachable in a real deployment | Routes and fakes exist only with `OVC_TEST_CONTROL=1`, and the clock and tick routes only with `OVC_CLOCK=test` as well; the processes refuse `OVC_TEST_CONTROL=1` unless the meeting provider is fake, mail is the sink and the database is a test or development database; the worker also refuses the database mail sink, which stores emails with their links, unless the database passes the same local host and name checks, and a process test proves it for a production database name; a test proves the routes are absent without it ([test harness](development.md#end-to-end-test-harness)); the refusal also requires a loopback listen address and loopback database hosts, checks the configured database name before connecting and the actual database name after, and refuses the test clock without the flag; the control routes accept only JSON from a loopback `Host` ([test harness](development.md#end-to-end-test-harness)). The integration-test fixture applies the same loopback host check to `OVC_TEST_DATABASE_ADMIN_URL`, including hosts from `PG*` variables and service files, before it connects. Residual risk: a loopback port forward, SSH tunnel or forwarded Unix socket to a remote server passes the host check, so only the database-name rule protects such a database from the processes; the fixture has no name rule, but it only creates, migrates and drops randomly named databases of its own, and refuses a pool that reaches any other database; the end-to-end deployments run with test control only on loopback ports, a database named `*_test` and the fake provider and mail sink, and serve the preview over HTTPS with a self-signed certificate created for each run, accepted only by the Playwright browsers and never installed into a trust store |
| T-37 | Script injection that steals the access token | Access token held in memory only, never in Web Storage; Content Security Policy with `script-src 'self'`, `object-src 'none'`, `base-uri 'none'`, and `connect-src`, `img-src` and `media-src` limited to the OVC origin and the storage host ([API conventions](../knowledge/specs/api.md#conventions), [sessions](../knowledge/specs/accounts.md#sessions-and-passwords)). ## Limitations and out of scope

- Uploaded files are not scanned for malware in the MVP; risky kinds (archives, executables) are refused instead.
- The hardening of the BigBlueButton host itself, whether its client loads external assets such as STUN servers (to be checked in the slice 7 probe for residency), and what participants record with their own devices.
- The object-storage bucket policy and the operator's credentials, which are deployment obligations.
- Message logs kept by the SMTP provider (limited to 30 days by the provider choice) and raw recording data on the conferencing host (deleted with the provider copy, to be confirmed by the slice 7 probe).
- Compromise of hosts or the database by an operator.
- Academic integrity: students sharing answers with each other outside OVC.

The assets OVC protects, the actors who might threaten them, the trust boundaries, and the control that answers each threat, with a link to the specification that defines it. Every change that touches a trust boundary maps itself to the identifiers here and updates this file in the same change ([AGENTS.md](../AGENTS.md#security)).

## Assets

- **Accounts and sessions:** credentials, refresh tokens, email and reset tokens.
- **Personal data** of adults: names, emails, avatars, presence, voices and faces in recordings.
- **A tutor's practice:** student cards and private notes, groups, schedule, library, answer keys.
- **Student work:** answers, files, scores, feedback, corrected files.
- **Conversations:** direct and group chats with attachments.
- **Live lessons:** who can see and hear them, and who can moderate.
- **Platform secrets:** token signing keys, the BigBlueButton shared secret, storage and SMTP credentials.

## Actors

- **Anonymous internet user** without an account.
- **Student** of one tutor reaching another student's work, another tutor's data, or answer keys.
- **Tutor** reaching another tutor's relationships with a shared student.
- **Former participant:** an ended relationship, a removed group member, or a stale or stolen token.
- **Holder of a leaked link:** an invitation, a join link, a playback URL, an unsubscribe link or a tutor code.
- **Forger of provider traffic:** someone who fakes BigBlueButton callbacks.
- **Malicious uploader or author** using files or text against other users.
- **Hostile web page or network peer** reaching a developer's local services.
- **Compromised dependency author or registry** shipping malicious or vulnerable code, images or tools.

## Trust boundaries

1. Browser ↔ API (REST and WebSocket): all client input is untrusted, including identifiers.
2. API ↔ BigBlueButton: only the API creates meetings and join links; callbacks into the API are untrusted until verified.
3. API and worker ↔ object storage: storage keys are internal; browsers reach objects only through short-lived signed URLs issued after authorization.
4. Browser ↔ BigBlueButton: media flows outside OVC; access depends on join links bound to the meeting's create time.
5. Worker ↔ SMTP provider and recipients' mailboxes: email content leaves OVC, and in the pilot bounce and complaint events come back through the provider's Data Streams stream.
6. Operator ↔ database through `ovc-admin`.
7. Developer machine ↔ local network and browser: local services and test control routes must not be reachable from outside the machine.
8. Repository ↔ supply chain: dependencies, container images and tools enter only pinned; lockfile dependencies are also scanned.
9. Coding agent ↔ repository and developer machine: agents act with the developer's shell; their configuration and the verification policy decide what they may run and what review a change gets.

## Threats and controls

| ID | Threat | Controls |
|---|---|---|
| T-1 | Credential stuffing and brute-force sign-in | Argon2id with the OWASP parameters and a bounded hashing limiter, per-email and per-IP throttling reserved atomically before any hashing (the per-IP slot first, so requests already over that limit add no per-email rows), generic failure messages ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). Residual risk: anyone who knows an email can keep it throttled with five wrong attempts every 15 minutes, so its owner gets `429` even with the right password until the window ends; an attempt refused by a limit returns its reserved slots, so many correct sign-ins in flight from one address cannot lock it out; the current-password check on change and deletion has its own per-account counter with the same numbers, so a stolen access token adds five guesses per 15 minutes to the sign-in budget (residual) |
| T-2 | Stolen or replayed refresh token | Rotation by compare-and-swap, reuse detection revoking the session, sign out everywhere, `HttpOnly` cookie, an absolute 30-day expiry; the cookie carries a MAC over its session and generation, so only a cookie the server issued can trigger reuse detection and a forged stale cookie cannot sign anyone out ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). The frontend serialises refreshes across the tabs of one browser with the Web Locks API, so a waiting tab sends the already-rotated cookie; a Playwright test reloads two tabs at once and requires the session to survive, and fails when the lock is removed. Sign out everywhere ends the tab that asks at once; other tabs and browsers end at their next request, because every request is checked against the revoked session, and a Playwright test proves another browser's session ends. Residual risk: a refresh whose response is lost after rotation, including one aborted by a reload or a closed tab while it is in flight, leaves the browser with the old cookie, and its next refresh counts as reuse and signs that browser out |
| T-3 | Account enumeration through sign-up, sign-in, reset or invitation pages | Sign-in answers `invalid_credentials` alike for an unknown email, a wrong password and a deleted account, verifies a placeholder hash for an unknown email and reveals a block only after the correct password (residual: after the hashing parameters change, accounts not yet rehashed verify at the old cost while unknown emails verify at the new one, so timing can tell them apart until those accounts sign in once); `202` with no session for every sign-up, with the same body and headers for a new and a taken email and a password hashed in both cases; identical `202` answers from forgot and the public resend for any email, with per-account sending limits counted per email and silent on those routes and on sign-up, which creates the account and answers `202` even over a limit (residual: a known email adds two small inserts to the same transaction, a timing difference far below network noise and slowed by the per-IP limit; and whoever signs up with a free email can sign in to the new unverified account with the password they chose, while for a taken email they cannot, which the 7-day cleanup and the per-IP limit bound but do not remove), invitation pages that always offer both paths, notice to the existing owner, card-creation limits per tutor ([registration](../knowledge/specs/accounts.md#registration-and-email-verification), [invitations](../knowledge/specs/accounts.md#invitations)); the forgot-password page shows the same "if an account exists" message for every email, and the sign-up page always continues to "Check your email"; residual: sign-up does more database work for a new email (the account, its profile, the sending-limit counters, the request and the outbox row in one transaction) than for a taken one (a lookup and the notice), so timing can hint whether an email is registered; since [ADR-0014](decisions/0014-students-join-through-their-tutor.md), sign-up on an invitation page answers the same `202 {}` with no session for a new and a taken email, with the password hashed in both cases, and leaves the invitation usable after a taken-email answer (a link holder who tries a taken email and later sees the link still valid learns nothing new, because the page offers sign-in either way); the page then signs in automatically with the chosen password and otherwise shows "Check your email, or sign in to accept" (residual: that the automatic sign-in works only for a new account, and that the tutor's card then shows "Email not confirmed", are the same kind of signal as ordinary sign-up followed by sign-in); a student sign-up with a code checks the code behind the per-IP request slot and before hashing, so an invalid code costs a slot and says nothing about the email ([invitations](../knowledge/specs/accounts.md#invitations), [registration](../knowledge/specs/accounts.md#registration-and-email-verification)) |
| T-4 | Theft or reuse of confirmation and reset tokens | Minted by the worker only when the email is sent, 32 random bytes stored only as a hash and never in an outbox payload; single-use through one conditional update under the account's row lock; 24 hours for confirmation and 1 hour for reset; invalidated by a newer email of the same purpose and by confirmation, reset and an active account's password change, which also drop queued emails that have not been sent; minted under the account's row lock after checking its state again, so a change that commits first is never undone by a later mint; bound to the account state, so a blocked or deleted account's token is refused with the same `token_invalid` as an unknown one; reset revokes all sessions, and a sign-in that races a reset creates no session because it starts only while the verified password hash is unchanged ([registration](../knowledge/specs/accounts.md#registration-and-email-verification)); confirmation and reset tokens also confirm a provisional link and release held join requests, but on a reclaim (a confirmation with a new password from a browser not signed in to the account, or a reset of an unverified account) only through the mailbox owner's explicit keep of each link and request, so whoever holds such a token chooses nothing a tutor will see without that choice ([provisional links and reclaim](../knowledge/specs/accounts.md#provisional-links-and-reclaim)) |
| T-5 | A tutor reaches another tutor's work with a shared student | Relationship-scoped resolution of every identifier, `not_found` outside scope ([ADR-0005](decisions/0005-tutor-centric-domain.md), [relationships](../knowledge/specs/accounts.md#tutorstudent-relationships), [API](../knowledge/specs/api.md)); every scoped route resolves path and body identifiers within the caller's relationships before any role or state refusal, so a `409` never confirms that an out-of-scope identifier exists, and the integration denial suite gives every operation with a path identifier a denial case and fails when one is missing ([API](../knowledge/specs/api.md#students-and-groups)); role and email confirmation are checked before the body is read, and the other role gets the unknown-route `404` with the same body and headers ([API](../knowledge/specs/api.md#api-specification)) (residual: response timing, an anonymous `401` against an unknown route's `404`, and a `405` with `Allow` for a wrong method reveal that a route exists, which the published OpenAPI document already does) (pending owner review) |
| T-6 | A student reaches another student's submission, or a group they left | Submissions resolved by owner; group access follows current membership ([groups](../knowledge/specs/accounts.md#groups), [pilot scenario 2](../knowledge/design/web/pilot-scenarios.md#scenario-2-group-homework-from-the-library)); a provisional or reclaim-pending student can never join a group, so group chats, group lessons and other students' work stay out of reach before confirmation; a removed, dropped or cleaned-up provisional link is discarded and never reactivated, and its data never passes to another account: the tutor's new card carries only the tutor's own display name, email and notes, and a card without an email never takes the account's email ([provisional links and reclaim](../knowledge/specs/accounts.md#provisional-links-and-reclaim)) |
| T-7 | A forwarded invitation link is accepted by the wrong person | Email-bound invitations accept only the matching account; single use; 14-day expiry; regeneration revokes ([invitations](../knowledge/specs/accounts.md#invitations)); the card's email binds sign-up and signed-in acceptance, compared after the sign-up normalisation; the link of an ended card is bound to its linked account and refuses every sign-up on its page; every mismatch is counted in one atomic update and the fifth revokes the link, which the card shows (residual: a link holder can revoke a leaked link on purpose, and can test up to four guesses of the bound email before the link is revoked); a link accepted before confirmation is only provisional and the tutor can remove it ([invitations](../knowledge/specs/accounts.md#invitations)); a link revoked after repeated wrong emails, and the revoked link of an ended card, are replaced with a fresh one only by the tutor's deliberate regeneration or send by email, counted against the regeneration limit of 50 per UTC day, and a sent link goes only to the card's own email; an email change on an invited card also issues a fresh link, under its own limit of 50 email changes per UTC day (pending owner review) |
| T-8 | Tutor codes are guessed or spammed | 8 characters from an unambiguous alphabet, per-student throttling, tutor approval of every request, regeneration ([tutor code](../knowledge/specs/accounts.md#tutor-code-and-join-requests)); codes are 8 characters from a 31-character alphabet without 0, 1, I, L and O, matched with case, spaces and hyphens ignored; entries are throttled to 10 per student per hour, held entries included, and a sign-up with a code also uses the per-IP counter of 10 per hour; regeneration is limited to 10 per tutor per UTC calendar day, and refused attempts are not counted (pending owner review); a code works only while its tutor's account is `active` ([tutor code](../knowledge/specs/accounts.md#tutor-code-and-join-requests)) |
| T-9 | Answer keys leak to students before release | Separate student schemas, reveal rules on the server, random option identifiers, a contract test ([answer visibility](../knowledge/specs/homework.md#answer-visibility)) |
| T-10 | An uninvited person joins a lesson | Authorization by roster or audience, join window and status; only a tutor join creates a meeting ([join flow](../knowledge/specs/realtime-and-video.md#join-flow)) |
| T-11 | Recordings exposed through public playback links | Media copied into OVC storage and served only after authorization through 5-minute signed URLs; provider copies deleted after copying, on deletion in any state and after holds expire; the conferencing host serves playback paths to the worker only ([recordings](../knowledge/specs/realtime-and-video.md#recordings)); until recordings land after the MVP, rooms are created with the MVP settings in [video](../knowledge/specs/realtime-and-video.md#video) (`record=false`, `autoStartRecording=false`, `allowStartStopRecording=false`, no recording-ready URL), the recording-ready callback route is not registered, and the host disables recording by default and keeps no meeting events, so the provider holds no recordings or raw meeting data |
| T-12 | Forged recording-ready or meeting-ended callbacks | Recording-ready accepted only with an `HS256` JWT signed by the shared secret whose `meeting_id` matches the routing key's meeting; the unsigned meeting-ended hint is confirmed with the provider, never ends a lesson, and its `recordingmarks` never settles reconciliation; idempotent upserts ([callbacks](../knowledge/specs/realtime-and-video.md#callbacks)); until recordings land after the MVP, rooms are created with the MVP settings in [video](../knowledge/specs/realtime-and-video.md#video) (`record=false`, `autoStartRecording=false`, `allowStartStopRecording=false`, no recording-ready URL), the recording-ready callback route is not registered, and the host disables recording by default and keeps no meeting events, so the provider holds no recordings or raw meeting data |
| T-13 | Malicious uploads: oversized files, disguised types, path traversal | Streaming size limits, content-based type allowlists, random keys, no archives or executables, `nosniff`; avatars are read up to 5 MB, checked by magic bytes, extension and decoded format, limited to 4096 × 4096 pixels before decoding, decoded and encoded again so no metadata or appended data survives, stored under 32 random bytes with a fixed file name, limited to 3 pending (checked again under the user's row lock) and 20 per hour per user, and refused when 16-bit or CMYK ([files](../knowledge/specs/files.md#contexts-and-limits), [avatars](../knowledge/specs/files.md#avatars)); the profile page's file filter and size check are conveniences, the server's detection is the control, its refusal is shown inline, and a Playwright test proves a file that is not an image is refused |
| T-14 | Script injection through messages, names, file names, prompts or feedback | Chat as plain text; one sanitising restricted-Markdown renderer; no raw HTML ([restricted Markdown](../knowledge/specs/homework.md#restricted-markdown)) |
| T-15 | Cross-site request forgery against the refresh cookie | `__Host-` cookie with `SameSite=Strict`, exact `Origin` equality on the refresh route (a same-site subdomain does not qualify), refresh is the only cookie-authenticated route, and sign-in, which sets the cookie, requires the same exact `Origin` and a JSON content type ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)) |
| T-16 | Clickjacking of OVC pages | OVC pages send `frame-ancestors 'none'` ([API conventions](../knowledge/specs/api.md#conventions)); only the BigBlueButton subdomain admits framing, and only by the OVC origin ([embedding](../knowledge/specs/realtime-and-video.md#embedding)). The page headers are defined once in `frontend/security-headers.ts`, sent by the preview server and asserted by the Playwright smoke; the production reverse proxy must reproduce them ([frontend checks](development.md#frontend-checks)) |
| T-17 | Unsubscribe or email links used to act as the user | Unsubscribe tokens change one preference and never sign in; email links point only to OVC pages ([preferences](../knowledge/specs/notifications.md#preferences-and-unsubscribe)) |
| T-18 | Personal data leaks to logs, emails, the provider or foreign services | Safe-content rules, digest without message text, participant data limited to display names, all processors in Russia ([observability](../knowledge/specs/observability.md#safe-content), [email](../knowledge/specs/notifications.md#email), [ADR-0008](decisions/0008-hosting-and-data-residency.md)); diagnostics and start-up messages never carry the text of library errors, panic values, SQL or query arguments (only stable kinds and OVC's own settings and refusal messages), rate-limit subjects are HMAC-SHA-256 values keyed from `OVC_JWT_SECRET` through HKDF, so no email or IP address is stored in counters, and sign-in records carry the user identifier and a reason, never an email; access records carry route templates or `unmatched` instead of paths ([observability](../knowledge/specs/observability.md#safe-content)); `X-Request-ID` values are accepted only in a safe form ([API conventions](../knowledge/specs/api.md#conventions)); request records name the authenticated account only by its UUID and role, bound after authentication succeeds, so a refused token adds nothing ([correlation](../knowledge/specs/observability.md#correlation)); tutor notes, card emails and tutor codes never reach diagnostics, and the tutoring events carry identifiers only; access records name the invitation route template, never the token, which a test checks for valid and malformed tokens ([observability](../knowledge/specs/observability.md#component-coverage)) |
| T-19 | Secret disclosure, including through agent tooling | Settings from the environment; environment files and keys ignored by Git, denied to agent file tools and refused by the `guard_secrets.py` hook for file tools and shell commands (heredoc bodies count as data unless they are fed to a shell or an interpreter, or expand variables); the same hook refuses the common forms of shell commands that print the environment or interpolated container credentials, checked by `check_guard_secrets.py`; until hosting exists, agents run local commands with the owner's development settings only through `tools/dev-env.sh` ([ADR-0009](decisions/0009-owner-approved-exceptions-and-visibility.md), item 7), which loads the root `.env` and `backend/.env` into one command without printing them, accepts only `OVC_` keys, turns shell tracing off, refuses to start the common environment printers, clears the `DEBUG`, `RETURN`, `ERR` and `EXIT` traps that a startup file may set, and keeps `BASH_ENV`, `ENV`, `ZDOTDIR` and `BASH_XTRACEFD` from reaching its command; the hook unwraps it, including when it runs as a shell script or is sourced, and refuses the common traced-shell forms around or inside it, and sees through `pnpm`, `npm`, `npx` and `pnpx`, including their shell-script options, so the common printing forms are refused through it too; checked by `tools/check-dev-env.sh` and `check_guard_secrets.py`. Residual risk: every command run through the wrapper holds those settings, and a program that prints its own environment is not recognised, so the files hold development values only and real provider secrets stay in `backend/.env.local`, which the wrapper never loads. Residual risk: the hook matches command text, so it guards against accidental disclosure, not against a determined agent; the forms it does not recognise are listed in [AI development verification](../knowledge/reviews/ai-development-setup.md#minimal-inventory); secrets absent from diagnostics and `meta_*` values, and secret settings held in a type that redacts itself in every format, log and JSON encoding, inside a function value, which formatting prints only as an address, so no format verb can print it even through a struct that holds it in an unexported field; a database URL whose user name or password is not percent-encoded is refused, so it cannot be misparsed into a logged host or database name, and the processes refuse the driver's own `PG*` environment variables so no credential bypasses the settings, while the integration-test fixture still reads them and the driver defaults, its host checked like any other; the fixture prints only error kinds and the names of the databases it creates, never driver error text (the driver still reads `~/.pgpass`, `~/.pg_service.conf` or another service file when the URL names a service, and the client certificate, key and root certificate files under `~/.postgresql/` from the process user's home directory) ([ADR-0004](decisions/0004-bigbluebutton-primary-provider.md)); local development credentials are required Compose variables with no defaults, and Gitleaks scans history and staged changes with redaction but never the working directory ([security scanning](development.md#security-scanning)); the storage keys are `Secret` settings, the S3 client is built from them alone and never takes credentials, an endpoint or a region from `AWS_*` variables, shared AWS files or instance metadata (depguard bans the packages that would; the SDK still reads a few `AWS_*` variables for its user agent and retry defaults), ignores proxy variables, and the integration and end-to-end tests take the local server's keys only through `tools/dev-env.sh`; Playwright traces are kept only for failed tests in the ignored `frontend/test-results/`, hold only generated test accounts and are never shared, and the per-run preview certificate's private key stays in that ignored folder; for the pilot ([ADR-0013](decisions/0013-pilot-deployment.md)) the WAL-G backup bucket's credentials and encryption key, the Yandex Postbox SMTP credentials and the Data Streams reader credential are `Secret` settings held outside the repository, and the backup service account reaches only its own bucket; the field encryption key `OVC_FIELD_ENCRYPTION_KEY` is a `Secret` setting required by the API and the worker, separate from `OVC_JWT_SECRET` so that rotating the signing secret never makes open links unreadable; a missing or malformed key is refused at start-up with a message naming only the variable, the side-effect-free `check-settings` subcommand prints only `ok` or that message, the cipher built from it redacts itself in every format and log, and the process tests and the end-to-end harness generate a fresh key for every run and pass it only in the child processes' environment (pending owner review); invitation tokens are stored as a hash and as AES-256-GCM ciphertext bound to the invitation identifier, and the ciphertext is cleared once the link is used, revoked or expired, so the database holds readable links only for open invitations, and only together with a key it does not contain (residual: the key is not rotated in the MVP; replacing it makes open links unreadable, and tutors regenerate them) ([invitations](../knowledge/specs/accounts.md#invitations)) |
| T-20 | Resource exhaustion through connections, uploads, messages or emails | WebSocket authentication timeout, inbound frame limits, bounded outbound queues and ping timeout ([connection](../knowledge/specs/realtime-and-video.md#connection)); message rate limits and a daily per-student chat attachment cap, with the tutor able to delete attachments in their channels ([messages](../knowledge/specs/realtime-and-video.md#messages)); upload concurrency, limits and quotas ([upload flow](../knowledge/specs/files.md#upload-flow)); bounded pagination; digest frequency limits. Per-IP limits use the client address set by OVC's own reverse proxy, never a client-supplied header; the HTTP server's header timeout, idle timeout, header size limit and per-request read and write deadlines, the 1 MiB JSON body limit on every operation, and readiness checks bounded to 1 s each (database, then storage) and shared by concurrent requests, so readiness floods hold at most one database connection; database connections time out after 5 s unless the URL sets its own timeout ([API conventions](../knowledge/specs/api.md#conventions)); password hashing runs at most `GOMAXPROCS` Argon2id hashes at once and answers `503` after waiting 5 s for a slot; the client address for per-IP limits is the TCP peer, or, only when the peer is inside `OVC_TRUSTED_PROXY_CIDRS`, the right-most `X-Forwarded-For` entry outside those ranges, and the settings refuse IPv4 ranges wider than /8, IPv6 ranges wider than /32 and IPv4-mapped IPv6 ranges, so no single range trusts every client, while a long list of ranges that adds up to everything remains the operator's responsibility; avatar uploads are bounded per user and per instance, and their decoding shares a 256 MiB budget per instance with at most one decode per user, charged by pixels and format, with a fixed allowance for WebP's lossless tables (residual: a slow upload holds one of the 32 instance upload slots for up to its 60-second read deadline, so a few accounts can keep uploads busy, though nothing else) ([avatars](../knowledge/specs/files.md#avatars)); transport deadlines always use the system clock, never the shared test clock ([sessions and passwords](../knowledge/specs/accounts.md#sessions-and-passwords)). Deployment obligation: OVC's reverse proxy must append the client address to `X-Forwarded-For` or overwrite the header; a proxy that passes a client's header through lets the client choose its own per-IP bucket, and a proxy that writes entries OVC cannot parse (with ports or brackets) puts every client behind it into the proxy's own bucket; avatars are served by streaming, at most 32 at once per instance, so anonymous requests cannot hold their bodies in memory (residual: a slow reader holds one of the 32 slots for up to the 35-second write deadline, so a few clients can keep avatars unavailable for everyone, though nothing else; a per-address cap is a later option); the two unpaginated slice 3 lists are bounded: `GET /groups` by the limit of 200 groups per tutor, archived ones included, and `GET /tutors` by the relationships tutors create for the student; group members are capped at 30 and visible pending requests at 50 per tutor ([API conventions](../knowledge/specs/api.md#conventions), [groups](../knowledge/specs/accounts.md#groups)) |

## Limitations and out of scope

- Uploaded files are not scanned for malware in the MVP; risky kinds (archives, executables) are refused instead.
- The hardening of the BigBlueButton host itself, whether its client loads external assets such as STUN servers (to be checked in the slice 7 probe for residency), and what participants record with their own devices.
- The object-storage bucket policy and the operator's credentials, which are deployment obligations.
- Message logs kept by the SMTP provider (limited to 30 days by the provider choice, which for the pilot's Postbox is a condition still to be confirmed) and raw recording data on the conferencing host after the MVP (deleted with the provider copy, to be confirmed by the recordings probe; in the MVP no recording is made).
- Compromise of hosts or the database by an operator.
- Academic integrity: students sharing answers with each other outside OVC.

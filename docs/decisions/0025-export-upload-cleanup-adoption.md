## Context

FR-18 lets every user download their data as one ZIP archive that the worker builds and writes to object storage through a multipart upload ([exports](../../knowledge/specs/files.md#exports)). The archive can outlive the reason it was allowed: its owner, or another person whose data it holds, may be deleted, purged, removed from a group or have their work erased while it is being built or while it waits to be downloaded. A build can fail half way, time out after 2 hours or lose the acknowledgement of its Complete request, the faults ADR-0019 was written for. ADR-0019's journal is keyed by an attachment: the intent's identity is the attachment identifier, recovery locks the attachment before the intent, the storage-delete outbox validates an attachment, and operator receipts name one. An export archive has no attachment row, no uploader request and no quota charge.

## Decision

Export archives adopt the durable cleanup journal of ADR-0019, its protocol unchanged except where this record names what replaces the attachment:

1. **Identity.** Each build gets a new random build identifier and a new random storage key under the `exports/` prefix, never reused, also when the same user builds again. The intent's immutable identity is the build identifier, with the subject kind `export_build`; the intents of the upload contexts carry the subject kind `attachment`. The journal still holds no account identifier, file name, content or credential, and no foreign key to the export row.
2. **Reservation at build start.** The move of an export from `queued` to `building` locks the export row, writes the build identifier, the key and the start time, creates the intent in its `opening` phase and reserves capacity, in one transaction. A request reserves nothing, so a deleted `queued` export needs no storage work and a queued export is left alone by invalidation, because its build reads current data.
3. **Capacity.** A fourth capacity class, `export`, holds at most 256 unresolved intents, separate from chat's 4,096, the library's 1,024 and homework's 1,024. A full class at build start leaves the export `queued`, and the export lane tries it again on a later tick; `POST /exports` answers `503 service_unavailable` with `Retry-After` when the class is already full at request, before the password is checked.
4. **Storage calls.** Create, the parts and Complete run outside database transactions, with SDK retries disabled for Create and Complete as for uploads. The multipart upload identifier is recorded on the intent once, NULL to ID, in a short transaction after Create and before the first part.
5. **One Complete.** Before the Complete request, a transaction locks the export row, then the intent, confirms the build identifier, the `building` state and that no cleanup was requested, and records `completion_started`. Exactly one Complete is sent, authorized by that committed marker.
6. **Publication.** After a definite successful acknowledgement, one transaction locks the export row, then the intent, and again confirms the build identifier, the `building` state and that no cleanup was requested; only then does it set the export `ready` with its size and expiry, record the 24-hour limit, remove the intent, release its capacity and insert the ready notification. Once cleanup was requested (by a deletion, an invalidation or a failure) the export never becomes `ready` and no ready notification is produced.
7. **Every other outcome requests cleanup.** An error, a timeout, a failed part, the 2-hour build bound, a refused publication check or a lost acknowledgement records `cleanup_requested` through the journal in the export's own transaction, which also sets the export `failed` with its kind, `withdrawn` for an invalidation, or deletes its row for a deletion by the user. Generation 0 aborts the multipart upload and deletes the key; a definite late acknowledgement after generation 0 was scheduled records generation 1, which deletes the object; a lost acknowledgement leaves the intent `uncertain` with its capacity held, the residual ADR-0019 accepts.
8. **Published archives.** Deleting, withdrawing or expiring a `ready` or `expired` export, whose intent is gone, deletes its row or sets it `failed` or `expired` with its key cleared and queues the object's deletion through the storage-delete outbox in the same transaction, with the kind `export_object` and the idempotency key `storage_delete:export:<build id>`; it creates no intent and needs no capacity, as ADR-0019 does for published objects.
9. **Lock order.** Every path that touches an export takes, after every business lock it already holds, the export row (`FOR UPDATE`, in user identifier order when it touches several), then the user's export limit row, then the intent, then the capacity row last. The export's state, build identifier and cleanup request are read only under the export row's lock.
10. **Recovery.** `uploads.recover` selects export intents beside upload intents through the same indexed keyset cursor, batches of 200, at most twenty batches and one 30-second pass; for an export intent it locks the export row found by the build identifier, if it still exists, before the intent. It reconciles exactly as for an upload, with "the export row in `building` with this build identifier and no cleanup requested" in place of "an uploading attachment", and "the export row `ready` with this build identifier" in place of "a pending or bound attachment whose ownership transferred", which it never deletes. A separate pass of the `exports.recover` job fails every `building` export whose build started more than 2 hours and 15 minutes ago by the injected clock and requests its cleanup, so a stopped worker does not leave a build stuck.
11. **Outbox worker.** The storage-delete lane accepts the kind `export_intent` with the payload `{build_id, storage_key, generation}` and the idempotency keys `storage_delete:export:<build id>:intent:0` and `:intent:1`. Its effect validates the immutable build identifier, key and generation against the intent, reads the current multipart upload identifier from the intent, aborts and deletes outside transactions, and rechecks under the export row's lock, if the row exists, and then the intent's, as ADR-0019 states for attachments.
12. **Operator commands.** `ovc-admin uploads inspect` and `ovc-admin uploads retry-cleanup` accept a build identifier as well as an attachment identifier; receipts are keyed by `(build identifier, attempt UUID)` with the subject kind, and keep every other rule of ADR-0019.
13. **Migration.** The migration that creates `exports` adds the subject kind to the intents (every existing intent gets `attachment`) and the `export` capacity row at zero. Old writers stop first, as ADR-0019 requires. Its rollback is refused while any `export_build` intent or any export row with a storage key remains, because the earlier code cannot delete their objects.

## Alternatives considered

- **Giving each archive an attachment row** in a new `export` context: reuses the journal as it is, but puts a worker-written archive among user uploads, where quota sums, pending limits, purges and download authorization would each need an exception, and the attachment would need an uploader the purge then clears.
- **Sharing the homework or library class:** a few slow multi-gigabyte builds could exhaust it and refuse users' uploads, and the reverse.
- **No journal, an unconditional delete at the end of a failed build:** loses cleanup ownership when the worker stops and deletes nothing for a Complete that lands after the delete, the faults ADR-0019 removes; an archive that should have been erased could stay readable in storage.
- **Reserving at request:** a waiting export would hold capacity it may never use, and every deletion of a queued export would need storage work.

## Consequences

The journal, its recovery scan, the storage-delete lane and the operator commands carry export builds beside uploads. A prolonged uncertain backlog can stop new builds, which then wait `queued`, and refuse new export requests with `503`, an accepted availability trade-off, not a claim of complete physical erasure. An unresolved remote completion or a persistent storage failure can keep an intent and its object until the operator acts, and a multipart upload created before its identifier was recorded is removed only by the bucket's lifecycle rule; T-48 records both. A file already downloaded is outside OVC.

## Context

Every agent that implemented a change ran the full local check run of the [development guide](../development.md#tool-setup) before it reported readiness, and again after each fix. The run took 186.7 seconds cold on an idle machine and several minutes under load. When several agents worked at once, their runs competed for the shared PostgreSQL, Docker, the per-user end-to-end run lock and the CPU, so runs failed for environmental reasons or took far longer than measured. The value of the full run is a `main` on which every check passes; running it in every implementing context added nothing to that.

## Decision

- **Change checks.** An implementing agent runs the checks of what its diff touches, from the [change-check table](../development.md#change-checks-and-the-merge-gate) of the development guide, and reports them as its readiness evidence. Any path the table does not list, or any doubt, means the full run. A check it did not run is reported as `deferred to the merge gate`, never as `passed`. "The checks" of the tiers and of the after-fix rule of ADR-0011 are the change checks.
- **Merge gate.** Before every merge into `main`, the coordinating agent runs the merge gate, `tools/merge-gate.sh`: the full local check run on the exact tree that `main` will hold. The coordinator runs `main`'s copy of the script from a scratch folder, pointed at the checkout with `--repo`, so a change to the gate is gated by the gate it replaces. The gate
  - takes a per-user merge-gate lock built like the end-to-end run lock, so the coordinators of parallel sessions never run two gates at once, and a second gate fails at once naming the holder;
  - for the full run, also takes the per-user end-to-end run lock before its first check and holds it until after its last (amended 2026-10-28, pending owner review), so no end-to-end run of another session or of the gate's own lanes adds its deployments and their PostgreSQL connections beside `go test`; any such run is refused, naming the gate; only the gate's own `pnpm e2e` adopts the lock, which the harness accepts only when the gate that holds it is an ancestor of the run and the run inherited the lock file open on the descriptor the gate names; a lock already held by a live process fails the gate before any check with a message naming the busy run lock, and the full run refuses a lock folder other than the account's default, where the harness keeps the run lock;
  - refuses to start, naming the setting without its value, when any of the following settings is present (amended 2026-10-28, pending owner review): exported shell functions and the shell start-up variables `BASH_ENV`, `ENV`, `SHELLOPTS` and `BASHOPTS`; the Git variables that select another repository, index or configuration (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, the object directory variables, `GIT_NAMESPACE`, `GIT_SHALLOW_FILE`, `GIT_REPLACE_REF_BASE`, `GIT_NO_REPLACE_OBJECTS` and every `GIT_CONFIG` variable); `GOFLAGS`, `GOWORK`, `GOTOOLCHAIN`, `GOPACKAGESDRIVER`, a `GOENV` other than `off`, `NODE_OPTIONS`, the harness's run-lock variable and every `npm_config_` or `pnpm_config_` variable; any setting `go env -changed` reports other than an allowlist of file locations, the telemetry mode, the module proxy and the instruction-set levels; and an effective pnpm `node-options`, `script-shell` or `shell-emulator`; the report prints the effective settings. `GODEBUG` is refused through `go env -changed`. It cannot detect a tool (`go`, `node`, `pnpm`, `git`, `ps`, `python3`, `bash`, `docker`) shadowed on `PATH`, or runtime variables that `go env` does not report, such as `GOMAXPROCS` and `GORACE`;
  - refuses a working tree with unstaged or untracked files (and, for a fast-forward merge, staged ones), and by name, without reading them, the ignored files that would change what the checks run (Compose overrides, `go.work`, `.npmrc` and pnpmfiles), so the tracked files the checks read are the tested tree; other ignored files stay outside it and can still change what the checks run, and the gate never inspects environment files, which `tools/dev-env.sh` loads for the backend and end-to-end commands and Vite's `loadEnv` reads for `OVC_FRONTEND_` variables;
  - records `main`'s commit at its start, the tested tree, the check list and the scope: `HEAD^{tree}` of the branch for `git merge --ff-only`, or `git write-tree` of the squashed index for `git merge --squash`, which must equal the branch merged into `main` (`git merge-tree --write-tree`);
  - after the merge, its finishing step checks that `main` advanced from the recorded commit only by this merge, that `main^{tree}` equals the tested tree and that the gate ran the full run (or the Markdown-only list for a Markdown-only scope). It detects a moved `main` or a differing tree only after the merge and cannot prevent it; it then fails and keeps the lock for the owner. Nothing is edited, restaged or committed between the gate and the merge. A failed squash gate leaves the staged squash on `main`, which only the owner unstages, because agents never reset or restore.
  - has a self-test check list for its own test only, which it refuses without an explicit test lock folder, on the repository the script belongs to and on any repository holding `tools/merge-gate.sh`, and which the finishing step never accepts.
- **Failures.** A failed command blocks the merge and sends the change back to its branch, where its fix follows the after-fix rule. One rerun is allowed only when the output shows a named infrastructure error and no test assertion failed (Docker or PostgreSQL unreachable, `too many clients`), quoted in the merge report; a test that fails and then passes is reported as failed and handled as a flaky-test bug; a second infrastructure failure goes to the owner. `too many clients` remains a named infrastructure error while the lanes run, because the gate cannot tell its own connections from those of other processes; when it recurs on the rerun, the owner treats it as a gate bug to fix in a follow-up change. Because the gate holds the end-to-end run lock throughout, a run-lock refusal in the log of its own end-to-end entry is a gate bug that allows no rerun, and a run lock already busy when the gate starts is neither a failed check nor an infrastructure error: no check ran, and the gate is started again once the holder has ended, without counting as the rerun (amended 2026-10-28, pending owner review). Every gate appends its result to a log in the lock folder, and the report lists the earlier attempts for the same tree. A check never turns green by weakening it. The gate's end-to-end run stops after 10 failed tests (`--max-failures=10`); it then exits non-zero, so the gate fails, and the tests it did not run count as not run, never as passed, so such a run shows that no test assertion failed only for the tests that ran (amended 2026-11-15, pending owner review). A rerun is a new gate of a change whose own diff is unchanged since its failed gate, apart from its rows in the slice's known-limitations file, even when `main` moved and even when the new `main` holds a fix for the failure. A gate counts as an after-fix gate only when the change's own diff changed, the readiness report names the failure it fixes and the evidence below is recorded; in doubt, it is a rerun. Every failed gate of a change that is gated again, the one infrastructure rerun included, gets a row of kind `rerun` or `after-fix` in the slice's known-limitations file, holding its date, its tested tree and base, the failing tests or checks, and the owner's decision for a rerun or the evidence for an after-fix gate; the row is written as part of the change's own commit before the next gate, so the next gate tests the tree that holds it, and the merge report repeats it. The one rerun after a named infrastructure error with no failed assertion needs no approval; every other rerun needs the owner's approval, recorded in its row before it runs; an after-fix gate needs its row and its evidence, but no approval (defined by the project owner on 2026-11-15; the row for every failed gate, the infrastructure rerun included, decided by the owner on 2026-11-17; pending owner review). This bullet is the one full text of the rerun and after-fix rules; `AGENTS.md`, ovc-verify and the development guide carry an identical summary of them, and where that summary and this bullet differ, the stricter rule applies (decided by the owner on 2026-11-17, pending owner review). The evidence of an after-fix gate covers every failed test or check of the previous gate as follows (decided by the owner on 2026-11-16 with the slice 10 plan's D11 and K10, together with the evidence for every failure, the pinned trees and the recorded evidence; tightened on 2026-11-17 after the slice 10.1 slice review with the match key, the command, the recorded lines and the run counts, including always 10 after runs; pending owner review):
  - **Failure quoted.** The evidence quotes each failure from that gate's command log, with the log's path and its SHA-256, and names the hunk of the change's diff since that gate that addresses it (file and line range).
  - **Match key.** A failed test's full title with its Playwright project, or its Go package and full test name, together with its failure location form its match key: the `file:line` of the failing assertion on the failed gate's tested tree or, when no assertion failed, the error kind (a timeout, a panic message, a console-error or request-failure rule, a teardown error). A failed check that is not a test is keyed by its command and its finding (the rule or advisory and its location).
  - **Command.** One command, the same on both trees, selects that test or check by the name it has on the failed gate's tested tree and runs it alone or only with its own file or package, adding no retry, repeat, skip, wider project selection or changed timeout: a Go test with the gate's own flags for its package (`-race` among them), `-count=1 -v` and a `-run` pattern anchored to the test (`^TestX$`, with its subtest path), a Playwright test with `--retries=0`, the failed gate's project, `-g` with its title and the `list` reporter, and any other check with the gate's own command for it.
  - **Trees.** The before run uses the failed gate's tested tree and the after run that tree plus only the change's own new diff; when `main` has moved, both run on the new base, the before run without the change's new diff, and lines moved by `main` are matched through the unchanged test body. Both tree hashes are recorded. On the before tree the test, or the check's configuration, is unchanged from the failed gate's tested tree. On the after tree the test still exists and the same name selects it, and neither the test nor any assertion of its match key is deleted, renamed, skipped or loosened, nor is a helper, fixture, test-runner or check configuration it uses loosened (for example its timeouts, retries, repeats, project selection or an assertion it makes); otherwise the next gate is a rerun. A fix that adds an ignore entry, a suppression, a rule exclusion or a looser setting to a check that is not a test goes to the owner, and its next gate is a rerun.
  - **Recorded lines.** Every run on either tree is recorded with its exit status and the lines of its output that name the test and its outcome: for a failure, the failure lines with their location; for a pass, the line that names the test as passed (`--- PASS: TestX`, or the passed line of the `list` reporter); for a check that is not a test, its finding lines or its summary line.
  - **What counts.** A before run reproduces the failure only when its lines match the match key; a run that exits non-zero for another reason, or prints no such lines, is recorded but is not a reproduction, and counts as neither a failure nor a pass. A run reported as `(cached)`, "no tests to run" or "No tests found" counts as not run, and the evidence then fails. On the after tree every run must pass, and a non-zero exit or a missing pass line is a failure.
  - **Run counts.** The after tree always gets 10 runs, all of which pass. When the first before run reproduces the failure, it is the only before run; when it does not, it starts a before series fixed at 10 runs, the first counting toward it, which needs at least one reproduction. Any other before-series count needs the owner's approval before the first before run, the 10 after runs have no exception, and no count is chosen after a run has been seen. A run or series is never repeated, discarded or replaced, so a further attempt makes the gate a rerun.
  - **Where it lives.** The evidence is written in the change's own commit before the next gate, in or linked from the failed gate's `after-fix` row of the slice's known-limitations file (a linked record lives under `knowledge/`); a failure without it keeps the gate a rerun under the rerun rule. No reviewer confirms the evidence before the gate; a run of the end-to-end suites or of the full backend tests for it is a heavy run that the coordinator schedules; the slice review re-verifies each `after-fix` row against its recorded evidence.
- **Concurrent lanes** (amended 2026-10-27, pending owner review). The gate keeps one ordered list of the full run, each entry tagged with its slot. `tools/check-tool-binaries.sh` runs alone first; then three lanes run at the same time, each in its own process group and each stopping at its own first failure: `go test -race` in lane A, the Gitleaks scans, the other backend checks and the gate's own test in lane B, and the documentation checks, the OSV-Scanner scans, the frontend checks other than the end-to-end suites and the hook and wrapper self-tests in lane C (lanes rebalanced 2026-10-27 and 2026-10-28, pending owner review); `pnpm e2e` runs alone last, only after every lane passed and every lane process ended, and after the clean tree and the hashes are checked again. The gate passes only when every entry has exactly one record with exit status 0, reported by the leader process of the lane its tag names through an anonymous pipe that the gate holds and that every command runs without, so on macOS no command can write or rewrite a record, while on Linux a command can reach the pipe through `/proc` and forge its result, so there the pipe guards only against accidental writes (T-41), and every lane's `wait` returned 0; processes a lane leaves behind must end within a grace period, or the gate fails. On interruption it stops every lane's process group and waits for it before it releases the lock, and it logs the attempt; the lock records the lane process groups, and a lock is stale only when neither the gate nor any of them is alive. Each command's output stays in an owner-only log folder inside the lock folder for seven days. golangci-lint is configured to let a second concurrent run wait instead of failing, because the lint rule test in lane A and the lint run in lane B overlap. From this amendment, the full run's budget figures are the gate's wall time, measured cold on an idle machine, and every check-budget record also reports the summed command seconds, the wall time per lane, the core count and what the cold measurement emptied. The lanes change what runs at the same time, not what runs: the commands, NFR-6.2, the change checks and the Markdown-only list, which still runs its commands one after another, are unchanged. An error caused by contention between lanes is a gate bug; `too many clients` is the one exception that still allows the single rerun of the failures rule, because its cause cannot be told from the output (amended 2026-10-28, pending owner review).
- **One gate per merge,** never batched, so a failure points at one change.
- **Check budget** (decided by the project owner on 2026-11-15 at the slice 9 slice review, pending owner review). The hard limit stays NFR-6.2's 600 s of gate wall time. A full-run gate starts only on an idle machine: the one-minute load average on its `gate start:` line is below 6, and no other check, test, build or measurement run started by an agent or by the owner's tools, in any repository, runs on the machine; the merge report quotes the `gate start:` line and states that nothing else ran; a gate that started at a load of 6 or more, or beside another run, is not used to merge: when no command failed and no failure appears in its command logs (an interrupted gate is judged by its logs, and a named infrastructure error in it uses up the one infrastructure rerun), its change is gated again on an idle machine without that start counting as the infrastructure rerun, and the breach gets a row in the slice's known-limitations file; otherwise it is a failed gate under the Failures bullet like any other, so it gets its row and the next gate is a rerun or an after-fix gate; a gate that merged in breach of the rule gets a row in the slice's known-limitations file, and the slice review checks the start lines in the gate's attempt log; only the coordinator enforces the rule, because the gate prints the load but does not refuse a start. When the median of the last three passing full-run gates on mains power exceeds 540 s, the consolidation question goes to the owner at the earliest slice review that is not yet resolved (for slice 10, a sub-slice's slice review). This idle-machine rule and question replaced, as a policy reduction decided by the owner on 2026-11-17 with the explicit approval it needs, the earlier rule that made a consolidation of the checks due before further feature work when that median exceeded 540 s (pending owner review). In the median, a gate counts as on battery power when its start or end line (`gate start: power: …` and `gate end: power: …`, printed by `tools/merge-gate.sh` since slice 10) says `battery` or its end line says `battery-during-run: yes`, and a gate whose power source is unknown counts as on mains power; because a battery gate leaves the median, every merge report lists the durations of the battery gates beside the median, and when two of the last three passing gates ran on battery, the coordinator reports this to the owner before the next feature change merges (amended 2026-11-16 with the gate's power and load lines, by the slice 10 plan the owner approved on 2026-11-16, pending owner review). A passing gate of 600 s or more, on any power source, goes to the owner as a multiple-choice question before that same change merges, and the change does not merge until the owner answers. A change to a check budget, such as a size or time limit, lands as its own change with its own reviews, never inside a feature change. At slice 9's close the last three passing gates (700.3, 639.9 and 716.1 s, all on mains power) had a median of 700.3 s, so slice 10 starts with a consolidation, which also makes the gate print its power source and its load at its start and end.
- **Merge report** to the owner after each merge: the change, the recorded base commit, the tested tree and its earlier attempts, `main^{tree}` after the merge (equal), the check list, the scope and every command with its exit result, as printed by the gate and its finishing step.
- **Markdown-only changes.** A change whose diff holds only regular Markdown files (mode 100644, no links, submodules or mode changes) under `docs/` and `knowledge/` that no test, script or generator reads gates on the documentation checks and Gitleaks over staged changes and over history, with the same lock, clean tree and hashes. `knowledge/architecture/detailed.md` is excluded, because the package-layer architecture test parses it; the gate excludes any other Markdown file whose name appears in any file of the repository that is not Markdown. A test or script that reads Markdown by walking a folder or by a pattern, without naming the file, is not detected; the documentation checks still run on every Markdown-only change.
- Tiers, reviewers, the security trigger, the after-fix rule, the slice review, NFR-6.2's budget and the content of every check are unchanged by the original decision; the later amendments of the failures rule define a rerun and an after-fix gate and the evidence an after-fix gate needs (pending owner review). The change that introduced this decision kept the earlier rule for itself: it ran the full run at readiness and again at its merge gate. Because `main` held no copy of the gate before it merged, that change was gated once by its own copy of `tools/merge-gate.sh`, after the full run at readiness under the earlier rule, and its merge report records that.

## Alternatives considered

- **The full run in every implementing agent:** the earlier rule; it proves each branch, but parallel runs contend for shared services and fail or slow down for reasons unrelated to the change.
- **One gate for a batch of merges:** fewer runs, but a failure no longer points at one change, and the batch has to be split to find it.
- **Full runs only at the slice close:** cheapest, but `main` could stay broken for a whole slice and every later change would build on it.
- **A script that derives the change checks from the diff** (`tools/check-changed.sh`): removes judgement from the table lookup; deferred and revisited at slice 5's close ([slice 5 plan](../../knowledge/plans/slice-5.md)), because the gate already catches a misjudged table before `main`. Revisited on 2026-10-29 ([revisit record](../../knowledge/analysis/check-changed-revisit-2026-10-29.md)): no slice 5 gate failure that the gate's result lines name came from a misjudged change-check set, and the record recommends keeping the script deferred until such a failure occurs or a hosted CI service is adopted; the owner has not decided yet (pending owner review).

## Consequences

- An implementing agent's readiness evidence is narrower; a wrongly chosen change-check set lets a review run on a diff that later fails the gate, after review. The gate catches it before `main`, and the table errs wide.
- Merges are serialised by the merge-gate lock; serial gates of about three minutes bound merges to roughly 15 to 20 an hour, far above the current pace.
- The coordinator reports the gate's evidence itself; the merge report carries the hashes and the command results the script printed, which reviewers and the owner can rerun (T-41).
- `main` receives only commits on which the full run passed, except Markdown-only changes and the explicitly bounded one-change owner exceptions below.
- A change to the gate script takes effect only after it has merged, because each gate runs `main`'s copy (T-41).
